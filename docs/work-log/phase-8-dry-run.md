## Part 1 — Findability (§5.3 method: BOOTSTRAP.md + SKILLS_INDEX.md only)

Routing rule applied, from the index itself (line 5): *"Match task type to a playbook first; else match task keywords to the Keywords field."* First pick below is the first skill an agent following that rule lands on, judged against the index's own **Use when** text.

### Task 1 — Competitor's booking site, same features, completely different look, own brand
- **First pick: `clone-redesign` (D16)** — index: *"Use when: an authorized engagement must rebuild a reference product's function — its flows, features, validation, states, and data behavior — as a competing or successor product with a completely original design, brand, and copy."* Keywords: *"clone, redesign, authorized, engagement, rebuild, reference, product, function."*
- **Playbook:** `clone-and-redesign` — routes clone-redesign as anchor (steps 2, 6, 9).
- **Distractors beaten:** `behavior-cloning` (specs only, no build mission) and the booking-scheduling playbook (builds a booking product from scratch; no reference product, no expression-separation mission). clone-redesign's Do NOT use also fences off the appearance-matching clone-rebuild path explicitly.
- **Verdict: PASS**

### Task 2 — Inherited half-abandoned shop, backups unknown, make it safe and live again
- **First pick: `project-takeover` (D15)** — index: *"Use when: a team or agent inherits an existing project it did not build — a handover from a departing developer, a contractor delivery, an acquired or rescued codebase, an abandoned repo being revived — and must take responsibility for it. This skill is the entry protocol: inventory what exists, get it running locally, audit it, build the risk map, and stabilize it, in that order, before any other work begins."* The task's wording ("inherited", "half-abandoned", "nobody knows if backups work") maps onto this entry protocol, including the audit/stabilize order.
- **Playbook:** `rescue-and-relaunch` — cites project-takeover as its anchor throughout (7 mentions, incl. its step table).
- **Distractors beaten:** e-commerce-store playbook (a build mission, not a rescue) and `legacy-migration` (project-takeover's own Do NOT use defers replacement to legacy-migration only *after* takeover completes).
- **Verdict: PASS**

### Task 3 — WordPress store to a modern stack without losing Google rankings
- **First pick: `seo-migration` (D9)** — index: *"Use when: any change that alters URLs, host, scheme, platform, templates, or information architecture at scale — a redesign that changes paths, a replatform/CMS change, a domain or www/non-www move… This skill owns the migration lifecycle only: inventory, mapping, carry-over, crawl-diff verification, launch sequencing, and post-launch monitoring with rollback triggers."* The task's defining constraint (rankings) is this skill's owned lifecycle.
- **Playbook:** `replatform-migration` — routes seo-migration (8 mentions) together with legacy-migration (7 mentions), i.e. the playbook holds both halves of the mission and seo-migration is its ranking-preservation anchor.
- **Distractors beaten:** `legacy-migration` (owns the stack move but not the ranking lifecycle; seo-migration's index entry is the one that names "replatform/CMS change") and `technical-seo` (standing crawl contract, explicitly fenced off in seo-migration's Do NOT use).
- **Verdict: PASS**

### Task 4 — Founder's no-code MVP, any-password login, turn it into a real product
- **First pick: `prototype-hardening` (D15)** — index: *"Use when: a rough MVP, demo, hackathon build, no-code export, or AI-generated prototype — software that was built to be shown, not to be trusted — is being promoted to real users, real data, or real money, and needs one deliberate conversion pass: replacing simulated behavior with real behavior, closing the security holes prototypes ship with…"* "No-code" is a verbatim keyword (*"prototype, hardening, rough, mvp, demo, hackathon, build, no-code"*); the any-password login is exactly a "simulated behavior / security hole prototypes ship with."
- **Playbook:** `prototype-to-production` — cites prototype-hardening as anchor throughout (12 mentions).
- **Distractors beaten:** `refactoring` and `legacy-migration` — prototype-hardening's Do NOT use fences both off by name for this case.
- **Verdict: PASS**

### Task 5 — AI search added to an existing help-center product, with a model-down fallback
- **First pick: `ai-retrofit` (D17)** — index: *"Use when: an AI capability is being added to a product that is already live and in use — an existing search, inbox, editor, checkout, support, reporting, or admin flow gains summarization, drafting, classification, extraction, recommendations, or a conversational surface — and existing users, existing data, existing habits, and uptime must survive the addition."* "An existing search… gains" + a live support product + an uptime/fallback requirement is this skill's seam exactly (*"This skill owns the seam between the old product and the new AI behavior: insertion, coexistence, rollout, and removal"*).
- **Playbook:** `ai-ify-existing-product` — cites ai-retrofit as anchor throughout (8 mentions).
- **Distractors beaten:** `embeddings-search` / `rag-retrieval` (the search technology, loaded *under* ai-retrofit per its Load-with/Depends-on structure) and `llm-integration` (the call path; ai-retrofit's Do NOT use reserves greenfield work to it).
