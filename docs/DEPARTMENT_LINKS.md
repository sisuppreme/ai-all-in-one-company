# DEPARTMENT_LINKS.md — Cross-Department Linkage Matrix

**Purpose.** No department works alone. This file is the repo-level linkage matrix from MASTER_BRIEF.md §3.11, reconciled with the skills' actual `Depends on` / `Feeds into` metadata (aggregated from all 227 SKILL.md files at Phase 5) and mirror-checked mechanically. It ships in the repo so a consuming agent sees the links too, not just the builder.

**Single-agent translation (§3.11 mechanism 7).** At consumption time there are no departments — one agent plays every role in sequence. Read each link as an ordered verification step: when your work crosses a link, run the check named in the backbone table (Section 4) or in the link's contract (`docs/contracts/`) before moving on. The links are checklists, not handoffs.

## 1. Link types and matrix rules

- **FEEDS** — A produces output B consumes.
- **CONSTRAINS** — A sets rules B must follow.
- **VERIFIES** — A checks B's output.
- **SHARES** — both sides read and write one artifact.

Rules (from §3.11, enforced by the mirror check in Section 3):

- CONSTRAINS and VERIFIES are always one-directional (→ or ←). Only FEEDS and SHARES may use ↔, and only where both sides genuinely produce and consume.
- Every → or ← in one row appears as its mirror in the other row.
- Where two one-directional FEEDS entries run in opposite directions between the same pair with different artifacts (e.g. D1 ↔ D12), they are written as two separate → / ← entries, not collapsed into a bare ↔.

## 3. Mirror check

Method: a script parsed the table above into typed claims — (row department, other department, link type, direction) — expanded the four fan-outs (D7, D8, D10, D15) to every other department, and verified: (a) every → claim has a matching ← or ↔ claim of the same type in the other row; (b) every ↔ claim is matched by a ↔ claim of the same type and appears only on FEEDS/SHARES links; (c) no CONSTRAINS or VERIFIES link is bidirectional; (d) every type named in one row for a pair is named in the other row.

**mirror check: PASS, 0 unmatched links** (final run: 262 (pair, type) keys, 280 directed claims, all mirrored; no CONSTRAINS or VERIFIES link is bidirectional). The script's first run failed with 4 unmatched links — the brief omissions recorded as correction C8 below — which were fixed in the partner rows and re-run to a clean pass.

Corrections made to the brief's §3.11 table to achieve a clean mirror (the brief's table states several links in one row only):

## 5. Reconciliation log — brief §3.11 vs skill metadata

The matrix was built from the brief's §3.11 table (normative for link types) and reconciled against the aggregated skill metadata (51 cross-department flow pairs extracted from the 227 SKILL.md files). Resolutions:

- **R1 — Backbone link 5's "↔" is pair shorthand, not a bidirectional link.** The backbone list writes "D3 ↔ D13", but the underlying link is CONSTRAINS, which the matrix rules make one-directional. The matrix carries D13 → D3 CONSTRAINS only. (Backbone links 12 and 13 are already written one-directionally in the brief — D16 ← D14, D16 ← D8 — and are carried as such.)
- **R2 — Constraint-delivery flows keep the CONSTRAINS type.** Metadata shows FEEDS-shaped edges running from constraining departments into consumers (clone-ethics feeds all seven D16 skills; reduced-motion feeds motion; secrets-management feeds ci-cd). These flows are how the constraint is *delivered*, not separate FEEDS links. Type stays CONSTRAINS per the brief; the Phase 4 template convention (Depends on = consumes inputs from) supports this reading.
- **R3 — D1 ↔ D12 is two one-directional FEEDS entries.** The brief lists only D12 → D1 (analytics to product decisions). Metadata adds the reverse flow (product-analytics depends on product-metrics). Both directions are genuine with distinct artifacts, so the matrix carries D1 → D12 (metric definitions) and D12 → D1 (analytics to product decisions) as separate entries.
- **R4 — D6 ↔ D15 is two one-directional FEEDS flows under one ↔.** The brief lists D6 → D15 (CI/CD tooling); metadata adds D15 → D6 (monorepo-tooling feeds ci-cd). Distinct artifacts each way; written as ↔ FEEDS in both rows.
- **R5 — D4 ↔ D12 made explicit in both directions.** D4 → D12 (logs, metrics, events; metadata: error-handling feeds error-tracking) and D12 → D4 (logging/error standards). The brief implies each direction in only one row (see C3).
- **R6 — D8's "things to test" inbound is the VERIFIES fan-out, plus named FEEDS where an artifact exists.** The brief's D8 row lists ← D3/D4/D5/D6/D11 with no type. In this matrix that inbound side is the D8 → ALL VERIFIES link; separate FEEDS entries exist only where a concrete artifact is named: D3 (UI builds), D5 (seed/test data), D6 (preview environments), D11 (payment test flows), D13 (a11y tests), D17 (AI gates). - **R7 — Phase 4 cross-review fixes are already reflected.** The reversed page-reconstruction Feeds-into edge (review F, F-1) was removed at Phase 4, so no false D16-internal direction leaks into this matrix. - **R8 — Metadata-only links added as FEEDS (8 additions).** Each is evidenced by named skill edges and covered by no brief link or fan-out: D13 → D14 (accessibility-law feeds legal-documents), D12 → D14 (audit-trails depends on logging), D5 → D11 (transactions-concurrency feeds payments), D12 → D5 (pipeline-orchestration depends on monitoring), D6 → D5 (pipeline-orchestration depends on ci-cd), D6 → D18 (incident-response feeds status-communications), D4 → D2 (multitenancy-saas depends on backend-auth), and the D11 ↔ D18 pair (subscriptions/dunning state to CX; trial-conversion feeds dunning).
