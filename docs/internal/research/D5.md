# D5 — Databases & Data: Phase 2 Research

Department: D5 (Databases & Data). Input to Phase 3 skill drafting. Anatomy basis: PROJECT_ANATOMY.md Part 3 (Databases and migrations, Caching, Search, Seed data rules) and Part 11 (Data warehousing, ETL and data pipelines, Read replicas and read scaling).

## 1. Department standard

Professional data practice today rests on five disciplines:

**Migration discipline.** Every schema change is a versioned, ordered, committed migration file; a tracking table records applied versions so every environment converges to the same schema. Changes are reversible or explicitly marked irreversible with a documented recovery path. Risky changes follow expand-and-contract: add the new shape, backfill, dual-write or switch reads, then drop the old shape in a later deploy — never one deploy that both changes the shape and depends on it. DDL runs inside a transaction where the engine supports transactional DDL (PostgreSQL does; MySQL largely does not). Applied migrations are immutable: fixing one means writing a new migration. (Rails Guides, Active Record Migrations; Prisma Migrate seeding/migration workflows.)

**Indexing and query discipline.** Indexes are designed from actual query patterns, not added speculatively. Foreign keys and tenant/filter columns are indexed by default. Performance work starts from `EXPLAIN (ANALYZE, BUFFERS)`: the plan must show an index scan (or index-only scan via covering indexes with `INCLUDE` columns) for hot paths, not a sequential scan over a large table. Covering indexes eliminate heap fetches when the query's columns fit in the index. Statistics stay current (`ANALYZE`/autovacuum) so the planner's choices stay honest.

**Cache-aside as the default cache pattern.** The application checks the cache first; on a miss it reads the database, stores the result under a deterministic key with a TTL, and returns it. Writes go to the database and delete (not update) the affected keys. The database is always the source of truth; the cache is disposable. Hot-key stampedes are controlled with request coalescing, locks, or probabilistic early refresh. (Redis official cache-aside documentation.)

**Backup and restore testing.** A backup that has never been restored is a hypothesis, not a backup. Professional practice: automated scheduled backups (base backup plus WAL archiving for point-in-time recovery on PostgreSQL), retention policy in writing, and a scheduled restore drill that restores into a scratch environment, runs the migration set and a smoke query suite, and records duration (measured RTO) and the recovery point achieved (measured RPO). Replica promotion is rehearsed, not improvised.

**Data-quality checks as pipeline gates.** Quality assertions — uniqueness, not-null, accepted values, referential integrity (dbt's four built-in generic tests), plus range, regex, freshness, and row-count checks (Great Expectations / dbt-expectations vocabulary) — run as part of the build, and a failing check fails the pipeline with a non-zero exit. Checks sit at layer boundaries (raw → cleaned → modeled), not only at the end. Thresholds (`mostly`-style tolerance) are used deliberately on real-world columns to avoid alert fatigue, never to silence a hard integrity rule.

## 2. Failure modes this department prevents

Drawn from the anatomy slop lines; each maps to the element that names it.

- **ORM auto-syncing tables in production; hand-edited production schema; applied migrations edited in place; migrations with no working rollback** — *Databases and migrations* (Part 3). Environments drift, deploys break against an unexpected schema, fixes become unreproducible manual SQL.
- **Caching with no TTL and no invalidation (stale prices forever); per-user data under shared keys (a cross-user data leak); the cache treated as the source of truth** — *Caching* (Part 3).
- **A `LIKE '%term%'` query on the main table presented as "search"; an index built once and never updated; results ordered by insertion instead of relevance** — *Search* (Part 3).
- **A seed that inserts duplicates on every run; demo accounts with guessable credentials shipped to production; real customer records copied into development seeds; a one-off SQL dump committed once and never maintained** — *Seed data rules* (Part 3).
- **A nightly CSV emailed around as "the warehouse"; dashboards querying the production primary at peak hours; revenue figures that change depending on who wrote the query** — *Data warehousing* (Part 11).
- **A chain of cron jobs and shell scripts with no dependency tracking; silent partial loads; transformations edited directly in production; no way to re-run a single day** — *ETL and data pipelines* (Part 11).
- **Replicas created but never routed to; checkout reading its own just-written order from a lagging replica and showing an empty cart** — *Read replicas and read scaling* (Part 11).

## 3. Per-skill research notes

### schema-design
- **Core method:** Model entities and relationships from the domain first, then map to tables: one table per aggregate root, foreign keys for relationships, constraints (`NOT NULL`, `UNIQUE`, `CHECK`, FK with explicit `ON DELETE` behavior) declared in the database, not only in app code. Normalize to 3NF by default; denormalize only for a measured read pattern, and record the reason in SCHEMA.md. Money is integer minor units or `numeric`, never float; timestamps are `timestamptz`; IDs are surrogate keys (UUID or identity) with natural keys protected by unique constraints.
- **Key rules:**
  1. Every invariant the business depends on exists as a database constraint, not just an application check.
  2. Every table has a primary key; every foreign key column is indexed.
  3. Nullable columns are a deliberate decision per column, documented when non-obvious.
  4. Soft delete is a product decision with a written retention rule, not a default habit.
  5. SCHEMA.md is updated in the same change as the migration that alters the schema.
- **Verification gates:** Schema lint in CI: fail on tables without a primary key and FK columns without an index (automatable SQL query against `information_schema`/`pg_catalog`). Constraint-presence check: a script asserts each SCHEMA.md-listed invariant maps to a named constraint.
- **Sources:** Rails Guides, Active Record Migrations (schema conventions) — https://guides.rubyonrails.org/v7.1.3/active_record_migrations.html ; anatomy Part 3, *Databases and migrations*.

### sql-fundamentals
- **Core method:** Write explicit SQL (or ORM calls whose generated SQL is inspected) with named columns — never `SELECT *` in application code. Use parameterized queries everywhere; string interpolation into SQL is forbidden. Understand the core operations cold: joins and their cardinality effects, aggregation with `GROUP BY`/`HAVING`, window functions, CTEs for readability, and set-based thinking instead of row-by-row loops.
- **Key rules:**
  1. All values reach SQL as bound parameters; identifiers (table/column names) come only from allowlists.
  2. Every query in code review shows its generated SQL at least once (log it in development).
  3. No N+1: collection loads are eager or batched, verified by query counts in tests.
  4. Aggregates and filters happen in the database, not by fetching rows and computing in the app.
  5. `NULL` semantics are handled explicitly (`IS NULL`, `COALESCE`, unique-with-null behavior).
- **Verification gates:** Static check in CI: grep/lint for string-concatenated SQL and `SELECT *` in the data-access layer (automatable). Query-count assertion in integration tests for list endpoints (automatable).
- **Sources:** PostgreSQL documentation, Text Search Functions and Operators (operator/function precision) — https://www.postgresql.org/docs/10/functions-textsearch.html ; anatomy Part 3.

### nosql-patterns
- **Core method:** Choose NoSQL only for a named access pattern the relational model serves badly (document-shaped reads, key-value lookups, wide-column time series, graph traversal). Model data around the queries: embed what is read together, reference what is shared or unbounded, and accept deliberate duplication with a written update strategy. Every duplicated field has one named source of truth.
- **Key rules:**
  1. The access patterns are listed before the data model; a pattern with no model entry does not ship.
  2. Unbounded arrays/documents are forbidden; growth per document is capped by design.
  3. Multi-document invariants use the engine's transaction support or an explicit reconciliation job — never hope.
  4. Schema validation rules (e.g. JSON Schema validators) are enabled on collections that accept writes.
  5. A documented exit note states what would trigger re-evaluating the relational default.
- **Verification gates:** Access-pattern coverage check: each listed pattern maps to a query in the repository that runs without a full collection scan (reviewable; partially automatable via profiler slow-query log review). Collection validator presence check via database metadata (automatable).
- **Sources:** Anatomy Part 3, *Databases and migrations* (skills mapping); pgvector docs for the counter-pattern — specialized data staying inside Postgres when it fits — https://access.crunchydata.com/documentation/pgvector/0.8.3/pdf/pgvector.pdf

### seed-data
- **Core method:** Two seed classes, kept separate: (a) required reference data (roles, plans, lookup values) that production also receives through the release process; (b) development-only sample data, synthetically generated, clearly synthetic (obviously fake names/emails on reserved domains such as `example.test`). Seeds run after migrations, are idempotent (upsert by natural key), and re-running changes nothing.
- **Key rules:**
  1. Seed scripts are idempotent; a second run produces identical row counts.
  2. Reference data and sample data live in separate files/entry points with separate commands.
  3. Sample data is never copied from production records — not even "anonymized" by hand.
  4. No seed creates credentials that work in production; development logins are documented as development-only and blocked by environment checks.
  5. Sample records are labeled in data or in environment (seeded flag / reserved domains) so they can never be mistaken for real users.
- **Verification gates:** Double-run test in CI: run migrations + seed twice on an empty database; assert identical row counts and a successful app boot (automatable — this is the anatomy Verify line). Pipeline scan: assert the production deploy pipeline contains no sample-data seed step (automatable grep of pipeline config).
- **Sources:** Prisma documentation, "Seeding" — https://www.prisma.io/docs/orm/v6/prisma-migrate/workflows/seeding ; anatomy Part 3, *Seed data rules*.

### transactions-concurrency
- **Core method:** Group every multi-write operation that must succeed or fail together into one transaction. Choose isolation deliberately: default read-committed with explicit row locks (`SELECT ... FOR UPDATE`) or optimistic locking (version column) for contended records; serializable only where the invariant demands it, with retry-on-serialization-failure. Keep transactions short; never hold one open across an external HTTP call.
- **Key rules:**
  1. Money movement, inventory decrement, and state-machine transitions always run in a transaction with a lock or version check.
  2. Retried operations are idempotent (see D11 webhooks/payments interplay) — a retry never double-applies.
  3. Deadlock and serialization failures are caught, logged, and retried with backoff, not surfaced as 500s by default.
  4. Long-running reports use a snapshot or replica, never a long open transaction on the primary.
  5. Lock ordering is consistent across code paths touching the same tables.
- **Verification gates:** Concurrency test: two parallel requests attempting the same contended operation (double-spend, double-book) assert exactly one effect (automatable integration test). Static review checklist: every multi-write service method is wrapped in a transaction (lint/review gate).
- **Sources:** Anatomy Part 3, *Databases and migrations* (transactional DDL) and *Payments and billing* (idempotency) — PROJECT_ANATOMY.md Part 3.

### tenant-isolation
- **Core method:** Pick the isolation model explicitly — shared schema with `tenant_id` + PostgreSQL row-level security (RLS) is the default for many-small-tenants SaaS; schema-per-tenant or database-per-tenant when regulation, size, or per-tenant restore demands it. In the shared model, RLS is the database-enforced backstop behind application scoping: every tenant table carries `tenant_id`, RLS is enabled and forced, one policy covers reads and writes (`USING` + `WITH CHECK`), and the tenant context is set per transaction with `SET LOCAL`/`set_config(..., true)` so pooled connections cannot leak context.
- **Key rules:**
  1. Every tenant-owned table — including child/join tables — has a non-null `tenant_id` and an index on it.
  2. The application connects as a non-owner role; owner/superuser/BYPASSRLS connections bypass policies and are forbidden for request traffic.
  3. Policies include `WITH CHECK`; a read-only policy lets inserts target other tenants.
  4. Tenant context is transaction-local, never session-level, under a connection pool.
  5. Background jobs and admin paths set tenant context explicitly per unit of work.
- **Verification gates:** Cross-tenant test suite: as tenant A, attempt select/insert/update/delete against tenant B's rows on every tenant table; all must return zero rows or fail (automatable). Catalog check: query `pg_policies`/RLS flags to assert every tenant table has RLS enabled and at least one policy (automatable).
- **Sources:** Encore, "Postgres Row-Level Security for Multi-Tenant SaaS" — https://encore.dev/articles/postgres-row-level-security-multi-tenant ; anatomy Part 3.

### migrations
- **Core method:** Migrations are timestamped/versioned files in the repo, applied in order by a runner that records applied versions in a tracking table. Each migration is reversible (`change`-style auto-reversal or explicit up/down); where reversal is impossible, the migration says so and names the recovery procedure. Large-table changes use expand-and-contract across deploys. Already-applied migrations are never edited — corrections are new migrations.
- **Key rules:**
  1. CI runs the full migration set from empty on every change; a failing migration fails the build.
  2. Every migration is tested down as well as up in CI (apply all, roll back one, re-apply).
  3. Data backfills run as separate, resumable jobs — not inside a schema migration on a large table.
  4. `CREATE INDEX CONCURRENTLY` (or engine equivalent) for indexes on large production tables, outside a transaction block where required.
  5. The committed schema file/structure dump is regenerated by the migration run, never hand-edited.
- **Verification gates:** Migration reversibility test in CI: from an empty database run all migrations, diff the resulting schema against the committed schema file, roll back the last migration, re-apply cleanly (automatable — the anatomy Verify line). Immutability check: CI fails if a migration file older than the latest applied version is modified (automatable via git diff against the release tag).
- **Sources:** Rails Guides, "Active Record Migrations" — https://guides.rubyonrails.org/v7.1.3/active_record_migrations.html ; Prisma Migrate workflows — https://www.prisma.io/docs/orm/v6/prisma-migrate/workflows/seeding

### query-performance
- **Core method:** Measure before optimizing: capture slow queries from the database's own statistics (`pg_stat_statements` or equivalent) and application query logs, then read `EXPLAIN (ANALYZE, BUFFERS)` for the worst offenders. Fix in order: missing index, wrong join/order, N+1, over-fetching columns, then engine tuning. Every optimization records the before/after plan and timing on production-shaped data, not on an empty development database.
- **Key rules:**
  1. No optimization ships without a before/after `EXPLAIN ANALYZE` on realistic row counts.
  2. Hot paths have a stated latency budget; regressions against it fail review.
  3. Pagination is keyset/cursor-based on large or unbounded lists; deep `OFFSET` is a defect.
  4. `SELECT` lists name columns; over-fetching wide rows (especially with blobs/text) is treated as a performance bug.
  5. Slow-query logging is on in production with a threshold, and the top offenders are reviewed on a schedule.
- **Verification gates:** Plan assertion tests: for each registered hot query, CI runs `EXPLAIN` against a seeded production-shaped fixture and fails if the plan shows a sequential scan on the large table (automatable). Query-count tests for N+1 on list endpoints (automatable).
- **Sources:** Anatomy Part 3, *Caching* and *Search* Verify lines (EXPLAIN-based); PostgreSQL documentation — https://www.postgresql.org/docs/10/functions-textsearch.html

### indexing
- **Core method:** Design indexes from the query log: B-tree for equality/range and ordering, composite indexes ordered equality-columns first then the range column, covering indexes with `INCLUDE` for hot read paths to reach index-only scans, GIN for full-text (`tsvector`) and JSONB containment, GiST/HNSW where the operator demands it. Remove unused indexes — each one taxes every write.
- **Key rules:**
  1. Every foreign key and every column used in tenant scoping is indexed.
  2. Composite column order follows the queries: equality first, range last; an index that no query can use leftmost is dead weight.
  3. Partial indexes are used for hot subsets (e.g. only `status = 'active'` rows) when the subset is small and stable.
  4. Index usage is audited on a schedule (`pg_stat_user_indexes`); unused indexes are dropped through a migration.
  5. New indexes on large tables are built concurrently and their size recorded.
- **Verification gates:** `EXPLAIN` assertion for registered hot queries shows `Index Scan`/`Index Only Scan`, not `Seq Scan` (automatable in CI against a seeded fixture). Unused-index report reviewed per release (automatable report; human sign-off).
- **Sources:** PostgreSQL documentation, Text Search (GIN on `tsvector`) — https://www.postgresql.org/docs/10/functions-textsearch.html ; pgvector docs (HNSW index construction) — https://access.crunchydata.com/documentation/pgvector/0.8.3/pdf/pgvector.pdf

### data-access
- **Core method:** All database access goes through one layer (repositories/ORM models/query builders) that owns parameterization, tenant scoping, pagination defaults, and timeouts. No SQL strings scattered in controllers or views. The layer enforces a per-query timeout, returns typed results, and exposes explicit transaction boundaries to services. Raw SQL is allowed inside the layer when the ORM cannot express the query — still parameterized, still reviewed.
- **Key rules:**
  1. Every query is parameterized; string-built SQL fails lint.
  2. Tenant scoping is applied by the layer (and backed by RLS), not remembered per call site.
  3. List methods require pagination parameters with a hard maximum page size.
  4. Every call has a statement timeout; a runaway query dies instead of piling up.
  5. Writes return the persisted entity or an explicit error — silent no-op writes are forbidden.
- **Verification gates:** Lint rule: no SQL construction outside the data-access package (automatable import/grep check). Integration test: a query exceeding the statement timeout is killed and surfaces a typed error (automatable).
- **Sources:** Anatomy Part 3 (skills mapping across elements); Encore RLS guide (scoping enforced in the database as backstop) — https://encore.dev/articles/postgres-row-level-security-multi-tenant

### backup-recovery
- **Core method:** Automated backups on a written schedule: periodic base backups plus continuous WAL archiving for point-in-time recovery (PostgreSQL), with retention tiers (daily/weekly/monthly) and at least one copy outside the primary provider account/region. Recovery is a rehearsed procedure: restore to a scratch instance, apply WAL to a target timestamp, run migrations check and smoke queries, record elapsed time and data-loss window.
- **Key rules:**
  1. A restore drill runs on a schedule (at least quarterly) and its measured RTO/RPO are recorded in the runbook.
  2. Backups are monitored; a missed backup alerts like an outage.
  3. Backup credentials and encryption keys are stored separately from the backups themselves.
  4. Deletion of backups requires a separate privilege from routine operations.
  5. Per-tenant restore limits are documented for the chosen tenancy model (shared-schema restore is row extraction, not a file restore).
- **Verification gates:** Restore-drill record exists and is current: date, recovery point achieved, duration, smoke-suite result (process gate; the drill itself is automatable as a scripted restore + smoke run). Backup freshness check: monitoring asserts the newest successful backup is younger than the schedule allows (automatable).
- **Sources:** Anatomy Part 5, *Backups* (restore-tested discipline); pgvector docs note on Postgres point-in-time recovery as a platform property — https://access.crunchydata.com/documentation/pgvector/0.8.3/pdf/pgvector.pdf

### read-replicas
- **Core method:** Writes and read-your-own-write queries go to the primary; tolerant reads (feeds, search, reporting, dashboards) route to asynchronous replicas. The application names its routing per query or per service — never globally by default. Replication lag is a monitored metric with an alert threshold; when lag exceeds the threshold, reads fall back to the primary or the feature degrades explicitly.
- **Key rules:**
  1. Consistency-critical reads (checkout, permissions, balances) are pinned to the primary.
  2. Every replica-routed read documents its staleness tolerance.
  3. Lag is measured continuously (replay lag in bytes/seconds) and alerted, not discovered by users.
  4. Replica promotion/failover is a documented, rehearsed runbook step.
  5. Connection strings for primary and replica are separate configuration; code never hardcodes hosts.
- **Verification gates:** Routing audit: configuration/code review asserts the pinned-primary list covers the named critical flows (review gate). Lag check: write a sentinel record on the primary and measure time-to-visible on the replica in staging; assert under the stated tolerance (automatable).
- **Sources:** AWS documentation, "Working with DB instance read replicas" — https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html ; anatomy Part 11, *Read replicas and read scaling*.

### caching
- **Core method:** Cache-aside by default: check cache → on miss read the database → store under a deterministic key with a TTL → return. Writes update the database and delete affected keys. Keys are namespaced by entity, version, and tenant where applicable. Cache only data that is expensive or hot and safe to serve slightly stale; per-user data is keyed per user or not cached at all. Stampede protection (lock, request coalescing, or early refresh) guards hot keys.
- **Key rules:**
  1. Every cached entry has a TTL; "no expiry" requires a written exception.
  2. Invalidation is delete-on-write; the database remains the only source of truth.
  3. Cache keys never mix tenants or users; a shared key holding per-user data is a blocker-severity defect.
  4. The application runs correctly (slower) with the cache flushed or down; cache failure never becomes wrong data.
  5. Cache hit ratio and evictions are monitored; a silent 0% hit ratio is treated as a bug.
- **Verification gates:** Anatomy Verify, automated: with query logging on, request the same resource twice and assert the second issues no database query; update the record and assert the old value is no longer served (automatable integration test). Key-namespace lint: cache key construction goes through one helper that includes tenant/user scope (automatable).
- **Sources:** Redis documentation, "Redis cache-aside" — https://redis.io/docs/latest/develop/use-cases/cache-aside/ ; anatomy Part 3, *Caching*.

### search-engines
- **Core method:** Start with PostgreSQL full-text search (`tsvector`/`tsquery`, weighted fields, `ts_rank`, GIN index) and graduate to a dedicated engine (Elasticsearch/OpenSearch/Typesense) only for a named need: typo tolerance, faceting at scale, language analyzers, or search load isolation. Either way, the index is a derived artifact: it is updated from the write path (transactional outbox or change events), is rebuildable from the database on demand, and results are ranked by relevance with filters/facets as structured parameters.
- **Key rules:**
  1. `LIKE '%term%'` on the primary table is never shipped as "search."
  2. Index freshness is a contract: the maximum lag between a write and its searchability is stated and monitored.
  3. Deleted/updated records leave the index in the same flow that changes the database.
  4. Ranking changes are evaluated against a fixed query set with expected top results, not by feel.
  5. The full index can be rebuilt from the source of truth by one documented command.
- **Verification gates:** Anatomy Verify, automated: create a record with a distinctive word and assert it appears in results; run `EXPLAIN` on the search query to confirm index use; delete the record and assert it disappears. Rebuild test: drop and rebuild the index in staging, assert result parity on the fixed query set (automatable).
- **Sources:** PostgreSQL documentation, "Text Search Functions and Operators" — https://www.postgresql.org/docs/10/functions-textsearch.html ; anatomy Part 3, *Search*.

### vector-db
- **Core method:** Default to pgvector inside PostgreSQL: a `vector(n)` column matching the embedding model's dimension, the distance operator that matches the model (`<=>` cosine, `<#>` inner product, `<->` L2), and an HNSW index (better speed/recall trade-off; IVFFlat when build time/memory dominates) created once data volume makes exact scan hurt. Embeddings are derived data: the source record, model name, and model version are stored alongside so a model change triggers a planned re-embed, not silent mixing. Graduate to a dedicated vector database only for a named scale or filtering need Postgres cannot meet.
- **Key rules:**
  1. The index operator class matches the query operator; a mismatched query silently falls back to a full scan.
  2. Vector dimension is fixed per column and validated on write against the producing model.
  3. Embeddings from different model versions never share an index without a version filter.
  4. ANN recall is measured against exact search on a sample before launch and after index-parameter changes.
  5. Every embedding row traces to its source record and chunking rule; orphaned embeddings are deleted with their source.
- **Verification gates:** Plan check: `EXPLAIN` on the nearest-neighbor query shows the HNSW/IVFFlat index in use, not a sequential scan (automatable). Recall check: compare ANN top-k against exact top-k on a sampled query set and assert recall at or above the stated threshold (automatable).
- **Sources:** pgvector documentation — https://access.crunchydata.com/documentation/pgvector/0.8.3/pdf/pgvector.pdf ; anatomy Part 3, *Search* and Part 8 (AI features).

### data-warehousing
- **Core method:** A separate analytical store (e.g. BigQuery's serverless model: columnar storage, storage/compute separation) loaded on a schedule from operational sources. Data is modeled into fact and dimension tables (or curated wide tables) with metric definitions owned in one place — a metrics layer or documented model definitions — so "revenue" means one thing everywhere. Analysts query the warehouse; the production primary is never a reporting backend.
- **Key rules:**
  1. No dashboard or report queries the production primary.
  2. Every headline metric has exactly one definition, in one named model, referenced by all consumers.
  3. Loads are scheduled, monitored, and idempotent; a re-run of a day's load produces the same warehouse state.
  4. Personally identifiable data entering the warehouse is minimized and access-controlled per dataset.
  5. Warehouse schemas are versioned code (models in the repo), not console edits.
- **Verification gates:** Reconciliation check: a headline metric (e.g. yesterday's order count) computed in the warehouse matches the source system within the stated tolerance, run on a schedule (automatable). Access audit: production primary's query log shows no reporting-tool connections (automatable log check).
- **Sources:** Google Cloud documentation, "BigQuery overview" — https://cloud.google.com/bigquery/docs/introduction?hl=vi ; anatomy Part 11, *Data warehousing*.

### etl-pipelines
- **Core method:** Pipelines move data in stages: ingest raw data unchanged into a landing zone, then transform (validate, deduplicate, join, model) into cleaned and modeled layers. Every transformation is code in the repo, parameterized by date/window so any single day can be re-run. Loads are idempotent (merge/upsert or partition-replace), so retries and backfills converge instead of duplicating. Quality checks (see data-quality) gate promotion between layers.
- **Key rules:**
  1. Raw ingested data is immutable; corrections happen in transformation, never by editing raw.
  2. Every pipeline run is parameterized and re-runnable for an arbitrary window (backfill is a feature, not an incident).
  3. Partial loads are impossible by construction: a failed transform publishes nothing (staging table + atomic swap, or transactional load).
  4. Transformations never run edited-in-production; changes deploy through the same review as application code.
  5. Each dataset names an owner and its source systems; lineage is written down.
- **Verification gates:** Failure-injection test in staging: kill a transformation mid-run and assert no partial output is published and the retry completes the full window (automatable). Idempotency test: run the same window twice, assert identical destination row counts and checksums (automatable).
- **Sources:** Apache Airflow documentation, "Concepts" — https://airflow.apache.org/docs/apache-airflow/2.0.0/concepts.html ; anatomy Part 11, *ETL and data pipelines*.

### data-ingestion
- **Core method:** Ingestion pulls from APIs, databases (batch extract or change data capture), files, and event streams into a landing zone, preserving the source payload and its provenance (source, extraction timestamp, source cursor/version). Contracts with sources are explicit: expected schema, delivery cadence, and volume range; deviations (schema drift, volume anomaly, late arrival) are detected at the gate and quarantined, not silently absorbed.
- **Key rules:**
  1. Every ingested record carries provenance: source system, extraction time, and batch/stream identifier.
  2. Schema drift fails loudly into a quarantine area; it never silently nulls or drops columns downstream.
  3. Incremental extraction uses a durable cursor (updated-at watermark, log position, or sequence) stored outside the job's memory.
  4. Re-delivered data is deduplicated by source primary key at load.
  5. Secrets for source systems live in secret storage, never in pipeline code or config files in the repo.
- **Verification gates:** Drift test: feed a payload with an added/renamed field in staging and assert the batch is quarantined and alerted, not loaded (automatable). Replay test: re-deliver a batch and assert destination counts are unchanged (automatable).
- **Sources:** Anatomy Part 11, *ETL and data pipelines*; Datadog dbt-expectations guide (freshness and schema assertions at the gate) — https://www.datadoghq.com/blog/dbt-data-quality-testing/

### pipeline-orchestration
- **Core method:** An orchestrator (Apache Airflow's model: workflows as code-defined DAGs, tasks with explicit states — queued, running, success, failed, up for retry — visible in one UI) owns scheduling, dependencies, retries, and backfills for all pipelines. Each task is idempotent, declares its dependencies explicitly, and has a retry policy with alerting on final failure. Run state and logs are kept long enough to audit the last failure without asking anyone.
- **Key rules:**
  1. No production pipeline runs on a bare cron entry outside the orchestrator.
  2. Every task declares: schedule, dependencies, retry count/backoff, timeout, and alert target.
  3. A task that exceeds its freshness SLA alerts before its consumers notice stale data.
  4. Backfill is a first-class operation with the same code path as scheduled runs.
  5. Orchestrator configuration and DAG code are versioned and reviewed like application code.
- **Verification gates:** Anatomy Verify, automated: open the orchestrator UI (or its API) and assert every pipeline shows a last successful run within its schedule window. Kill test: terminate a task in staging and assert it retries per policy, alerts on exhaustion, and publishes no partial output (automatable).
- **Sources:** Apache Airflow documentation, "Concepts" — https://airflow.apache.org/docs/apache-airflow/2.0.0/concepts.html ; anatomy Part 11, *ETL and data pipelines*.

### data-quality
- **Core method:** Quality is enforced by executable assertions attached to datasets, in the vocabulary the tooling shares: uniqueness, not-null, accepted values, and referential integrity (dbt's built-in generic tests), extended with range, regex/format, row-count, freshness, and distribution checks (Great Expectations / dbt-expectations). Checks are declared next to the model they guard, run in CI and in the pipeline, and a failure blocks promotion of that dataset. Tolerances (`mostly`-style thresholds) are permitted on noisy real-world columns with the threshold written next to the check; integrity rules (keys, references, money sums) get zero tolerance.
- **Key rules:**
  1. Every primary key has unique + not-null tests; every foreign key has a relationships test.
  2. Every pipeline layer boundary has at least one row-count or freshness check.
  3. A failing check fails the run with a non-zero exit and an alert naming the dataset and check.
  4. Check results are stored and trended; a check that "always passes" after a source change is investigated, not celebrated.
  5. Business-rule checks (e.g. order totals equal line-item sums) exist for every money path.
- **Verification gates:** The check suite itself is the gate: `dbt build`/checkpoint run exits non-zero on any failed assertion, wired into CI and the orchestrator (automatable). Negative test: inject a duplicate key and an orphaned foreign key into a staging fixture and assert the suite catches both (automatable).
- **Sources:** Datadog, "Implement dbt data quality checks with dbt-expectations" — https://www.datadoghq.com/blog/dbt-data-quality-testing/ ; anatomy Part 3, *Seed data rules* (data-quality in skills mapping) and Part 11.

## 4. Open risks for Phase 3

1. **Seed data vs the Real Content Rule (QB-10) — the sharpest line in this department.** Seed/sample data exists to make environments boot and tests deterministic; it must never cross into being presented as real. Rules Phase 3 must encode in the seed-data skill itself: sample data is synthetic and visibly synthetic (reserved domains, obviously placeholder names); it is labeled in data (seeded flag) or confined to non-production environments by pipeline construction; production receives reference data only (roles, plans, lookups), never demo users, demo testimonials, or demo metrics. A dashboard populated by seed data in production is fake functionality and fake content simultaneously — the skill must state this as a blocker, and the production-pipeline scan gate (no sample-seed step) is the enforcement.
2. **RLS is a backstop, not the wall.** Tenant isolation depends on connection-role hygiene (non-owner role, no BYPASSRLS) and transaction-local context under pooling. A Phase 3 skill that teaches policy syntax without the role/pooling rules will produce isolation that silently does not apply. The cross-tenant test suite must be drafted as part of the skill, not left as advice.
3. **Migration reversibility has engine limits.** PostgreSQL transactional DDL makes most reversals clean; MySQL and some operations (enum changes, large backfills) do not reverse. Phase 3 must not promise universal rollback — it should teach the "irreversible with named recovery procedure" escape hatch explicitly.
4. **Cache correctness depends on write-path completeness.** Delete-on-write only works if every write path goes through the data-access layer; a single raw-SQL job bypassing it reintroduces stale-forever bugs. The caching and data-access skills must cross-reference each other, or Phase 3 will draft two skills that each assume the other solved it.
5. **pgvector recall gates need a fixture, not a slogan.** The recall-vs-exact check requires a fixed evaluation query set per project; Phase 3 should ship the check as a procedure with a placeholder-free template (synthetic vectors generated in the test, not copied sample data — see risk 1).
6. **Warehouse reconciliation tolerance is a product decision.** "Matches within tolerance" needs a per-metric number at drafting time; leaving it vague makes the gate decorative. Phase 3 drafting should force a stated tolerance field in the reconciliation check template.
7. **Backup drills measure the primary only.** Replica promotion, per-tenant extraction, and warehouse reload are separate recovery paths; the backup-recovery skill should name them as separate drills or Phase 6 proof projects will test only the easiest path.
