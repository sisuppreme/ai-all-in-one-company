## 1. Department standard

Professional analytics, observability, and performance practice today, as D12 will teach it:

- **Instrument once, with OpenTelemetry, and correlate everything.** Applications emit three signals — traces, metrics, logs — carrying the same trace ID and resource attributes, exported through a collector to whatever backend the project uses. The test of observability is behavioral: pick one production request and reconstruct its full cross-service path, pivoting from a span to that service's logs for the same trace ID, without SSH or new code. Sources: OpenTelemetry, "Observability primer", https://opentelemetry.io/docs/concepts/observability-primer/ ; PROJECT_ANATOMY.md, "Observability".
- **Monitor the four golden signals, as percentiles.** Every user-facing service charts latency, traffic, errors, and saturation; latency is tracked at p50/p95/p99, never as an average, and error latency is separated from success latency. A dashboard that charts CPU while the checkout endpoint returns unmeasured 500s is the canonical failure. Sources: Google, *Site Reliability Engineering*, "Monitoring Distributed Systems", https://sre.google/sre-book/monitoring-distributed-systems/ ; PROJECT_ANATOMY.md, "Monitoring".
- **Alert on SLO burn rate, not on causes.** Pages fire on symptom-based, multi-window, multi-burn-rate alerts over an SLO's error budget. The SRE Workbook's recommended starting parameters for a 99.9% SLO over a 30-day window (verified 2026-11-21): page at burn rate 14.4 over 1h/5m windows (2% of budget), page at 6 over 6h/30m (5%), ticket at 1 over 3d/6h (10%); the short window proves the burn is still happening (1/12 of the long window in the paging pairs). CPU-threshold pages that fire on every deploy are the anti-pattern. Every page is actionable and links a runbook; anything slower-burning is a ticket, anything informational is a dashboard. Sources: Google, *The Site Reliability Workbook*, "Alerting on SLOs", https://sre.google/workbook/alerting-on-slos/ ; PROJECT_ANATOMY.md, "Alerting".
- **Logs are structured, central, and clean.** Every production log line is parseable JSON with a consistent field set (timestamp, level, service, trace/request ID, message), shipped off the host to a central store with retention limits — containers are ephemeral, so local log files are lost logs. Passwords, tokens, card numbers, and other sensitive data are never logged, per OWASP. Sources: OWASP, *Logging Cheat Sheet*, https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html ; PROJECT_ANATOMY.md, "Logging".
- **The tracking plan comes before instrumentation, and it is enforced.** Events are designed from the questions the business needs answered, named under one convention — Segment's Object-Action framework ("Product Viewed", "Order Completed") is the reference model — with properties, types, and owners written into a tracking plan that lives with the code. Incoming events are validated against the plan (Segment Protocols is the commercial reference; a JSON Schema plus a CI lint is the portable equivalent), so misspelled or duplicate event names are caught at build or ingest, not discovered in a broken funnel months later. No values and no personal data go into event names. Sources: Twilio Segment, "Naming conventions: why you need them for clean data", https://www.twilio.com/en-us/resource-center/naming-conventions-for-clean-data ; Segment documentation, "Data Collection Best Practices" (tracking plan guidance), https://segment-docs.netlify.app/docs/protocols/tracking-plan/best-practices/ ; PROJECT_ANATOMY.md, "Analytics".
- **Field data decides web performance; lab data diagnoses it.** Core Web Vitals are assessed on real-user field data at the 75th percentile, separately for mobile and desktop, over a rolling 28-day window. The current thresholds (web.dev, verified 2026-11-21; unchanged since INP replaced FID as the responsiveness vital on March 12, 2024):

  | Metric | Good | Needs improvement | Poor |
  |---|---|---|---|
  | LCP (loading) | ≤ 2.5 s | > 2.5 s to 4 s | > 4 s |
  | INP (responsiveness) | ≤ 200 ms | > 200 ms to 500 ms | > 500 ms |
  | CLS (visual stability) | ≤ 0.1 | > 0.1 to 0.25 | > 0.25 |

  A page passes only when all three are good. Lab tools (Lighthouse) reproduce and diagnose; they never overrule a failing field score. Source: web.dev, "Web Vitals", https://web.dev/articles/vitals ; PROJECT_ANATOMY.md, "Performance budgets".
- **Budgets are CI gates, not strategy documents.** A budget file in the repo names numeric limits for the Core Web Vitals, resource sizes/counts, and API latency; Lighthouse CI enforces them on every merge — its `assert` block guards audit values (LCP, total blocking time, CLS) and `budget.json` caps timings, resource sizes, and resource counts per type — exiting non-zero on a breach. Multiple runs are collected and the median asserted, because a single throttled run is noise. Field monitoring then watches the same budgets in production. Sources: PROJECT_ANATOMY.md, "Performance budgets" (verify step: `lhci autorun` present and passing in CI); "Enforcing Performance Budgets with Lighthouse CI", https://www.performanceisolation.com/monitoring-measuring-third-party-performance/enforcing-performance-budgets-with-lighthouse-ci/ (verified 2026-11-21).
- **Money numbers reconcile to the processor of record.** Revenue analytics never trusts its own event stream: analytics revenue is a projection, the payment provider's records (D11's domain) are the truth, and a scheduled reconciliation diffs the two and explains every discrepancy (refunds landing later, disputes, test-mode leakage, missed webhooks). Sources: PROJECT_ANATOMY.md, "Analytics" (skills: revenue-analytics); D11 research file, §1 (provider is the source of truth for money state).
- **Experiments are pre-registered and health-checked.** Each experiment records its hypothesis, one primary metric, planned runtime/sample size, and decision rule before launch; results are read with a sample-ratio-mismatch (SRM) health check, confidence intervals, and at least one full business cycle of runtime. Peeking, early stopping, and cherry-picked secondary metrics are treated as invalid results, not as wins. Sources: PROJECT_ANATOMY.md, "Growth experimentation"; Optimizely experimentation strategy documentation, https://docs.optimizely.com/experimentation-strategy/docs/take-action-based-on-the-results-of-an-experiment
- **Telemetry is personal data and is consent-gated.** Event streams, logs, and traces describe identifiable people's behavior. Collection of non-essential analytics waits for consent state, properties are minimized (no emails, names, or free-text PII in events or logs), retention is limited, and deletion requests must propagate to analytics and log stores. The rules themselves are D14's; D12 skills implement them and hand off at the points marked in §4. Sources: PROJECT_ANATOMY.md, "Analytics" ("consent mode so no data fires before the user agrees"); OWASP *Logging Cheat Sheet* (above).

## 3. Per-skill research notes

### product-analytics

- **Core method:** Start from decisions, not tools. Take the product's metric set from D1 (product-metrics owns definitions; D12 owns measurement) and build a measurement plan: each metric maps to the events and properties that compute it, the platform that stores them, and the review cadence that reads them. Set up the platform deliberately (project structure, identity rules, retention), instrument the primary conversion and retention flows first, validate every event in the platform's debug/realtime view before release, and run a recurring data-quality review (orphan events, volume anomalies, broken funnels).
- **Key rules:**
  1. No metric appears on a dashboard unless its definition and its source events are written down; "numbers nobody defined" is the failure this skill exists to prevent.
  2. Identity is decided once, in writing: what the anonymous ID is, when identify happens, and how pre- and post-login behavior stitches — retroactive identity fixes are the most expensive analytics repair there is.
  3. Non-essential analytics does not fire before consent state is known; consent state is itself recorded so reports can state their coverage honestly (rules: D14 cookie-consent, privacy-laws).
  4. Prefer fewer, well-shaped events with rich properties over an event per button; every event names the question it answers and its owner (per Segment's tracking-plan practice).
  5. Dashboards ship with a stated audience and decision; a dashboard nobody acts on is deleted, not archived forever.
- **Verification gates:** Tracking-plan coverage check (automatable): every metric in the product's metrics document maps to at least one implemented, validated event — an unmapped metric fails the check. Consent test (automatable): a fresh session with consent denied produces zero analytics requests in the network log. Pre-release validation: the primary conversion flow is run in a test session and each expected event is confirmed, correctly named and parameterized, in the platform's debug view (anatomy "Analytics" verify step).
- **Sources:** PROJECT_ANATOMY.md, "Analytics"; Segment documentation, "Data Collection Best Practices", https://segment-docs.netlify.app/docs/protocols/tracking-plan/best-practices/

### event-tracking

- **Core method:** Treat the event taxonomy as an API contract. Maintain the tracking plan as a versioned file in the repo (event name, properties with types, required/optional, owner, the question answered). Generate or hand-write a typed wrapper so application code can only emit planned events. Validate twice: a CI lint checks emitted event names and property shapes against the plan, and ingest-side validation (schema registry or platform Protocols equivalent) flags violations in production data.
- **Key rules:**
  1. One naming convention, enforced mechanically: Object-Action, past tense, one casing standard for events and one for properties, chosen once (Segment recommends Title Case events, snake_case properties; the choice matters less than the enforcement).
  2. No dynamic values in event names and no property keys generated from data — the value goes in a property, or one event becomes hundreds and every report fragments.
  3. Name the outcome, not the widget: "Order Completed" survives a redesign and counts successes; "Checkout Button Clicked" counts clicks that failed validation.
  4. No personal data in event names or properties (no emails, names, free text that can contain PII); user identifiers travel as IDs only (rules: D14 privacy-laws).
  5. Renaming an event is a breaking change: it ships with a plan-version bump, a migration note for affected reports, and a deprecation window — never a silent rename.
- **Verification gates:** Tracking-plan lint in CI (automatable): a build that emits an event absent from the plan, or with a property of the wrong type, fails. Schema-diff check (automatable): the plan file's diff is reviewed like an API diff; unplanned removals fail the check. Production violation report: a scheduled query/lint over recent events lists any name not in the plan; a non-empty list is a defect, not a curiosity.
- **Sources:** Twilio Segment, "Naming conventions: why you need them for clean data", https://www.twilio.com/en-us/resource-center/naming-conventions-for-clean-data ; PROJECT_ANATOMY.md, "Analytics" (slop: duplicate or misspelled event names).

### experimentation-platform

- **Core method:** Build experimentation as a pipeline with gates, not a toggle. Assignment is a deterministic hash of experiment ID + unit ID (usually user ID), so a unit's variant is stable across sessions and devices and reproducible in a test. Exposure is logged as an event (experiment, variant, timestamp) into the same analytics stream as outcomes. Analysis is pre-registered: hypothesis, one primary metric, guardrail metrics, minimum runtime/sample, and the decision rule are written before launch; results unlock only after the SRM health check passes.
- **Key rules:**
  1. Assignment must be stable and server-verifiable: the same unit always sees the same variant, and the assignment function is unit-tested — flicker and cross-device variant flips invalidate everything downstream.
  2. Sample ratio mismatch is a stop condition: if observed split deviates significantly from the configured split, the experiment is broken (logging, bucketing, or bot filtering), and no result is read until the cause is found (Optimizely's Stats Engine treats SRM as a health indicator; the skill teaches the check, chi-squared on observed vs expected counts).
  3. No peeking-based decisions: either fix the horizon in advance or use a sequential/always-valid method; stopping at two days because a variant is "winning" is recorded as an invalid experiment.
  4. Run at least one full business cycle; keep experiments on the same surface mutually exclusive or layered, so overlapping tests cannot contaminate each other.
  5. Every concluded experiment leaves a record — hypothesis, result with confidence interval, ship/kill decision — including losers and inconclusive runs; the record is the product of the program.
- **Verification gates:** Assignment determinism test (automatable): a fixed set of unit IDs hashed twice, across simulated sessions, yields identical variants. SRM gate (automatable): the analysis job computes the split check and refuses to render a verdict while it fails. Exposure-completeness check (automatable): exposure events reconcile with assignment counts within a stated tolerance; a gap means results are computed on partial data and must say so.
- **Sources:** PROJECT_ANATOMY.md, "Growth experimentation"; Optimizely experimentation strategy documentation, https://docs.optimizely.com/experimentation-strategy/docs/take-action-based-on-the-results-of-an-experiment

### revenue-analytics

- **Core method:** Mirror D11's money discipline on the reporting side. Define each revenue metric once, in writing (recognized vs collected revenue, MRR treatment of trials, discounts, refunds, and failed payments), compute it from the payment provider's records rather than from analytics events, and run a scheduled reconciliation that diffs analytics-reported revenue against provider exports and classifies every difference (refund timing, dispute, test-mode record, missed webhook, currency conversion).
- **Key rules:**
  1. The provider of record wins every dispute: when the analytics pipeline and the provider disagree, the provider figure is reported and the pipeline is fixed (D11 research §1 states the same rule from the payments side).
  2. Test-mode and internal transactions are excluded by construction (a filter on the source query), never by hand-cleaning a spreadsheet.
  3. Refunds and disputes are attributed to the original transaction's period for cohort and LTV reporting, and shown separately in cash reporting — one metric silently mixing the two is how both become wrong.
  4. Currency handling is explicit: amounts are stored in the transaction currency with the conversion rate and date used for reporting currency; no silent single-rate conversions.
  5. Every revenue dashboard states its source and its last successful reconciliation time; a dashboard whose reconciliation is stale displays that fact.
- **Verification gates:** Reconciliation diff (automatable): the scheduled job compares analytics revenue to the provider export for the period; unexplained difference must be zero (or every cent itemized) before the period is "closed". Definition lint (automatable): each revenue metric in dashboards traces to the written definition document; a metric with no definition fails the documentation check. Test-mode leak test (automatable): a query asserts zero test-mode transactions in the reporting tables.
- **Sources:** PROJECT_ANATOMY.md, "Analytics" (revenue named as an analytics purpose; revenue-analytics listed as a serving skill); D11 research file, §1 (provider is the source of truth for money state; reconciliation repairs drift).

### logging

- **Core method:** One logging standard for the whole system: a shared logger that emits single-line JSON with a fixed field set (timestamp, level, service, environment, trace ID, request ID, message, plus structured context fields), propagates the trace ID across service boundaries, ships logs off-host via a collector/shipper to a central store, and tiers retention (hot search window, then cheaper archive, then deletion per the retention schedule D14's rules set). Levels are a contract: `error` means a human may need to act; debug logging is off by default in production and can be raised per-service temporarily.
- **Key rules:**
  1. Never log secrets or personal data: passwords, tokens, authorization headers, card numbers, and session IDs are redacted by the logger's field denylist, not by developer memory (OWASP Logging Cheat Sheet).
  2. No unstructured logging in production paths: `console.log`-style free text in server code is a lint failure (anatomy verify step: the count in production paths must be zero).
  3. Every request-scoped log line carries the trace/request ID; a log line that cannot be tied to a request is of forensic value only by luck.
  4. Log the event, not the data dump: structured context fields (order ID, status, duration) instead of serialized objects that leak whatever the object happens to contain.
  5. Log volume is a cost and a signal: noisy success-path logging at scale is treated as a defect (it buries errors and bills like them); high-cardinality identifiers belong in log fields, not in metric labels (that rule lives in monitoring).
- **Verification gates:** Source lint (automatable): grep/lint for raw console logging and for logger calls missing the standard field set in production paths returns zero hits. Redaction test (automatable): a staging request carrying a known canary token and password is made, and a search of the central store for those strings returns nothing. Trace-join test: pick one failed request from the error tracker and confirm every service it touched returns entries under its trace ID (anatomy "Logging" verify step).
- **Sources:** OWASP, *Logging Cheat Sheet*, https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html ; PROJECT_ANATOMY.md, "Logging".


### monitoring

- **Core method:** Build monitoring from the user inward. For each user-facing service, define its SLIs from the requests users make (availability and latency ratios from server-side metrics), expose metrics in a scrapable form (Prometheus-style), pre-aggregate expensive queries with recording rules, and review saturation signals for the resources the service depends on (D6 owns host/cluster saturation; D12 owns the service-level view). The four golden signals are the minimum chart set per service; per-endpoint error rate and latency percentiles are the working view.
- **Key rules:**
  1. Latency is always percentiles (p50/p95/p99) with success and error latency charted separately; averages are banned from dashboards and alerts because they hide exactly the tail users feel.
  2. Every metric label is low-cardinality by design: user IDs, request IDs, full URLs, and error strings never become labels (they explode storage and belong in logs/traces); a cardinality budget is part of adding a metric.
  3. A service is not "monitored" until its golden-signal dashboard exists and its error rate is queryable per endpoint — a homepage ping is uptime theater, not monitoring.
  4. Metrics configuration (scrape configs, recording rules) lives in the repo and parses cleanly: `promtool check rules` (or the platform equivalent) is a CI step, per the anatomy verify step.
  5. Missing data is itself a signal: an absent metric (scrape down, exporter dead) alerts through the alerting skill's dead-man's-switch pattern rather than reading as "zero errors".
- **Verification gates:** Config check (automatable): `promtool check rules` / config lint passes on every change to monitoring configuration. Coverage check (automatable): a script lists user-facing services from the service registry and asserts each has the golden-signal metric set exposed; a service missing any signal fails. Cardinality audit (automatable): a scheduled query lists the highest-cardinality series and flags any label matching ID/URL patterns.
- **Sources:** Google, *Site Reliability Engineering*, "Monitoring Distributed Systems", https://sre.google/sre-book/monitoring-distributed-systems/ ; PROJECT_ANATOMY.md, "Monitoring".

### alerting

- **Core method:** Alerting is a policy layer over monitoring, built from SLOs. For each user-facing SLO, implement the SRE Workbook's multi-window, multi-burn-rate alerts (page at 14.4× over 1h/5m and 6× over 6h/30m for a 99.9% SLO; ticket at 1× over 3d/6h — parameters recomputed for other SLO targets from the same budget-consumption logic, verified 2026-11-21). Route pages through an alert manager with deduplication, grouping, and a documented escalation chain; attach the runbook link and the dashboard link to every alert payload; review the alert inventory on a cadence and delete or demote any alert that repeatedly requires no action.
- **Key rules:**
  1. Page on symptoms users experience (error-budget burn, failed synthetic checks on critical flows), not on causes (CPU, disk, a single host) — causes are ticket or dashboard material unless they are the symptom (Workbook principle; anatomy slop line is the CPU alert).
  2. Every page must be actionable by the person paged, at the hour paged; if the correct response is "wait" or "ignore", the alert is reclassified, not endured.
  3. Every alert carries: what is broken, user impact, the runbook link, and the escalation path. An alert without a runbook link does not ship.
  4. Silence is a managed state: inhibitions and maintenance silences are time-boxed and recorded; a permanently muted alert is a deleted alert pretending otherwise.
  5. Alert quality is measured: track pages per period and the share that required action (the Workbook's precision concern); a falling action share triggers an alert-review task, not more tolerance.
- **Verification gates:** Rules check (automatable): `promtool check rules` passes on the alert rule files in CI. Fire drill (automatable in staging): a staging service is stopped and the page must reach the on-call channel within the documented time, carrying a runbook link (anatomy "Alerting" verify step). Inventory audit (automatable): a scheduled report lists alerts with no runbook link, alerts silent beyond their time box, and alerts that fired repeatedly with no linked incident — each is a defect.
- **Sources:** Google, *The Site Reliability Workbook*, "Alerting on SLOs", https://sre.google/workbook/alerting-on-slos/ ; PROJECT_ANATOMY.md, "Alerting".

### dashboards

- **Core method:** Dashboards are products with users (the on-call engineer at 3 a.m., the founder on Monday), built as code and organized by question. Three standard layers: a product overview (the metrics D1 defined, from product-analytics), a per-service golden-signal dashboard generated from one template, and an incident view (the same service dashboard annotated with deploys and incidents). Dashboards are provisioned from the repo (Grafana provisioning/JSON or platform equivalent) so they are reviewable, versioned, and identical across environments.
- **Key rules:**
  1. Every panel answers a named question and shows units, a threshold or SLO line where one exists, and a time window appropriate to the question; a panel nobody can state the question for is removed.
  2. One template, every service: golden-signal dashboards are generated from a single template so services are comparable and a new service gets a correct dashboard by construction (monitoring owns the signals; dashboards own their presentation).
  3. No console-only dashboards: anything that exists only in a web UI is unreviewed and unrecoverable; dashboard changes go through the same review as code.
  4. Averages are banned here too (see monitoring): latency panels show percentile bands; error panels show rate and count.
  5. Deploy and incident annotations are on by default — a graph without the "what changed" overlay forces the reader to reconstruct causality from memory.
- **Verification gates:** Provisioning check (automatable): dashboards deploy from the repo to a scratch instance and render without datasource errors; a hand-edited production dashboard shows up as drift against the repo version. Template coverage check (automatable): every service in the registry has a dashboard instance generated from the golden-signal template. Freshness check: the product overview's panels all return data for the last 24 hours (the anatomy "Monitoring" verify step applied to the dashboard layer).
- **Sources:** PROJECT_ANATOMY.md, "Monitoring" (good line: every user-facing service has a dashboard built on the four golden signals); Google, *Site Reliability Engineering*, "Monitoring Distributed Systems", https://sre.google/sre-book/monitoring-distributed-systems/

### error-tracking

- **Core method:** Capture every unhandled error — client and server — in a dedicated tracker (Sentry is the reference implementation), grouped into issues by stack trace and fingerprint, tagged with release, environment, and the request's correlation ID so an issue pivots straight into logs and traces. Upload source maps (and server symbolication inputs) as part of the release pipeline so stacks are readable code, not minified offsets. Triage is a cadence with owners: new issues are assigned, regressions (an issue resurging in a newer release) page or ticket by user impact, and release health (crash-free sessions/users) is read at every deploy.
- **Key rules:**
  1. An error users can hit must exist as a tracked issue with a readable stack; "the logs probably have it" is not error handling (anatomy "Error handling": full detail lands in the tracker within seconds, with the correlation ID).
  2. Source maps are part of the release artifact: a release that ships without its maps uploaded is an incomplete release, because every stack from it is undebuggable.
  3. Grouping is curated: fingerprint rules merge one root cause into one issue and split distinct causes sharing a generic message; a tracker where one bug is 400 issues gets ignored, which is the same as having no tracker.
  4. Expected errors are not noise in the tracker: handled, user-facing errors (validation, 404s by design) are logged or counted as metrics, not captured as issues; the tracker is reserved for defects.
  5. User impact drives priority: issues are ranked by affected users and by whether the flow is revenue- or trust-critical, not by raw count alone.
- **Verification gates:** Synthetic-error test (automatable): a staging build triggers a known error; it must appear in the tracker, grouped as one issue, with a de-minified stack, the correct release tag, and a correlation ID that resolves in the log store. Release check (automatable): CI asserts the source-map upload step ran for the release being deployed. Regression drill: mark a resolved issue, reintroduce its error in staging, and confirm the tracker flags it as a regression rather than a new issue.
- **Sources:** PROJECT_ANATOMY.md, "Error handling" and "Logging" (skills: error-tracking); OpenTelemetry, "Observability primer" (correlation model), https://opentelemetry.io/docs/concepts/observability-primer/


### apm

- **Core method:** APM in this repo means OpenTelemetry-based application performance monitoring: automatic plus manual instrumentation of services using OTel semantic conventions, traces sampled with a stated strategy (a head-based baseline rate, with errors and slow requests always kept — via tail sampling at the collector where volume justifies it), metrics exemplars linking a latency spike to example traces, and per-service views (throughput, error rate, duration percentiles, top endpoints, downstream dependencies) built from the same telemetry that feeds monitoring and logging.
- **Key rules:**
  1. One instrumentation standard: OTel libraries and semantic conventions everywhere; a service instrumented with a proprietary one-off agent is a future migration and a present correlation break.
  2. Trace context propagates across every boundary the request crosses — HTTP, queues, background jobs (job payloads carry the trace context) — or the trace silently ends at the exact boundary where incidents live.
  3. Sampling is a written decision with a reason: what rate, what is always kept (errors, slow outliers), and what the blind spot costs; "whatever the default was" is not a sampling strategy.
  4. Span attributes follow the cardinality rule from the other side: rich, high-cardinality detail belongs on spans and log fields (that is what they are for); it never leaks into metric labels.
  5. Instrumentation coverage is inventoried: every service and every async path is listed as instrumented or explicitly not, so "no trace" is a known gap, not a surprise during an incident.
- **Verification gates:** Trace-completeness test (automatable): a synthetic request is driven through the primary flow in staging and its trace must contain spans from every service and async hop it touched; a missing span fails (anatomy "Observability" verify step, applied as a gate). Propagation test (automatable): an enqueued job's spans join the originating trace. Coverage check (automatable): the instrumentation inventory is diffed against the service registry; an unlisted service fails the check.
- **Sources:** OpenTelemetry, "Observability primer", https://opentelemetry.io/docs/concepts/observability-primer/ ; PROJECT_ANATOMY.md, "Observability".

### performance-budgets

- **Core method:** Budgets are set per page template (never as a site-wide average that hides a bad template), anchored to the Core Web Vitals thresholds plus size budgets (JavaScript, total weight, image weight, request counts) and an API latency budget (p95 per critical endpoint). They live in a budget file in the repo and are enforced in two places: in CI by Lighthouse CI (`lhci autorun` — assertions on metric values, `budget.json` for resource sizes/counts, median of multiple runs), and in production by field-data monitoring against the same numbers. A breach has exactly two exits: fix it, or take a written waiver with an owner and an expiry date.
- **Key rules:**
  1. The budget file names numeric limits for LCP, INP, CLS, and bundle size at minimum (anatomy verify step) — a budget expressed as "fast" or "lightweight" is not a budget.
  2. Lab enforcement uses the median of several runs on a pinned setup; a single-run gate is noise-driven and trains the team to ignore or game it.
  3. Budgets ratchet: a template comfortably inside budget gets its size budget tightened to current reality plus headroom, so today's win cannot silently become next quarter's bloat.
  4. Third-party scripts are a named budget line of their own (the `third-party` resource type in `budget.json`): every tag pays rent, and adding one is a budget decision, not a marketing afterthought.
  5. Waivers expire. An expired waiver fails the build again; a permanent waiver is a budget increase and must be recorded as one.
- **Verification gates:** CI gate (automatable): `lhci autorun` runs on the merge pipeline and a failed assertion blocks the merge — the anatomy verify step (performance check present and passing on the last merge) is the audit form of this gate. Budget-file check (automatable): a lint asserts the budget file exists and names numeric LCP/INP/CLS/bundle limits per template. Field check (automatable): a scheduled job compares 28-day field p75 per template against the budget and opens a defect on breach, because CI green does not imply field green.
- **Sources:** web.dev, "Web Vitals", https://web.dev/articles/vitals ; "Enforcing Performance Budgets with Lighthouse CI", https://www.performanceisolation.com/monitoring-measuring-third-party-performance/enforcing-performance-budgets-with-lighthouse-ci/ ; PROJECT_ANATOMY.md, "Performance budgets".

### core-web-vitals

- **Core method:** Measure field first: real-user monitoring (the web-vitals library or the platform's RUM) reports LCP, INP, and CLS per page template, device class, and country, assessed at the 75th percentile over a rolling 28-day window against the web.dev thresholds (LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1 — all three good to pass; verified 2026-11-21). Diagnose in the lab: reproduce the failing template under throttled conditions and decompose the metric — LCP into its subparts (time to first byte, resource load delay, resource load duration, element render delay), INP into long tasks and main-thread blocking, CLS into the specific shifting elements — then fix the dominant subpart, not the metric in the abstract.
- **Key rules:**
  1. Field data is the verdict, lab data is the flashlight: a template is failing while its field p75 fails, whatever a desktop lab run on a fast connection says (the anatomy slop line: the 4 MB hero video that "looked fine on the office connection").
  2. Report per template and per device class, never as one site-wide number — mobile and desktop are assessed separately, and the average of a fast homepage and a slow checkout is a lie about both.
  3. INP is the current responsiveness vital (it replaced FID on March 12, 2024): skills and budgets must not be written against FID, and INP work means keeping the main thread free — breaking up long tasks, deferring non-essential JavaScript — not optimizing first input alone.
  4. CLS fixes are structural: dimensions reserved for images, embeds, and ads before they load; content is never injected above existing content after render except in direct response to user input.
  5. Every fix is verified in field data over the following window, not just in the lab run that suggested it; a fix that does not move field p75 is reverted or reworked, not celebrated.
- **Verification gates:** Field report (automatable): a scheduled job emits per-template p75 for the three vitals (mobile and desktop separately) against the thresholds; any template outside "good" opens a tracked defect. RUM integrity check (automatable): beacon volume per template is compared to pageview volume; a template whose beacons vanish is reported as unmeasured, never as passing. Lab reproduction check: for each failing template, a throttled lab run reproduces the failure mode before optimization work begins (no reproduction, no fix attempt).
- **Sources:** web.dev, "Web Vitals", https://web.dev/articles/vitals ; PROJECT_ANATOMY.md, "Performance budgets".

### performance-optimization

- **Core method:** Optimization is a measured loop, run jointly with D8's load-testing and D3/D5's implementation skills: (1) find the constraint in field or load data (the slow template, the p99 endpoint, the saturated resource); (2) profile to the specific cause (a query plan, a long task, an unindexed scan, an oversized bundle); (3) make the smallest change that addresses that cause; (4) verify with the same instrument that found the problem — field p75 over the next window, or the k6 threshold suite re-run — and record before/after in the change itself. D12 owns the finding and the verifying; the fix itself is executed by the owning department's skill (D3 frontend, D5 data, D4 backend).
- **Key rules:**
  1. No optimization without a measurement that names the problem and a measurement that proves the fix; "should be faster" changes are reverted if the after-measurement is missing.
  2. Optimize the tail, not the average: targets are stated at p95/p99 for APIs and p75 for web vitals; an average that improves while p99 worsens is a regression wearing a costume (anatomy load-testing slop: averages that hide the p99 tail).
  3. Load claims require a real load test: scripted virtual users on the journeys that matter (login, checkout — not the homepage alone) with codified thresholds, e.g. k6 `http_req_failed: ['rate<0.01']` and `http_req_duration: ['p(95)<200']`, failing the run on breach (anatomy "Load and performance testing"; D8 owns the test craft, D12 owns reading results into budgets).
  4. Caching is a correctness decision before it is a speed decision: what is cached, where, and how it invalidates is written down (D5 owns cache implementation); an optimization that serves stale prices or another user's data is a defect, not a win.
  5. Every optimization records its cost side too — complexity added, cache to maintain, infrastructure to pay for — so performance work competes honestly with feature work (anatomy "Cost optimisation" is D6's element; D12 consumes its numbers when a fix proposes bigger infrastructure).
- **Verification gates:** Before/after evidence check (automatable): a performance-labeled change must attach the before/after measurement (field report excerpt or load-test summary) or the change is incomplete. Threshold re-run (automatable): the k6 suite (or the project's equivalent) passes its codified thresholds after the change, in the same environment class as the baseline run. Budget re-check (automatable): the performance-budgets CI gate and field check both pass post-change; an optimization that fixes one template by bloating another fails here.
- **Sources:** Grafana k6 thresholds documentation, https://grafana.com/docs/k6/next/using-k6/thresholds/ ; PROJECT_ANATOMY.md, "Load and performance testing" and "Performance budgets".

## 4. Open risks for Phase 3

- **Event data is personal data — the D14 handoff must be structural, not a footnote.** Analytics events, logs, and traces describe identifiable behavior: user IDs, IP addresses, click paths, and (when developers are careless) emails and free text inside properties. Phase 3 drafters must build D14's rules into the skills as gates, not advice: consent state checked before collection (product-analytics, event-tracking), PII denylists enforced by lint and redaction tests (logging, event-tracking), retention limits and DSAR deletion that provably reach analytics platforms, log stores, and trace backends (privacy-laws, dsar-handling, data-residency own the rules). Open question for drafters: several analytics platforms cannot truly delete a single user's historical events on lower tiers — the skill must say what to do then (stop collecting identifiers, document the limitation) rather than pretend deletion happened.
- **The D6 boundary will be tested by real incidents.** The split stated in this file and in D6's (D6: infrastructure, platform, pipeline, on-call mechanics; D12: product/application signals, SLO policy, dashboards as products) is clean on paper, but saturation is where it blurs: a database CPU spike is D6's signal and D12's latency SLI at once. Phase 3 should draft the two departments' monitoring/alerting skills against each other — D6's alerting content should cover infra alert plumbing and escalation mechanics, D12's the burn-rate policy and dashboard/alert content — and cross-reference rather than duplicate, or the repo will ship two alerting doctrines. D6's research file already flags this dependency ("monitoring/logging/alerting depth → D12"); sequencing D12's monitoring, logging, and alerting skills early in Phase 3 unblocks D6's.
- **Lab green, field red.** Lighthouse CI budgets are necessary and insufficient: lab runs use one device profile and one network, while field p75 reflects real phones, real networks, and real third-party behavior. If Phase 3 writes performance-budgets as a CI-only skill, teams will pass every gate and still fail real users. The field-check gate in performance-budgets and the field-first rule in core-web-vitals exist to prevent this; drafters should keep both and resist merging them away.
- **Low-traffic products break the statistics.** Burn-rate alerts assume enough requests that a burn rate is meaningful (the SRE Workbook itself notes low-traffic ambiguity), Core Web Vitals field data needs enough visits per template to form a p75, and most experiments on a small product will never reach their planned sample size. Proof-scale projects (P1 TaskBoard and similar) sit exactly in this regime. Phase 3 skills need an explicit low-traffic mode: longer windows and ticket-only alert tiers, lab-plus-RUM hybrid judgment for vitals, and honest "underpowered — decide on guardrails and qualitative evidence" as a legitimate experiment outcome, instead of thresholds that silently never fire or, worse, fire on noise.
- **Free-tier observability is a budget decision (D-005).** Retention windows, sampling rates, event volumes, and seat limits on free tiers of error trackers, analytics platforms, and APM backends all truncate exactly the data these skills depend on; the limits also change without notice, so this file deliberately records none of them. Drafters should write each skill to state its minimum viable telemetry (what must survive sampling/retention cuts) and to date any vendor-limit claim it cannot avoid, rather than baking in numbers that decay.
- **Taxonomy and definitions are tool-neutral or they are lock-in.** If event names, metric definitions, and dashboard queries are written in one vendor's dialect, changing analytics or observability vendors means losing history and re-instrumenting. The tracking plan, the metric definitions, and dashboards-as-code are the portable artifacts; Phase 3 should keep vendor specifics in the setup sections of skills and the contracts vendor-neutral, so a migration is a re-implementation of collectors, not a re-definition of what the business measures.
- **Single-agent compatibility cuts both ways.** Everything in this department is maintainable by one agent only because it is code and config in a repo: tracking plan, alert rules, dashboards, budget files. The risk is the opposite temptation — SaaS consoles where a human clicked through a setup wizard. Drafters should require the repo artifact for every console action (provisioning files, exported configs, runbook notes), so the single agent who inherits the project can reconstruct the whole observability stack from the repo alone; any step that exists only in a vendor UI must be written down as a procedure in the skill, or it does not exist for the next agent.
