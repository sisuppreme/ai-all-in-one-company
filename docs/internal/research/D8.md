# D8 — Quality Assurance & Testing: Phase 2 Research

Department scope: proving, mechanically, that what was built actually works — and that what claims to work is not simulated. D8 owns 15 skills: unit-testing, integration-testing, e2e-testing, browser-verification, visual-regression, accessibility-testing, load-testing, chaos-testing, contract-testing, security-testing, test-strategy, qa-gates, test-data, bug-triage, placeholder-scan.

Adjacent ownership: D6 owns the pipeline mechanics (ci-cd) that run D8's gates; D13 owns accessibility standards and remediation (D8 owns the test execution); D7 owns security fixes and penetration-testing authorization (D8 owns security test execution in the pipeline); D12 owns performance budgets as product decisions (D8's load-testing enforces them). D8 is the executing department for the DET-FAKE family: the Fix fields name builder skills (backend-auth, api-building, payments, data-access), but the persistence and network tests that produce the verdict are run by placeholder-scan, browser-verification, and e2e-testing.

## 1. Department standard

How professional QA work runs today, in the order evidence is produced:

**The portfolio is pyramid-shaped, on purpose.** Mike Cohn's test pyramid (from *Succeeding with Agile*, 2009; canonical treatment in Ham Vocke's "The Practical Test Pyramid" on martinfowler.com) allocates effort by cost and precision: many small, fast unit tests at the base, fewer integration tests against real collaborators in the middle, very few end-to-end tests at the top. The two rules that survive every retelling: write tests at different granularities, and the higher a test sits, the fewer of them there should be. Google's testing blog offered a 70/20/10 unit/integration/e2e split as "a good first guess" (2015) — a starting heuristic, not a standard. The inverted shape (the "ice cream cone": thin unit layer, thick manual/UI layer) is the named anti-pattern the pyramid exists to prevent (https://www.martinfowler.com/articles/practical-test-pyramid.html).

**Tests assert user-visible behavior and run isolated.** Playwright's official best practices set the e2e bar: test what the user sees and does, keep every test fully isolated with its own data and state, locate elements by role and label (`getByRole`, `getByLabel`) instead of CSS/XPath, use web-first assertions that auto-wait, and never use fixed sleeps (https://playwright.dev/docs/best-practices). The same principles apply one layer down: a unit test that depends on execution order, wall-clock time, or a shared fixture is a defect in the suite, not a nuisance.

**Integration means real collaborators, mocked only at the system edge.** The middle layer runs the code against a real database (typically a throwaway container started by the test harness), a real HTTP server, real migrations. Mocks are for third parties you do not control (payment providers, email APIs) and are replaced by the provider's own sandbox or recorded fixtures — never a hand-written fake of your own database or your own API, which tests the fake instead of the system (anatomy, Testing element; Vocke, above).

**Contracts are verified by machine, and deployment reads the verdict.** In consumer-driven contract testing (Pact), the consumer's tests record the interactions it actually depends on; the contract is published to a broker; provider CI replays every interaction against the real provider and publishes the verification result; `pact-broker can-i-deploy` then answers, mechanically, whether a version is safe to deploy to an environment — exit code, not opinion (https://docs.pact.io/university/introduction/step13). A contract that copies the provider's full response schema is a known failure mode: it breaks on harmless field additions and trains everyone to ignore it (anatomy, Contract testing element).

**Visual truth is a pixel diff against a reviewed baseline.** Rendered screenshots of key pages and states are compared against baselines committed to the repo (Playwright: `expect(page).toHaveScreenshot()`, baselines regenerated deliberately with `--update-snapshots`). The browser, viewport, and fonts are pinned; dynamic regions are masked; a baseline changes only through a reviewed pull request, never as a side effect of a failing run (https://playwright.dev/docs/test-snapshots).

**Accessibility is automated scan plus hands.** axe-core runs in CI on key pages and states and fails the build on violations (missing labels, invalid ARIA, insufficient contrast). Playwright's own documentation is explicit that automated tests detect only some accessibility problems, so the automated gate is paired with keyboard-only walkthroughs, focus-order checks, and screen-reader passes on critical flows before release (https://playwright.dev/docs/accessibility-testing). "WCAG compliant" is a claim about the whole audit, never about a scan result alone.

**Load is a pass/fail threshold, not a chart.** Load scripts model real user journeys (login, browse, checkout — not the homepage alone) with ramp, hold, and spike phases. Pass/fail is codified before the run as thresholds on percentiles and error rate — Grafana k6's documented pattern is `http_req_duration: ['p(95)<200']` and `http_req_failed: ['rate<0.01']` — and a breached threshold exits the test non-zero and blocks the pipeline (https://grafana.com/docs/k6/next/using-k6/thresholds/). Averages are not reported as results; the p95/p99 tail is where systems collapse.

**Chaos is an experiment, not vandalism.** The Principles of Chaos Engineering method: define a measurable steady state, hypothesize it holds, inject a real-world failure (killed instance, severed dependency, added latency) into the smallest blast radius that tests the hypothesis, watch for deviation, and abort on pre-set criteria. An experiment record without hypothesis, blast radius, and abort criteria is not chaos testing (https://principlesofchaos.org/).

**Security testing follows a named methodology and runs in CI.** The OWASP Web Security Testing Guide provides 100+ test cases with stable IDs (e.g., WSTG-INFO-05, information leakage in comments and metadata) across categories from information gathering to business logic. Scanners (dependency, configuration, SAST) run on every change for breadth; manual testing covers what scanners cannot see — authorization and business-logic flaws. Every finding is recorded with evidence, severity, and remediation, and retested after the fix (anatomy, Security testing element).

**Gates are mechanical and the suite must be able to fail.** Every layer above lands as a required status check in CI (GitHub's model: workflows build and test every pull request, required checks block merge while red — https://docs.github.com/en/actions/get-started/continuous-integration). The anatomy's verification standard for the suite itself is a seeded-fault check: deliberately break an assertion, a threshold, or a CSS rule, and the corresponding gate must go red. A gate that has never been observed failing is decoration. Performance budgets are gates of the same kind: Core Web Vitals thresholds (LCP ≤ 2.5s, INP ≤ 200ms, CLS ≤ 0.1 at the 75th percentile) enforced per page template, e.g. by Lighthouse CI in the pipeline (https://web.dev/articles/vitals; anatomy, Performance budgets element).

**Test data is manufactured, deterministic, and disposable.** Tests build their own data through factories/fixtures with known values, run against a database that is created and destroyed by the harness, and never share mutable state between tests. Seed and fixture data are labeled as such and kept out of production (DET-FAKE-014); production data is never copied into test environments without sanitization. Data a test needs is part of the test, versioned with it.

**Flakes are defects with a budget, not weather.** A flaky test is quarantined only as a tracked, owned state with an expiry date and a ticket; CI retries (Playwright's documented mechanism) exist to gather evidence (traces, videos) about intermittency, not to launder it. The flake rate is measured per suite; a suite whose failures are routinely re-run until green has no gates, whatever its dashboard says.

**Defects are triaged on two independent axes.** Every report enters one queue through a template (reproduction steps, environment, expected vs. actual). Triage validates, deduplicates, sets severity (technical impact) independently from priority (business urgency), assigns a named owner, and schedules the fix or records an explicit won't-fix decision; aging and reopened defects are re-evaluated on a cadence (anatomy, Bug triage element).

## 3. Per-skill research notes

### unit-testing
- **Core method:** One test file per module, run by the stack's fast runner (Vitest, pytest, JUnit). Each test arranges its own inputs, calls one unit, and asserts on outputs and observable side effects — never on internal implementation details that a refactor would break without changing behavior. External collaborators are replaced by test doubles at the unit boundary only. The suite runs in seconds-to-minutes locally and is the first CI job.
- **Key rules:** (1) Every test must be able to fail: assert on a specific expected value; a test that only checks "does not throw" is marked as a smoke test and never counts toward coverage of logic. (2) No shared mutable fixtures, no order dependence — the suite passes with tests shuffled and with any single test run alone. (3) No real network, database, filesystem, or wall-clock: time and randomness are injected. (4) Bug fixes land with the failing test first (or in the same commit), so the regression is permanently pinned. (5) Coverage is a floor signal for untested code, not a target: chase uncovered branches in money, auth, and data-loss paths first.
- **Verification gates:** Seeded-fault check — mutate one assertion's expected value (or run a mutation-testing sample on core modules) and confirm the suite goes red (automatable; the anatomy Testing element's verify step). Suite passes under `--shuffle`/random order and single-test isolation runs in CI (automatable). Suite wall-time budget enforced in CI (e.g., job timeout set from TESTING.md; a breach fails the job).
- **Sources:** Ham Vocke, "The Practical Test Pyramid," https://www.martinfowler.com/articles/practical-test-pyramid.html ; PROJECT_ANATOMY.md, Testing (unit/integration/e2e) element.

### integration-testing
- **Core method:** Tests that run real components together: the API against a real database started by the harness (throwaway container or ephemeral schema), real migrations applied, real HTTP through the framework's test client or a booted server. Third-party services are replaced by the provider's sandbox or a contract-verified stub, never by a hand-written fake of the project's own components. Each test seeds exactly the data it needs and the database is destroyed or reset between tests.
- **Key rules:** (1) The database under test is created by the project's real migrations, not a hand-maintained test schema — schema drift between test and production is itself a failure. (2) Every write endpoint has at least one test that reads the result back through a different surface (API read, second endpoint, or direct query) — this is the integration-level form of the DET-FAKE persistence test. (3) Transaction, permission, and tenant-boundary behavior is tested at this layer: a cross-tenant read attempt must return nothing. (4) Tests clean up by construction (fresh database/transactions rolled back), never by deleting rows other tests might own. (5) Slow tests are tagged and reported; the layer's total runtime is budgeted like the unit layer's.
- **Verification gates:** Full layer runs green from a clean checkout with no pre-existing database (automatable in CI). Negative control: point the suite at a database with one migration reverted — it must fail (automatable). Cross-tenant/authorization test cases present for every multi-tenant entity (checklist gate in review, execution automated).
- **Sources:** Ham Vocke, "The Practical Test Pyramid" (narrow vs. broad integration tests), https://www.martinfowler.com/articles/practical-test-pyramid.html ; PROJECT_ANATOMY.md, Testing element.

### e2e-testing
- **Core method:** A small suite of Playwright journeys covering the flows the business cannot afford to break — signup, login, the core transaction (e.g., checkout), and the top admin action — each fully isolated, creating its own account and data through the UI or a setup API. Tests locate by role/label, use web-first assertions, and run against a deployed preview or staging build in Chromium plus at least one of Firefox/WebKit. Failure paths are journeys too: the decline card declines, the invalid form errors, the killed dependency degrades visibly.
- **Key rules:** (1) No fixed sleeps, ever; waiting is by assertion on visible state or network response. (2) No test depends on another test's data or on execution order; each journey provisions and names its own records. (3) The suite stays small by rule: a flow earns an e2e test by revenue/risk, everything else is pushed down the pyramid — new e2e tests name the lower layer that cannot cover the case. (4) Every fake-functionality class in DET-FAKE that touches a covered flow gets its probe here: reload persistence, second-account convergence, decline path, empty-state honesty. (5) Failures produce trace, screenshot, and video artifacts uploaded from CI; a failure without artifacts is re-run locally before triage.
- **Verification gates:** Suite exits 0 from CI on the preview deployment (automatable; required status check). Seeded-fault check: break one user-visible assertion target (change a heading, disable a submit handler) in a throwaway build — the matching journey must fail (automatable). Provider test-mode suite: documented decline/test cards produce visible declines (automatable, per DET-FAKE-006/007).
- **Sources:** Playwright, "Best Practices," https://playwright.dev/docs/best-practices ; Stripe testing documentation (test and decline cards), https://docs.stripe.com/testing .

### browser-verification
- **Core method:** The rendered-truth pass, distinct from the committed e2e suite: an agent drives the actual build (preview deployment or production URL) in a real browser and inspects what a user would meet — pages render without console errors or failed requests, layout holds at target viewports, and interactive claims are probed live. This is the execution vehicle for the DET-FAKE persistence test and network test (perform the action, reload, sign out/in, second browser; watch the network tab for a real write) and for the DET-VIS parameters that need screenshots and computed styles rather than source reading.
- **Key rules:** (1) Verify the deployed artifact, not the dev server: the URL, build SHA, and environment are recorded with the results. (2) Every probed claim produces evidence — screenshot, network capture, or before/after values — filed with the check, not a bare "looks fine." (3) Console errors and failed (4xx/5xx) requests on any loaded page are findings by default; whitelisting one requires a written reason. (4) Probes use fresh accounts created for the pass, so staged content (DET-FAKE-013/014) cannot hide behind a curated demo account. (5) Viewports and browsers match the project's stated support matrix; a pass at desktop width only is reported as exactly that.
- **Verification gates:** Scripted smoke pass: load every route in the sitemap/route list, fail on any page with a console error, failed request, or blank render (automatable via Playwright script). DET-FAKE two-test protocol executed and recorded for every interactive feature on the release checklist (checklist gate; the persistence/network steps themselves are scriptable per feature).
- **Sources:** skills/detection/fake/PARAMETERS.md, "How to run the check" (persistence + network tests) ; Playwright, "Best Practices," https://playwright.dev/docs/best-practices .

### visual-regression
- **Core method:** Playwright screenshot comparisons (`toHaveScreenshot`) for the pages and component states where layout is the product: marketing pages, dashboards, checkout, email-critical screens. Baselines are generated in the pinned CI environment (same container, browser build, and fonts as the comparison runs), committed to the repo, and compared on every pull request with a small, configured pixel threshold. Dynamic regions (timestamps, avatars, ads) are masked in the test, not tolerated by raising the global threshold.
- **Key rules:** (1) Baselines change only through a reviewed PR whose description states the intentional design change; regenerating baselines to make a red run green without review is a process violation. (2) The environment is pinned end-to-end — a font or browser-version change is a deliberate, repo-wide baseline event, not a per-test fix. (3) A failing diff produces the diff image as a CI artifact; triage reads the diff, never just re-runs. (4) Coverage is by page/state inventory from the design system, not by enthusiasm: every template gets at least its default, empty, and error states. (5) Animations are disabled or frozen in screenshot tests (Playwright's documented approach) so motion never becomes flake.
- **Verification gates:** Seeded-change check: shift a header by 20px in a throwaway branch — the visual job must fail with a diff artifact (automatable; anatomy Visual regression element's verify step). Baseline-drift report: count of baselines changed per release is produced automatically; unexplained mass changes block release (automatable).
- **Sources:** Playwright, "Visual comparisons," https://playwright.dev/docs/test-snapshots ; PROJECT_ANATOMY.md, Visual regression testing element.

### accessibility-testing
- **Core method:** Two layers, both mandatory. Automated: `@axe-core/playwright` scans every key page and state in CI and fails the build on violations. Manual: a scripted keyboard-only walkthrough of the critical flows (Tab order, visible focus, no traps, all actions reachable), a focus-order review, and a screen-reader pass (NVDA/VoiceOver) on the top journeys before release. Findings are filed as defects with the WCAG criterion named, and remediation belongs to D13/D3 — this skill owns detection and retest.
- **Key rules:** (1) Zero-violation is the gate for the automated scan on covered pages; a violation is fixed or filed with an owner and date — never suppressed in the test config without a ticket reference. (2) Automation is never reported as conformance: release notes say "axe scan clean; keyboard and screen-reader pass done on flows X, Y" — Playwright's docs themselves state automated tests detect only some problems. (3) Every form control, dialog, and interactive widget on a covered page is exercised keyboard-only at least once per release. (4) Test in the states users actually meet: error states, empty states, and dialogs, not just pristine pages. (5) Contrast and label checks run on the real rendered page, not on design files.
- **Verification gates:** CI axe suite exits 0; removing a form label in a throwaway branch makes it fail (automatable seeded-fault check; anatomy Accessibility element's verify step). Keyboard walkthrough checklist completed and signed per release for the named critical flows (checklist gate).
- **Sources:** Playwright, "Accessibility testing," https://playwright.dev/docs/accessibility-testing ; PROJECT_ANATOMY.md, Accessibility testing element.

### load-testing
- **Core method:** Grafana k6 scripts model the real journey mix (login, browse, search, checkout in production-like proportions) as virtual users with ramp-up, steady hold, and spike stages, run against staging or a production-like environment with production-shaped data volumes. Thresholds are written into the script before the run — p(95)/p(99) latency and error-rate ceilings derived from the project's performance budgets — and k6's exit code gates the pipeline. Results are archived per release so regressions are visible as trends, not rediscovered.
- **Key rules:** (1) No averages as results: report and gate on percentiles and error rate; a mean that hides a collapsing p99 is a failed report. (2) The scenario mix and data volume are stated in the script header; a run against an empty database is labeled a smoke run and cannot satisfy a release gate. (3) Thresholds come from the budget/SLO documents (D12), and loosening one is a reviewed change to those documents, never an edit inside the test PR. (4) Third parties are stubbed or sandboxed — a load test never hammers a real payment or email provider. (5) Every bottleneck found is filed as a defect with the run's evidence attached; "it got slow at 400 users" without a profile is not a finding.
- **Verification gates:** Tighten one threshold below current performance in a throwaway run — k6 must exit non-zero and block (automatable; anatomy Load element's verify step). Release gate: the standard scenario passes its thresholds on the release candidate (automatable in CI or a scheduled pipeline).
- **Sources:** Grafana k6, "Thresholds," https://grafana.com/docs/k6/next/using-k6/thresholds/ ; PROJECT_ANATOMY.md, Load and performance testing element.

### chaos-testing
- **Core method:** Experiments follow the Principles of Chaos Engineering: pick a user-facing steady state (successful checkouts per minute, p95 latency, error rate), write the hypothesis that it holds under a named failure, inject that failure (kill an instance, sever a dependency, add latency) at the smallest blast radius that tests the hypothesis, and compare experiment against steady state with an abort switch armed throughout. Experiments start in staging, graduate to production only with a game-day record, and rerun on a cadence and after resilience-relevant changes.
- **Key rules:** (1) No hypothesis, no experiment: the record (hypothesis, blast radius, abort criteria, steady-state graphs before/during/after) is written before injection, not reconstructed afterward. (2) The abort switch is tested before the failure is injected. (3) Blast radius starts at one instance/one dependency and grows only after a clean run at the smaller radius. (4) A disproven hypothesis becomes a defect with an owner the same day; the experiment does not rerun until the fix lands. (5) Customer-impacting windows are scheduled and announced per the project's incident-communication practice (D18) — surprise is for the system, not for users or support.
- **Verification gates:** Experiment record completeness check: hypothesis, blast radius, abort criteria, and graphs present for the most recent run (checklist gate, mechanically checkable for field presence). Resilience regression: the standard experiment set (instance kill, dependency loss) passes on the release candidate in staging (automatable where the platform supports scripted injection).
- **Sources:** Principles of Chaos Engineering, https://principlesofchaos.org/ ; PROJECT_ANATOMY.md, Chaos and resilience testing element.

### contract-testing
- **Core method:** For each consumer–provider pair, the consumer's test suite runs its real HTTP client against a Pact mock server and records only the interactions and fields it actually depends on (with type matchers, not literal copies of full responses). Contracts publish to a Pact Broker (hosted, or the open-source broker self-hosted) tagged with the consumer version; provider CI fetches and replays them against the real provider with provider states setting up each interaction, and publishes verification results back. Deployment pipelines call `pact-broker can-i-deploy` against the target environment before promoting.
- **Key rules:** (1) The contract holds what the consumer uses, nothing more: adding a field to a response must never break a contract; removing or retyping a used field must. (2) Verification results are worthless unread — the deploy gate queries them mechanically; a red can-i-deploy blocks promotion like a red test. (3) Provider states are real setup code (seeded records, stubbed downstreams), not hand-written response fixtures, or the replay tests nothing. (4) Contracts are versioned artifacts tied to commit SHAs and branches in the broker; a pact with no version is not publishable. (5) In a single-repo full-stack project, the same flow runs inside one pipeline with the broker optional — the consumer test, provider verification, and gate still execute as separate, ordered steps.
- **Verification gates:** Seeded break: change a required response field's type in the provider — provider verification must fail and can-i-deploy must report the version not deployable (automatable; anatomy Contract element's verify step). Pipeline check: deploy job contains a can-i-deploy step whose failure blocks promotion (config inspection, automatable).
- **Sources:** Pact Docs, "Step 13 — Using a PactFlow Broker" (broker, verification, can-i-deploy), https://docs.pact.io/university/introduction/step13 ; PROJECT_ANATOMY.md, Contract testing element.

### security-testing
- **Core method:** Execution of the OWASP Web Security Testing Guide as a checklist per release: categories relevant to the app (information gathering, authentication, authorization, session management, input validation, business logic) worked through with stable test IDs (e.g., WSTG-INFO-05) and pass/fail evidence recorded per case. Automated breadth comes from CI scanners — dependency vulnerabilities, SAST, secrets scanning, container/config scanning (D7 owns the tooling choices and fixes). Manual effort concentrates where scanners are blind: authorization matrices (replay privileged requests as a low-privilege user — the DET-FAKE-021 probe), IDOR sweeps, and business-logic abuse.
- **Key rules:** (1) Every finding is recorded with evidence, severity, and remediation, and is retested after the fix — an unretested fix is an open finding. (2) Scanner output is triaged, never pasted raw into a ticket: each result is confirmed exploitable, accepted with a written risk note, or marked false positive with the reason. (3) Authorization is tested from the attacker's seat: for every privileged endpoint, a test replays it with a lower-privilege session and requires rejection. (4) Test scope and authorization are explicit — testing runs against the project's own staging/production-like environments under D7's authorization rules; third-party systems are never in scope. (5) Release evidence names the WSTG categories executed for this release; categories skipped are listed as skipped, with the reason.
- **Verification gates:** CI scanner suite runs on every change and fails on new critical/high confirmed findings (automatable). Authorization-matrix tests (privilege-replay per privileged endpoint) pass in the integration/e2e layers (automatable). Per-release WSTG execution record exists with evidence for at least the app-relevant categories (checklist gate).
- **Sources:** OWASP Web Security Testing Guide (WSTG-INFO-05), https://owasp.github.io/www-project-web-security-testing-guide/stable/4-Web_Application_Security_Testing/01-Information_Gathering/05-Review_Webpage_Content_for_Information_Leakage ; OWASP Session Management Cheat Sheet, https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html .

### test-strategy
- **Core method:** The written plan, kept in TESTING.md, that decides where each kind of proof lives for this project: the pyramid allocation by layer, which flows earn e2e coverage and why, which quality attributes get dedicated testing (visual, accessibility, load, chaos, contract, security), the environments each layer runs in, and the budgets (runtime per layer, flake rate, threshold sources). It is written before the suites grow, reviewed when the architecture changes, and every other D8 skill executes against it.
- **Key rules:** (1) Every requirement class in the project's acceptance criteria maps to at least one named layer that can catch its failure; unmapped classes are listed as accepted risks, in writing. (2) The strategy names what is *not* tested and why — silent gaps are the failure mode, explicit exclusions are engineering. (3) Layer budgets are numbers (suite runtime, e2e count ceiling, flake ceiling), so drift from the pyramid is measurable rather than felt. (4) New test types enter the strategy before they enter the repo; a suite nobody owns is deleted or adopted at the next strategy review. (5) The strategy is stack-agnostic in structure (layers, gates, budgets) and stack-specific only in tool names, so it survives a framework change.
- **Verification gates:** Strategy-to-suite audit: sample the acceptance criteria and confirm each maps to an existing, running suite (script-assisted checklist; run per release). Layer census: CI reports test counts and runtime per layer; a census that violates the strategy's budgets fails the review gate (automatable report).
- **Sources:** Ham Vocke, "The Practical Test Pyramid," https://www.martinfowler.com/articles/practical-test-pyramid.html ; PROJECT_ANATOMY.md, Testing element and Appendix A (TESTING.md file research).

### qa-gates
- **Core method:** The definition and wiring of the merge/release gates themselves: which checks are required status checks (unit, integration, e2e smoke, visual, axe, placeholder-scan, lint/build, contract verification, can-i-deploy), what thresholds they enforce (from TESTING.md and the performance-budget file), and how a red gate is appealed (fix, or a written waiver with owner and expiry recorded in the project log — never a silent bypass). Gates are configured as code (workflow files, branch protection) and versioned with the repo.
- **Key rules:** (1) A gate is a command with an exit code, not a judgment: if a human must decide whether it passed, it is a review checklist item, labeled as such, and never reported as an automated gate. (2) Gate definitions and thresholds live in files that predate the change they judge; changing a threshold and the code it failed on in the same PR requires the waiver record and a second justification entry — the threshold change is reviewed as a standards change, not smuggled as a fix. (3) Every gate must have a witnessed failure: seeded-fault checks (broken assertion, removed label, shifted header, tightened k6 threshold) are run when a gate is created and after any pipeline change. (4) Bypass mechanisms (admin merge, `[skip ci]`) are logged and counted; a rising bypass count is itself a quality finding. (5) Flaky gates are quarantined visibly with owner and expiry (see test-strategy budgets) — a gate the team habitually re-runs until green is removed or fixed, never left as noise.
- **Verification gates:** Negative-control suite: a scheduled pipeline run against a branch with one seeded fault per gate class; every gate must report red (automatable — this is the meta-gate that keeps all others honest). Branch-protection audit: required checks list diffed against TESTING.md's gate list (automatable via platform API).
- **Sources:** GitHub Docs, "Continuous integration" (required status checks gating merge), https://docs.github.com/en/actions/get-started/continuous-integration ; web.dev, "Web Vitals" (budget thresholds LCP 2.5s / INP 200ms / CLS 0.1), https://web.dev/articles/vitals .

### test-data
- **Core method:** Data for tests is manufactured by code: factories/builders with sensible defaults and per-test overrides, deterministic seeds for anything random-looking, and lifecycle owned by the harness (database created by migrations, populated per test or per suite, destroyed after). Shared reference data (countries, plans, tax tables) is loaded from the same fixtures development uses. Demo/seed data for development environments is built by the same machinery, clearly labeled, and structurally excluded from production (environment guard in the seed entry point).
- **Key rules:** (1) No test reads data it did not create or explicitly load: shared mutable fixtures are the root cause of order dependence and are banned. (2) Seed data is never presented as real: fixture users, testimonials, and metrics carry the seed marker end-to-end, and the production seed path refuses to run outside an explicit demo flag (DET-FAKE-013/014). (3) No production data in test environments; if production-shaped data is needed, it is generated at the same shape or sanitized under D14's privacy rules. (4) Factories produce valid-by-default objects — a factory that needs three overrides to make a legal record teaches every test the wrong shape. (5) Time-dependent data is generated relative to an injected clock, so tests do not rot as the calendar moves.
- **Verification gates:** Isolation proof: the full suite passes with randomized test order and with each test file run standalone (automatable in CI). Seed-guard check: invoking the seed command with production environment variables exits non-zero (automatable). Fixture scan: seed/fixture files are included in the placeholder-scan sweep for real-looking personal data (automatable).
- **Sources:** Playwright, "Best Practices" (test isolation, own data per test), https://playwright.dev/docs/best-practices ; skills/detection/fake/PARAMETERS.md (DET-FAKE-014, seed data shipped as real users).

### bug-triage
- **Core method:** One intake queue, one template, one cadence. Reports require reproduction steps, environment, expected vs. actual, and evidence (screenshot, trace ID, request/response). Triage sessions validate each report (reproduce or return for information), deduplicate against open and closed defects, set severity (technical impact) and priority (business urgency) as separate fields, assign a named owner, and slot the fix or record a won't-fix/defer decision with its reason. Aging reports and reopened defects are re-reviewed on the cadence; closure requires a verification step (the fix's regression test or a retest note), not just a merged PR.
- **Key rules:** (1) Severity and priority are never the same field and never default to "high": an unclassified report is incomplete, and a queue where everything is high priority has no priority. (2) No reproduction path, no scheduling: reports that cannot be reproduced go back with the specific information needed, and stay visibly in that state. (3) Duplicates are linked to the canonical defect, not closed silently — the duplicate count is signal about user impact. (4) Every defect that escaped a gate names the gate that should have caught it; recurring escapes change the gate, not just the code. (5) A defect closes on verified behavior (regression test green, or retest evidence attached), and reopens without penalty when verification was wrong.
- **Verification gates:** Queue audit: sample 10 open defects — each must carry reproduction steps, environment, severity and priority as separate fields, a named owner, and a state change within the triage cadence (script-assisted checklist; anatomy Bug triage element's verify step). Escape analysis per release: count of production defects with a named should-have-caught gate is reported automatically from defect fields (automatable report).
- **Sources:** PROJECT_ANATOMY.md, Bug triage and defect management element (severity/priority workflow) ; Bug triage process guide, https://www.bugreel.io/blog/bug-triage-process-guide .

### placeholder-scan
- **Core method:** The department's weapon against fake functionality, run in two passes. Static pass: sweep the production build and source for the fingerprints of simulation — lorem ipsum and placeholder copy, TODO/stub handlers (DET-CODE-003), hardcoded fixture arrays rendered as catalogs, `blob:`-only upload paths, success toasts with no preceding request, seed/fixture files reachable from production code. Dynamic pass: execute the DET-FAKE checklist against the running build — the persistence test and network test per interactive feature, wrong-password and decline-card probes, fresh-account emptiness checks. Findings are filed as defects at the DET parameter's severity (blocker for undisclosed simulation of a core function; a labeled demo is never flagged).
- **Key rules:** (1) The scan list is versioned in the repo and grows by rule: every fake that reaches production adds its fingerprint to the static pass and its probe to the dynamic pass. (2) A "success" UI state with no corresponding server write in the network capture is a blocker finding by definition, not a style note. (3) Scan scope is the shipped artifact: production bundle, production routes, production seed state — a clean staging demo does not clear a dirty production build. (4) Allow-list entries (a genuinely labeled demo mode, a sample template download) name the label that makes them honest and expire with the release that was supposed to remove them. (5) The scan never grades its own homework: the scan configuration is part of the reviewed repo, and removing a rule requires the same waiver record as loosening any qa-gate.
- **Verification gates:** Static sweep exits 0 on the production build; seeding a stub handler or a fixture-rendered list in a throwaway branch makes it exit non-zero (automatable seeded-fault check). Dynamic checklist executed per release with evidence filed for every interactive feature (checklist gate; probes scriptable per feature via browser-verification).
- **Sources:** skills/detection/fake/PARAMETERS.md (DET-FAKE-001…022; Fix fields name placeholder-scan for DET-FAKE-015 and DET-FAKE-018) ; PROJECT_ANATOMY.md, Part 12 testing elements.

## 4. Open risks for Phase 3

- **Single-agent self-grading is this department's central hazard.** In this repo's operating model one agent writes the code, writes the tests, and reads the results — every incentive points toward green. The structural countermeasures the skills must encode, not merely recommend: (a) gates are commands with exit codes, defined in files committed *before* the work they judge; (b) seeded-fault negative controls run on a schedule, so a gate that silently stopped biting is itself caught; (c) threshold changes and test changes in the same PR require a waiver record with owner and expiry (qa-gates rule 2); (d) baselines (visual, contract, performance) update only through reviewed diffs whose description names the intentional change; (e) quarantine is a counted, expiring state, so flakes cannot be parked invisibly. Phase 3 drafters should treat any gate phrased as "the agent checks that…" without a command, an artifact, or a diff as unfinished.
- **Assertion-free coverage gaming.** Coverage percentage is the easiest number to inflate with tests that execute code and assert nothing. The unit-testing and qa-gates skills need the mutation-sampling/seeded-fault mechanism spelled out as a runnable procedure, or coverage gates will certify hollow suites.
- **Environment truth vs. free-tier CI budgets (D-005).** Full layers (three browsers, visual, load, contract verification) on every PR can exhaust free CI minutes; the strategy skill must define which gates run per-PR, which run on merge/nightly, and which run per-release — without letting "nightly" become "never" for the expensive gates. The Phase 1 FP work already showed 39 of 44 DET-VIS parameters are untestable from fetched text; they land on browser-verification and visual-regression in the Phase 6 proof, which must be budgeted as real work, not assumed.
- **Visual baseline fragility.** Font rendering and browser builds differ across machines; unless baselines are generated and compared inside one pinned container image, visual-regression will produce the exact failure the anatomy names — a test deleted instead of configured. The skill must specify the pinning mechanism, not just the tool.
- **Contract testing without a broker.** Single-repo full-stack projects (the common case for this repo's playbooks) have no second team and no broker budget; the file-based, single-pipeline variant in the contract-testing notes needs to be a first-class path in the skill, or drafters will either skip contracts or cargo-cult a broker nobody runs.
- **Chaos and load against real infrastructure.** Load tests can cost money and can hit third parties; chaos in production under a single agent has no human watching the abort switch. The skills must stage both (staging first, production only with records, caps, and scheduling) and state plainly which proof projects may skip production chaos and why.
- **Test data vs. privacy.** Production-shaped test data is the perennial shortcut; the sanitization path crosses D14 (privacy) and D5 (data) ownership. The test-data skill needs a hard rule with a mechanical guard (the seed/production refusal check), because a policy sentence alone will not stop a hurried import.
- **Triage theater.** An agent can generate a tracker full of plausible, well-formatted tickets that nobody acts on — the anatomy's exact slop line. bug-triage's defense is the audit gate (sampled defects must show owners, cadence-fresh state changes, and verified closures); Phase 3 should keep that audit mechanical and scheduled, or triage becomes another artifact that merely looks real — the failure this whole department exists to catch.
