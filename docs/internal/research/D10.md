# D10 Research — Project Memory & Documentation

Phase 2 research file. Direct input to Phase 3 drafting of the 10 D10 skills. Sources verified 2026-11-21.

## 1. Department standard

Professional project documentation today runs on five converging practices:

- **Docs as code.** Documentation is written in plain-text markup, stored in Git beside the code, reviewed in pull requests, tested in CI, and published on merge. The Write the Docs community names five borrowed practices: issue trackers for doc gaps, version control, plain-text markup, code review, and automated tests. This is the operating system every D10 skill assumes. (https://sourcegraph.com/blog/documentation-as-code)
- **Diátaxis for content shape.** Documentation is organized by reader need into four forms — tutorials (learning), how-to guides (tasks), reference (facts), explanation (background) — kept separate because mixing them serves no reader well. Diátaxis decides *what goes in* the docs; docs-as-code decides *how they ship*. (https://diataxis.fr/)
- **Keep a Changelog + Semantic Versioning for change history.** One curated file, newest first, six fixed categories (Added, Changed, Deprecated, Removed, Fixed, Security), ISO 8601 dates, an Unreleased section, and version numbers that signal impact per SemVer. (https://keepachangelog.com/en/1.1.0/ ; https://semver.org/spec/v2.0.0.html)
- **ADR practice for decisions.** One short record per significant decision, kept in the repo. Nygard's 2011 format is five sections (Title, Status, Context, Decision, Consequences); MADR 4.0.0 (2024) adds decision drivers, considered options with pros/cons, YAML frontmatter status, and a Confirmation section stating how compliance will be checked. Records are numbered, never rewritten once accepted — a changed decision gets a new record that supersedes the old one. (https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions ; https://adr.github.io/madr/)
- **SRE memory culture for operations.** Runbooks are standardized, executable procedures — Tom Limoncelli's seven sections (service overview, build info, procedures, etc.) are the widely cited shape — and each alert links to its runbook. Postmortems are blameless, written after defined triggers, structured as impact / timeline / contributing causes / follow-up actions with owners, and closed only when preventive actions are in place. Before a service changes hands, Google SRE runs a Production Readiness Review that hunts for "landmines" and agrees takeover conditions. (https://www.pagerduty.com/resources/automation/learn/what-is-a-runbook/ ; https://sre.google/workbook/postmortem-culture/ ; https://www.atlassian.com/incident-management/handbook/postmortems ; https://cloud.google.com/blog/products/gcp/how-sres-find-the-landmines-in-a-service-cre-life-lessons)
- **Mechanical enforcement in CI.** Mature doc systems run markdownlint for structure, lychee for link checking, Vale for prose/style at error level, and a freshness gate: critical pages carry a `last_reviewed` date and the build fails when it exceeds the review window. Prose linters check style, not truth — accuracy still needs review and task tests. (https://datadef.io/guides/en/docs-checks-in-ci ; https://microsoft.github.io/code-with-engineering-playbook/documentation/tools/automation/)
- **A platform file floor.** GitHub's community profile recognizes README, LICENSE, CONTRIBUTING, SECURITY, CODE_OF_CONDUCT, SUPPORT, and GOVERNANCE by name and surfaces them in the UI; CODEOWNERS assigns reviewers per path. D10's mandated set (PROJECT_ANATOMY Appendix A, extended by DECISIONS.md D-006) builds on this floor. (https://docs.github.com/en/enterprise-cloud@latest/communities/setting-up-your-project-for-healthy-contributions/creating-a-default-community-health-file)

## 2. Failure modes this department prevents

From PROJECT_ANATOMY slop lines, by element:

- **Documentation** — "A single sprawling README that mixes tutorial, reference, and rationale; sections generated to look complete while describing features that do not exist; and no owner or update path, so it rots in place."
- **Changelog** — "A changelog that is a dumped git log, a wall of 'bug fixes and improvements,' or entries describing features that never shipped."
- **Handover** — "A handover consisting of a repository link and a cheerful message; a 'handover document' that lists components but no failure modes, no credentials path, no open risks, and no accepting owner."
- **Project status tracking and postmortems** — "A README still containing the project generator's boilerplate, a status doc last updated at kickoff, and a postmortem that names a person to blame and ends with 'be more careful.'"
- **Decision records (Appendix A, DECISIONS.md row)** — the failure the ADR practice exists to prevent: rationale living only in chat or memory, so a later maintainer must "blindly accept the decision or blindly change it" (Nygard).

## 3. Per-skill research notes

### project-templates

- **Core method:** Scaffold every new project from a versioned template that emits the full extended mandated set (Appendix A 22 + D-006 additions: LICENSE, CODEOWNERS, `docs/adr/`, issue/PR templates, .gitignore, dependabot.yml; community files CODE_OF_CONDUCT, SUPPORT, GOVERNANCE where the project is public). GitHub template repositories copy structure but cannot substitute variables; cookiecutter-style generation (Jinja + `cookiecutter.json`) fills project name, owner, and stack choices. Conditional files (CONTENT_METADATA, PAYMENT_SECURITY, CLONE_DESIGN_SYSTEM) are emitted only when the project type triggers them.
- **Key rules:**
  1. Every mandated file is present in the output, or explicitly recorded as not-applicable with a reason — never silently absent.
  2. Templates ship structure, headings, and fill-in prompts — never invented facts, names, metrics, or testimonials (Real Content Rule). Placeholder tokens are variables to be replaced, not content.
  3. The template itself is versioned and changelogged like a product; a template change is a decision-log entry when it alters the mandated set.
  4. Generated projects must pass the same lint/link gates as hand-written ones from the first commit.
- **Verification gates:** Automatable — generate a fresh project and diff the file manifest against the mandated set for that project type; scan output for unreplaced `{{ }}` tokens and TODO markers; run markdownlint over all generated files.
- **Sources:** https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-template-repository ; https://simonwillison.net/2021/Aug/28/dynamic-github-repository-templates/

### documentation-writing

- **Core method:** Classify before writing: every page is exactly one Diátaxis form (tutorial, how-to, reference, explanation) and is written only for that reader need. Content is produced and maintained docs-as-code: same repo, same review, same CI as the code it describes. Style follows a written word list and timeless-writing discipline — document the current state, avoid "currently / new / latest," use active voice and consistent terminology.
- **Key rules:**
  1. One page, one Diátaxis mode. A page that teaches and lists reference facts gets split.
  2. Never document a feature, flag, or behavior that has not been verified against the actual system; unverified content is the department's core defect.
  3. Every page has a named owner and a review trigger (code change in its area, or its freshness window expiring).
  4. Terminology comes from the project word list; a new term is defined at first use or not used.
  5. Doc changes ship in the same change as the code change they describe, or the gap is filed as a tracked issue.
- **Verification gates:** Automatable — markdownlint (structure), lychee (links, scheduled for external URLs), Vale at error level (style/terminology), freshness gate on `last_reviewed` front matter. Manual — the anatomy task test: an unfamiliar reader completes one learn/task/lookup task per doc type using only the docs.
- **Sources:** https://diataxis.fr/ ; https://developers.google.com/style/timeless-documentation ; https://datadef.io/guides/en/docs-checks-in-ci

### readme-writing

- **Core method:** The README is the project's front door and index, not its manual: what it is, who it is for, current status, a quickstart that actually runs, and links into the doc set (ARCHITECTURE, runbook, CHANGELOG, DECISIONS). Depth lives behind the links; the README stays short enough to read in one sitting.
- **Key rules:**
  1. No generator or template boilerplate survives into a shipped README — it is replaced or deleted at project start.
  2. Every quickstart command is executed verbatim, in order, before the README ships or changes; a command that fails is a README bug.
  3. Badges and status claims only if they reflect real, current systems (live CI, real version) — no decorative shields.
  4. The README links to each mandated file; it never duplicates their content, so there is one canonical copy of every fact.
- **Verification gates:** Automatable — extract quickstart code blocks and run them in a clean environment, assert exit 0; lychee over README links; grep for known boilerplate strings from common generators. Manual — a new reader states what the project is and how to run it after one read.
- **Sources:** https://docs.github.com/en/enterprise-cloud@latest/communities/setting-up-your-project-for-healthy-contributions/creating-a-default-community-health-file ; https://sourcegraph.com/blog/documentation-as-code

### runbook-writing

- **Core method:** One runbook per incident class or repeated procedure, written to be executed under pressure by someone who did not build the system. Shape follows Limoncelli's sections (service overview, build/deployment info, procedures, escalation) as popularized by PagerDuty: trigger/symptom first, then numbered steps with exact commands, the expected output at each step, a branch or escalation when reality differs, and verification that the fix worked. The alert links to the runbook; the runbook lives in the repo under code review.
- **Key rules:**
  1. Steps are actions with expected results, not explanations. If a step's output can differ, the runbook says what to do in each case.
  2. Prerequisites — access, credentials location, tools — are stated up front, never discovered mid-incident.
  3. Every runbook ends with an escalation path naming a role (not only a person) and a verification step that proves resolution.
  4. A runbook is updated in the same change as any incident that used it and exposed an error, and after any change to the procedure it describes.
  5. Generic process (declare incident, open timeline) is referenced, not copied into every runbook.
- **Verification gates:** Automatable — freshness gate on `last_reviewed`; lychee over linked dashboards/tools; structural check that required sections (trigger, prerequisites, steps, escalation, verification) exist. Manual — cold run: someone other than the author executes the runbook in a drill or tabletop and completes it without asking a question.
- **Sources:** https://www.pagerduty.com/resources/automation/learn/what-is-a-runbook/ ; PROJECT_ANATOMY Appendix A, runbook.md row (Google SRE practice).

### postmortem-writing

- **Core method:** Blameless postmortem after defined triggers (Google SRE: user-visible downtime, data loss, on-call manual intervention; Atlassian: severity 1–2 mandatory). Fixed structure: summary, impact, timeline built from logs, contributing causes (plural — systems and processes, not a person), mitigation, and follow-up actions. A named owner drives it through drafting, review, and approval; it closes only when preventive actions are filed and tracked.
- **Key rules:**
  1. Blameless by construction: refer to people by role, frame causes as systems/processes; "be more careful" is not an action.
  2. The timeline comes from logs, alerts, and timestamps — never from unaided memory.
  3. Every follow-up action has an owner, a due date, and a tracking ID in the project's tracker; an action without all three does not count.
  4. Causes are contributing and multiple; a single "root cause" line that stops at the trigger is incomplete.
  5. The postmortem is published where the whole team can find it and is linked from progress.md and the relevant runbook.
- **Verification gates:** Automatable — template-completeness check: all required sections present, and every action row has non-empty owner and due-date fields. Manual — blameless-language review pass by someone not involved in the incident; anatomy check: most recent incident has a postmortem with owned, dated actions.
- **Sources:** https://sre.google/workbook/postmortem-culture/ ; https://www.atlassian.com/incident-management/handbook/postmortems

### decision-logs

- **Core method:** ADR practice. Each significant decision gets one numbered file in `docs/adr/` (`NNNN-short-title.md`), written at decision time. Default to Nygard's five sections (Title, Status, Context, Decision, Consequences); escalate to MADR when the decision is contested — adding decision drivers, considered options with pros/cons, and a Confirmation section. DECISIONS.md is the index that links every record; it is not a second copy of their content. Accepted records are immutable except for status: a reversal is a new ADR that supersedes the old one and links to it.
- **Key rules:**
  1. One decision per file; numbers are sequential and never reused.
  2. Context states the forces at play neutrally, as facts; the Decision is written in active voice ("We will…").
  3. Consequences include the negative ones — what becomes harder, what risk is accepted.
  4. Status lifecycle is closed: proposed → accepted → deprecated or superseded-by-ADR-NNNN. No other values.
  5. Rejected options are recorded for contested decisions, with why they lost — that is what stops the decision being reopened.
- **Verification gates:** Automatable — filename/numbering lint (pattern, no gaps or reuse), status value in the allowed set, every ADR file linked from DECISIONS.md and every index link resolving (script cross-check), MADR linting where MADR format is used. Tooling exists: adr-tools (https://github.com/npryce/adr-tools).
- **Sources:** https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions ; https://adr.github.io/madr/

### changelog

- **Core method:** Keep a Changelog discipline. One CHANGELOG.md, newest first. An `## [Unreleased]` section collects notable changes as they land, under the six categories only (Added, Changed, Deprecated, Removed, Fixed, Security). At release, Unreleased is renamed to `## [X.Y.Z] - YYYY-MM-DD` and a fresh Unreleased opens. The version bump follows SemVer: breaking → major, feature → minor, fix → patch — the categories present in a release must be consistent with the bump.
- **Key rules:**
  1. Written for users: entries describe the effect on them, not the implementation or the commit.
  2. Curated, never generated from the raw git log; merge commits and internal refactors with no user effect are omitted.
  3. The entry lands in the same change as the behavior it describes — a release never goes out with an empty Unreleased that should have content.
  4. Dates are ISO 8601; versions are SemVer; no version heading exists without a corresponding release.
- **Verification gates:** Automatable — parser check: headings match `## [Unreleased]` or `## [X.Y.Z] - YYYY-MM-DD`, category headings are a subset of the six, dates are ISO 8601 and in descending order, and the top version equals the project's version source of truth (git tag or package version). Cross-check: three sampled entries each correspond to a real change in the release.
- **Sources:** https://keepachangelog.com/en/1.1.0/ ; https://semver.org/spec/v2.0.0.html

### progress-tracking

- **Core method:** One maintained progress.md is the project's status of record: done, in progress, blocked (with blocker and owner), and next — each entry dated. It is updated in the same change as the work it reports, so status is a by-product of doing the work, not a separate reporting ritual. Decisions are appended to DECISIONS.md as they happen; incidents link their postmortems. Status claims must match the deliverables — the anatomy Verify test is the standard: README and progress record carry dates within the current work cycle and agree with the actual state of the work.
- **Key rules:**
  1. No undated status. An entry without a date is treated as stale and removed or re-verified.
  2. "Done" means the artifact exists and is findable — every done item names or links what was produced.
  3. Blocked items name the blocker, its owner, and what unblocks them; "waiting" alone is not a status.
  4. progress.md reports state, it does not narrate effort; history belongs in git and the work log.
- **Verification gates:** Automatable — freshness gate: progress.md's last commit date (`git log -1`) falls within the current work cycle; link/artifact check: files named as done exist in the repo. Manual — sample three entries and confirm each against the actual deliverable.
- **Sources:** https://datadef.io/guides/en/docs-checks-in-ci (freshness-gate pattern) ; PROJECT_ANATOMY Part 11, "Project status tracking and postmortems" (progress.md is a brief-internal file — no external standard exists for the name; the discipline above is the project's own).

### memory-retrieval

- **Core method:** Retrieval is designed, not hoped for: the mandated file set has fixed names and locations, README/docs index links every mandated file, DECISIONS.md indexes every ADR, and each fact has exactly one canonical home that other documents link to instead of copying. In a docs-as-code repo, retrieval is plain-text search (grep/git log) over consistently named files plus the index pages — no hosted search service, which keeps it working for a single agent with only the repo. Superseded documents are marked and linked to their replacement, never silently deleted, so an old answer is visibly old.
- **Key rules:**
  1. One canonical location per fact; duplicates are replaced by links at the moment they are noticed.
  2. Every mandated file is reachable from the README or docs index in at most two hops.
  3. File and heading names follow the set's conventions, so a searcher can guess the term that will hit (decision → DECISIONS.md/`docs/adr/`, incident → postmortem/runbook).
  4. Retrieval is tested, not assumed: the handover cold-run and a scripted known-fact search are the acceptance tests.
- **Verification gates:** Automatable — lychee crawl starting at the README/index: zero mandated files orphaned (unreachable); scripted retrieval test: a fixed list of known-fact queries (e.g. "which database," "current version," "on-call escalation") must return the canonical file among the top grep hits. Manual — a fresh reader answers five project questions using only the repo, timed.
- **Sources:** https://sourcegraph.com/blog/documentation-as-code ; https://docs.github.com/en/enterprise-cloud@latest/communities/setting-up-your-project-for-healthy-contributions/creating-a-default-community-health-file

### handover

- **Core method:** Handover is a process with an acceptance test, modeled on Google's Production Readiness Review: a readiness review against a checklist (the mandated file set, fresh and complete), walkthroughs of architecture and failure modes, an explicit landmines list — known risks with the evidence for each — a documented credentials path (where secrets live and how access is granted, never the secrets themselves), and a named receiving owner who accepts the transfer. handover.md is maintained during the project and finalized at transfer, not written from scratch at exit.
- **Key rules:**
  1. No handover without a named accepting owner; the acceptance is recorded in handover.md with a date.
  2. Open risks and landmines are listed explicitly, each with evidence or a link — "none known" must be a stated finding, not an omission.
  3. The credentials path names systems and grant procedure; secret values never appear in handover materials.
  4. Runbooks, postmortems, and DECISIONS.md are part of the transfer — the receiver gets the project's memory, not only its code.
- **Verification gates:** Automatable — checklist manifest: all mandated files present and within their freshness windows (reuses the project-templates manifest diff and freshness gates). Manual — the anatomy cold-run test: using only the handover materials, the receiving owner deploys the project, finds the runbook, names the top open risks, and states who accepted the transfer; any failed step is a handover gap that blocks sign-off.
- **Sources:** https://cloud.google.com/blog/products/gcp/how-sres-find-the-landmines-in-a-service-cre-life-lessons ; PROJECT_ANATOMY Part 1, "Handover."

## 4. Open risks

- **Brief-internal files have no external standard.** progress.md, handover.md, fact-sheet.md, stack.md and several other mandated names are this project's own conventions (Appendix A marks them UNVERIFIED as external conventions). Drafters must write content specs from the anatomy elements alone and must not dress them up as industry standards.
- **DECISIONS.md vs `docs/adr/` duality.** External ADR practice is one file per decision in `docs/adr/`; the brief and this build also keep a DECISIONS.md. The decision-logs drafter must fix the relationship (index vs records) in the skill itself, or projects will maintain both badly.
- **Freshness windows are policy, not standard.** No source fixes a universal review window for runbooks/progress/docs. Drafters must set per-tier defaults, label them as project policy, and make them parameters — a hardcoded number will be wrong for some project types.
- **Single-agent compatibility constrains the gates.** Several standard gates assume GitHub Actions and hosted CI. Every gate in these skills must also be runnable as a local script by one agent with only the repo (git, grep, a Markdown parser); the CI workflow is a wrapper, not the gate.
- **Changelog's version source of truth varies by stack** (git tag, package.json, VERSION file). The changelog gate must detect or be told the source; assuming one will produce false failures.
- **Postmortem triggers and severity scales are organization-specific.** Google's and Atlassian's triggers are examples, not universals; the skill must parameterize trigger thresholds or small projects will either over- or under-produce postmortems.
- **project-templates depends on unsettled inputs.** Which conditional files fire depends on project type classifications owned by D1/D2 playbooks (payments, content, clone); until those land, the template skill's decision table has holes the drafter must mark rather than guess.
- **Retrieval testing is the weakest gate.** The scripted known-fact search test needs a per-project query list; a generic list shipped in the skill will test the template's facts, not the project's. Drafters should make the query list a required project artifact (e.g. in handover.md) or the gate degrades to the link crawl alone.
