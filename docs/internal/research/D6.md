# D6 — DevOps & Infrastructure: Phase 2 Research

Department scope: everything between "the code is merged" and "the service is running, reachable, observable, and recoverable in production." D6 owns 17 skills: ci-cd, preview-environments, deployment-strategies, containers, kubernetes, infrastructure-as-code, servers-vps, hosting, free-tiers, cdn-strategy, domains-dns, ssl-certificates, scaling, reliability, incident-response, rollback, cloud-costs.

Adjacent ownership: D5 owns backup-recovery and migrations; D7 owns secrets-management; D12 owns monitoring/logging/alerting dashboards as products. D6 skills consume those outputs and own the pipeline, the platform, and the operational posture. Where a DET-INF parameter's Fix names a non-D6 skill, the D6 note says so.

## 1. Department standard

How professional DevOps work runs today, in the order a change travels:

**Build once, verify automatically, promote the same artifact.** Every push and pull request triggers CI on a clean runner: install from the lockfile, lint, build, run unit/integration/e2e layers. Required status checks gate the merge; a red pipeline is a stop, not background noise (DET-INF-001/002). The merged commit produces one immutable, versioned artifact (container image by digest, or a platform build) that is promoted unchanged through preview → staging → production, so what was tested is exactly what ships. DORA's continuous-delivery capability research names the practices that drive this: test automation, deployment automation, trunk-based development (short-lived branches merged to mainline at least daily), and loosely coupled architecture (https://dora.dev/capabilities/continuous-delivery/).

**Deploy progressively, roll back by repointing.** Release strategy is chosen per risk: rolling replacement as the baseline, blue-green (two identical environments, router switch, instant return) or canary (small traffic share first, metrics-gated promotion) for higher-risk changes. Deployment and release are separate events — feature flags decouple them. Production deploys in GitHub Actions are gated by environment protection rules (required reviewers, deployment-branch restrictions, wait timers) before the job can access production secrets (GitHub Docs, "Managing environments for deployment," https://docs.github.com/en/enterprise-server@3.11/actions/managing-workflow-runs-and-deployments/managing-deployments/managing-environments-for-deployment). Rollback is a rehearsed repoint to the previous artifact, never a forward fix under pressure.

**Infrastructure is code, state is shared, drift is a finding.** Compute, network, DNS, and storage are declared in Terraform/Pulumi/CloudFormation (or the platform's committed config files), reviewed like code, applied from CI. State is remote with locking; `plan` runs read-only in review and any unexplained drift fails the change (DET-INF-024). Console changes are emergencies, back-ported the same day.

**TLS is automated end to end.** Certificates come from an ACME CA (Let's Encrypt's 90-day certificates exist specifically to force automation) or are provider-managed. Renewal runs on a timer (Certbot systemd timer/cron), a deploy hook reloads the server after renewal, and an expiry alert fires weeks ahead as a backstop (DET-INF-016). Server TLS follows the Mozilla Intermediate profile: TLS 1.2+ only, current ciphers, HSTS after HTTPS is stable, HTTP 301-redirects to HTTPS, zero mixed content (DET-INF-014/015).

**Reliability is budgeted, not hoped for.** Services carry SLOs built on user-facing SLIs (availability, latency percentiles). The error budget (100% − SLO; a 99.9% 30-day SLO = 43.2 minutes of allowed downtime) governs release pace: budget healthy → ship; budget exhausted → freeze and fix (Google SRE Workbook). Monitoring covers the four golden signals — latency (percentiles, error latency separated), traffic, errors, saturation. Alerts are symptom-based, multi-window burn-rate alerts on the SLO (page at fast burn, ticket at slow burn), each alert linked to a runbook and routed to a named on-call rotation with escalation (DET-INF-011/012/028). Logs are structured JSON with trace IDs, shipped to a central searchable store with retention; OpenTelemetry correlates traces, metrics, and logs under one trace ID.

**Recovery is rehearsed, with numbers.** Every workload has written RTO/RPO targets and a chosen strategy on the AWS-documented spectrum (backup and restore → pilot light → warm standby → multi-site). Backups are automated, encrypted, stored outside the primary failure domain, and restore-tested on a cadence — a backup that has never been restored is a hypothesis (DET-INF-008/009/010). Incidents run under a named Incident Commander who coordinates and communicates but does not personally fix; every significant incident produces a blameless postmortem with owned, dated follow-ups (PagerDuty Incident Response Guide).

**Cost is allocated and alarmed from day one.** Following the FinOps cycle (Inform, Optimize, Operate): ≥90% of spend is allocated to a service/team via tags or accounts, unit costs (per request, per customer) are visible, budget alerts and anomaly detection (e.g., AWS Budgets + Cost Anomaly Detection) catch runaway spend before the invoice does (DET via cloud-costs; anatomy Cost optimisation element).

**Free tiers are a launch vehicle with printed limits, not a production plan.** Per D-005, projects launch on free tiers at $0 spend — but every tier in the stack is recorded with its cap, its sleep/expiry behavior, its commercial-use terms, and the date checked, plus a usage alert below the cap where the provider offers one. Verified examples (checked 2026-11-21): Render free web services spin down after 15 minutes without inbound traffic, take about a minute to spin back up, share 750 free instance hours per workspace per month, lose local filesystem changes on spin-down, and Render's docs say not to use them for production applications; Render free PostgreSQL expires 30 days after creation (https://render.com/docs/free). Vercel's Hobby plan includes 100 GB Fast Data Transfer and 1M function invocations per month and cannot buy extra usage; Netlify's Free plan carries a 300-credit monthly limit; GitHub Actions is free on standard runners for public repositories with 2,000 included minutes/month for private repos on GitHub Free (anatomy Free-tier options element, as of 2026-11).

## 3. Per-skill research notes

### ci-cd
- **Core method:** One pipeline definition in the repo (`.github/workflows/*.yml` or platform equivalent) triggered on push and pull request: checkout → install from lockfile → lint → build → unit/integration/e2e → publish immutable artifact → deploy jobs per environment. Status checks are required on the protected branch. Delivery performance is reviewed with the DORA four keys (deployment frequency, lead time for changes, change fail rate, failed-deployment recovery time) computed from pipeline + incident records, not vibes.
- **Key rules:** (1) The pipeline must be able to fail: a deliberately broken test turns the check red and blocks merge — verify this, don't assume it. (2) Build once: the artifact deployed to production is bit-identical to the one tested in staging (digest/tag recorded per deploy). (3) No skipped tests, `continue-on-error`, or commented-out steps on gating jobs. (4) Dependencies install from the lockfile in CI (`npm ci`, `--frozen-lockfile`); no installs at container start or deploy time. (5) Dependency updates flow as automated PRs (Dependabot/Renovate) and base images are scanned in CI (DET-INF-025).
- **Verification gates:** Throwaway PR with a failing test → workflow runs, reports failure, merge blocked (automatable via API check on check-run status). Artifact-digest equality check between staging and production deploy records (scriptable). Workflow lint (e.g., actionlint) in CI itself.
- **Sources:** GitHub Docs, "Continuous integration," https://docs.github.com/en/actions/get-started/continuous-integration ; DORA, "Continuous delivery," https://dora.dev/capabilities/continuous-delivery/

### preview-environments
- **Core method:** Every pull request gets an ephemeral environment built from the same artifact path as production: platform-native previews (Vercel/Netlify Deploy Previews) or a pipeline-spun namespace/stack per PR, seeded with non-production data, torn down on merge/close. The preview URL is posted on the PR automatically and is the unit of review.
- **Key rules:** (1) Previews never point at production data or production credentials — separate database, separate secrets (DET-INF-003). (2) Preview config differs from production only by env values, never by code path. (3) Teardown is automatic; orphaned previews are a cost and attack-surface leak. (4) Preview count/age is capped and visible, because preview sprawl is how free CI minutes and platform quotas die.
- **Verification gates:** Open a test PR → preview URL appears, serves the PR's commit SHA, and uses a non-production database host (scriptable check on env + response). Close the PR → preview is gone within the documented window.
- **Sources:** Netlify Docs, "Create deploys" (Deploy Previews), https://docs.Netlify.com/site-deploys/create-deploys ; Vercel Docs, "Deploying Git Repositories with Vercel," https://vercel.com/docs/v1/features/repositories/

### deployment-strategies
- **Core method:** Choose the strategy per change risk and record the choice: rolling (default), blue-green (two identical environments, smoke-test the idle one, switch the router, keep the old one warm for instant return), canary (small traffic percentage, compare error rate/latency against baseline, promote or auto-abort on thresholds). The same immutable artifact is promoted preview → staging → production; production jobs sit behind environment protection rules (required reviewers, branch restrictions). Deploy and release are decoupled with feature flags for anything user-visible and risky.
- **Key rules:** (1) No manual deploy steps: no FTP/SFTP copies, no SSH `git pull` + restart, no builds on the production server (DET-INF-004). (2) Every deploy produces a record: artifact digest, commit SHA, who/what/when — the live revision is always identifiable. (3) Database changes ship as expand-and-contract so old and new code both run during the promotion window (DET-INF-018). (4) Config comes only from environment variables/config service per target; the artifact itself never changes between environments (DET-INF-007). (5) A strategy without a defined abort condition is not a strategy: canary/blue-green name the metric and threshold that sends traffic back.
- **Verification gates:** Deploy-history audit: last three deploys each resolve to a commit SHA + artifact digest (scriptable). Staging drill: run a canary/blue-green switch and the switch-back, timed, with the abort threshold exercised.
- **Sources:** GitHub Docs, "Managing environments for deployment," https://docs.github.com/en/enterprise-server@3.11/actions/managing-workflow-runs-and-deployments/managing-deployments/managing-environments-for-deployment ; PROJECT_ANATOMY.md Part 4, Deployment element (Vercel Git workflow as the good example).

### containers
- **Core method:** One Dockerfile per service, multi-stage: a build stage with the full toolchain, a slim runtime stage carrying only the artifact and its runtime dependencies. Dependencies install before source is copied (layer-cache order), the process runs as a non-root user, and the image is tagged by version and digest — never `latest` (DET-INF-026). A committed `.dockerignore` keeps secrets, `.git`, and local artifacts out of the build context.
- **Key rules:** (1) Pin base images to a specific version tag; for production builds pin by digest. (2) No secrets in `ENV`/`ARG` or any layer — runtime injection or BuildKit secret mounts only (DET-INF-005). (3) Final stage runs non-root (`USER` set) and contains no compiler/SDK. (4) One process per container; exec-form `CMD`/`ENTRYPOINT` so the app is PID 1 and receives signals. (5) Images are scanned in CI and rebuilt regularly so base-image patches actually land (DET-INF-025).
- **Verification gates:** `hadolint` (or equivalent) passes on every Dockerfile in CI (automatable). Image scan (Trivy) reports no unpatched criticals at release. Scripted check: deployed image reference is a digest/version tag, not `latest`.
- **Sources:** Docker Docs, "Building best practices," https://docs.docker.com/build/building/best-practices/

### kubernetes
- **Core method:** Kubernetes is adopted only when the workload needs it (multiple services, real scaling/failover requirements) — otherwise a platform or a VPS is the professional choice. Workloads are declared as manifests/Helm charts in Git, applied by the pipeline. Every container declares resource requests and limits sized from observed usage; utilization-based autoscaling (HPA) measures against the request, so no request = no autoscaling. Liveness and readiness probes reflect real ability to serve (DET-INF-020).
- **Key rules:** (1) Every workload sets requests and limits; BestEffort pods (no resources at all) are evicted first and are not a production posture (DET-INF-027). (2) Readiness checks dependencies, liveness does not — confusing them causes restart loops during dependency outages. (3) Stateless tiers run ≥2 replicas across failure domains behind a Service; state lives in managed stores or replicated operators, not in a pod on the same box (DET-INF-019). (4) Rollout history is kept so `kubectl rollout undo` is always available (see rollback). (5) Manifests are the IaC: console/`kubectl edit` changes are emergencies, back-ported same day (DET-INF-024).
- **Verification gates:** `kubectl apply --dry-run=server` + manifest lint in CI (automatable). Probe test in staging: stop a dependency → readiness fails, pod drains, liveness does not restart-loop. Kill-one-pod drill: service stays up.
- **Sources:** Kubernetes Docs, "Configure Liveness, Readiness and Startup Probes," https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/ ; Kubernetes Docs, "Deployment" (rollout history/undo), https://kubernetes.io/docs/concepts/workloads/controllers/deployment/

### infrastructure-as-code
- **Core method:** All durable infrastructure — compute, network, load balancers, DNS, storage, IAM — is declared in code (Terraform/Pulumi/CloudFormation, or a managed platform's committed config files, which count as its IaC) in the project repo or a named companion deployment repo. Workflow: change → `plan` in the PR showing exactly what will change → review → apply from CI. State is remote, locked, and access-controlled; environments are stamped from the same modules with different variables.
- **Key rules:** (1) `plan` against live state reports no changes (or only intended ones) — unexplained drift is a fail, not a curiosity (DET-INF-024). (2) Before declaring "no IaC," check companion deployment repos and non-Terraform declarative systems; the test is declaration + convergent application, not the tool brand. (3) State files are never committed with secrets, never edited by hand, and are themselves backed up. (4) Modules are versioned and reused across environments; per-environment copy-paste forks are drift factories. (5) Destroy is a reviewed operation with the same plan gate as create.
- **Verification gates:** CI runs `terraform plan` (read-only) on every infra PR and on a schedule; non-empty unscheduled plan = drift alert (automatable). Fresh-environment build test: apply the code into an empty account/namespace and pass smoke checks.
- **Sources:** HashiCorp, "Terraform Language Documentation," https://developer.hashicorp.com/terraform/language ; HashiCorp, Terraform state documentation (cited in DET-INF-024), https://developer.hashicorp.com/terraform/language/state

### servers-vps
- **Core method:** A VPS is a legitimate production host when run like one: provisioned by script/playbook (not by remembered console clicks), hardened to a maintained baseline, patched on a cadence, and fronted by a reverse proxy terminating TLS. The server is treated as replaceable: everything needed to rebuild it lives in the repo.
- **Key rules:** (1) Baseline hardening before first deploy: directory listing off, version banners suppressed, only required ports open, unused services/vhosts removed, default pages gone (DET-INF-022). (2) Debug/admin surfaces are never reachable on the public host; admin sits behind auth + network restriction (DET-INF-021). (3) OS and package patching is scheduled and recorded; an unpatched-since-provisioning box is a finding (DET-INF-025). (4) Deploys land as artifacts (containers or release directories with symlinks), never as in-place edits on the live server (DET-INF-004/017). (5) Logs ship off the box; a full disk on an unmonitored VPS is the classic silent killer, so disk saturation has an alert (DET-INF-027).
- **Verification gates:** External port scan reconciled against the architecture document (automatable). `curl -sI` banner/listing checks in the release checklist. Rebuild drill: provision a fresh VPS from the repo's scripts and pass smoke tests, timed.
- **Sources:** DET-INF-021/022 sources (OWASP Logging Cheat Sheet exposure guidance), https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html ; PROJECT_ANATOMY.md Part 4, Infrastructure/Hosting elements.

### hosting
- **Core method:** Pick the host by workload shape and record the decision with its real limits: Git-connected managed platform (Vercel/Netlify/Render/Fly.io) for standard web apps, cloud provider for special requirements, VPS/containers for cost or control. The record names region(s), scaling behavior, sleep policy, bandwidth/build caps, and the exit path. Production is verified from outside: the public URL loads over HTTPS from a different network, and the dashboard shows the deployment built from the current commit.
- **Key rules:** (1) A named production deployment with availability requirements does not run as a single instance with its database on the same box unless that risk is a recorded decision with an exit path (DET-INF-019). (2) Health checks reflect the app's real ability to serve, not a static page (DET-INF-020). (3) No debug surfaces, default configs, or unthrottled auth endpoints ride along with the hosting choice (DET-INF-021/022/023). (4) Platform config files are committed and treated as the IaC of record; console and config must match (DET-INF-024). (5) Ephemeral-filesystem platforms never hold state: uploads and databases live in real stores, because redeploys and spin-downs delete local files (Render free behavior, checked 2026-11-21).
- **Verification gates:** External check: production URL from a second network returns the app over valid HTTPS; deployment's commit SHA == repo HEAD (scriptable). Host-limit sheet exists in project docs with caps + date checked.
- **Sources:** Netlify Docs, "Create deploys," https://docs.Netlify.com/site-deploys/create-deploys ; Render Docs, "Deploy for Free" (free-tier behavior), https://render.com/docs/free

### free-tiers
- **Core method:** For each provider in the stack, read the official pricing/limits page and record, in the project notes: the cap, what happens at the cap (hard stop vs. billing starts), sleep/expiry behavior, commercial-use terms, and the date checked. Set a usage alert below the cap where offered. Choose the stack so the binding constraint is known before launch, and name the first paid upgrade and its trigger (D-005: stay at $0 until the user sets a cap).
- **Key rules:** (1) No invented limits — a number without an official page and a check date does not go in a launch plan. (2) Never run a production business on a personal/non-commercial-use-only tier. (3) Sleeping tiers (e.g., Render free: spin down after 15 idle minutes, ~1 minute spin-up, filesystem lost on spin-down — checked 2026-11-21) are for demos and validation, not for anything with users, webhooks, or scheduled jobs. (4) Expiring resources are launch blockers: Render free PostgreSQL expires 30 days after creation (checked 2026-11-21) — record the expiry date in the project notes the day it is created. (5) Watch shared pools: Render's 750 free instance hours are per workspace per month, not per service (checked 2026-11-21); Vercel Hobby cannot purchase extra usage past its caps (100 GB transfer, 1M invocations, as of 2026-11), so hitting a cap means downtime or a plan change, not a bill.
- **Verification gates:** Free-tier sheet audit: every provider in the stack has cap + behavior + terms + date checked, all ≤90 days old (checklist gate). Usage alerts exist below each hard cap where the provider supports them.
- **Sources:** Render Docs, "Deploy for Free," https://render.com/docs/free ; Vercel Pricing, https://vercel.com/pricing ; Netlify Pricing, https://www.netlify.com/pricing/ ; GitHub Docs, "GitHub Actions billing," https://docs.github.com/en/billing/concepts/product-billing/github-actions (all as recorded in PROJECT_ANATOMY.md Part 4, Free-tier options element).

### cdn-strategy
- **Core method:** Static assets and cacheable responses are served from a CDN in front of the origin, with cache rules set per content type: fingerprinted static assets cached long with immutable headers, HTML short or revalidated, authenticated/API responses never publicly cached. The CDN/WAF layer is also the edge control point: TLS termination, HTTP→HTTPS redirect, and rate limiting for auth and expensive endpoints (DET-INF-023).
- **Key rules:** (1) Cache keys and invalidation are designed, not defaulted: a deploy must purge or version assets so users never get a mixed old/new page. (2) Rate-limit rules exist for login, password-reset, signup, and paid-cost API paths, stricter for unauthenticated traffic, with alerting on sustained abuse. (3) Origin is shielded where the platform allows it (origin only accepts CDN traffic), otherwise the CDN is decoration. (4) Mixed content is impossible by construction: all asset URLs are HTTPS or protocol-relative behind the CDN (DET-INF-015).
- **Verification gates:** Header audit on key routes (`curl -sI`): cache-control matches the per-type policy, HTTPS redirect present (automatable). Throttle test: scripted repeated logins from one IP trigger 429/block.
- **Sources:** Cloudflare Docs, "Rate limiting rules," https://developers.cloudflare.com/waf/rate-limiting-rules/ ; PROJECT_ANATOMY.md Part 4, Hosting element (CDN serving model).

### domains-dns
- **Core method:** The domain is an organizational asset: registered to the organization (or demonstrably recoverable by it), auto-renew on, MFA on the registrar account, transfer lock on. DNS is managed as records with intent: apex + `www` to the host (CNAME flattening/ALIAS at apex where needed, never a bare CNAME breaking other apex records), TXT records for certificate validation and mail authentication (SPF, DKIM, DMARC). Zone changes are versioned or at least exported, and expiry is monitored (DET-INF-030).
- **Key rules:** (1) Before any migration, lower TTL (proxied Cloudflare records default to an automatic 300s TTL, as of 2026-11), make the change, verify, then raise TTL — "propagation" is never an excuse for a record that was never created. (2) Records are verified with `dig` against the host's documented targets, not by eyeballing a dashboard. (3) Mail records ship with the domain setup, not after the first spam-folder incident. (4) No record points at a tutorial's example IP or a decommissioned host; stale records are removed in the same change that replaces them.
- **Verification gates:** `dig +short <domain> A` / `www CNAME` output matches the hosting record sheet (automatable, run post-change and quarterly). Registrar checklist: auto-renew + MFA + transfer lock verified with evidence.
- **Sources:** Cloudflare Docs, "DNS record types," https://developers.cloudflare.com/dns/manage-dns-records/reference/dns-record-types/

### ssl-certificates
- **Core method:** HTTPS everywhere, automated: certificates are provider-managed or ACME-issued (Let's Encrypt via Certbot/acme.sh), renewal runs unattended on a timer, and a deploy hook reloads the server with the new cert. Configuration follows the Mozilla Intermediate profile. An expiry alert weeks ahead is the backstop, not the mechanism (DET-INF-014/015/016).
- **Key rules:** (1) HTTP 301-redirects to HTTPS on every route including APIs; HSTS is enabled once HTTPS is proven stable. (2) TLS 1.2+ only with current ciphers; legacy protocol exceptions require a documented expiry date. (3) Renewal is proven, not assumed: `certbot renew --dry-run` (or provider equivalent) passes at setup and after any server change. (4) Zero mixed content: no `http://` asset or API references on HTTPS pages. (5) Wildcards use DNS-01; per-host certs use HTTP-01 or the webserver plugin — the challenge type is chosen deliberately, not by whichever tutorial was open.
- **Verification gates:** External scan (SSL Labs or `testssl.sh`) at launch and after TLS changes: grade + protocol list recorded (automatable). Cert-expiry monitor shows >30 days remaining at all times; renewal dry-run in the ops checklist.
- **Sources:** Mozilla, "Server Side TLS," https://wiki.mozilla.org/Security/Server_Side_TLS ; OWASP, "Transport Layer Protection Cheat Sheet" (cited in DET-INF-014), https://cheatsheetseries.owasp.org/cheatsheets/Transport_Layer_Protection_Cheat_Sheet.html

### scaling
- **Core method:** Scale from measurements, not forecasts: golden-signal dashboards show where saturation actually approaches (CPU, memory, disk, connections, queue depth). Stateless tiers scale horizontally (replicas behind a load balancer, or HPA against resource requests); stateful tiers scale by managed replication/read paths chosen with D5. Every workload declares requests/limits and saturation alerts fire before exhaustion (DET-INF-027).
- **Key rules:** (1) No requests/limits = no autoscaling and first-in-line eviction; sizing comes from observed p95 usage, reviewed after load tests and traffic changes. (2) Autoscaling has a ceiling: max replicas is a cost decision, set deliberately (see cloud-costs). (3) Load-test before the traffic event, not during it; the tested ceiling is a recorded number. (4) Scale-down is part of the design (stabilization windows, graceful drain) — flapping replicas are an outage generator. (5) A single small VPS expresses scaling as a documented capacity ceiling + saturation monitoring; the fail is having neither.
- **Verification gates:** Load test report on file: throughput/latency at the recorded ceiling, autoscaler behavior observed end to end (automatable with k6/Locust in staging). Manifest audit: 100% of production workloads carry `resources:` blocks.
- **Sources:** Google, *Site Reliability Engineering*, "Monitoring Distributed Systems" (golden signals, saturation), https://sre.google/sre-book/monitoring-distributed-systems/ ; DET-INF-027 (requests/limits/saturation standard).

### reliability
- **Core method:** Reliability is run as a system: SLOs on user-facing SLIs, an error budget that gates release pace, golden-signal monitoring, burn-rate alerting to a named on-call, rehearsed rollback, tested backups, and a DR plan with written RTO/RPO matched to a chosen strategy (backup-and-restore → pilot light → warm standby → multi-site). Reliability work is prioritized by budget burn, not by whoever shouted last.
- **Key rules:** (1) Every production service has an SLO and a visible remaining error budget; a service with no SLO has no reliability standard to draft against. (2) Alerts are symptom-based and actionable, each with a runbook link; cause-based CPU alerts that fire every deploy get deleted or demoted to tickets (DET-INF-012). (3) An independent external probe checks the public URL and pages through the same path as internal alerts — if the host dies, detection must not die with it (DET-INF-028). (4) Backups exist, live outside the primary failure domain, and are restore-tested on a cadence with timings recorded (DET-INF-008/009/010; execution owned by D5 backup-recovery). (5) DR is a game day, not a document: failover is executed on schedule and actual RTO/RPO are filed against targets.
- **Verification gates:** Quarterly reliability review checklist: SLOs defined, last restore drill dated, last DR game day dated, alert-to-runbook linkage sampled (automatable link check). Burn-rate alert rules pass `promtool check rules` in CI.
- **Sources:** Google, *The Site Reliability Workbook*, "Alerting on SLOs," https://sre.google/workbook/alerting-on-slos/ ; AWS, "Disaster recovery options in the cloud," https://docs.aws.amazon.com/whitepapers/latest/disaster-recovery-workloads-on-aws/disaster-recovery-options-in-the-cloud.html ; AWS Well-Architected, Reliability Pillar, https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/welcome.html

### incident-response
- **Core method:** A rehearsed process, adapted from the Incident Command System: the page reaches a named on-call rotation with at least two escalation levels; for major incidents an Incident Commander coordinates, delegates all repair work (never fixes personally), owns the communication cadence, and a scribe keeps the timeline. Users are told via a status page/comms channel prepared before it is needed. Every significant incident closes with a blameless postmortem: timeline, root cause, and follow-up actions with owners and due dates (DET-INF-029).
- **Key rules:** (1) The runbook covers the top failure modes with exact commands and lives where the on-call can reach it at 3 a.m. — a chat message is not a runbook. (2) One voice speaks for the incident: status updates come from the IC/liaison on a stated cadence, even when the update is "still investigating." (3) Mitigate first, diagnose second: rollback/restore beats debugging forward under outage pressure. (4) Postmortems blame systems, never people, and their action items are tracked to completion like features. (5) Severity levels and who can declare an incident are written down before the first incident.
- **Verification gates:** On-call inspection: current week's rotation names ≥2 escalation levels (automatable via paging-tool API). Last-incident audit: record names an IC, contains a timeline, links a postmortem whose actions have owners/dates.
- **Sources:** PagerDuty, *Incident Response Guide*, "Different Roles," https://docs.pagerduty.com/ops-guides/incident-response-guide/different-roles ; Google, *Site Reliability Engineering*, "Managing Incidents," https://sre.google/sre-book/managing-incidents/

### rollback
- **Core method:** Every release is reversible by construction: artifacts are immutable and versioned, the previous version stays deployable (platform rollback, blue/green idle environment, Kubernetes rollout history), and data changes follow expand-and-contract so the old code runs against the new schema during the rollback window. Rollback is the default first response to a bad deploy; fix-forward is the exception that needs justification.
- **Key rules:** (1) The exact rollback action (command or console step) is written in the runbook before the release ships — naming it during the incident is too late (DET-INF-017). (2) Migrations never drop or rename in the same release that stops using the old shape; contract steps wait at least one release (DET-INF-018). (3) Rollback is drilled in staging on a cadence and timed against a target (e.g., previous version serving within 5 minutes). (4) The currently live version is always knowable: deploy records map production → artifact digest → commit SHA. (5) Feature-flagged releases roll back by flag flip first — seconds, no redeploy.
- **Verification gates:** Staging drill: deploy a deliberately broken version, execute the documented rollback, previous version healthy within target time, both revisions visible in history (automatable/timed). Release checklist blocks merge when a migration lacks a down path or a documented forward-fix exception.
- **Sources:** Kubernetes Docs, "Deployment" (rolling back a Deployment), https://kubernetes.io/docs/concepts/workloads/controllers/deployment/ ; PROJECT_ANATOMY.md Part 5, Rollback element.

### cloud-costs
- **Core method:** FinOps in three motions — Inform: billing data ingested and allocated by tag/account so cost per service is visible, with unit economics (cost per request/customer) reported next to revenue; Optimize: waste removed (idle instances, oversized databases, orphaned storage), steady-state capacity bought at commitment discounts; Operate: budgets with multi-threshold alerts (actual and forecasted) and anomaly detection running continuously, rightsizing reviewed on a cadence, not in an annual panic.
- **Key rules:** (1) ≥90% of spend allocated to a named service/team; unallocated spend is itself a finding. (2) Every account has a budget alert before it has workloads; anomaly detection (e.g., AWS Cost Anomaly Detection) is enabled from day one because misconfigured autoscalers bill hourly (see scaling ceilings). (3) Tags are enforced at creation (IaC defaults), not backfilled before the audit. (4) "Optimisation" never means turning off monitoring, backups, or redundancy — those are the product, not overhead. (5) Under D-005, pre-revenue projects sit at $0 on free tiers; the first paid line item requires the recorded trigger from the free-tiers sheet, not a surprise invoice.
- **Verification gates:** Monthly cost review artifact: allocation ≥90%, budget + anomaly alerts active, most recent rightsizing/waste report <1 quarter old (checklist gate; allocation % is scriptable from billing exports). Tag-coverage report from the billing export.
- **Sources:** FinOps Framework overview (FinOps Foundation, via Microsoft Learn), https://learn.microsoft.com/cloud-computing/finops/framework/finops-framework ; AWS Docs, "Getting started with AWS Cost Anomaly Detection," https://docs.aws.amazon.com/cost-management/latest/userguide/getting-started-ad.html

## 4. Open risks for Phase 3

1. **Free-tier defaults vs. production-grade defaults collide head-on.** D-005 says free tiers first, $0 spend; the department standard says no single points of failure, restore-tested backups, external probing, and paging. Several of those are impossible or explicitly discouraged on free tiers (Render's own docs say free web services are not for production applications, checked 2026-11-21). Phase 3 drafting must define explicit **posture tiers** (e.g., "validation posture" on free tiers vs. "production posture") inside the hosting/reliability/free-tiers skills, stating which DET-INF parameters are waived at which tier and what event (first user, first payment, first SLA) forces promotion — otherwise the skills will contradict each other and the detection parameters.
2. **Free-tier facts decay fast.** Every limit cited here (Render spin-down and 750 hours, Vercel Hobby caps, Netlify credits, GitHub minutes) is dated 2026-11 and will rot; providers have a history of shrinking free tiers with little notice. Drafters must encode the *verification procedure* (read the official page, record cap + date, set the alert) as the durable rule and treat all numbers as dated examples, plus add a re-check cadence — a skill that hardcodes today's numbers becomes misinformation.
3. **Single-agent operability.** This repo must work for one agent with no team: on-call rotations, required reviewers, and an Incident Commander who "does not personally fix" assume multiple humans. Phase 3 must translate each practice honestly for the single-operator case (escalation = the user; reviewer gate = a deliberate pause + checklist) without quietly dropping the control — the D15 research flagged the same translation problem, so the pattern should be decided once and reused.
4. **Platform specificity vs. provider neutrality.** Half of D6's concrete checks are platform-shaped (GitHub Actions, Vercel/Netlify/Render behaviors, Terraform). Skills drafted too specifically age out or fail on other stacks; drafted too generally, they lose their verification gates. Recommended pattern (mirrors D17's): provider-neutral rule + dated, platform-specific annex.
5. **Kubernetes scope creep.** kubernetes is one of 17 skills, but most OmniForge proof projects will be single-service apps where Kubernetes is the wrong answer. The skill must open with an adoption test and an explicit "use a platform/VPS instead" branch, or drafters will produce cluster ceremony for projects that need a $0–7 host.
6. **Boundary friction.** DET-INF fixes route heavily through skills D6 does not own (secrets-management → D7, backup-recovery → D5, monitoring/logging/alerting depth → D12). Phase 3 sequencing must draft those first or write D6 skills against their researched interfaces, or cross-references will dangle.
7. **Verification gates that need a live environment.** Many D6 gates (kill-a-pod drills, restore timings, throttle tests, DR game days) can only run against real infrastructure, which under $0 spend means free-tier sandboxes with real limits (sleeping services cannot be probed meaningfully). Drafters should mark which gates are launch-blocking vs. posture-tier-deferred, or Phase 6 proof projects will fail gates they were never funded to pass.
