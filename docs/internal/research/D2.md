## 1. Department standard — how professional architecture work runs today

**Architecture is documented as a small set of living artifacts, not a big up-front design document.** The working set on a professional team is: (1) C4 diagrams (system context, container, component; code level only where it earns its keep), kept as code or in a tool that diffs with the repo; (2) one ADR per significant decision, in the repo, immutable once accepted; (3) the API contract as a machine-readable file that is the source of truth, with everything else (docs, clients, tests) generated from or checked against it. The C4 model (Simon Brown) is the de facto diagramming standard because its four levels give each audience the zoom it needs and forbid the single all-purpose box-and-arrow picture (https://c4model.com/). MADR is the most-used ADR template: context, considered options, decision outcome, consequences, in one Markdown file per decision (https://adr.github.io/madr/).

**API-first is the default workflow for anything with more than one consumer.** The contract (OpenAPI 3.1 for request/response HTTP) is drafted and reviewed before or alongside implementation, then enforced in CI: a linter (Spectral or Redocly CLI) checks style and completeness, a diff tool (oasdiff) fails the build on unapproved breaking changes against the shipped baseline, and contract tests prove the running service matches the document (tooling survey: https://apidog.com/blog/open-source-cli-tools-api-design/; gate design: https://www.api-contract-testing.com/api-contract-fundamentals-tool-selection/breaking-change-detection/). Zalando's published guidelines are the reference example of this operating model at scale: API-first is a MUST, the OpenAPI file must be published, backward compatibility must not break, and compliance is checked by an automated linter (Zally) rather than by review memory (https://opensource.zalando.com/restful-api-guidelines/).

**Compatibility is a defined term, not a judgment call.** Google's API design guidance enumerates which changes are breaking (removing or renaming a field, method, or enum value; changing a field's type; changing a resource name format; changing visible behavior) and which are safe (adding interfaces, methods, fields, enum values), and ties them to major/minor version semantics (https://cloud.google.com/apis/design/compatibility/). Semantic Versioning 2.0.0 supplies the numbering contract for both libraries and APIs (https://semver.org/).

**Tenancy is chosen per layer, from a named model, with isolation enforced by the platform.** Microsoft's multitenancy guidance frames the decision as a trade-off among isolation, cost, and operational complexity, and catalogs the data-layer models (shared database with tenant key and row-level security, database per tenant, sharded/hybrid with a tenant catalog) together with their failure modes, including the noisy-neighbor problem and per-tenant restore difficulty in shared models (https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/service/sql-database). The standing rule across the guidance: prefer the simplest model that meets isolation and compliance requirements, and never let isolation depend on each developer remembering a filter.

**Events are contracts too.** Event-driven work is specified with the same rigor as HTTP APIs: AsyncAPI 3.1.0 describes message-driven APIs in a machine-readable document (channels, operations, message payloads, protocol bindings) (https://www.asyncapi.com/docs/reference/specification/v3.1.0), and CloudEvents 1.0 standardizes the event envelope (required attributes: `specversion`, `id`, `source`, `type`) so events stay routable and deduplicatable across brokers and vendors (http://cloudevents.io/). Fowler's pattern analysis is the shared vocabulary for choosing among event notification, event-carried state transfer, event sourcing, and CQRS — four different patterns that teams routinely conflate under one label (https://www.martinfowler.com/articles/201701-event-driven.html).

**Patterns are selected from a catalog against a stated problem, not adopted as fashion.** The microservices.io pattern language (Chris Richardson) is the working catalog for distributed-systems patterns — Saga, transactional outbox, CQRS, event sourcing, database per service — each documented with the problem it solves, its forces, and its consequences, which is exactly the shape an architecture decision needs (https://microservices.io/). The department default is a modular monolith unless a pattern's stated problem is demonstrably present.

## 2. Failure modes this department prevents

Each item names the anatomy element whose "Slop looks like" line it quotes or paraphrases (PROJECT_ANATOMY.md Part 2, plus Part 11 for event-driven).

- **System architecture** — "A single auto-generated box-and-arrow diagram with generic labels ('Frontend', 'Backend', 'Database'), no actors, no protocols, and no relationship to the actual code." D2 prevents it by requiring C4 levels with named protocols on every arrow and a drift check against the deployable units in the repo.
- **Stack decisions** — "A README listing a fashionable stack … with no rationale, no alternatives considered, and versions that do not match the project's actual dependency files." Prevented by the ADR-per-component rule and a manifest cross-check.
- **API contracts** — "Endpoint behavior described only in prose chat messages; error responses that vary per endpoint; fields appearing in examples that the real API never returns." Prevented by contract-as-source-of-truth plus lint, diff, and contract-test gates.
- **Data models** — "One generic table or collection per noun with stringly-typed fields, no constraints, no indexes beyond the primary key, and duplicated copies of the same entity updated inconsistently." Prevented by access-pattern-first modeling and constraint/index review.
- **Code organisation** — "Giant `utils` and `helpers` folders, a single `services` directory holding unrelated logic, files named `misc.ts`, and layers that import each other in both directions." Prevented by feature/domain module boundaries with enforced dependency direction.
- **API documentation** — "A documentation page listing endpoints that return 404, example payloads with fields the API rejects, and 'TODO: document errors' sections shipped as final." Prevented by generating docs from the contract and executing documented examples as a gate.
- **Multi-tenancy** — "A `tenant_id` column added to some tables but enforced in application code only where the developer remembered, with admin and reporting queries bypassing it entirely." Prevented by platform-enforced scoping and the cross-tenant access test.
- **Versioning** — "Version numbers bumped at random (1.0 to 3.0 for a typo fix), breaking API changes shipped under the same version, and no changelog connecting versions to changes." Prevented by semver rules wired to the contract-diff gate.
- **Event-driven architecture** (Part 11) — "A message queue installed as decoration while services still call each other synchronously, events used as disguised commands a producer secretly depends on, and no schema, ordering, or replay story for the event stream." Prevented by named-pattern selection, AsyncAPI contracts, and the consumer-outage test.
- **Feature flags and experimentation** (Part 2, D2 co-owns with D4) — "Permanent `if (true)` branches, flags with names like `new_feature_v2_final`, no record of who owns a flag." Prevented by the toggle taxonomy (release / experiment / operations / permissioning), each flag carrying an owner and an expected lifespan (https://martinfowler.com/articles/feature-toggles.html).

## 3. Per-skill research notes

### 3.1 system-design

**Core method.** Start from requirements and quality attributes (scale, latency, consistency, availability, tenancy), not from components. Decompose into containers (deployable units and data stores) and the runtime paths between them; name the protocol and data format on every path. Record each significant choice as an ADR at the moment it is made. Design the failure behavior (timeouts, retries, backpressure, degradation) for every cross-container call in the same pass as the happy path. Revisit the design when a quality attribute changes, not on a calendar.

**Key rules for the drafter.**
1. Every container in the diagram must correspond to a deployable unit, data store, or external system that exists in the repo or infrastructure config — no aspirational boxes.
2. Every arrow carries a protocol or format label (HTTPS/JSON, gRPC, AMQP, SQL); an unlabeled arrow fails review.
3. The design must state, per cross-boundary call: timeout, retry policy, and what the caller does when the callee is down.
4. Default topology is a modular monolith; a distributed design must cite the requirement (independent scaling, team autonomy, isolation) that forces it, in an ADR.
5. Data ownership is drawn on the diagram: each store has exactly one owning container that writes to it.

**Verification gates.** Manual: walk the container diagram against the repo's deployable units and infrastructure config (the anatomy Verify step). Automatable: a checklist script that fails if ARCHITECTURE.md lacks a container section or if any ADR referenced by the design is missing from `docs/decisions/`.

**Sources.** C4 model — https://c4model.com/ · Pattern language for distributed designs — https://microservices.io/

### 3.2 c4-diagrams

**Core method.** Produce exactly the levels the audience needs: Level 1 system context (the system, its users, and external systems), Level 2 containers (applications, data stores, queues), Level 3 components inside a container only where internal structure is non-obvious. Level 4 (code/class) is generated by tools or omitted. Keep diagrams as code (Structurizr DSL, PlantUML, or Mermaid) in the repo so they diff and review like code. One diagram per view, with a legend; never merge audiences into one picture.

**Key rules for the drafter.**
1. Every element is typed (person, software system, container, component) and every relationship line is labeled with the interaction and protocol.
2. Container diagrams must show data stores and queues as first-class containers, not as annotations.
3. A diagram that no longer matches the system is a defect: diagrams are updated in the same change that alters the architecture, and the ADR for that change links the diagram.
4. No generic labels: "Frontend / Backend / Database" as the whole model is an automatic fail (anatomy slop line for System architecture).
5. External systems are shown with the direction of each integration and whether it is synchronous or asynchronous.

**Verification gates.** Automatable: render check — the diagram source compiles/renders in CI (e.g., PlantUML or Mermaid CLI exits 0), so a broken diagram file fails the build. Manual: element-by-element diff against the deployment config each release.

**Sources.** C4 model, including the notation and diagram guidance — https://c4model.com/

### 3.3 stack-selection

**Core method.** Write the selection criteria before naming candidates: requirements fit, data-model fit, team skill, ecosystem maturity and maintenance health, license, operational cost, hosting constraints, exit cost. Score each candidate against the same criteria in a comparison table. Choose, then record the decision as an ADR (MADR format) with at least one seriously considered alternative and the accepted downsides. Pin exact versions in the dependency manifest in the same change; the ADR, the manifest, and the README stack list must agree.

**Key rules for the drafter.**
1. No stack component is adopted without an ADR whose status is "accepted" and which names a rejected alternative and why it lost.
2. Criteria are written before candidates are evaluated; "popular" and "used at a big company" are not criteria.
3. Versions named anywhere in prose must match the dependency manifest; a mismatch is a defect (anatomy slop line for Stack decisions).
4. A component with no maintenance activity, a copyleft license conflict, or no production hosting path on the target platform is disqualified, and the disqualification is recorded.
5. Re-evaluating a settled stack requires a new ADR that supersedes the old one; silent swaps are forbidden.

**Verification gates.** Automatable: script cross-checks that every top-level dependency in the manifest maps to an ADR file in `docs/decisions/` (name or tag match) and that version strings in the README equal the manifest's. Manual: criteria table exists and predates the decision (git history).

**Sources.** MADR template and guidance — https://adr.github.io/madr/ · Twelve-Factor config/portability constraints as selection criteria — https://12factor.net/config

### 3.4 api-architecture

**Core method.** Design the API as a product surface, resource-first: identify resources and their relationships from the domain model, assign stable identifiers, and define operations against the house style guide (one guide per company — Zalando's and Google's are the reference models). Draft the OpenAPI document before implementation, review it as a contract (naming, error model, pagination, filtering, idempotency), then implement against it. Errors use one format everywhere (Problem Details style: type, title, status, detail). Collections get pagination and filtering in the first version, not as a retrofit.

**Key rules for the drafter.**
1. The OpenAPI document is written or updated in the same change as any API behavior change — contract first, code second.
2. One error format for every endpoint; per-endpoint error shapes are a blocking defect (anatomy slop line for API contracts).
3. Every list endpoint paginates (cursor preferred) and states its ordering; unbounded list responses are forbidden.
4. Mutating endpoints state their idempotency story (safe method, idempotency key, or documented non-idempotent with retry warning).
5. Resource names are plural nouns; verbs appear only as named custom actions on a resource, per the house guide — pick one convention (Google AIP-style colon actions or sub-resource actions) and apply it uniformly.

**Verification gates.** Automatable: Spectral or Redocly lint of the OpenAPI file in CI with the house ruleset (operationIds present, descriptions present, naming rules) — build fails on errors. Automatable: contract tests (Schemathesis-style or framework tests generated from the spec) run against the implementation. Manual: design review of the spec diff before implementation starts.

**Sources.** Zalando RESTful API Guidelines (API-first, compatibility, error and naming rules) — https://opensource.zalando.com/restful-api-guidelines/ · Google API compatibility and design rules — https://cloud.google.com/apis/design/compatibility/ · Lint/diff tooling survey — https://apidog.com/blog/open-source-cli-tools-api-design/

### 3.5 api-versioning

**Core method.** Version only on breaking change, and define "breaking" by the published compatibility list, not by feel. Within a major version, only backward-compatible changes ship (additive fields, new endpoints, new enum values where consumers are required to tolerate unknowns). A breaking change increments the major version and starts a deprecation window: old and new run side by side, the old version emits deprecation signals (Deprecation/Sunset headers and changelog entries), and removal happens only after the announced date and a consumer check. Version identifier placement (path segment for public HTTP APIs, per house guide) is chosen once and never mixed.

**Key rules for the drafter.**
1. The breaking/non-breaking classification follows the enumerated list (remove/rename/retype = breaking; add = safe); anything unlisted is treated as breaking until ruled otherwise.
2. A breaking change shipped under the same major version is a release-blocking defect (anatomy slop line for Versioning).
3. Every version has a changelog entry connecting the version to its changes; "latest" is never the only nameable version.
4. Deprecation requires three artifacts before the window starts: the sunset date, the migration path, and the consumer notification (docs + headers).
5. Consumers must be required to ignore unknown fields and enum values; the contract states this so additive changes stay safe.

**Verification gates.** Automatable: `oasdiff breaking <baseline> <new>` in CI against the last shipped spec — unapproved breaking changes fail the build; a major-version bump plus an ADR is the only way through. Automatable: grep the running service's metadata/health endpoint and compare its version to the release tag.

**Sources.** Semantic Versioning 2.0.0 — https://semver.org/ · Google, "Compatibility" (breaking vs non-breaking change lists) — https://cloud.google.com/apis/design/compatibility/ · Breaking-change gate design — https://www.api-contract-testing.com/api-contract-fundamentals-tool-selection/breaking-change-detection/

### 3.6 api-documentation

**Core method.** The reference documentation is generated from the OpenAPI document — never hand-maintained in parallel — so paths, schemas, and status codes cannot drift from the contract. Around the generated reference, humans write only what generation cannot: authentication walkthrough, one runnable example per endpoint group, the error catalog, and the changelog. Examples are real requests with realistic (non-sensitive) data, and they are executed against a running instance as part of verification. Docs publish with the API version they describe; old versions stay reachable during their deprecation window.

**Key rules for the drafter.**
1. If it is not in the OpenAPI document, it is not documented; if it is in the document, it renders in the reference — no side wikis as the source of truth.
2. Every endpoint documents its error responses with the shared error format; "TODO: document errors" shipped as final is a blocking defect (anatomy slop line).
3. Every example payload must be accepted by the real API (fields, types, required values) — verified by execution, not by eye.
4. Authentication is documented as a complete flow (obtain credential, send it, expiry/refresh, failure response), not as the sentence "use your API key."
5. Each release updates the docs changelog in the same change as the contract.

**Verification gates.** Automatable: execute three (or all) documented example requests against a staging instance in CI and assert documented status code and response shape (the anatomy Verify step, mechanized). Automatable: Redocly/Spectral rules requiring descriptions and examples on every operation.

**Sources.** OpenAPI Specification 3.1.0 (the document the docs are generated from) — https://spec.openapis.org/oas/v3.1.0 · Redocly CLI lint/bundle in the docs pipeline — https://apidog.com/blog/open-source-cli-tools-api-design/

### 3.7 api-paradigms

**Core method.** Choose the paradigm per interaction shape, and be able to state why in one paragraph that lands in an ADR. REST/HTTP+JSON is the default for resource CRUD and public APIs. GraphQL earns its place when multiple client types need divergent, client-shaped reads over a richly connected graph — paid for with schema governance, query-cost controls, and persisted-query or depth limits. gRPC fits internal service-to-service calls needing strict contracts and streaming performance. Event-based interfaces (AsyncAPI) fit facts that multiple consumers react to independently. tRPC-style end-to-end-typed RPC is acceptable inside a single TypeScript codebase with no external consumers. Mixed paradigms are fine; unexamined defaults are not.

**Key rules for the drafter.**
1. The paradigm choice is an ADR that names the interaction shape (CRUD, client-shaped reads, streaming, fan-out facts) driving it.
2. GraphQL APIs must ship with query depth/complexity limits and a deprecation policy on fields (`@deprecated` in the schema); an unbounded public GraphQL endpoint is a defect.
3. A paradigm is never chosen to hide a modeling problem: if the resources cannot be named, REST will not fix it and neither will GraphQL.
4. Each paradigm in use has its contract artifact in the repo: OpenAPI for REST, SDL for GraphQL, AsyncAPI for events — no contract, no interface.
5. Public consumers get the most boring paradigm that fits (REST first); internal novelty does not leak into the public surface.

**Verification gates.** Automatable: schema validation in CI for whichever artifacts exist — OpenAPI lint, GraphQL SDL lint/validation against the spec's type system rules, AsyncAPI validation. Manual: the ADR exists and its stated interaction shape matches the API's actual dominant traffic.

**Sources.** GraphQL Specification, October 2021 edition (type system, validation, deprecation) — https://spec.graphql.org/October2021/ · OpenAPI Specification 3.1.0 — https://spec.openapis.org/oas/v3.1.0 · AsyncAPI Specification 3.1.0 — https://www.asyncapi.com/docs/reference/specification/v3.1.0

### 3.8 data-architecture

**Core method.** Model from access patterns: list the reads and writes each main screen and job performs, then choose structures that serve them. For relational stores: entities, keys, and integrity constraints first, indexes derived from the named queries. For document stores: embed what is read together and owned together, reference what is shared or independently growing — the decision is made per relationship, deliberately (MongoDB's modeling guidance is the reference method). Cross-service data is owned by one service; other services hold references or replicated read models, never shared write access to another service's tables. Evolution happens only through versioned migrations.

**Key rules for the drafter.**
1. Every entity in the requirements maps to a schema object; every relationship is declared (foreign key, reference, or an explicit documented decision to denormalize, with the consistency cost stated).
2. Stringly-typed fields for typed facts (dates, money, enums, statuses) are forbidden; money is integer minor units or a decimal type, never float (anatomy slop line for Data models).
3. Every query used by a main screen is backed by an index, proven with the database's explain-plan tool, not assumed.
4. The same fact has exactly one writable home; copies are read models with a named synchronization mechanism and a stated staleness bound.
5. Tenant-owned tables carry the tenant key from the first migration in any multitenant design (see 3.10) — retrofitting it is treated as a redesign, not a migration.

**Verification gates.** Automatable: migration lint/CI run that applies all migrations to an empty database and runs the schema diff against the declared model. Automatable: explain-plan checks for the named main-screen queries in a test harness. Manual: duplicate-fact audit — pick three core facts and trace each to its single writable home.

**Sources.** MongoDB Manual, data modeling (embed vs reference by access pattern) — http://mongodocs.github.io/core/data-modeling-introduction.html · Database-per-service and data ownership patterns — https://microservices.io/

### 3.9 architecture-patterns

**Core method.** Work from a named catalog (microservices.io pattern language; Fowler's event-driven and enterprise patterns) and select by problem statement: each pattern entry states the problem, the forces, the solution shape, and the consequences — the skill requires the architect to fill in all four for the project at hand before adopting. Default composition for a typical web application: modular monolith with feature modules, transactional outbox if events are published, saga only when a business transaction genuinely spans services, CQRS only when read and write shapes demonstrably diverge. Patterns are adopted one at a time, behind an ADR, with the exit cost noted.

**Key rules for the drafter.**
1. No pattern without a stated problem it solves in this project; "for scale" without a load figure is not a problem statement.
2. Adopting Saga, CQRS, or event sourcing requires the ADR to name the compensating transactions, the read-model synchronization, or the event store and replay procedure respectively — the hard part is the deliverable, not the label.
3. A queue or broker in the diagram while all interactions remain synchronous request/response is decoration and fails review (anatomy slop line, Event-driven architecture).
4. Every pattern adoption records its consequences accepted (eventual consistency window, operational components added) in the ADR.
5. Prefer the pattern's simplest variant (choreography before orchestration for short sagas; single read model before multiple) and record what would trigger the complex variant.

**Verification gates.** Manual: pattern audit — for each pattern claimed in ARCHITECTURE.md, find its mechanism in code (outbox table, compensating handlers, read model) or mark the claim false. Automatable: dependency-rule check in CI for module boundaries (e.g., lint rules forbidding cross-module imports except through public interfaces).

**Sources.** Microservices.io pattern language (Saga, CQRS, event sourcing, transactional outbox, database per service) — https://microservices.io/ · Fowler, "What do you mean by 'Event-Driven'?" — https://www.martinfowler.com/articles/201701-event-driven.html

### 3.10 multitenancy-saas

**Core method.** Define "tenant" first (customer organization, individual consumer, or sub-unit), because the definition drives isolation, billing, and data-sovereignty requirements. Then choose the model per layer from the named catalog: compute is usually shared with tenant context resolved per request; data is one of shared schema with tenant key (pool), schema/database per tenant (silo), or hybrid (bridge) with a tenant catalog routing each tenant to its store. Isolation is enforced by the platform — tenant context set at the request boundary, data access scoped automatically (ORM filter, row-level security), background jobs and exports included. Noisy-neighbor controls (rate limits, quotas, per-tenant observability) are part of the model, not an afterthought.

**Key rules for the drafter.**
1. Tenant context is established once, at the edge (from the authenticated principal or subdomain), and propagated; code never accepts a tenant ID from an unauthenticated request body.
2. Every tenant-owned table carries the tenant key, every query path — including admin, reporting, export, and background jobs — is scoped by it; an unscoped path is a blocker defect (anatomy slop line for Multi-tenancy).
3. The chosen model per layer is an ADR citing the isolation/compliance/cost trade-offs from the tenancy catalog; hybrid placements are enumerated tenant by tenant in the catalog.
4. Per-tenant operations are designed, not improvised: backup/restore granularity, data export, and tenant deletion (including legal erasure) are specified for the chosen model.
5. New tenants are provisioned by an automated, tested procedure; manual database edits are not a provisioning path.

**Verification gates.** Automatable: the cross-tenant test suite — authenticate as tenant A, attempt reads/writes/exports against tenant B's known resource IDs through every interface class (API, export, report, job trigger); every attempt must return 403/404 and write nothing. Automatable: schema check that every table flagged tenant-owned has a non-null tenant key column and an index leading with it. Manual: noisy-neighbor review — per-tenant rate limits and usage metrics exist.

**Sources.** Microsoft Learn, multitenancy and Azure SQL Database (partitioning and tenancy strategies, row-level security, noisy neighbor) — https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/service/sql-database · Microsoft Learn, multitenancy tenancy models for Cosmos DB (partition key per tenant vs account per tenant) — https://learn.microsoft.com/en-us/azure/cosmos-db/multi-tenancy-vector-search

### 3.11 event-driven

**Core method.** Name the pattern before building: event notification (a fact is announced; consumers fetch state if needed), event-carried state transfer (the event carries the data consumers need), event sourcing (events are the store of record), or CQRS (separate write and read models synchronized by events) — Fowler's taxonomy, because the four have different consistency and coupling consequences. Specify every event as a contract: an AsyncAPI document, a CloudEvents envelope (specversion, id, source, type), a versioned payload schema, and a named owner. Design consumers to be idempotent and order-tolerant; design publication to be atomic with the state change (transactional outbox). State the ordering scope (per aggregate/key, via partitioning) and the replay procedure for every stream.

**Key rules for the drafter.**
1. Events are facts in the past tense (`OrderPlaced`), never commands in disguise that a producer secretly depends on a specific consumer executing (anatomy slop line).
2. Every event type has: an entry in the AsyncAPI document, a payload schema with a version, an owning team/service, and a list of known consumers.
3. Consumers must be idempotent (deduplicate on event `id` + source) and must tolerate out-of-order delivery within the stated ordering scope; poison messages go to a dead-letter queue with an alert, never an infinite retry.
4. Publication is atomic with the business write (transactional outbox or an event store); "write to the database, then publish, hope both succeed" is a defect.
5. Event payloads carry the minimum data the pattern requires; event-carried state transfer with full entity snapshots requires an explicit ADR because of the coupling and privacy cost (events must not carry sensitive personal data beyond need — Zalando's event rules make the same demand).

**Verification gates.** Automatable: AsyncAPI validation in CI, plus schema-compatibility check of new payload schemas against the previous version (backward-compatibility rules as in 3.5). Automatable: consumer contract tests replaying recorded events. Manual/mechanized: the consumer-outage test — disable one consumer in staging, confirm producers keep working, then restore it and confirm the backlog drains with no duplicates applied (the anatomy Verify step).

**Sources.** Fowler, "What do you mean by 'Event-Driven'?" — https://www.martinfowler.com/articles/201701-event-driven.html · AsyncAPI Specification 3.1.0 — https://www.asyncapi.com/docs/reference/specification/v3.1.0 · CloudEvents (CNCF, envelope attributes) — http://cloudevents.io/ · Zalando event guidelines (events as interface, registration, compatibility, no sensitive personal data) — https://opensource.zalando.com/restful-api-guidelines/

### 3.12 domain-driven-design

**Core method.** Start with the language: workshops and example-driven conversations with domain experts produce a ubiquitous language — one term, one meaning, used identically in conversation, code, schema, and API. Find the bounded contexts by where the language changes meaning (the same word, e.g. "order," meaning different things in sales vs fulfillment is the boundary signal), and draw a context map naming each relationship (shared kernel, customer/supplier, anti-corruption layer). Inside a context, model aggregates around consistency invariants: an aggregate is the unit of transactional consistency, references between aggregates are by identity, and domain events mark state changes that other contexts react to. Tactical patterns (entities, value objects, repositories, domain services) are applied only inside a context that has earned them.

**Key rules for the drafter.**
1. Every bounded context has a name, a one-paragraph responsibility, its context-map relationships, and an owning module/service — recorded in ARCHITECTURE.md; a context that exists only in a slide is not a context.
2. Aggregate boundaries follow invariants: if two objects must be consistent in the same transaction, they are in one aggregate; if not, they reference by ID and accept eventual consistency.
3. Cross-context communication goes through the context map's declared mechanism (API, events, anti-corruption layer); direct reads of another context's tables are forbidden.
4. The ubiquitous language is testable: type, field, and endpoint names in a context use its glossary terms verbatim; a synonym introduced in code is a defect.
5. Anemic pass-through layers are named as such: CRUD-over-one-table areas are modeled as simple CRUD modules, not dressed in tactical DDD vocabulary they do not use.

**Verification gates.** Manual: glossary cross-check — sample type and field names from the codebase and API schemas and match them against the context glossaries. Automatable: module dependency rules in CI enforcing that one context's internals are not imported by another (the same gate as 3.9's boundary check, scoped by context). Manual: pick one invariant and find the aggregate that enforces it in a single transaction.

**Sources.** Eric Evans, *Domain-Driven Design Reference* (definitions of bounded context, aggregate, ubiquitous language; domainlanguage.com) — cited as the canonical summary of the book's model · Pattern context for how DDD boundaries interact with data ownership and sagas — https://microservices.io/

### 3.13 adr-writing

**Core method.** One file per decision, MADR format, stored in the repo (default `docs/decisions/`, numbered `NNNN-title.md`). Each record carries: title, status (proposed / accepted / deprecated / superseded by NNNN), context and problem statement, decision drivers, considered options (at least two, with the rejected ones' trade-offs stated honestly), decision outcome, and consequences — positive, negative, and neutral. Records are immutable once accepted; a change of mind is a new ADR that supersedes the old one and links both ways. Write the ADR in the same change as the work it governs, while the alternatives are still genuinely remembered.

**Key rules for the drafter.**
1. An ADR with only one considered option is incomplete: the rejected alternative and the reason it lost are the record's most valuable content.
2. Consequences must include at least one negative or cost; an all-positive consequences section means the trade-off was not examined.
3. Status is maintained: when a decision is reversed, the old ADR's status is updated to "superseded by" the new one in the same commit — the folder must never contain two contradictory "accepted" records on the same question.
4. Titles state the decision, not the topic ("Use PostgreSQL for the primary store," not "Database discussion").
5. ADRs record decisions, not designs: the full design lives in ARCHITECTURE.md or the contract; the ADR links to it.

**Verification gates.** Automatable: lint script over `docs/decisions/` — every file parses, has a status line from the allowed set, a considered-options section with ≥2 options, and superseded records link to an existing successor. Automatable: the stack cross-check from 3.3 (each major manifest dependency has an ADR). Manual: sample one ADR and confirm a reader can reconstruct why the choice was made without interviewing the author.

**Sources.** MADR — Markdown Architectural Decision Records (template and guidance) — https://adr.github.io/madr/

## 4. Open risks — what Phase 3 drafters will struggle with

1. **House style guide dependency.** api-architecture, api-versioning, and api-documentation all presume one company API style guide (naming case, error format, pagination shape, version placement). Zalando and Google disagree on details (e.g., Zalando mandates snake_case properties; Google AIPs use camelCase field names). Phase 3 must pick one coherent profile and encode it in the Spectral ruleset; drafting the three skills independently will produce contradictions. Recommend: draft a single `docs/internal/API_STYLE_PROFILE.md` decision first (executor-level ADR), then draft the three skills against it.
2. **Gate tooling must actually run in the target environments.** Spectral, Redocly CLI, and oasdiff are Node/Go CLIs; the skills will be executed by agents in sandboxes that may lack network access for `npx` fetches. Drafters should specify pinned, vendored, or pre-installed tooling and a documented manual fallback for every automated gate, or the gates will be silently skipped in practice.
3. **C4 drift checking is only semi-automatable.** There is no reliable off-the-shelf tool that proves a diagram matches a codebase; the container-vs-deployables check is a structured manual walk. Drafters risk writing a gate that sounds automated but is not. The skill should encode the walk as an explicit checklist with named artifacts to compare, and say plainly that it is manual.
4. **Multitenancy gates depend on D5/D7 deliverables.** The cross-tenant test suite and row-level-security patterns sit on database and auth work owned by other departments; D2's skill can specify the tests but cannot implement their fixtures. Drafters should mark these gates as "specifies, executed by D8 with D5 fixtures" to avoid a skill that promises a check nobody can run.
5. **Event-driven scope creep.** Event sourcing and CQRS are the two patterns agents most over-apply. The research position (simplest variant, ADR must name the hard part) is easy to state and hard to keep concrete in a SKILL.md; drafters should include worked negative examples (a CRUD app where event sourcing is the wrong answer, and what to build instead) rather than more positive ones.
6. **DDD without domain experts.** The ubiquitous-language method assumes access to people who know the domain; in this company's single-agent and client-brief contexts, the "expert" is often a requirements document. Drafters will need a fallback procedure (derive the glossary from requirements and fact sheets, flag every inferred term) or the skill will stall at its first step.
7. **Versioning policy for non-HTTP surfaces.** The compatibility lists verified here are HTTP/proto-centric. Event payloads, GraphQL schemas, and database schemas each need their own breaking-change lists in the skills; the sources above cover events (Zalando/AsyncAPI) and GraphQL (spec deprecation) only partially, so drafters must derive the rest from the HTTP list by analogy and mark it as derived.
