# D4 Research — Backend & APIs (Phase 2)

Purpose: the research base for drafting the 16 D4 skills in Phase 3. Every claim below traces to PROJECT_ANATOMY.md (Parts 2, 3, 11), a DET parameter file, or a source verified by web search on 2026-11-21. Audience: Phase 3 skill drafters for D4.

## 1. Department standard

Professional backend practice today, as D4 will teach it:

- **Resource-oriented REST over HTTP semantics.** Endpoints model resources (plural noun collections, nested only where ownership is real), methods carry their RFC 9110 meaning — GET safe and side-effect-free, PUT/DELETE idempotent by design, POST neither — and status codes are chosen by a written decision rule (201 + `Location` on create, 204 on empty success, 400 malformed, 409 state conflict, 412 precondition failed, 422 business-rule rejection), never 200-with-an-error-string. Published style guides (Microsoft REST API Guidelines, Zalando RESTful API Guidelines, Google AIPs) agree on this core even where they differ on casing and versioning. Sources: RFC 9110, https://apiguide.dev/specifications/http-semantics ; Zalando RESTful API Guidelines, http://opensource.zalando.com/restful-api-guidelines/
- **Contract-first, machine-checked.** The OpenAPI description is the source of truth; it is linted in CI and exercised by contract tests against the running service, so documentation, implementation, and tests cannot drift apart silently. Source: OpenAPI Specification v3.1.0, https://spec.openapis.org/oas/v3.1.0 (via PROJECT_ANATOMY.md, "API contracts").
- **One error format everywhere.** Errors are RFC 9457 problem details (`application/problem+json`: `type`, `title`, `status`, `detail`, `instance`, plus extension members such as per-field validation errors and a correlation ID). The client never receives a stack trace, SQL fragment, or internal path; the full exception is logged server-side against the same correlation ID. Sources: RFC 9457, https://ftp.kaist.ac.kr/rfc/rfc9457.html ; OWASP Error Handling Cheat Sheet, https://cheatsheetseries.owasp.org/cheatsheets/Error_Handling_Cheat_Sheet.html
- **Idempotency is designed, not hoped for.** Non-idempotent POSTs that move money, create orders, or send messages accept an `Idempotency-Key`: the server stores the key with a hash of the request and the first response, replays the stored response on retry, and rejects key reuse with a different body. Zalando's guidelines describe exactly this key-cache pattern with transactional update of resource and key together; Stripe's API implements it in production. Sources: Zalando guidelines (idempotency section, URL above); Stripe, "Idempotent requests", https://docs.stripe.com/api/idempotent_requests
- **Validation at the boundary, authorization on every request.** All input is validated server-side against allowlist schemas before it is trusted or stored; every protected operation runs an authentication check and an object-level authorization check (does this identity own this object?) on the server. OWASP's API Security Top 10 (2023) puts broken object-level authorization (API1) and broken function-level authorization (API5) at the top of real-world API failures. Sources: OWASP Input Validation Cheat Sheet, https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html ; OWASP API Security Top 10 (2023), summary at https://orca.security/resources/blog/owasp-api-security-top-10/
- **Slow, expensive, or third-party work leaves the request.** Email, media processing, webhook delivery, and provider calls run as background jobs: enqueue in the same transaction as the state change where possible, process with bounded attempts and exponential backoff with jitter, park exhausted jobs in an inspectable failed set / dead-letter queue, and make handlers idempotent because delivery is at-least-once. Source: BullMQ production patterns (attempts, backoff, failed-set as DLQ), https://railway.com/guides/bullmq-jobs-retry-dlq and https://soundscode.com/nestjs/nest-queue-retries
- **Realtime is chosen by direction and scale, not fashion.** One-way server→client updates use server-sent events (plain HTTP, automatic reconnect, `Last-Event-ID` catch-up); bidirectional traffic uses WebSocket with heartbeat and reconnect-with-backoff; both authenticate at connection time and fan out through a pub/sub layer once more than one instance runs. Polling is a fallback, not a realtime strategy. Sources: MDN, "EventSource", https://developer.mozilla.org/en-US/docs/Web/API/EventSource ; MDN, "WebSocket" (via PROJECT_ANATOMY.md, "Real-time features").
- **Uploads are hostile until processed.** Files bypass the app server where possible (presigned URL direct to object storage), are validated by allowlist extension plus signature — never by the client-supplied Content-Type — renamed to server-generated names, size-limited, scanned, and served only through signed URLs or an authorizing handler. Sources: OWASP File Upload Cheat Sheet, https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html ; AWS S3 presigned URLs (via PROJECT_ANATOMY.md, "File storage and media handling").
- **Every endpoint is resource-capped.** Rate limits (per account, per endpoint, plus a concurrency cap on expensive routes), request-size limits, and execution timeouts are defaults, with 429 responses that name the limit and carry retry guidance. Unbounded operations are OWASP API4:2023 (Unrestricted Resource Consumption). Sources: Stripe, "Rate limits", https://edge-docs.stripe.com/rate-limits ; OWASP API Security Top 10 (2023), URL above.
- **Flags decouple deploy from release.** Risky paths ship behind flags with an owner, a type (release, experiment, ops, permissioning), and an expiry; percentage rollouts bucket deterministically on a stable user key; every flag has a tested fallback and a kill path that works without a redeploy. Sources: Pete Hodgson, "Feature Toggles", https://martinfowler.com/articles/feature-toggles.html ; LaunchDarkly, "Kill switches, progressive rollouts, and user targeting", https://LaunchDarkly.com/blog/kill-switches-progressive-rollouts-user-targeting/

## 3. Per-skill research notes

### api-building
- **Core method:** Implement endpoints contract-first: route → authenticate → authorize (object-level) → validate against schema → run the domain operation in a transaction → serialize through a response mapper that exposes only contract fields. Writes that must not duplicate (orders, payments, sends) accept an `Idempotency-Key` and store key + request hash + response. Every handler ends in one of two exits: the success serializer or the problem-details error path — no third shape.
- **Key rules:**
  1. A handler is not done until its effect survives reload and a second client (the DET-FAKE persistence test); a 200 response is not evidence of an effect.
  2. Never trust a client-supplied amount, role, owner ID, or price; recompute or look up server-side.
  3. Check-then-act sequences (stock, uniqueness, balance) run inside a transaction or behind a unique constraint — the database arbitrates races, not application hope (DET-CODE-030).
  4. No stub, fixture, or in-memory stand-in may answer a production route (DET-CODE-003, DET-FAKE-015/016).
  5. Long work returns 202 with a status resource and continues as a job; the request never blocks on a provider.
- **Verification gates:** Contract test suite against the running service in CI (automatable); persistence test per write endpoint — perform, reload, re-read from a second session, assert the effect (automatable); duplicate-submit test with one idempotency key asserting a single effect (automatable).
- **Sources:** PROJECT_ANATOMY.md, "API implementation"; Stripe, "Idempotent requests", https://docs.stripe.com/api/idempotent_requests

### rest-conventions
- **Core method:** One written convention sheet per API, derived from RFC 9110 semantics and a published style guide, enforced by linting the OpenAPI document: plural kebab-case collection paths, no verbs in URLs (non-CRUD actions modeled as sub-resources or `POST /resource/{id}:action` per the chosen guide), one pagination style (cursor preferred for large or fast-changing collections), one field-casing rule, one filtering/sorting grammar, major version in the path only when a breaking change ships, with a deprecation window.
- **Key rules:**
  1. GET never changes state; anything reachable by a crawler or prefetcher must be safe.
  2. Status codes follow the department decision rule (see §1); errors are never 200.
  3. Every list endpoint paginates from day one — retrofitting pagination breaks clients that assumed complete results.
  4. PUT replaces, PATCH partially modifies, DELETE removes; repeating PUT/DELETE must land on the same end state.
  5. Breaking change = new major version or an additive-only evolution; released versions are never silently mutated.
- **Verification gates:** OpenAPI lint with a ruleset encoding the convention sheet (Spectral/Redocly) in CI (automatable); convention checklist diff review on every new endpoint (manual, checklist-driven).
- **Sources:** Zalando RESTful API Guidelines, http://opensource.zalando.com/restful-api-guidelines/ ; RFC 9110 summary, https://apiguide.dev/specifications/http-semantics

### validation
- **Core method:** Every inbound payload — body, query, path, headers — is parsed through a declared schema (types, formats, lengths, ranges, allowlists, unknown-field policy) at the edge of the handler, before any business logic or persistence. Syntactic checks are followed by semantic checks (date ranges ordered, referenced objects exist and are visible to the caller). Failures return 422 problem details listing each field and rule broken, and write nothing.
- **Key rules:**
  1. Server-side always; browser validation is UX, not a control (DET-CODE-019).
  2. Allowlist over denylist: enumerate what is accepted; reject unknown fields on write endpoints to block mass assignment (OWASP API3:2023 BOPLA).
  3. Business invariants live once, server-side; the client may mirror them for UX but the server copy is the only enforcement (DET-CODE-027).
  4. Validate the decoded/canonical form (filenames, Unicode, encodings), not the raw string, so bypass spellings fail.
  5. Size before parse: body-size and field-count caps run before schema work so validation itself cannot be exhausted.
- **Verification gates:** Boundary/fuzz test pack per endpoint — wrong types, oversized strings, unknown fields, inconsistent ranges — asserting rejection and zero partial state change (automatable); schema-vs-OpenAPI drift check in CI (automatable).
- **Sources:** OWASP Input Validation Cheat Sheet, https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html ; OWASP API Security Top 10 (2023), https://orca.security/resources/blog/owasp-api-security-top-10/

### feature-flags
- **Core method:** Flags are created in a central registry before code references them, each with an owner, a type (release / experiment / ops / permissioning, per the Fowler taxonomy), a default value that is the safe value, and an expiry date. Evaluation happens server-side through one toggle router; rollouts bucket deterministically by hashing a stable user key so a user never flickers between variants. Release flags are removed — code and flag — once rollout completes; the removal is part of the feature's definition of done.
- **Key rules:**
  1. The flag-off path is a tested product path, not an afterthought; a kill switch whose fallback is broken is decoration.
  2. No permanent flags: a flag past its expiry fails review; `if (true)` and renamed leftovers (`new_feature_v2_final`) are defects.
  3. Permissioning flags never substitute for authorization checks — a flag may hide a feature, the API still enforces who may use it (DET-FAKE-021).
  4. Flag changes in production are logged with actor and reason, like deploys.
  5. Experiments need a metric, a hypothesis, and an end date before the flag is created (with D12's experimentation-platform).
- **Verification gates:** Registry-vs-codebase diff: every flag key referenced in code exists in the registry with owner and unexpired date (automatable); staging flip test — toggle one release flag off and confirm the feature disappears with no redeploy (automatable).
- **Sources:** Pete Hodgson, "Feature Toggles", https://martinfowler.com/articles/feature-toggles.html ; LaunchDarkly, kill switches and progressive rollouts, https://LaunchDarkly.com/blog/kill-switches-progressive-rollouts-user-targeting/

### sdk-design
- **Core method:** The SDK is a product surface generated or hand-maintained against the same OpenAPI contract the server is tested against: typed models for every resource, one client object owning base URL, authentication, timeouts, and retries (retries only for idempotent operations or requests carrying an idempotency key), and errors surfaced as typed exceptions mapped from problem details. Versioning follows semver and tracks the API major version; a changelog and a runnable quickstart ship with every release.
- **Key rules:**
  1. The quickstart is a test: if a new user cannot complete the documented first task using only the README, the SDK is not done.
  2. Never hand-roll divergence: an SDK method that behaves differently from the raw API (extra defaults, swallowed errors, silent retries of non-idempotent calls) is a bug.
  3. Timeouts are mandatory and configurable; an SDK call that can hang forever will.
  4. Raw escape hatch: consumers can always reach the underlying HTTP layer for fields the SDK has not modeled yet.
  5. Deprecations are announced in the changelog and marked in code for at least one minor cycle before removal.
- **Verification gates:** Quickstart execution test in a clean project in CI (automatable); SDK-vs-contract conformance run — the same contract suite executed through the SDK (automatable).
- **Sources:** PROJECT_ANATOMY.md, "API implementation" (Stripe maintains official server-side SDKs for seven languages against one API behavior), https://docs.stripe.com/sdks/server-side ; Semantic Versioning 2.0.0, https://semver.org/

### backend-auth
- **Core method:** Identity is proven server-side on every request. Passwords are hashed with a vetted memory-hard algorithm (Argon2id/bcrypt class) with per-user salt; sessions are high-entropy opaque IDs (or signed tokens with server-side revocation) issued at login, rotated on authentication and privilege change, carried in Secure + HttpOnly + SameSite cookies for browser clients, and expired on logout, idle timeout, and absolute timeout. OAuth/OIDC flows delegate to D11's oauth-sso but the session they produce obeys the same rules. Login, signup, and reset endpoints are rate-limited and return generic errors that do not reveal whether an account exists.
- **Key rules:**
  1. Client state is never evidence of authentication: a `localStorage` flag, a hidden route, or a client-sent role is decoration (DET-FAKE-001, DET-FAKE-002).
  2. Signup is not done until the account record exists, the password is hashed, and a second login from a clean session succeeds (DET-FAKE-003).
  3. Password reset is a credential change: single-use, expiring token; all existing sessions revoked on reset; a reset that "succeeds" without changing the credential is a blocker (DET-FAKE-020).
  4. Failed-login responses are identical for unknown user and wrong password; timing and body must not enumerate accounts.
  5. Secrets and session IDs never appear in URLs, logs, or error responses.
- **Verification gates:** Auth test pack in CI — wrong password rejected, session survives reload, logout kills the session server-side, direct API call without credentials returns 401 (automatable); user-table inspection confirming hashed, salted passwords (automatable query + manual review).
- **Sources:** OWASP Session Management Cheat Sheet, https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html ; PROJECT_ANATOMY.md, "Authentication and authorization implementation"

### rbac
- **Core method:** Permissions are modeled as role → permission sets following the NIST RBAC reference model, and enforced by a server-side policy check inside the handler (or middleware bound to the route), never by UI visibility. Object-level checks (this user owns this record, or holds a role that may act on it) run separately from function-level checks (this role may call this operation at all) — OWASP API1 and API5 respectively. Role assignment is itself an admin-only, audit-logged operation; the permission matrix is a document in the repo that tests are generated from.
- **Key rules:**
  1. Deny by default: a route with no policy entry is unreachable, not open.
  2. The client never supplies the role that authorizes its own request; role comes from the server-side session/record only.
  3. Every permission change and every denied admin attempt lands in the audit log with actor, target, and timestamp.
  4. Tenant scope is part of the check: role grants rights inside one tenant context, never across tenants (cross-tenant test from PROJECT_ANATOMY.md, "Multi-tenancy").
  5. Cosmetic enforcement is a blocker: hiding a button while the endpoint answers is DET-FAKE-021, not a partial implementation.
- **Verification gates:** Authorization matrix test — for each role, every protected endpoint is requested with valid, missing, and other users' credentials, asserting 401/403 and no data leakage (automatable, generated from the permission matrix); cross-tenant access test (automatable).
- **Sources:** NIST CSRC, "Role Based Access Control", https://csrc.nist.gov/projects/role-based-access-control ; OWASP API Security Top 10 (2023), https://orca.security/resources/blog/owasp-api-security-top-10/

### user-reporting
- **Core method:** Every user-generated surface carries an in-product report action (per content item and per account) that creates a structured record — reporter, target, category, context snapshot — and routes it into a moderation queue with severity tiers. Reports are acknowledged to the reporter, tracked to a decision, and every enforcement action (label, reduce, remove, suspend, ban) is logged with the policy cited and is appealable. This skill owns the reporting intake and record; queue operations and enforcement policy sit with D7's content-moderation, and the staff surface with admin-tools.
- **Key rules:**
  1. A report button that emails an unmonitored inbox or writes nothing is a fake feature (DET-FAKE class; anatomy "Content moderation" slop).
  2. The reporter's identity is protected: the reported party never learns who reported them.
  3. Severe categories (child safety, credible threats, illegal material) jump the queue and trigger the escalation path immediately, not in FIFO order.
  4. Report volume and outcomes are data: repeat-offender and brigading patterns are computed from report records, which is impossible if reports are emails.
  5. The reporter gets a closure signal (received / decided) without disclosing enforcement detail.
- **Verification gates:** End-to-end report trace in staging — file a report as a test user, follow the record into the queue, decide it, and confirm the decision, policy citation, and reporter closure all exist (automatable except policy judgment); queue-aging report shows no report older than the tier's SLA (automatable).
- **Sources:** Trust & Safety Professional Association curriculum (via PROJECT_ANATOMY.md, "Content moderation and trust & safety"), https://www.tspa.org/curriculum/ts-curriculum/content-moderation-simulation/

### admin-tools
- **Core method:** A separate, staff-authenticated surface generated from or built over the same domain services users hit — never a parallel write path into the database. Every action reuses the service layer (so validation, authorization, and side effects match the product), runs under scoped staff roles, requires confirmation for destructive operations, offers reversal where the domain allows, and writes an audit record (actor, action, target, before/after, timestamp) for every mutation. Payment-adjacent views follow the PCI rule from the anatomy: card data stays with the provider (hosted collection, SAQ A scope); admin screens show at most brand + last 4 and must never render or log a full PAN.
- **Key rules:**
  1. An admin action that does not persist is a blocker, not a stub (DET-FAKE-010); dashboards must compute from live records (DET-FAKE-004).
  2. Staff roles are least-privilege and enforced server-side; a hidden URL is not access control.
  3. No raw SQL in production as an operating procedure: if support needs an action twice, it becomes an admin tool with an audit trail.
  4. Refunds, bans, and data corrections are two-step (prepare → confirm) and reversible or compensatable where possible.
  5. Admin sessions are stricter than user sessions: shorter idle timeout, re-authentication for high-impact actions.
- **Verification gates:** Limited-role denial test — a read-only staff role attempts a mutation and is refused server-side (automatable); audit-completeness test — perform a test refund/correction and confirm the audit record with actor and timestamp (automatable); PAN-pattern scan over admin pages and logs (automatable).
- **Sources:** Django admin documentation and Stripe PCI guidance (via PROJECT_ANATOMY.md, "Admin and internal tools"), https://docs.djangoproject.com/en/4.2/ref/contrib/admin/ and https://stripe.com/guides/pci-compliance

### queues-jobs
- **Core method:** Work that is slow, retryable, or owed to a third party is modeled as a job: a named type, a versioned payload of IDs (not whole objects), and a handler that is idempotent because delivery is at-least-once. Enqueue happens in the same database transaction as the state change that causes it (transactional outbox where the store and queue differ). Handlers run with bounded attempts, exponential backoff with jitter, and a fast path for permanent failures (bad address, 4xx from a provider) that skips remaining attempts. Exhausted jobs land in a failed set / dead-letter queue that is inspected, alerted on, and replayable. Progress states shown to users are read from real job state (DET-FAKE-022).
- **Key rules:**
  1. Attempts default to 1 in common queue libraries — a job with no explicit retry policy has silently chosen "lose the work" (DET-CODE-023's dropped-work failure in job form).
  2. Payloads carry IDs and are re-read at execution time; a job that embeds a stale object snapshot acts on old data.
  3. Every job type has a named owner, a max-attempts value, and a dead-letter destination before it ships.
  4. Scheduled/recurring jobs are registered idempotently at deploy, so redeploys never duplicate them.
  5. Queue depth and oldest-job age are monitored; a growing queue is an incident, not a backlog to admire.
- **Verification gates:** Failure-injection test — kill the worker mid-job and make the provider fail, assert the job retries with backoff and completes exactly once in effect (automatable); DLQ drill — force a job to exhaust attempts and confirm it is parked, alerted, and replayable (automatable).
- **Sources:** BullMQ retry/DLQ patterns, https://railway.com/guides/bullmq-jobs-retry-dlq and https://soundscode.com/nestjs/nest-queue-retries ; PROJECT_ANATOMY.md, "Webhooks" and "Notifications" (queued processing as the standard shape)

### realtime
- **Core method:** Choose the transport by traffic shape: SSE for server→client streams (status feeds, notifications, progress), WebSocket for bidirectional traffic (chat, collaboration), long-polling only as a degraded fallback. Connections authenticate during the handshake (cookie session or short-lived token — never a long-lived credential in the URL), subscribe to channels scoped by authorization (a client cannot subscribe to another tenant's channel), and heartbeat to detect dead peers. Events carry IDs and sequence numbers so a reconnecting client can catch up or be told to resync; beyond one instance, a pub/sub backplane (for example Redis) fans events out — per-process subscription memory is a single-instance trap named in the anatomy.
- **Key rules:**
  1. Reconnect is part of the protocol: exponential backoff with jitter client-side, catch-up or explicit resync on reconnect, no silent gaps.
  2. A `setInterval` poll presented as realtime is a defect (anatomy slop), not an implementation choice.
  3. Authorization is per channel, checked at subscribe time and re-checked when permissions change — connecting once does not grant a stream forever.
  4. Backpressure is designed: slow consumers are buffered with a cap, then dropped with a resync signal, never allowed to grow memory unboundedly.
  5. Presence and "live" indicators derive from real connection/event state; a timer-driven indicator is DET-FAKE-018.
- **Verification gates:** Two-session test — act in one client, assert the other updates without refresh (automatable); drop-and-reconnect test asserting catch-up with no missed or duplicated events (automatable); unauthenticated connection attempt rejected (automatable).
- **Sources:** MDN, "WebSocket" and "EventSource", https://developer.mozilla.org/en-US/docs/Web/API/EventSource ; PROJECT_ANATOMY.md, "Real-time features"

### file-uploads
- **Core method:** The app server authorizes and registers the intent, then issues a short-lived presigned URL so bytes flow directly from the client to private object storage; the database stores only metadata and the object key. Validation runs in layers per the OWASP sheet: authenticated user, size cap, extension allowlist checked on the decoded filename, content signature sniffing (the client Content-Type is never trusted), server-generated filename, and malware scanning before the file becomes visible. Downloads are authorized per request and served via signed URL or a handler that maps an opaque ID to the object — buckets are never public by default.
- **Key rules:**
  1. An upload is not complete until the object exists in storage and the metadata row points at it; a button that discards the file is DET-FAKE-012.
  2. Nothing user-supplied reaches a filesystem path: stored names are generated, original names are display metadata only.
  3. Files are inert where they rest: stored outside any executable path, served with safe Content-Type and `Content-Disposition`, never rendered as active content from the app's origin.
  4. Size and type limits are enforced at the storage layer (presigned policy) as well as in code, so a forged direct upload still fails.
  5. Orphan cleanup is a job: uploads never attached to a record are reaped on a schedule.
- **Verification gates:** Upload round-trip — upload through the UI, confirm the object in the bucket, the metadata-only row, unauthenticated access denied, and signed-URL expiry enforced (automatable); hostile-file pack — double extension, spoofed Content-Type, oversized file, polyglot — all rejected (automatable).
- **Sources:** OWASP File Upload Cheat Sheet, https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html ; AWS S3 presigned URLs (via PROJECT_ANATOMY.md, "File storage and media handling"), https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html

### media-processing
- **Core method:** Processing (thumbnails, transcodes, waveform/OCR/extraction, re-encode for safety) runs as queued jobs off the request path: upload lands in a quarantine state, a job produces the derivatives and normalized master, and only then does the asset become publishable. Images are decoded and re-encoded to an allowed format (which also strips embedded payloads and metadata not meant to ship); video transcodes target a fixed ladder of renditions for adaptive delivery through the CDN. Every derivative records its source object, recipe version, and status so reprocessing after a recipe change is a batch job, not archaeology.
- **Key rules:**
  1. Processing libraries run with resource limits (time, memory, pixel/frame caps) — decompression bombs are an upload class, not a surprise (OWASP File Upload threats).
  2. A failed transcode leaves the asset visibly failed with a retry path; it never silently serves the raw original in its place.
  3. User-visible state tracks the pipeline honestly: processing → ready / failed, read from job state (DET-FAKE-022).
  4. Metadata handling is deliberate: EXIF location data is stripped from user photos by default; document metadata rules are set per product, not by library default.
  5. Derivatives are regenerable: the stored original plus recipe must reproduce every served rendition.
- **Verification gates:** Golden-file test — a fixed input set produces derivatives matching expected dimensions, formats, and duration (automatable); bomb-resistance test — a decompression-bomb fixture is rejected within resource limits without worker death (automatable in staging).
- **Sources:** OWASP File Upload Cheat Sheet (image re-encoding, parser-exploit threats), https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html ; PROJECT_ANATOMY.md, "File storage and media handling"

### notifications
- **Core method:** A domain event creates a notification record first — the in-app inbox row is the source of truth — and channel dispatch (push via FCM/APNs, web push, and handoff to D11 for email/SMS) happens from a queue. Device tokens are stored per user and device, sends record provider responses, and tokens a provider reports as invalid are pruned. Preferences and opt-outs are checked at dispatch time, not at event time, and every notification deep-links to the object it concerns. This skill owns push and in-app; transactional email/SMS mechanics belong to D11, consumed through the same event.
- **Key rules:**
  1. The inbox is data, not a view over constants: a bell rendering a hardcoded list is DET-FAKE-013.
  2. Sends never run synchronously inside the triggering request; a slow provider must not slow the user's action.
  3. One event, one notification per recipient per channel — dispatch is idempotent against event ID so retries do not double-notify.
  4. Security and billing events (password changed, payment failed) bypass marketing opt-outs but never the user's channel-blocking rights; the distinction is written down.
  5. Token hygiene is continuous: invalid tokens pruned on provider feedback, tokens rotated on re-registration, no orphan tokens after logout on shared devices.
- **Verification gates:** Trigger test — fire the event on a test account and assert the inbox row exists and the push arrives on a real device/browser (automatable except device receipt, which is a scripted check on the test device); dead-token test — invalidate a token and confirm the failure is logged and the token pruned (automatable).
- **Sources:** Firebase Cloud Messaging documentation (via PROJECT_ANATOMY.md, "Notifications"), https://firebase.google.com/docs/cloud-messaging

### error-handling
- **Core method:** One error taxonomy and one exit path: domain code throws (or returns) typed errors carrying a problem type, and a single global handler maps them to RFC 9457 problem details with the right status, a correlation ID, and field-level detail for validation failures. Unexpected exceptions become a generic 500 problem — no message, no stack, no SQL — while the full exception, request context, and correlation ID go to structured logs and error tracking (D12). Errors are classified by who can fix them: caller-fixable (4xx with actionable detail), conflict (409/412), dependency failure (502/503 with retry guidance), and ours (500, alerted).
- **Key rules:**
  1. No empty catches and no catch-log-rethrow noise: an error is handled, translated, or propagated — never swallowed (DET-CODE-005, DET-CODE-006).
  2. Different failures get different signals: identical messages for different failures (DET-CODE-022) make incidents undebuggable and clients unable to react.
  3. Client errors never leak internals: no table names, file paths, framework versions, or provider payloads in any response (OWASP ASVS error-handling requirement).
  4. Fail closed on security checks: an error inside an authorization or validation step denies the operation, never waves it through.
  5. Every 5xx is observable: if an error is worth returning, it is worth a log record and a metric with the same correlation ID the client received.
- **Verification gates:** Error-shape contract test — a suite that forces each error class and asserts the problem-details shape, status, and absence of internal markers (stack frames, SQL, paths) in the body (automatable); fuzz/negative-path run asserting no unhandled-exception response ever reaches a client (automatable).
- **Sources:** RFC 9457, https://ftp.kaist.ac.kr/rfc/rfc9457.html ; OWASP Error Handling Cheat Sheet, https://cheatsheetseries.owasp.org/cheatsheets/Error_Handling_Cheat_Sheet.html

### rate-limiting
- **Core method:** Limits are set per route class, not globally guessed: a generous per-account ceiling for ordinary reads, strict per-account and per-IP limits on authentication and other sensitive flows, and a separate concurrency cap for expensive operations (search, export, AI calls, uploads). A token-bucket (or equivalent) limiter at the edge or middleware counts per key; rejections return 429 with the limit identified and `Retry-After` guidance; metered downstream calls (SMS, email, paid APIs) carry their own tighter budgets because their cost is money, not just compute. Legitimate-client behavior (SDK backoff with jitter) is documented so good clients survive limits gracefully.
- **Key rules:**
  1. The limiter key must not be client-spoofable: keying on a forwarded-IP header without a trusted proxy chain is a bypass, not a limit (anatomy slop).
  2. Every list/export/search endpoint has a maximum page size and a query-cost ceiling; unbounded operations are DET-CODE-033 and OWASP API4:2023.
  3. Auth endpoints are limited independently of the global budget, per account and per IP, so credential stuffing cannot hide inside general traffic.
  4. Limits are configuration with owners, reviewed like code — a limit nobody can explain is either an outage or a hole waiting for a date.
  5. 429 is a contract: machine-readable, names the limit, and states when to retry; clients are never told to "try again later" with no number.
- **Verification gates:** Burst test — scripted traffic above each documented limit asserts 429s with retry headers while a second key and normal-rate traffic pass unaffected (automatable); spoof test — forged forwarding headers do not reset the caller's budget (automatable).
- **Sources:** Stripe, "Rate limits", https://edge-docs.stripe.com/rate-limits ; PROJECT_ANATOMY.md, "Rate limiting and abuse controls"; OWASP API Security Top 10 (2023) API4, https://orca.security/resources/blog/owasp-api-security-top-10/

## 4. Open risks for Phase 3

1. **Stack neutrality vs. concreteness.** These notes are deliberately framework-free, but Phase 3 skills must name concrete defaults (a schema validator, a queue library, a flag registry shape) or drafters will each invent their own. Recommendation: D2/D15 pick the reference stack's backend pieces before D4 drafting starts, and each D4 skill states its pattern in stack-neutral terms plus one worked reference-stack example.
2. **Boundary disputes with D11 and D7.** Webhooks, transactional email/SMS, and OAuth are D11-owned but D4-shaped (queued, idempotent, problem-details errors); auth depth overlaps D7's security skills. Phase 3 needs a single cross-reference pass so skills cite each other instead of duplicating or contradicting — especially notifications (D4) vs. transactional-email (D11), and backend-auth (D4) vs. auth-hardening (D7).
3. **Idempotency scope creep.** The key-cache pattern is well documented for payments-style POSTs, but which endpoints in a typical OmniForge project must accept keys (all creates? only money-moving ones?) is a judgment call the api-building skill must settle explicitly, or every project will draw the line differently.
4. **Realtime on free tiers.** The Phase 1/6 free-tier constraint (D-005) collides with realtime: long-lived connections and pub/sub backplanes are the first features free hosts restrict. The realtime skill needs a tested degraded mode (SSE-only, then polling fallback) or proof projects will fail QA for infrastructure reasons misread as code defects.
5. **Detection coverage asymmetry.** DET-FAKE and DET-CODE give D4 strong behavioral tests, but there is no DET family yet for performance-under-load behavior of queues and limiters; the rate-limiting and queues-jobs gates above assume staging load tests that Phase 3 must specify concretely, or those gates will be the first to be skipped.
