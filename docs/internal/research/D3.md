## 1. Department standard — how professional frontend/design work runs today

**Design decisions live as data: tokens in the DTCG format, transformed by a build step.** The Design Tokens Community Group (a W3C Community Group) published the first stable version of the Design Tokens Specification, 2025.10, on 28 October 2025: a vendor-neutral JSON format in which every token is an object with `$value`, `$type`, optional `$description`/`$deprecated`/`$extensions`, and dot-path aliases so a semantic token can point at a primitive one (https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/; full spec: https://www.designtokens.org/tr/2025.10/). Style Dictionary v4+ reads DTCG files natively and transforms them into CSS custom properties, Tailwind themes, or native constants; Terrazzo and Tokens Studio are the other named reference implementations (https://styledictionary.com/info/dtcg/). The working structure is three tiers — primitive (raw values) → semantic (role: `color-action-primary`) → component — and theming (light/dark, multi-brand) happens at the semantic tier without duplicating files. Professional rule that follows: components consume semantic tokens only, and the token file is the single place a visual value may be defined.

**Interfaces are built component-first and documented in a workshop, not assembled page by page.** Component-driven development builds small, isolated components bottom-up and composes pages from them; Storybook is the standard workshop, with one story per variant and state so behavior (focus, keyboard, disabled, loading) is correct once and visible to reviewers (https://storybook.js.org/blog/structuring-your-storybook/). Mature public systems — GOV.UK, IBM Carbon — publish components with usage guidance that includes when *not* to use them (GOV.UK button: https://design-system.service.gov.uk/components/button/). Visual regression on stories (screenshot diffing) is the normal regression net for appearance, complementing unit tests for logic.

**Performance is a budget enforced in CI, not a post-launch cleanup.** The acceptance numbers are Google's Core Web Vitals thresholds, assessed at the 75th percentile of real visits: LCP ≤ 2.5s, INP ≤ 200ms, CLS ≤ 0.1 (thresholds as published by Google on web.dev; reproduced with the needs-improvement/poor bands at https://aemorph.com/guides/core-web-vitals/). Teams turn them into build gates with Lighthouse CI assertions (`largest-contentful-paint`, `cumulative-layout-shift`, and resource-summary byte budgets as errors in `.lighthouserc`) plus a bundle-size tool (size-limit or bundlesize) per chunk, so a regression fails the build instead of reaching users (https://www.debugutils.dev/blog/performance-budgets/; CI wiring detail: https://www.code-splitting.com/bundle-analysis-and-performance-budgets/enforcing-performance-budgets-in-ci/). Department consequence: image weight, font loading, and hero media are budget decisions made at design time, not optimizations attempted later.

**Accessibility floors are numeric and testable.** WCAG 2.2 AA is the working baseline: text contrast ≥ 4.5:1 (3:1 for large text), non-text contrast ≥ 3:1 for control boundaries and focus indicators, pointer targets ≥ 24×24 CSS px (SC 2.5.8, with spacing exceptions; platform guidance of 44pt/48dp is the comfort target), and content must reflow at 320 CSS px wide with no page-level horizontal scrolling (SC 1.4.10) (criteria and numbers summarized at https://convarso.com/blog/web-accessibility-guide-wcag/). Contrast is checked on token pairs automatically; target size and reflow are checked in the layout pass.

**Motion is a tokenized system with a reduced-motion variant, not decoration.** Durations and easing curves are tokens like any other value; animation is restricted to `transform` and `opacity` for compositing performance; and every non-essential animation is removed or replaced when the user requests reduced motion — via the `prefers-reduced-motion` media query (https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion) and W3C technique C39 for suppressing animation (https://www.w3.org/WAI/WCAG22/Techniques/css/C39.html). Scroll effects are built with CSS scroll-driven animations or IntersectionObserver, never per-frame scroll handlers, and content is visible if the script never runs (https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Scroll-driven_animations/Timelines).

**Client architecture separates server state from client state.** Server data lives in a dedicated query cache (TanStack Query or framework loaders) keyed by query key, with explicit freshness, background refetch, deduplication, and retry-with-backoff; its documented defaults are the reference behavior (https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults). Client state (UI, session, shared app state) lives in components, the URL, or a store with one owner per fact and one-way updates. Copying server data into a global store and hand-synchronizing it is the recognized anti-pattern this split exists to prevent.

## 2. Failure modes this department prevents

Each item names the anatomy element (PROJECT_ANATOMY.md Part 7), its "Slop looks like" line, and the DET-VIS parameters that detect it. D3 skills are the Fix named in those parameters.

- **Design system and design tokens** — "A 'system' that is one gradient, one font, and copy-pasted cards, with raw hex values scattered through components and no semantic layer." Detected by DET-VIS-001 (uniform section padding), DET-VIS-004 (mechanical spacing, no rhythm breaks), DET-VIS-017 (purple-blue gradient signature), DET-VIS-020 (single accent monoculture), DET-VIS-021 (one default shadow everywhere), DET-VIS-043 (inconsistent radius language).
- **Component library** — "A folder of near-duplicate components with inconsistent props, no stories, and pages that bypass the library with one-off markup." Detected by DET-VIS-003 (identical card grids), DET-VIS-007 (components break on real content lengths), DET-VIS-025 (mixed icon styles), DET-VIS-026 (icon-in-tinted-circle formula), DET-VIS-031 (one button treatment everywhere), DET-VIS-033 (badge/pill saturation), DET-VIS-036 (pricing-table fingerprint).
- **Layout and responsive design** — "One desktop screenshot layout, a single `max-width: 768px` media query that stacks everything, and content hidden on mobile 'because it didn't fit.'" Detected by DET-VIS-002 (centered-everything), DET-VIS-005 (one container width), DET-VIS-008 (zigzag alternation), DET-VIS-037 (breakpoint collapse, major), DET-VIS-038 (horizontal overflow on mobile, blocker), DET-VIS-039 (fixed hero height clipping, major).
- **Typography** — "Five font families, gradient or all-caps headline text, 12 arbitrary font sizes, and body copy at low contrast gray." Detected by DET-VIS-011 (default font pairing), DET-VIS-012 (flat type scale), DET-VIS-013 (edge-to-edge line length, one leading for all sizes), DET-VIS-014 (no micro-typographic detail), DET-VIS-015 (one case, one weight for all headings), DET-VIS-016 (emoji as iconography, major), DET-VIS-018 (gradient text on headline).
- **UI states** — "A generic spinner for every wait, 'No data' as the only empty copy, raw error codes or stack text shown to users, and no confirmation after actions." Detected by DET-VIS-032 (missing or fake UI states, major) and DET-VIS-042 (hover-dependent dead ends, major).
- **Motion and animation** — bounce/parallax on everything, inconsistent per-component durations, motion that blocks input, and total disregard of the reduced-motion preference. Detected by DET-VIS-040 (uniform fade-up on every section) and DET-VIS-041 (reduced motion ignored, major).
- **Imagery and iconography (frontend-core / design-system)** — generic stock or AI imagery depicting nothing real, AI image artifacts, fake browser-frame mockups, invented logo clouds, unsourced round-number stat bands. Detected by DET-VIS-023 (imagery mismatch, major), DET-VIS-024 (AI image artifacts, blocker), DET-VIS-027 (identical avatar circles, major), DET-VIS-029 (aspect-ratio chaos/monotony), DET-VIS-030 (screenshot-in-browser-frame mockups, major), DET-VIS-034 (logo cloud of invented marks, major), DET-VIS-035 (stat band with round numbers).
- **Color on real surfaces** — white/light text on mid-tone gradients and pastel panels picked aesthetically and never contrast-checked. Detected by DET-VIS-022 (unchecked contrast in colored sections, major) and DET-VIS-019 (dark background with neon glow).

## 3. Per-skill research notes

### 3.1 frontend-core

**Core method.** Build from semantic HTML outward: landmarks and native elements first, framework components second, custom widgets last. Treat the performance budget and the accessibility floor as feature requirements, not polish. Every page must work at 320px, on keyboard alone, and with images or scripts failed, before it is considered built.

**Key rules for the drafter.**
1. Landmarks, headings, and native controls before any `div`-based imitation; a clickable `div` is a defect, not a shortcut.
2. Every image ships with reserved dimensions (`width`/`height` or aspect-ratio) so nothing shifts after load (CLS budget).
3. No hard-coded color, spacing, or radius values in components — semantic tokens only (enforced with design-tokens, §3.3).
4. Imagery must depict the real product, place, or people, or be clearly generic decoration; AI artifacts in photography (hands, in-image text, logos) are a blocker (DET-VIS-024).
5. JavaScript is budgeted per route; a feature that breaks the bundle budget is redesigned or split, not shipped heavy.

**Verification gates.** Automatable: Lighthouse CI assertions in CI (LCP ≤ 2500ms, CLS ≤ 0.1 as errors; JS byte budget via size-limit), axe-core run over key routes with zero critical violations. Manual: keyboard-only walk of the primary flow; 100%-zoom image inspection pass for DET-VIS-023/024.

**Sources.** Core Web Vitals thresholds (web.dev, reproduced) — https://aemorph.com/guides/core-web-vitals/ · Performance budgets in CI — https://www.debugutils.dev/blog/performance-budgets/

### 3.2 design-system

**Core method.** The system is four artifacts, not one: the token set, the component library, written usage rules (including when *not* to use a component), and a changelog. Decisions are made once, recorded, and consumed everywhere; a visual choice that exists only inside one page's code is not part of the system. WCPM absorb: this skill is the primary home for WCPM's visual-language and anti-pattern material — the "one gradient, one font" failure is a system-governance failure before it is a styling failure.

**Key rules for the drafter.**
1. Every visual decision on a shipped page traces to a token, a library component, or a documented one-off exception with a reason.
2. Each component's documentation states purpose, variants, and at least one "do not use when" case, on the GOV.UK pattern.
3. The system is versioned; a token or component change ships with a changelog entry and a visual-regression pass, never as a silent edit.
4. Section composition varies by content role (hero, proof, dense content, closing) — a page where every section has the same padding, alignment, and loudest element fails system review (DET-VIS-001/002/010).
5. Proof elements (metrics, quotes, product shots) may outrank headings in visual weight; hierarchy serves the message, not a template.

**Verification gates.** Manual: per-milestone DET-VIS cluster review of screenshots at 1440px and 390px against §2 of this file. Automatable: the token-coverage and contrast gates owned by design-tokens (§3.3) run as this skill's enforcement arm.

**Sources.** GOV.UK Design System — https://design-system.service.gov.uk/components/button/ · DTCG stable announcement — https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/

### 3.3 design-tokens

**Core method.** Author tokens once in DTCG-format JSON (`$value`, `$type`, aliases), in three tiers: primitive → semantic → component. Transform with Style Dictionary (or Terrazzo) into CSS custom properties and any other platform outputs the project needs. Themes are semantic-tier overrides of the same token names. WCPM absorb: token-level defaults are where several WCPM tells are born (one shadow, one radius scatter, gradient signatures) — the token file is where they are prevented.

**Key rules for the drafter.**
1. Components reference semantic tokens only; primitive values never appear in component code.
2. No raw hex, pixel, or millisecond values in component styles — the only definitions live in the token source files.
3. Every token carries a `$description`; retired tokens are marked `$deprecated` with a pointer to their replacement, not silently deleted.
4. Elevation, radius, spacing, and duration are scales with named roles (e.g. radius: input/card/pill), applied by role — this is the direct counter to DET-VIS-021 and DET-VIS-043.
5. Semantic foreground/background pairs are chosen to pass contrast before they are named (see gate below), including on tinted and gradient surfaces (DET-VIS-022).

**Verification gates.** Automatable: Style Dictionary build in CI (a broken alias fails the build); a lint (stylelint custom rule or a grep-based script) that fails on hex/px literals in component style files; a contrast script that computes WCAG ratios for every semantic text-on-surface token pair and fails below 4.5:1 (3:1 for large-text pairs). Manual: token-diff review on any token change.

**Sources.** Design Tokens Format Module 2025.10 — https://www.designtokens.org/tr/2025.10/ · Style Dictionary DTCG support — https://styledictionary.com/info/dtcg/

### 3.4 component-library

**Core method.** Build components bottom-up in Storybook, one story per variant and state, against tokens. Pages are assembled from the library; a page needing something new extends the library instead of hand-rolling markup. Behavior (focus order, keyboard interaction, disabled semantics) is implemented and tested once, inside the component.

**Key rules for the drafter.**
1. Every component ships its full applicable state set — default, hover, focus-visible, active, disabled, loading, error — or the state matrix explicitly says why a state does not apply (DET-VIS-032).
2. One icon set, one stroke weight, one metaphor style across the whole library (DET-VIS-025); emoji are never structural icons (DET-VIS-016).
3. Components are stress-tested with real, messy content: long names, long words, maximum-length labels — overflow or clipping is a component bug (DET-VIS-007).
4. Variants express hierarchy (primary/secondary/destructive/text; sizes by context), not one treatment at one size for everything (DET-VIS-031).
5. Badges and pills are rationed: a badge must carry information the user can act on (DET-VIS-033).

**Verification gates.** Automatable: Storybook test-runner plus screenshot visual-regression over all stories in CI; a grep gate that flags raw `<button>`/`<input>` markup in page code duplicating a library component. Manual: story-coverage review — every variant and state in the matrix has a story.

**Sources.** Structuring your Storybook — https://storybook.js.org/blog/structuring-your-storybook/ · GOV.UK button component — https://design-system.service.gov.uk/components/button/

### 3.5 motion

**Core method.** Specify motion like type: a small set of duration and easing tokens, applied to state changes and continuity. Every animation names its purpose — feedback, continuity, or one deliberate moment of attention — before it is built. Animate `transform` and `opacity` only. Design the reduced-motion variant in the same pass, not as a retrofit. WCPM absorb: WCPM's motion tells (uniform fade-up, decorative parallax) are countered here and in scroll-experiences.

**Key rules for the drafter.**
1. No animation without a named purpose; "it looked empty" is not a purpose.
2. A global fade-up applied to every section is forbidden (DET-VIS-040); most content is simply present.
3. Under `prefers-reduced-motion: reduce`, parallax, auto-playing motion, and non-essential animation are off; state changes remain legible without movement (DET-VIS-041).
4. Durations and easings come from the motion tokens — no per-component improvisation.
5. Motion never blocks input and never delays access to content; interactive feedback is effectively immediate.

**Verification gates.** Automatable: a Playwright pass with reduced-motion emulation asserting that flagged animations are disabled/absent; a CSS check that a `prefers-reduced-motion` block exists whenever animation is used. Manual: DevTools rendering-emulation walk of the main flows.

**Sources.** MDN, prefers-reduced-motion — https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion · W3C technique C39 — https://www.w3.org/WAI/WCAG22/Techniques/css/C39.html

### 3.6 scroll-experiences

**Core method.** Treat scroll effects as progressive enhancement layered over fully visible content. Implement with CSS scroll-driven animations (`animation-timeline: scroll()` / `view()`) or IntersectionObserver — never scroll event handlers doing per-frame layout work. Choreography paces a story (progress, reveal of genuinely sequential content); it never gates reading.

**Key rules for the drafter.**
1. Content is visible with JavaScript disabled and if the timeline never runs; reveal-on-enter starts from visible, not from `opacity: 0` set by CSS alone.
2. No scroll-jacking: the user's scroll position and speed are never overridden.
3. Parallax and scroll-linked motion are disabled under reduced motion (with motion, §3.5).
4. Scroll progress indicators are optional decoration; they must never be the only place progress or position is communicated.
5. Pinned/sticky sections must not trap focus or obscure focused elements (WCAG 2.4.11 focus-not-obscured risk).

**Verification gates.** Automatable: Playwright with JavaScript disabled asserting every section's text is present in the rendered page. Manual: DevTools Performance recording during a full scroll, checking for long tasks tied to scroll handlers.

**Sources.** MDN, scroll-driven animation timelines — https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Scroll-driven_animations/Timelines · CSS Scroll-Driven Animations spec — https://drafts.csswg.org/scroll-animations/

### 3.7 layout-responsive

**Core method.** Design mobile-first with fluid grid/flex layouts; add breakpoints where the content breaks, not at device names; use container queries so components respond to their own space. Width is a design variable — narrow for reading, wide for galleries, full-bleed for imagery. Reserve media dimensions so layout is stable while assets load.

**Key rules for the drafter.**
1. No page-level horizontal scrolling at any width from 320px up; wide content (tables, code) gets a contained scroll region or a reformat, never page overflow (DET-VIS-038, blocker; WCAG reflow at 320 CSS px).
2. Mobile layouts are recomposed, not just stacked: order follows priority, the type scale and spacing rhythm adjust, tap targets stay ≥ 24×24 CSS px with 44px as the working target (DET-VIS-037).
3. Heroes size to content with `min-height`; fixed `100vh`/pixel heroes that clip text or CTAs on short screens are forbidden (DET-VIS-039).
4. One container width for every section is a defect; width follows content role (DET-VIS-005).
5. Body text columns stay near a readable measure (~70–80 characters) at wide viewports instead of running to the container edge.

**Verification gates.** Automatable: Playwright screenshot matrix at 320/390/768/1440px plus an overflow assertion (`document.scrollingElement.scrollWidth <= innerWidth`) on every route. Manual: continuous resize walk from 320px to 1920px checking for overlap, orphans, and unreadable line lengths.

**Sources.** GOV.UK layout style — https://design-system.service.gov.uk/styles/layout/ · WCAG 2.2 criteria summary (reflow, target size) — https://convarso.com/blog/web-accessibility-guide-wcag/

### 3.8 typography

**Core method.** Define a small tokenized type system — display, heading levels, body, caption, data — on a modular scale with role-specific size, line-height, and tracking, using fluid `clamp()` sizing between viewports. Load at most two families, only the weights used, self-hosted or efficiently delivered with `font-display` and subsetting. WCPM absorb: WCPM's typography tells (default pairings, flat scales, gradient text) are this skill's home ground.

**Key rules for the drafter.**
1. Font sizes come only from the type-scale tokens; an off-scale size in a component is a defect (DET-VIS-012).
2. Hierarchy must be unmistakable: on marketing/editorial pages the largest heading is dramatically larger than body (the DET-VIS-012 check uses 2.5× body as the floor), captions distinctly smaller.
3. Case and weight vary by level and purpose; one weight and one case pattern across all heading levels fails review (DET-VIS-015).
4. Micro-typography is finished work: tracked-out uppercase labels, real quotation marks and en/em dashes in prose, tabular numerals in tables and data (DET-VIS-014).
5. Emphasis is achieved with weight, size, italic, or a solid accent — gradient-clipped headline text is not a default device (DET-VIS-018); body text never sits below AA contrast, including "muted" gray styles.

**Verification gates.** Automatable: a computed-style audit script listing distinct font families, sizes, and weights per page, diffed against the token scale — any value not in the scale fails. Manual: micro-typography scan of headings and prose for straight quotes, hyphen-as-dash, and untracked caps labels.

**Sources.** GOV.UK headings and typography styles — https://design-system.service.gov.uk/styles/headings/ · Design Tokens Format Module (typography tokens) — https://www.designtokens.org/tr/2025.10/

### 3.9 ui-states

**Core method.** Specify every data-dependent view as a state matrix before building it: loading, empty (first use / no results / cleared), error, partial, success. Loading uses skeletons matched to the final layout (a bare spinner only for short, bounded waits); empty states explain what belongs here and offer the next action; errors say what happened in plain language and offer recovery; success confirms completion.

**Key rules for the drafter.**
1. No silently blank containers, ever: every view renders a designed state for every condition it can be in (DET-VIS-032).
2. Raw error codes, stack text, and "No data" as sole copy are forbidden; error copy names the problem and the next step.
3. Every mutating action ends in a visible success confirmation (or an error state with retry); silent completion is a defect.
4. Hover enhances but never gates: every hover reveal has a tap/click and keyboard-focus equivalent (DET-VIS-042).
5. Skeleton shapes match the final layout so the loading→loaded transition does not reflow the page (CLS budget, §3.1).

**Verification gates.** Manual (primary, per the anatomy Verify step): for each main view, screenshot four states — throttled network (loading), empty account (empty), blocked API request (error), completed action (success). Automatable: Playwright tests that mock empty and error API responses and assert the corresponding state components render.

**Sources.** NN/g, Designing Empty States in Complex Applications — https://www.nngroup.com/articles/empty-state-interface-design/ · W3C technique C39 (state changes under reduced motion) — https://www.w3.org/WAI/WCAG22/Techniques/css/C39.html

### 3.10 frontend-state

**Core method.** Classify state before storing it: local component state for one widget; a store (Redux, Zustand, signals, or framework context) for state genuinely shared across the app; the URL for anything shareable or bookmarkable; and server data — never in this layer at all (it belongs to data-fetching, §3.11). Updates flow one way through explicit actions or setters.

**Key rules for the drafter.**
1. Every piece of shared state has exactly one owner and one update path; two components holding copies of the same fact is a defect.
2. Shared state is never mutated in place from arbitrary components; changes go through the store's actions/reducers.
3. Server data is never copied into the client store and hand-synchronized — that is the anti-pattern the state/fetching split exists to kill.
4. State is not stored in the DOM (classes, data attributes, hidden inputs) as a source of truth.
5. Shareable view state (filters, selected tab, pagination) lives in the URL so refresh, back button, and shared links behave.

**Verification gates.** Manual: the trace test — pick each shared fact, name its owner and update path, change it in one view, and confirm every dependent view updates without reload. Automatable: where the stack provides one, a lint rule forbidding direct store mutation outside actions (e.g. Redux-style immutability lint); absence of such a rule must be recorded, not silently skipped.

**Sources.** Redux principles (single source of truth, read-only state, pure reducers), as summarized at — https://www.freecodecamp.org/news/an-intro-to-redux-and-how-state-is-updated-in-a-redux-application-839c8334d1b1/ · TanStack Query important defaults (the server-state boundary) — https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults

### 3.11 data-fetching

**Core method.** Keep server state in a dedicated query cache (TanStack Query, or framework loaders/actions in Next.js/Nuxt-style stacks) keyed by a stable query-key scheme that mirrors the API's resources. Set freshness (`staleTime`) per data type, refetch in the background on mount/focus/reconnect, deduplicate in-flight requests, retry failures with backoff, and let mutations invalidate or optimistically update exactly the affected queries.

**Key rules for the drafter.**
1. No fetch-on-mount `useEffect` sprawl: all server reads go through the query layer, so the same endpoint is never hit five times for one page.
2. Requests are cancellable or keyed so fast navigation cannot let a stale response overwrite a newer view (no race-condition rendering).
3. Every query's loading and error outcomes land in the view's state matrix (ui-states, §3.9); errors are never swallowed silently.
4. Cached data is labeled by behavior, not hope: if data can be stale, the freshness window is a deliberate per-query decision.
5. Optimistic updates always carry a rollback path on mutation failure.

**Verification gates.** Automatable: a Playwright network-count test — navigate view A → B → A and assert the shared endpoint was requested once, then served from cache with background revalidation. Manual: go offline mid-session and confirm the designed error state appears and recovers on reconnect.

**Sources.** TanStack Query, Important Defaults — https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults

### 3.12 client-routing

**Core method.** Give every meaningful view a real URL. Define routes (data-router objects or file-based routes) with nested layouts, route loaders that fetch before render, per-route error boundaries, and a designed 404. Navigation uses the router's link component; guards redirect for UX while the API remains the actual authorization boundary.

**Key rules for the drafter.**
1. No state-flag navigation: refresh, deep link, and the back button must all land on the correct view.
2. No full-page reloads inside the SPA and no hash-only URLs on public, indexable sites.
3. Route guards are UX only — protected data is authorized by the API on every request, never by the router.
4. Unknown paths render the designed 404 view with a path back into the product; a blank screen on a bad URL is a defect.
5. On navigation, scroll position is restored or reset deliberately and focus moves to the new view's heading/main region for keyboard and screen-reader users.

**Verification gates.** Automatable: Playwright pass — cold-load a nested route in a fresh tab, traverse five views with back/forward, and load a nonsense URL asserting the 404 view. Manual: refresh-on-every-route sweep during QA.

**Sources.** React Router data-router guide (loaders, error boundaries), as cited in PROJECT_ANATOMY.md Part 7 — https://micropyramid.com/blog/react-router-for-navigation/

### 3.13 forms

**Core method.** Build label-first: every control gets a visible, programmatically associated label; instructions and format hints appear before or within the label, where forms-mode screen readers will encounter them; validation runs on blur and submit; errors are reported inline against their field (`aria-describedby`, `aria-invalid`) and summarized at the top with focus moved to the summary. `autocomplete` attributes let browsers fill known data; submission guards against duplicates and ends in confirmation.

**Key rules for the drafter.**
1. Placeholder text is never the only label, and a red border is never the only error signal — every error is text that names the field and the fix.
2. Entered data survives validation errors; a form that clears input after one mistake fails review.
3. Validation does not fire on every keystroke; required fields are marked in text, not by color or asterisk alone.
4. One bad field must be findable and fixable by keyboard alone, with focus managed to the error summary on submit.
5. Submission is idempotent from the user's side: double-clicks and retries cannot create duplicate records, and success is confirmed (with ui-states, §3.9).

**Verification gates.** Automatable: axe-core form rules in CI (labels, aria) plus a Playwright keyboard-only test — submit empty, then with one bad field — asserting focus lands on the error summary and each error names its field. Manual: screen-reader pass on the primary form.

**Sources.** W3C WAI, Developing for Web Accessibility (labels, instructions, error help) — http://www.w3.org/WAI/tips/developing/ · NN/g empty-state guidance (form-adjacent state copy) — https://www.nngroup.com/articles/empty-state-interface-design/

### 3.14 data-visualisation

**Core method.** Start from the message, not the library: name the one-sentence statement the chart must make (change over time, comparison, share, correlation, flow, geography), then choose the chart family that answers it — lines for time, bars for comparison, scatter for correlation. Label series directly where possible, use one accent color for the story and gray for context, and ship an accessible table or text alternative with every chart.

**Key rules for the drafter.**
1. Bar charts start at zero; a truncated bar axis is a defect unless explicitly justified and flagged on the chart.
2. No 3D charts, no pie charts with more than a handful of slices, no dual axes implying correlation without a stated basis.
3. Color encodes meaning and is checked for colorblind distinguishability; rainbow palettes are forbidden.
4. Every chart carries axis labels, units, and the data source with its date — an unsourced chart is treated like an unsourced statistic (see DET-VIS-035 escalation).
5. The chart's type must match its message; if the one-sentence message cannot be stated, the chart is decoration and is removed.

**Verification gates.** Manual: the message test per chart (state the message, check the type), plus axis and labeling inspection. Automatable: a DOM check that every chart element (`canvas`, `svg` chart root) has an accompanying data table or an `aria-describedby`/visually-hidden text summary.

**Sources.** Datawrapper, A friendly guide to choosing a chart type — https://www.datawrapper.de/blog/chart-types-guide

### 3.15 pwa-offline

**Core method.** Ship a valid manifest (name, icons, display mode) and a service worker with an explicit per-resource strategy: precache the app shell at `install`, clean old caches at `activate`, and intercept `fetch` with cache-first for static assets and network-first or stale-while-revalidate for data. Cache names are versioned so updates actually reach users. Claim PWA capability only if the core task survives offline.

**Key rules for the drafter.**
1. Cache-everything-forever is forbidden; every cached class of resource has a strategy and a lifetime.
2. The offline experience is designed: a real offline page/state in the product's design system, never the browser default error.
3. A manifest without a working service worker (or vice versa) is a defect — the pair ships together or not at all.
4. Service-worker updates are planned: users must not be stranded on a weeks-old cached app; the update flow is part of the design.
5. Offline capability is scoped honestly: if only the shell works offline, the UI says so rather than implying full function.

**Verification gates.** Automatable: Lighthouse installability/PWA audits in CI; a Playwright test that loads the app, switches to offline, reloads, and completes the core task (or reaches the designed offline state). Manual: DevTools Application tab — service worker active, manifest parses, cache contents match the stated strategy.

**Sources.** MDN, Offline and background operation — https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation

### 3.16 webgl-3d

**Core method.** Use a maintained library (Three.js or Babylon.js) over raw WebGL. Build the fallback first: check for a usable context, and if WebGL is unavailable, render a static image or content equivalent. Cap device pixel ratio, scale quality to device capability, pause rendering when the canvas is offscreen, and handle context loss explicitly.

**Key rules for the drafter.**
1. WebGL never gates content: every 3D scene has a fallback that conveys the same information or product view.
2. A full-screen WebGL hero that blocks or delays primary content fails the performance budget review (§3.1) by default and needs explicit justification.
3. Auto-rotation and camera motion stop under `prefers-reduced-motion`; user-controlled motion remains available.
4. The canvas carries a text alternative describing what it shows; keyboard users can reach and operate any control the scene exposes.
5. Frame budget is verified on a low-end device, not the development machine; quality scaling engages before frame rate collapses.

**Verification gates.** Manual: disable/block WebGL and confirm the fallback renders and the page's message survives; profile frame rate on a low-end phone. Automatable: a Playwright run with WebGL disabled (browser launch flag) asserting the fallback element is visible.

**Sources.** MDN, Getting started with WebGL — https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/Tutorial/Getting_started_with_WebGL

## 4. Open risks

**R1 — Single-agent design-system consistency across a long project (the department's structural risk).** A human team keeps a system coherent through shared memory, design review, and a second pair of eyes. The single agent has none of these by default: across a long build its context resets between sessions, and the predictable failure is slow drift — a slightly different padding here, an off-scale font size there — which is exactly the cluster pattern DET-VIS exists to catch (DET-VIS-001/004/012/043 are drift detectors). The agent also cannot trust its own "looks consistent" judgment: the DET-VIS calibration section records that human detection of AI-generated sites is barely better than chance, so self-review by eye is a near-chance instrument. Mitigations, in order of load carried: (1) automated gates do the remembering — the token-literal lint, the contrast script, the computed-style type audit, and the overflow assertion (§3.3, §3.7, §3.8) run at every milestone, not at the end; (2) the system is externalized in project files — DESIGN_TOKENS.md and the design-system changelog are re-read at the start of every frontend work session, before any page is touched; (3) Storybook stories are the visual memory: a component changed in week six is diffed against its week-one screenshots by visual regression, not by recollection; (4) a scheduled DET-VIS pass (desktop + mobile screenshots, parameters walked in ID order, cluster rule applied) is a playbook step after every major section, so drift is caught while it is still one component wide. Residual risk stays real: gates catch values, not taste — composition monotony (DET-VIS-002/008/010) is only caught by the screenshot review, which is why that review is a gate and not a suggestion.

**R2 — WCPM inheritance is not yet verified into D3 rules.** A large share of DET-VIS parameters (002, 005, 006, 008, 010, 013, 015, 017–019, 024, 026, 028, 030, 033, 035, 039, 044) cite "WCPM inheritance (Phase 2 verification pending)," and the calibration section of PARAMETERS.md already showed one WCPM number (55.5% human detection accuracy) to be untraceable as stated. Until the integration agent's mapping and verification land, §3 rules that rest mainly on those parameters — notably design-system composition rules (§3.2 rule 4) and typography hierarchy floors (§3.8 rule 2) — should be treated as well-grounded practice, not as measured fact, and re-checked at integration.

**R3 — Browser support is uneven for the newest platform features.** CSS scroll-driven animations and container queries are still rolling out across engines; scroll-experiences (§3.6) must degrade to "content simply present" on unsupported browsers, which is safe only because the no-JS/no-timeline visibility rule is absolute. WebGPU is displacing WebGL as the forward API while WebGL remains the compatible target — webgl-3d (§3.16) guidance will age faster than any other skill in this department and should be first in the re-verification queue.

**R4 — The performance budget binds hardest exactly where AI generation is most generous.** Generated pages default to heavy hero media, multiple font families, and animation libraries; the CWV budget (LCP ≤ 2.5s at the 75th percentile on real devices) is usually lost on a mid-range Android phone, not on the development machine. The risk is process-shaped: if the budget is only measured at the end, the fixes are redesigns. Lighthouse CI assertions must therefore be wired from the first deployable page (D6 dependency), not added as a Phase 6 activity.

**R5 — Asset provenance and licensing.** Fonts, icon sets, and stock imagery carry licenses that generated output routinely ignores (DET-VIS-034's invented logo clouds are the visible symptom). D3's rules require real, licensed assets, but verifying provenance is a D14/legal dependency this department cannot close alone; until then, every asset's source and license must be recorded in the project files at the moment it is added, not reconstructed later.
