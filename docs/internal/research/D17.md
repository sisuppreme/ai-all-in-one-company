# D17 — AI Features & Applied ML: Phase 2 Research

Input to Phase 3 skill drafting for the 10 D17 skills. Method and failure-mode citations draw on PROJECT_ANATOMY.md Part 8; external claims are sourced inline and were verified against the cited pages on 2026-11-21. No prices are quoted: provider pricing changes faster than this file's review cycle, so cost rules are expressed as budgets and metering duties, not numbers.

## 1. Department standard

Professional applied-AI practice today treats the model as a bounded, nondeterministic dependency behind application-owned contracts — never as a component features call directly.

- **One integration layer.** All model calls go through a single server-side client module that owns provider selection, API keys, timeouts, capped retries with backoff, streaming, and error mapping. Provider differences are absorbed behind an internal interface (request in, structured result or typed error out) so a provider or model swap touches one module, not every feature.
- **Structured outputs by default.** Wherever output feeds code or UI structure, the call carries a JSON Schema and the response is validated before use. OpenAI's Structured Outputs constrains non-refusal output to the supplied schema (`strict: true`), while the application still handles refusals, incomplete responses, and business rules the schema cannot express. Free-text parsing of model output is a defect, not a technique.
- **Prompts are source code.** Prompts live in version control or a prompt registry, are reviewed like code, and are regression-tested before release. Anthropic's prompting best practices — be clear and direct, be specific about output format and constraints, give instructions as sequential steps, use relevant and diverse examples — are the authoring baseline.
- **Evals are the unit tests.** Every AI feature has a golden dataset (fixed inputs, reference answers or rubrics, edge cases) and an automated runner whose scores gate prompt, model, and retrieval changes. Graders are chosen cheapest-first: deterministic string/schema checks, then similarity, then a pinned model judge calibrated against human labels.
- **Guardrails per OWASP LLM Top 10 (2025).** The department designs against the current list: LLM01 Prompt Injection, LLM02 Sensitive Information Disclosure, LLM03 Supply Chain, LLM04 Data and Model Poisoning, LLM05 Improper Output Handling, LLM06 Excessive Agency, LLM07 System Prompt Leakage, LLM08 Vector and Embedding Weaknesses, LLM09 Misinformation, LLM10 Unbounded Consumption. Retrieved content is untrusted data, never instructions; state-changing tools are gated by deterministic server-side policy, not model judgment.
- **Metering and budgets from day one.** Every call is traced with prompt/model version, tokens in/out, latency, cost, and retrieval sources. Per-feature and per-user budgets, cheaper-model routing for simple tasks, and a tested non-AI fallback are part of the design, not later optimizations.

## 2. Failure modes this department prevents

Drawn from the slop lines of PROJECT_ANATOMY.md Part 8 (element names cited):

- **LLM integration:** "A chatbot widget pasted from a tutorial, API key exposed in client code, no timeout, no schema validation, and `JSON.parse` on raw model text." Ad hoc calls also break silently when a model is deprecated.
- **Prompt engineering:** "One vague paragraph — 'you are a helpful assistant, answer nicely' — hard-coded in three places, no examples, no version, and prompt fixes shipped without any test."
- **AI safety and guardrails:** "No moderation on input or output, retrieved web text concatenated directly into the system prompt, and a model allowed to call payment or deletion tools unchecked."
- **RAG and retrieval:** "Whole PDFs dumped into the prompt, no chunking or permission filter, no citations, and no check that retrieved text actually supports the answer."
- **Embeddings and semantic search:** "A new embedding model swapped in without re-indexing, vectors compared across incompatible models, or semantic search shipped with no keyword fallback for exact names and codes."
- **Recommendations:** "'Recommended for you' that is identical for every visitor, recommends out-of-stock or already purchased items, and logs no events to learn from."
- **Search relevance:** "Boosting whatever a manager searched for, no labeled test queries, sorting by date and calling it relevance, or an LLM reranker with no latency or quality budget."
- **AI evaluation:** "No dataset, a judge trusted without checking its agreement with human labels, or an eval run once at launch and never again."
- **AI observability and cost control:** "No usage logging, one shared API key for every feature, retries with no cap, and the largest model used for trivial classification tasks." The first symptom of failure is the provider invoice.

## 3. Per-skill research notes

### llm-integration

- **Core method:** Build one server-side client module per application: it assembles system prompt + history + tools, sends with an explicit timeout and idempotency key where the provider supports it, enforces a JSON Schema on the reply, validates, and maps every failure (rate limit, refusal, malformed output, timeout) to a typed application error. Retries are capped with exponential backoff; on exhausted retries the feature degrades to a smaller/cheaper model or a non-AI path. Model IDs and parameters live in config, never scattered literals.
- **Key rules:**
  1. API keys exist only in server-side secrets; any key found in client code or a shipped bundle is a release blocker.
  2. No feature code calls a provider SDK directly — the wrapper is the only caller.
  3. Every call sets a timeout and a maximum token budget; unbounded calls are forbidden.
  4. Structured output (schema + validation) is mandatory wherever output is consumed programmatically.
  5. Refusals and incomplete responses are handled states, not exceptions discovered in production.
- **Verification gates:** Integration test suite with the provider mocked for malformed JSON, a 429, a timeout, and a refusal — the fallback path must execute in each case (automatable in CI). Static check that no provider SDK import exists outside the wrapper module.
- **Sources:** OpenAI, Structured model outputs — https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses ; PROJECT_ANATOMY.md Part 8, "LLM integration".

### prompt-engineering

- **Core method:** Prompts are authored as files in a versioned prompts directory (or registry) with a fixed anatomy: role/task statement, context, sequential instructions, few-shot examples covering normal and edge cases, explicit output format, and explicit constraints. Every change is a reviewed diff, and the change is not releasable until the feature's eval suite passes against the new wording. The "colleague test" applies: a person with minimal context should be able to follow the prompt.
- **Key rules:**
  1. One canonical copy of each prompt; duplication across codebases or dashboards is a defect.
  2. Instructions are clear, direct, and sequential; output format and constraints are stated, not implied (Anthropic guidance).
  3. Examples are relevant, diverse, and include at least one edge case and one refusal/abstention case where applicable.
  4. No prompt change ships without an eval run recorded against it (links to ai-evaluation).
  5. Secrets, credentials, and sensitive business data never appear in a prompt (OWASP LLM07: system prompt leakage is assumed possible).
- **Verification gates:** `git log` on prompt files shows reviewed history (process gate); prompt-regression eval passes the feature's recorded floor before merge (automatable).
- **Sources:** Anthropic, Prompting best practices — https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/be-clear-and-direct ; PROJECT_ANATOMY.md Part 8, "Prompt engineering".

### ai-safety

- **Core method:** Defense in depth around the model, mapped to the OWASP LLM Top 10 (2025). Inputs are screened (moderation/topical checks) before or in parallel with the main call. All retrieved or third-party content is delimited and labeled as untrusted data. Outputs are validated and filtered before display or downstream use (LLM05). Tools are allowlisted with least-privilege scopes; state-changing or irreversible actions require deterministic server-side policy checks and, where the product warrants it, human confirmation — never model judgment alone (LLM06). Design assumes the system prompt can leak (LLM07), so it contains no secrets.
- **Key rules:**
  1. Retrieved content is data, never instructions; instruction-like text inside documents or web pages is ignored by construction (delimiters + explicit instruction hierarchy), not by hope.
  2. Tool access is an allowlist with per-tool argument validation in application code.
  3. Input and output guardrails both exist; either one alone is insufficient.
  4. Blocked input produces a safe, honest fallback response — never a silent empty result.
  5. Guardrail accuracy/latency/cost trade-offs are measured (OpenAI guardrails cookbook), not assumed.
- **Verification gates:** A versioned red-team set of direct and indirect injection payloads (in user messages, documents, and web content) runs in CI; the release gate is that no payload in the critical set executes an instruction, leaks the system prompt, or triggers an unauthorized tool call. Tool-call audit: every state-changing call in test traces passes through the policy check.
- **Sources:** OWASP Top 10 for LLM Applications (2025), as listed at https://www.promptfoo.dev/docs/red-team/owasp-llm-top-10/ ; OpenAI, How to implement LLM guardrails — https://developers.openai.com/cookbook/examples/how_to_use_guardrails ; PROJECT_ANATOMY.md Part 8, "AI safety and guardrails".

### rag-retrieval

- **Core method:** An indexing pipeline chunks documents (chunk size chosen by eval, not default), embeds them, and stores vectors with metadata including source ID and access-control attributes. At query time: embed the question, retrieve top candidates, optionally rerank, filter by the requesting user's permissions before anything reaches the prompt, and insert surviving chunks as cited context with an instruction to answer only from that context or abstain. Answers carry citations to chunk/source IDs so a wrong answer can be traced to corpus or generation.
- **Key rules:**
  1. Permission filtering happens at retrieval, before prompt assembly — never by asking the model to ignore unauthorized content.
  2. Every generated claim in a grounded answer must be attributable to a retrieved chunk; the prompt requires citation or abstention.
  3. The corpus is correctable: fixing a source document and re-indexing fixes the answer, and re-indexing is a documented, repeatable operation.
  4. Retrieved text is passed as untrusted data (see ai-safety) — a poisoned document must not become an instruction channel (OWASP LLM04/LLM08).
  5. Chunking, top-K, and reranking choices are recorded and changed only against retrieval evals.
- **Verification gates:** Golden question set with two halves — answerable questions whose answers exist in exactly one indexed document (correctness + citation check) and unanswerable questions (abstention required); traces must show retrieved chunk IDs and the permission filter applied (automatable).
- **Sources:** OpenAI, Fine-tuning for retrieval augmented generation (RAG) with Qdrant — https://developers.openai.com/cookbook/examples/fine-tuned_qa/ft_retrieval_augmented_generation_qdrant ; Google Cloud, Improve search and RAG quality with ranking API — https://docs.cloud.google.com/generative-ai-app-builder/docs/ranking ; PROJECT_ANATOMY.md Part 8, "RAG and retrieval".

### embeddings-search

- **Core method:** One embedding model, recorded by name and dimension, encodes the whole corpus offline and queries at runtime; an ANN index returns candidates by cosine or dot-product similarity. Retrieval is hybrid by default: vector results are combined with keyword matching so exact names, SKUs, and codes survive. Model or dimension changes trigger a full re-index and a recall re-measurement before rollout.
- **Key rules:**
  1. Vectors from different models or dimensions are never mixed or compared in one index.
  2. Index metadata records embedding model + dimension; a mismatch with config fails the build/deploy check.
  3. A keyword fallback always exists for exact-match queries.
  4. Embedding model selection is an eval decision (recall on a fixed query set), not a default.
  5. Embedding stores inherit the corpus's access controls (OWASP LLM08).
- **Verification gates:** Fixed query set with known relevant items; recall@K is measured before and after any model/index change and must not regress below the recorded baseline (automatable).
- **Sources:** OpenAI, Vector embeddings — https://developers.openai.com/api/docs/guides/embeddings ; PROJECT_ANATOMY.md Part 8, "Embeddings and semantic search".

### recommendations

- **Core method:** Events first: views, clicks, purchases are logged in a defined schema from launch, because a recommender without events cannot learn. Candidate generation (behavior-based, content-similarity via embeddings, or a managed service) is followed by a hard filter — purchased, unavailable, ineligible items never pass — then ranking, then serving with a documented popularity/quality fallback for cold-start users. Managed offerings follow the same shape: Google Cloud's Vertex AI Search for commerce returns ranked product IDs only after products are uploaded, user events recorded, and a model and serving config are active.
- **Key rules:**
  1. Exclusion filtering (owned, out-of-stock, ineligible) is deterministic code after ranking candidates, not a model responsibility.
  2. Every user segment has a defined fallback; an empty recommendation slot is a bug.
  3. Recommendations are logged with the model/config version so quality can be attributed and rolled back.
  4. "Recommended" surfaces must actually personalize: identical output for different histories fails review.
  5. Business boosts are explicit configuration, visible in the serving config — not hidden hard-coded promotions.
- **Verification gates:** Two test users with different histories must receive different lists; excluded and out-of-stock items must never appear in any response; a cold-start user must receive the documented fallback (automatable API tests).
- **Sources:** Google Cloud, Get recommendations (Vertex AI Search for commerce) — https://cloud.google.com/retail/docs/predict ; PROJECT_ANATOMY.md Part 8, "Recommendations".

### search-relevance

- **Core method:** Two stages: retrieval gathers candidates (lexical + semantic), a ranking stage scores them from weighted signals — semantic relevance, keyword similarity, freshness, popularity, document fields, explicit business rules. Tuning is driven by a versioned judgment set: queries with graded relevance labels, scored offline with NDCG@K. Online click/conversion data and zero-result/reformulation reports validate changes before full rollout. Google Cloud documents the same pattern for Vertex AI Search custom ranking: a weighted expression over relevance signals, tuned systematically rather than anecdotally.
- **Key rules:**
  1. No ranking change ships without an offline NDCG comparison against the previous release on the judgment set.
  2. The judgment set is versioned and grows from real query logs, especially zero-result and reformulated queries.
  3. Anecdote-driven boosts ("a manager searched X") are forbidden; a fix must help the query class, not one query.
  4. Any LLM reranker carries an explicit latency and cost budget and a timeout fallback to the non-LLM ranking.
  5. Zero-result rate is a monitored metric with an owner.
- **Verification gates:** Offline eval script reports NDCG@10 for candidate vs. current ranking; a regression blocks release (automatable). Search analytics review confirms zero-result queries are triaged into the judgment set.
- **Sources:** Google Cloud, Customize search results ranking — https://cloud.google.com/generative-ai-app-builder/docs/custom-ranking ; PROJECT_ANATOMY.md Part 8, "Search relevance".

### ai-evaluation

- **Core method:** Each AI feature owns a golden dataset: realistic inputs (seeded from production logs and failure modes, not invented happy paths), reference answers or explicit rubrics, and edge/adversarial cases, stored as a single versioned artifact. A runner executes the current prompt + model + retrieval stack; graders are stacked cheapest-first — deterministic checks (exact match, schema, forbidden strings), similarity, then a pinned model judge for semantic criteria. Reports give overall pass rate and per-category breakdowns, are stored with each change, and failed production cases are added back into the dataset.
- **Key rules:**
  1. A feature without a golden dataset does not ship; an eval run once at launch and never again is treated as no eval.
  2. Model judges are calibrated against human-labeled items before being trusted, and re-calibrated when the judge model changes; judge model and temperature are pinned.
  3. Dataset changes are versioned and reviewed like code — silently editing the test to pass is the cardinal sin.
  4. Train/tuning examples and eval items are kept separate to avoid measuring memorization.
  5. Every prompt, model, or retrieval change records its eval delta in the change itself.
- **Verification gates:** Eval suite runs in CI on prompt/model/retrieval changes; release requires overall pass rate at or above the feature's recorded floor and no category regression beyond the feature's set tolerance (automatable). Judge-vs-human agreement is re-measured on a labeled sample at each judge change.
- **Sources:** OpenAI, Getting started with evaluations/datasets — https://developers.openai.com/api/docs/guides/evaluation-getting-started ; Building golden datasets for LLM evals — https://www.n4n.ai/blog/golden-datasets-for-llm-evals-how-to-build-one ; PROJECT_ANATOMY.md Part 8, "AI evaluation".

### ai-observability

- **Core method:** Every model interaction emits one trace with child spans for retrieval, guardrails, tool calls, and generation, carrying: feature name, prompt version, model ID, tokens in/out, latency, computed cost, retrieved chunk IDs, guardrail verdicts, and the final outcome. Traces are sampled at a rate that keeps failure cases at 100% capture. Dashboards aggregate by feature, model, and prompt version; alerts fire on error-rate spikes, latency regressions, and quality-signal drops (eval-score drift on sampled production traffic, user feedback rate). A bad production answer must be reproducible from its trace alone.
- **Key rules:**
  1. No trace, no ship: a feature that cannot show prompt version + tokens + cost + retrieval sources for a request is not observable and does not launch.
  2. Prompts and outputs are logged under the product's privacy rules — secrets and PII are redacted before logging, and log retention is defined.
  3. Feedback signals (thumbs, corrections, escalations) are captured on the trace so failures can be mined into the golden dataset.
  4. One tracing schema across providers; provider-specific fields are normalized at the wrapper (see llm-integration).
  5. Cost and usage are broken down per feature and per model — LangSmith-style automatic token/cost recording per trace and per project is the reference behavior, whether built or bought.
- **Verification gates:** Fire a test request and confirm the trace contains prompt version, token counts, cost, and retrieval spans (automatable assertion on the tracing backend). Redaction test: a request containing a known secret string must not store that string in any log.
- **Sources:** LangChain, LangSmith cost tracking — https://docs.langchain.com/langsmith/cost-tracking ; PROJECT_ANATOMY.md Part 8, "AI observability and cost control".

### ai-cost-control

- **Core method:** Cost is engineered, not monitored after the fact. Each feature gets a token budget per request, per user, and per period, enforced in the wrapper: request size caps, capped retries, and routing rules that send simple tasks (classification, extraction, short rewrites) to smaller/cheaper models and reserve large models for tasks whose evals justify them. Usage is metered per feature from the observability stream; alerts fire at budget thresholds; when a cap is hit, the feature degrades — cheaper model, reduced context, or the non-AI fallback — rather than failing open. This is also the mitigation for OWASP LLM10 (unbounded consumption), including abuse-driven cost attacks.
- **Key rules:**
  1. Every feature has a named budget and an owner; "the provider invoice" is never the first signal.
  2. Retries and agent loops have hard iteration and spend caps; an uncapped loop is a release blocker.
  3. Model choice per task is justified by eval scores at that tier, not by defaulting to the largest model.
  4. Per-user quotas and rate limits exist on every paid-model endpoint, authenticated or not.
  5. When budgets are exhausted, degradation is graceful and honest (fallback or clear unavailability), never silent quality collapse.
- **Verification gates:** Budget test in staging: set a low test cap, drive traffic past it, and confirm the alert fires and the fallback engages (automatable). Load/abuse test: repeated maximal requests from one identity are throttled at the quota.
- **Sources:** OWASP LLM10:2025 Unbounded Consumption, as listed at https://www.promptfoo.dev/docs/red-team/owasp-llm-top-10/ ; LangChain, LangSmith cost tracking — https://docs.langchain.com/langsmith/cost-tracking ; PROJECT_ANATOMY.md Part 8, "AI observability and cost control".

## 4. Open risks for Phase 3

- **Provider and model churn is the normal case, not an exception.** Models are deprecated, renamed, and repriced; even tooling dies — OpenAI's own docs now carry a deprecation notice for its Evals platform (read-only 2026-10-31, shutdown 2026-11-30, per the evaluation getting-started guide cited above). Phase 3 skills must therefore never hard-code a model name, endpoint shape, or vendor feature as the method: skills state the contract (schema-validated output, golden dataset, budget) and name provider features only as dated examples.
- **Provider-neutrality pattern for all 10 skills:** every skill is written against the wrapper interface (llm-integration), the versioned-prompt discipline, and the eval gate. Provider-specific notes belong in a clearly marked, dated annex per skill so a swap means rewriting an annex, not the skill.
- **Judge and grader drift:** model judges change behavior when providers update them; skills must require pinned judge models and periodic re-calibration against human labels (see ai-evaluation), or eval scores become incomparable across time.
- **OWASP list revision:** the LLM Top 10 is revised on a roughly annual cycle and a separate Agentic AI list now exists; ai-safety should cite the list by year and include a re-check step rather than embedding the ten items as permanent truth.
- **RAG corpus risk:** retrieval quality depends on corpus hygiene and permission metadata owned by other departments (D5 data, D14 legal); Phase 3 must state these as explicit dependencies, or rag-retrieval will be drafted as if the corpus were trustworthy by default — OWASP LLM04/LLM08 say it is not.
- **Cost data volatility:** because no prices are recorded in this file, ai-cost-control must be drafted around metering, budgets, and routing rules that survive repricing; any Phase 3 example that needs a number must pull it from the provider's live pricing page at drafting time and date it.
