# D11 Research — Integrations & Payments (Phase 2)

Purpose: the research base for drafting the 12 D11 skills in Phase 3. Every claim below traces to PROJECT_ANATOMY.md (Part 11 depth elements: Webhooks, Transactional email and SMS, Payments and billing, Third-party integrations; Part 9 trial/churn elements), a DET parameter file, or a source verified by web search on 2026-11-21. Provider-specific behavior is dated or kept provider-neutral. Audience: Phase 3 skill drafters for D11.

## 1. Department standard

Professional integrations-and-payments practice today, as D11 will teach it:

- **The provider is the source of truth for money state; your database is a mirror.** Charges, subscription status, invoice state, refunds, and disputes live at the payment provider first. Local rows are projections built from API reads and webhook events, and a scheduled reconciliation job diffs the mirror against the provider and repairs drift — because webhooks get missed, endpoints go down, and dashboards get clicked. Sources: PROJECT_ANATOMY.md, "Payments and billing"; Stripe, "Receive Stripe events in your webhook endpoint", https://docs.stripe.com/webhooks
- **Webhook discipline is non-negotiable and identical everywhere.** Verify the signature (HMAC over the *raw* request body, constant-time compare, timestamp tolerance against replay — Stripe's libraries default to five minutes), persist the event keyed on its provider event ID, return 2xx immediately, and process asynchronously from a queue. Delivery is at-least-once and unordered, so handlers deduplicate by event ID and *converge* state ("set status to X") instead of incrementing it. A signed event is necessary but not sufficient: before fulfilling, reconcile the event against the expected order — account, amount, currency, and state. Sources: Stripe webhook documentation (URL above); PROJECT_ANATOMY.md, "Webhooks".
- **Every money-moving request carries an idempotency key.** Checkout creation, charges, refunds, and subscription changes are created server-side with an idempotency key derived from the business operation (cart/order ID), so a retried request, a double-click, or a double submit produces exactly one charge. Card data goes directly to the provider (hosted checkout or provider JS elements), keeping your servers out of PCI scope — the SAQ A posture. Sources: Stripe, "Idempotent requests", https://docs.stripe.com/api/idempotent_requests ; PROJECT_ANATOMY.md, "Payments and billing".
- **Subscription state is driven by the invoice lifecycle, never by local timers.** Access follows paid invoices; renewal failure moves the subscription into a dunning sequence (provider retries plus customer notification plus a payment-update path) before access is cut; cancellation, pause, and trial-end behavior are configured explicitly per state — including what happens with no payment method on file — rather than inherited from provider defaults. Sources: Stripe, "Subscription invoices", https://docs.stripe.com/billing/invoices/subscription ; Stripe, "Use free trial periods on subscriptions", https://docs.stripe.com/billing/subscriptions/trials/free-trials ; PROJECT_ANATOMY.md, Part 9 trial-conversion element.
- **Dunning is a designed funnel, not an afterthought.** Retry timing uses the provider's smart retry machinery where available (Stripe Smart Retries: ML-chosen retry times; Stripe's documented default for new accounts, checked 2026-11-21, is up to 8 retries within 2 weeks, configurable), failed-payment emails fire on the first failure with a hosted payment-update link, and the end of the sequence has one defined outcome — cancel, mark unpaid, or pause — chosen per product, with involuntary-churn recovery measured separately from voluntary churn. Sources: Stripe, "Automate payment retries", https://docs.stripe.com/billing/revenue-recovery/smart-retries ; Stripe, "Automatic collection", https://docs.stripe.com/invoicing/automatic-collection ; PROJECT_ANATOMY.md, Part 9 churn-prevention element.
- **Disputes are deadline work with a one-shot submission.** A dispute immediately debits the amount plus a fee; the response window is short and network-set (Stripe documents typically 7–21 days, checked 2026-11-21), evidence can be submitted only once with no edits afterward, and the issuer then decides over weeks. Prevention (recognizable statement descriptors, receipts, renewal reminders, easy cancellation and refunds) beats response, because networks count disputes received, not disputes won. Sources: Stripe dispute documentation as summarized in search results, 2026-11-21; PROJECT_ANATOMY.md, "Payments and billing".
- **OAuth is built to RFC 9700, profiled by the OAuth 2.1 draft.** Authorization code flow with PKCE (S256 only — `plain` is forbidden) for every client including server-side ones, exact-string redirect URI matching, no implicit or resource-owner-password grants, no bearer <redacted> in query strings, and refresh tokens for public clients either rotated with reuse detection or sender-constrained. Identity comes from OpenID Connect: validate the ID token's signature against the issuer's JWKS, and check `iss`, `aud`, `exp`, and `nonce`. Status note (verified 2026-11-21): RFC 9700 (OAuth 2.0 Security Best Current Practice, BCP 240) was published January 2025 and is the implementable floor; OAuth 2.1 is still an IETF Internet-Draft (draft-ietf-oauth-v2-1), not an RFC — teach its profile, never cite it as a finished standard. Sources: RFC 9700; RFC 7636 (PKCE); draft-ietf-oauth-v2-1 (work in progress).
- **Email that must arrive is authenticated and measured.** Sending domains publish SPF (RFC 7208) and sign DKIM (RFC 6376), with a DMARC record (RFC 7489) whose policy domain aligns with the visible From: domain; delivery, bounce, and complaint outcomes return via provider events and are stored against each message. Since February 2024, Google and Yahoo enforce SPF + DKIM + DMARC (at least `p=none`, aligned) for bulk senders (~5,000 messages/day to personal accounts), with one-click unsubscribe (RFC 8058) on marketing mail and a spam-rate ceiling of 0.3%; Microsoft applies the same set to Outlook.com senders since May 5, 2025 (all verified 2026-11-21). Transactional and marketing streams use separate subdomains so a marketing reputation problem cannot take password resets down with it. Sources: Amazon SES, "Complying with DMARC authentication protocol in Amazon SES", https://docs.aws.amazon.com/ses/latest/dg/send-email-authentication-dmarc.html ; Google email sender guidelines as summarized in search results, 2026-11-21; PROJECT_ANATOMY.md, "Transactional email and SMS".
- **SMS is a registered, consent-based channel, not an API call.** In the US, application-to-person messaging over 10-digit long codes requires brand and campaign registration through The Campaign Registry (via the provider, e.g. Twilio); unregistered traffic is blocked or filtered (Twilio surfaces this as error 30034). Every send traces to a recorded opt-in, opt-out keywords (STOP) are honored automatically, delivery is tracked through provider status callbacks to a terminal state, and throughput/segmentation limits follow the registered campaign type. Rules differ by country — the skill teaches the registration-and-consent pattern, with US specifics dated. Sources: Twilio A2P 10DLC documentation as summarized in search results, 2026-11-21; Twilio, "Track the Message Status of Outbound Messages", https://www.twilio.com/docs/messaging/guides/track-outbound-message-status
- **Every third-party call is wrapped, timed, and degradable.** Each integration sits behind an internal adapter that owns the provider's API shape; calls carry explicit timeouts, retry transient failures with exponential backoff and jitter, validate response shapes before use, and trip a circuit breaker during provider outages so the product degrades instead of hanging. Credentials are per-environment, held in secret storage, and never shipped to the client bundle. Sources: Microsoft Learn, Azure Architecture Center, "Circuit Breaker Pattern", https://learn.microsoft.com/en-gb/azure/architecture/patterns/circuit-breaker ; PROJECT_ANATOMY.md, "Third-party integrations".

## 3. Per-skill research notes

### payments
- **Core method:** Delegate the charge to the provider and mirror the state. Build the checkout server-side: create the order in `pending` state, create the provider checkout session/PaymentIntent with amount and currency computed from server-side catalog data and an idempotency key derived from the order ID, and hand the browser to the provider-hosted page or provider JS elements so card data never touches your server. Grant access only from the verified webhook (or a server-side API re-read of the payment object), never from the success redirect. Record refunds against the original payment, and run a scheduled reconciliation diff between local payment rows and the provider's list.
- **Key rules:**
  1. Amounts, currency, and line items are computed server-side from the catalog; a client-supplied amount is a defect, not a convenience (anatomy slop).
  2. Every create/charge/refund call carries an idempotency key tied to the business operation; a retry with the same key must return the original result (DET-FAKE-006 double-charge variant).
  3. The success page is a display state only — entitlement changes happen in the webhook handler or a verified server-side fetch, so a user who closes the tab still gets what they paid for.
  4. Card data never transits or rests on your infrastructure: hosted checkout or provider elements only (SAQ A posture); no PAN in logs, metadata, or error reports.
  5. Test mode end-to-end before live: test card purchase grants access, double-submit produces one charge, webhook replay produces one grant (anatomy "Verify").
- **Verification gates:** Double-submit test — fire the checkout creation twice with the same idempotency key and assert exactly one charge exists at the provider (automatable); reconciliation diff — script compares local payments table against provider API export and exits non-zero on any unmatched row (automatable); test-mode purchase script asserting entitlement flips only after the webhook is processed (automatable).
- **Sources:** Stripe, "Idempotent requests", https://docs.stripe.com/api/idempotent_requests ; PROJECT_ANATOMY.md, "Payments and billing".

### subscriptions
- **Core method:** Model the lifecycle as the provider's state machine, mirrored locally: trialing → active → past_due → canceled/unpaid, with every transition driven by invoice and subscription webhook events, not local clocks. Define, per plan, the behavior the provider leaves configurable: trial length and whether a payment method is required upfront, the missing-payment-method outcome at trial end (invoice, pause, or cancel), proration behavior on plan change, and the cancellation path (cancel at period end vs immediately, plus what the customer keeps). Entitlement checks read the mirrored state, and a periodic sync re-reads active subscriptions from the provider to catch missed events.
- **Key rules:**
  1. No local timer ever grants, extends, or revokes access — only provider lifecycle events and verified API reads do.
  2. Trial-end behavior is configured explicitly for both card and no-card cases; inheriting provider defaults is a finding (anatomy Part 9 trial-conversion).
  3. Cancellation is a real state change at the provider plus a confirmation to the user; a UI-only cancel is DET-FAKE territory.
  4. Plan changes state their proration and effective-date behavior in the UI before the user confirms.
  5. Every subscription row carries the provider subscription ID and current period end; entitlement logic never infers state from payment history alone.
- **Verification gates:** Lifecycle walk in test mode with test clocks — create trial, advance time, assert trial-will-end event, renewal charge, past_due on failed card, and recovery on card update each produce the configured local state (automatable with provider test clocks); missed-webhook drill — disable the endpoint for one renewal cycle, re-enable, and assert the periodic sync repairs the mirror (automatable).
- **Sources:** Stripe, "Subscription invoices", https://docs.stripe.com/billing/invoices/subscription ; Stripe, "Use free trial periods on subscriptions", https://docs.stripe.com/billing/subscriptions/trials/free-trials

### refunds-disputes
- **Core method:** Treat refunds as a product flow and disputes as deadline casework. Refunds: expose an explicit refund action (admin or self-serve per policy) that calls the provider against the original payment with an idempotency key, records reason and amount, reverses entitlement per a written rule (immediate vs end of paid period), and confirms to the customer by email. Disputes: on the dispute-created webhook, alert a named owner the same day, assemble the evidence pack matched to the dispute reason (receipt, delivery/access logs, terms acceptance, communication record) well inside the response window, submit once — submission is final — and track the outcome to closure. Prevention runs in parallel: recognizable statement descriptor, receipts on every charge, renewal reminders, and an easier refund path than the bank.
- **Key rules:**
  1. A refund is not done until the provider confirms it and the local payment row, entitlement, and customer notification all reflect it.
  2. Partial refunds state what happens to access and remaining balance before execution, not after a complaint.
  3. The dispute deadline from the provider dashboard is the working deadline; internal assembly targets days earlier because the evidence submission cannot be edited or supplemented (Stripe behavior, checked 2026-11-21).
  4. Never refund to a different destination than the original payment method through the payments flow — exceptions are a manual, logged, out-of-band decision.
  5. Dispute and refund rates are reported metrics with alert thresholds, not surprises discovered in the provider dashboard.
- **Verification gates:** Refund test — issue full and partial refunds in test mode and assert provider state, local mirror, entitlement, and notification email all agree (automatable); dispute drill — fire a test dispute event and assert the alert reaches the owner queue and an evidence checklist is created with the deadline attached (automatable).
- **Sources:** Stripe dispute documentation (response window and one-shot submission, checked 2026-11-21); PROJECT_ANATOMY.md, "Payments and billing".

### invoicing-tax
- **Core method:** Generate invoices from the billing system of record, not from templates in code: sequential, gapless invoice numbers per legal entity; line items copied from the charged amounts; customer legal name, address, and tax ID collected at checkout where the regime requires it; the invoice PDF/receipt is the provider's or a render of the same stored data. Tax is handled by configuration and provider tooling — a tax engine or the payment provider's tax product (e.g. Stripe Tax) computes and records the tax on each transaction from the customer's location and the product's tax category. The skill teaches implementation patterns — data to collect, fields to store, where the engine plugs in, how to render compliant documents — and stops there.
- **Key rules:**
  1. **This skill never gives jurisdiction tax advice and never hardcodes a tax rate, threshold, or registration rule from memory.** Rates and rules come from the configured tax engine or a qualified accountant; anything jurisdiction-specific in a project document is dated and sourced or removed.
  2. Invoice numbers are issued once, in sequence, by one authority; voided invoices are retained and marked, never deleted or renumbered.
  3. The amount on the invoice equals the amount charged at the provider to the minor unit — a render-time recomputation that can drift is a defect.
  4. Credit notes, not edited invoices, correct an issued invoice.
  5. Tax fields (customer tax ID, place-of-supply evidence, tax category per product) are captured at purchase time; reconstructing them later from support tickets is the failure mode.
- **Verification gates:** Invoice-integrity check — script asserts invoice numbers are sequential with no gaps or duplicates and every invoice total equals its provider charge (automatable); render-diff test — regenerate an invoice from stored data and diff against the issued document (automatable).
- **Sources:** Stripe, "Subscription invoices", https://docs.stripe.com/billing/invoices/subscription ; PROJECT_ANATOMY.md, "Payments and billing".

### dunning
- **Core method:** Build failed-payment recovery as an explicit sequence with three layers. Layer 1, provider retries: enable the provider's smart retries or a custom schedule sized to the product's billing period (Stripe's documented new-account default — up to 8 retries within 2 weeks — is a starting configuration to review, not a law; checked 2026-11-21). Layer 2, customer contact: failed-payment email on first failure with a hosted, login-light payment-update link, reminders spaced across the retry window, and in-app banners while the subscription is past due. Layer 3, resolution: one configured end state — cancel, mark unpaid, or pause — plus the access rule during the grace window (full access, read-only, or none), stated in the product's terms. Measure recovery rate (recovered ÷ failed) as the skill's headline metric.
- **Key rules:**
  1. The first failure notifies the customer the same day; silent retrying burns the window in which a card update is most likely.
  2. Card-updater/network-token features at the provider are enabled where offered — many "failures" are reissued cards, not unwilling customers.
  3. Hard declines (stolen card, closed account) exit the retry sequence immediately into the contact layer; retrying them is cost without chance (Stripe documents that it does not retry hard declines).
  4. Access during past_due follows one written rule applied identically by entitlement checks everywhere — no per-page improvisation.
  5. Dunning copy states the amount, what happens next, and the deadline; it never threatens an action the sequence will not actually take.
- **Verification gates:** Decline-card walk — run a subscription renewal against a test decline card and assert the retry schedule, first-failure email, banner, and end-state transition all occur as configured (automatable in test mode with test clocks); recovery-report check — the recovery-rate report exists and reconciles against provider failed/recovered counts (automatable).
- **Sources:** Stripe, "Automate payment retries", https://docs.stripe.com/billing/revenue-recovery/smart-retries ; Stripe, "Automatic collection", https://docs.stripe.com/invoicing/automatic-collection

### webhooks
- **Core method:** One receiving pattern for every provider, inbound and outbound. Inbound: expose a raw-body endpoint per provider; verify the signature with the provider's library over the exact bytes received (reject on failure or stale timestamp); insert the event into an events table with a unique constraint on the provider event ID; return 2xx; process from a queue with handlers that converge state and tolerate duplicates and out-of-order arrival; log every delivery and processing outcome, with a replay path for events that arrived while you were down (provider event re-fetch or resend). Outbound (sending events to customers): sign payloads with a per-endpoint secret, retry failures with backoff over days, log attempts, expose delivery status, and let customers rotate secrets and replay events.
- **Key rules:**
  1. Verification runs on the raw body before any JSON parsing middleware touches the route; a parsed-and-reserialized body fails verification and is the most common self-inflicted outage.
  2. Acknowledge only after the event is durably stored; processing happens in the worker, never in the request (anatomy slop: heavy processing before responding).
  3. Deduplication is a database constraint on event ID, not an application-level check — concurrent duplicate deliveries must collide safely.
  4. Handlers are written as state convergence ("set to the event's state") so duplicates, retries, and reordering are no-ops rather than double effects (DET-FAKE-022).
  5. A forged request with a bad signature is rejected and logged; the endpoint is public by design and the signature is the only authentication.
- **Verification gates:** Forgery test — POST a correctly shaped event with an invalid signature and assert rejection with no state change (automatable); duplicate-delivery test — send the same real event twice via provider tooling and assert a single effect (automatable); replay test — disable processing, deliver events, re-enable, and assert the backlog converges the mirror (automatable).
- **Sources:** Stripe, "Receive Stripe events in your webhook endpoint", https://docs.stripe.com/webhooks ; PROJECT_ANATOMY.md, "Webhooks".

### transactional-email
- **Core method:** Send through a provider from an authenticated domain, as a background job, with outcomes recorded. Setup: dedicated sending subdomain, SPF and DKIM published and aligned, DMARC record progressing from `p=none` monitoring to enforcement, transactional and marketing on separate subdomains/streams. Runtime: the app enqueues a message with a template ID and data; the worker sends via the provider; provider delivery/bounce/complaint events return by webhook and are stored against the message row, so "did the reset email arrive" is a query, not a guess. Templates are versioned in the repo with plain-text parts; every transactional template names the action, the expiry where relevant, and the "wasn't you" path.
- **Key rules:**
  1. No transactional mail leaves an unauthenticated domain; SPF, DKIM, and DMARC alignment are verified in the message headers of a real test send before launch (anatomy "Verify").
  2. "Email sent" in the UI means accepted by the provider with a message ID stored — and delivery status is tracked to delivered/bounced, never assumed from API success (DET-FAKE-013).
  3. Bounces and complaints suppress future sends to that address automatically; re-mailing a hard-bounced address damages the domain for every user.
  4. Verification codes and reset links are single-use, expiring, and rate-limited at both send and confirm (handoff to D7 for the security depth).
  5. Bulk/marketing mail is a different stream with one-click unsubscribe (RFC 8058) and honors the Google/Yahoo/Microsoft sender requirements; transactional templates carry no marketing content that would reclassify them.
- **Verification gates:** Authentication check — script queries DNS for SPF/DKIM/DMARC and sends a test message asserting `Authentication-Results` shows all three passing and aligned (automatable); bounce drill — send to a provider bounce-simulator address and assert the message row records the bounce and the address is suppressed (automatable); end-to-end arrival test for signup and password-reset flows in staging (automatable).
- **Sources:** Amazon SES, "Complying with DMARC authentication protocol in Amazon SES", https://docs.aws.amazon.com/ses/latest/dg/send-email-authentication-dmarc.html ; RFC 7208, RFC 6376, RFC 7489, RFC 8058; PROJECT_ANATOMY.md, "Transactional email and SMS".

### sms
- **Core method:** Send through a messaging provider from a registered identity, with consent on file and status tracked per message. Setup (US pattern, dated 2026-11-21): register the brand and campaign with The Campaign Registry through the provider (A2P 10DLC for long codes; toll-free verification and short codes are separate regimes), attach numbers to the approved campaign, and configure status callbacks. Runtime: the app enqueues the message; the provider returns a message SID; status callbacks advance the message through queued → sent → delivered/undelivered/failed, stored against the send. Opt-in is captured with source and timestamp before the first send; STOP/HELP keywords are handled by the provider configuration and verified by test; quiet hours and per-country rules are configuration, not code comments.
- **Key rules:**
  1. No send without a recorded opt-in for that number and message category; a phone number collected for delivery updates is not consent for marketing.
  2. Unregistered US A2P traffic is blocked or filtered by carriers — registration status is a launch checklist item with evidence, not an assumption (Twilio error 30034 is the symptom).
  3. Delivery is a tracked terminal state per message, not the provider API's acceptance response (DET-FAKE-013, DET-FAKE-022).
  4. Opt-out is honored immediately and permanently for the category; the suppression list is checked inside the send path, not by the caller.
  5. Verification/OTP messages use short codes in the copy, expire fast, and are rate-limited per number to blunt toll fraud (handoff to D7).
- **Verification gates:** Status-callback test — send to a test number and assert the message row reaches a terminal delivered state via callback (automatable); opt-out drill — reply STOP from a test handset and assert suppression blocks a subsequent send attempt (automatable); registration-evidence check — campaign status read from the provider console/API is recorded in the launch checklist (manual evidence, scriptable where the provider exposes status).
- **Sources:** Twilio, "Track the Message Status of Outbound Messages", https://www.twilio.com/docs/messaging/guides/track-outbound-message-status ; Twilio A2P 10DLC registration documentation (checked 2026-11-21); PROJECT_ANATOMY.md, "Transactional email and SMS".

### oauth-sso
- **Core method:** Consume identity through OpenID Connect on top of OAuth 2.0 built to the RFC 9700 profile: authorization code flow with PKCE (S256) for every client type, exact-string redirect URI registration, `state` for CSRF and `nonce` for ID-token binding, ID-token validation against the issuer's published JWKS (signature, `iss`, `aud`, `exp`), and account linking keyed on the issuer + subject pair — never on email alone. Sessions are your own: the provider authenticates, your app issues and manages its session, and logout/revocation behavior (including enterprise SSO requirements like SAML for larger customers, via a specialist provider) is a stated design decision. The OAuth 2.1 draft's consolidated profile is the target shape; RFC 9700 is the normative floor while 2.1 remains a draft (status verified 2026-11-21).
- **Key rules:**
  1. Implicit flow and resource-owner-password flow are forbidden in new integrations; tokens never travel in query strings or fragments.
  2. An unverified or merely-present email from a provider never links or creates a privileged account — linking requires the verified issuer + `sub` identity or an authenticated user confirming while signed in.
  3. Redirect URIs are exact strings registered per environment; wildcard or pattern matching is a defect (RFC 9700).
  4. Refresh tokens for public clients are rotated with reuse detection or sender-constrained; a detected reuse revokes the token family.
  5. Provider outages degrade to your existing sessions — a login-provider outage must not log out or lock out users with live sessions.
- **Verification gates:** Flow test — scripted authorization-code + PKCE login against the provider's test tenant asserting token validation rejects a tampered ID token and a wrong-`aud` token (automatable); redirect test — attempt login with an unregistered redirect URI variant and assert provider rejection (automatable); linking test — two providers returning the same email produce one account only through the explicit linking path (automatable).
- **Sources:** RFC 9700 (OAuth 2.0 Security Best Current Practice); RFC 7636 (PKCE); draft-ietf-oauth-v2-1 (work in progress, checked 2026-11-21); PROJECT_ANATOMY.md, "Third-party integrations".

### third-party-apis
- **Core method:** Integrate behind an adapter per provider: one internal interface in your domain's terms, one module that speaks the provider's API, owns its auth, pagination, and error shapes, and translates failures into your error taxonomy. Every outbound call is configured with connect/read timeouts, retries only for idempotent operations or with idempotency keys, exponential backoff with jitter, and a circuit breaker per provider; responses are validated against a schema before use, and raw responses are logged (secrets redacted) for dispute-grade debugging. Each integration ships with a degradation statement — what the product does when this provider is down — and a sandbox/staging test against the provider's test environment.
- **Key rules:**
  1. No provider SDK types or response objects leak past the adapter into domain code; provider replacement must be a one-module change.
  2. An integration is not "done" when it works once in development — it is done when the dead-endpoint test passes: staging pointed at a dead URL degrades per the statement instead of hanging (anatomy "Verify").
  3. Retrying a non-idempotent provider call without an idempotency key is a defect of the same class as double-charging.
  4. Provider rate limits are respected by design (token bucket, queueing), and a 429 triggers backoff, not a retry storm.
  5. Contract drift is detected: response-schema validation failures alert, because providers change shapes without changing version numbers.
- **Verification gates:** Dead-endpoint drill in staging — assert the product stays within its latency budget and shows the designed degradation (automatable); schema-validation suite over recorded provider fixtures, including malformed-response cases (automatable); secret scan — repo and built frontend bundle grepped for provider keys in CI (automatable).
- **Sources:** Microsoft Learn, Azure Architecture Center, "Circuit Breaker Pattern", https://learn.microsoft.com/en-gb/azure/architecture/patterns/circuit-breaker ; PROJECT_ANATOMY.md, "Third-party integrations".

### api-keys-management
- **Core method:** Manage credentials as inventory with a lifecycle: issued (per environment, per purpose, least-privilege scope — restricted keys where the provider offers them, e.g. Stripe restricted keys), stored (secret manager or environment, never the repo, never the client bundle), used (server-side only; the browser gets scoped, short-lived tokens minted per session when a provider supports publishable/client-safe keys), rotated (on a schedule and immediately on suspicion, with overlap so rotation is not an outage), and revoked (departure, leak, or decommission — with git history treated as leaked forever). Maintain a key register: which keys exist, where they live, who/what uses them, when they were last rotated. Outbound keys for your own API customers follow the same pattern plus hashed storage and prefix identification.
- **Key rules:**
  1. A secret found in a commit, bundle, screenshot, or log is compromised: rotate first, investigate second; deleting the line does not unpublish history (anatomy Part 3, "Configuration and secrets").
  2. Test and live credentials are different keys in different stores; a test key in production config is a launch blocker.
  3. Webhook signing secrets are credentials too — per-endpoint, rotatable, and covered by the register.
  4. Client-visible keys are only the ones the provider designed to be public (publishable keys), and they are still domain/referrer-restricted where the provider allows.
  5. Every key has an owner and a rotation date in the register; an orphan key is revoked, not left running.
- **Verification gates:** Secret scanning in CI over the repo and built artifacts (gitleaks-class tooling) with a zero-findings gate (automatable); rotation drill — rotate one staging credential end-to-end using only the register's instructions and assert the integration stays green (automatable/manual evidence); register audit — script lists keys present in the secret store and diffs against the register (automatable).
- **Sources:** PROJECT_ANATOMY.md, "Third-party integrations" and Part 3 "Configuration and secrets"; Stripe restricted-keys documentation (provider pattern, checked 2026-11-21).

### sdk-embeddables
- **Core method:** Ship client-side pieces — provider payment elements, your own embeddable widgets, and SDK wrappers — as a versioned, minimal-surface integration layer. For payment capture, load the provider's JS (e.g. Stripe.js with Elements/Payment Element) so card data flows browser → provider directly; your page handles only tokens/IDs and renders state from server-confirmed outcomes. For your own embeddables: a small loader snippet that injects a sandboxed (iframe) widget, a documented postMessage or attribute-based configuration contract, semantic versioning with a changelog, and a supported-versions policy. Everything embeddable is tested in a hostile host page (conflicting CSS, CSP restrictions, slow network) before release.
- **Key rules:**
  1. The client SDK never holds a secret key and never decides an outcome: amounts, entitlements, and success are server-confirmed (DET-FAKE-007 is what an unchecked client-side card form becomes).
  2. Embeds are sandboxed — iframe isolation by default; a widget that requires the host to disable CSP or paste inline scripts is not shippable.
  3. The loader is versioned and immutable per version; "latest" URLs are for development only, never the documented production integration.
  4. Client-side validation is UX only (formatting, obvious errors); the server re-validates everything that matters.
  5. Third-party scripts load with subresource integrity or from the provider's own origin per the provider's instructions — never self-hosted copies of a provider's payment JS.
- **Verification gates:** Hostile-host test page — widget renders and functions under a strict CSP and a CSS-reset host (automatable with browser tests); version-pin check — documentation examples and the loader agree on the current version string (automatable); payment-element test — test-mode purchase through the embedded element completes with card data never appearing in your server's request logs (automatable log scan).
- **Sources:** Stripe.js / Payment Element documentation (provider pattern, checked 2026-11-21); PROJECT_ANATOMY.md, "Payments and billing" and "Third-party integrations".

## 4. Open risks for Phase 3

- **Proof project P1 depends on this department.** P1 "TaskBoard" (the single-agent proof) ships Stripe billing, so payments, subscriptions, webhooks, and dunning must be drafted early enough — and concretely enough — for one agent to implement test-mode billing end-to-end without improvising. If the D11 skills stay abstract, P1's billing is where the whole system gets found out. Drafters should write the Stripe test-mode walk (test clocks, test cards, webhook replay) as a first-class procedure inside the skills, not an appendix.
- **Tax is the sharpest scope risk.** invoicing-tax sits next to regulated advice. The skill must teach data capture, document integrity, and engine integration — and explicitly refuse rate/threshold/registration determinations. Phase 3 review should grep the drafted skill for any hardcoded rate or jurisdiction rule stated without a dated source; any hit is a defect.
- **Provider facts decay.** Smart-retry defaults, dispute windows and fees, A2P registration steps, and sender requirements all changed within the last two years and will change again. Every provider-specific claim in a D11 skill needs a "checked <date>" marker and a re-verification step in the skill's own maintenance notes; undated provider claims should be treated as defects at review.
- **OAuth 2.1 is a draft.** Skills must not cite it as a standard. The teachable rule is "RFC 9700 floor, 2.1 profile as target shape," and the oauth-sso skill needs a note to re-check the draft's status at each revision — if 2.1 publishes as an RFC, several "draft" caveats flip at once.
- **Email/SMS compliance is jurisdiction- and carrier-shaped.** The file states the US SMS regime and the Google/Yahoo/Microsoft sender rules as dated, sourced patterns. Drafters must not generalize them into universal law: other countries have their own sender-ID and consent regimes, and the skills should teach "identify the regime for your sending countries" as step one.
- **Reconciliation is easy to under-specify.** The department standard makes the local database a mirror with a scheduled diff, but Phase 3 must decide the concrete contract: which objects reconcile, how often, and what auto-repairs vs alerts. If left vague, every project will implement the webhook half and skip the diff — and drift will be discovered by customers.
- **Boundary friction with D4 and D7.** Webhooks overlap D4's queues-jobs (processing) and api-keys-management overlaps D7's secrets-management; transactional-email overlaps D4's notifications. Drafters should cross-reference rather than duplicate: D11 owns provider semantics and money/message state; D4 owns transport mechanics; D7 owns the security depth (OTP abuse, key compromise response).
