# D15 Research — Developer Experience, Tooling & Maintenance

Phase 2 research for department D15. Direct input to Phase 3 drafting of the 8 D15 skills. Anatomy basis: PROJECT_ANATOMY.md Part 6, "Developer experience and maintenance"; Part 2, "Configuration" and "Versioning".

## 1. Department standard

Professional DX work today rests on five commitments:

1. **The environment is code, not folklore.** Tool versions are declared in a committed file and installed by a tool, not by a wiki page. The current reference implementations are the Development Containers specification — a `devcontainer.json` describing image, features, lifecycle commands, and editor settings, consumable by multiple editors and CI (https://containers.dev/implementors/json_reference/) — and polyglot version managers such as mise, where one `mise.toml` pins runtimes and CLI tools per project and `mise install` materializes them (https://mise.jdx.dev/dev-tools/). Config that varies per deploy lives in environment variables, strictly separate from code (Twelve-Factor, Factor III: https://12factor.net/config).
2. **Releases are numbered by contract, not by mood.** Semantic Versioning 2.0.0: MAJOR for incompatible changes, MINOR for backward-compatible features, PATCH for backward-compatible fixes; a published version is never modified (https://semver.org/). Commit history feeds the number: Conventional Commits maps `fix:` → PATCH, `feat:` → MINOR, and `BREAKING CHANGE:` / `!` → MAJOR, making the bump derivable by tooling (https://www.conventionalcommits.org/en/v1.0.0/). The human record follows Keep a Changelog: one section per version, newest first, ISO 8601 dates, six change types — Added, Changed, Deprecated, Removed, Fixed, Security (https://keepachangelog.com/en/2.0.0/).
3. **Dependencies are a managed surface, not a snapshot.** A lockfile is committed and installs in CI are reproducible (`npm ci` / frozen-lockfile equivalents). Updates arrive as small, frequent, individually reviewable pull requests from automation — Dependabot via `.github/dependabot.yml` (https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/configure-version-updates) or Renovate, which covers many ecosystems and lockfile maintenance from one config (https://docs.renovatebot.com/modules/manager/npm/). Security updates are separated from feature updates and merged faster.
4. **Refactoring is a disciplined, behavior-preserving workflow.** Fowler's definition: restructure internal structure without changing observable behavior, in small steps, on green tests, wearing only one of the "two hats" (adding function vs. refactoring) at a time; preparatory refactoring before a feature and comprehension refactoring while reading code are named workflows, not afterthoughts (https://martinfowler.com/articles/workflowsOfRefactoring/fallback.html).
5. **Legacy is replaced incrementally, never by big-bang rewrite.** The Strangler Fig pattern puts a routing facade in front of the old system and migrates one slice at a time (transform → coexist → eliminate); inside a codebase, Branch by Abstraction introduces an abstraction layer so old and new implementations coexist on trunk, and Parallel Change (expand → migrate → contract) makes breaking changes in non-breaking steps (https://kindatechnical.com/software-engineering/large-scale-change-strangler-branch-abstraction.html; pattern overview: https://microservices.io/post/refactoring/2023/06/21/strangler-fig-application-pattern-incremental-modernization-to-services.md.html).

Debt is classified before it is paid: Fowler's Technical Debt Quadrant (deliberate/inadvertent × prudent/reckless) decides whether an item gets scheduled repayment, a risk flag, or a process fix (summary: https://learningloop.io/glossary/technical-debt).

## 2. Failure modes this department prevents

Drawn from the anatomy slop lines:

- **Developer experience and maintenance (Part 6):** "works on my machine" setup with undocumented manual steps; no lockfile or version pins; a changelog that stopped at v1.0; TODO comments standing in for a debt process; setup taking days of tribal knowledge; dependencies rotting into unpatched vulnerabilities; untraceable releases; code nobody dares to touch.
- **Versioning (Part 2):** version numbers bumped at random (1.0 → 3.0 for a typo fix); breaking API changes shipped under the same version; no changelog connecting versions to changes; bug reports that cannot be tied to the code that produced them.
- **Configuration (Part 2):** `if (environment === "prod")` branches choosing hardcoded URLs; real API keys in committed config files; silent defaults pointing at production; every environment quietly running different code.
- **Feature flags and experimentation (Part 2, served jointly with D4/D2):** permanent `if (true)` branches and ownerless flags — the D15 angle is flag/version hygiene: stale toggles are a debt class with an owner and an expiry, per the toggle taxonomy (release, experiment, ops, permissioning) in Hodgson's "Feature Toggles" (https://martinfowler.com/articles/feature-toggles.html).

## 3. Per-skill research notes

### dev-environment

- **Core method:** Declare the whole toolchain in committed files: runtime/tool versions in one pin file (`.tool-versions`, `mise.toml`, or the ecosystem equivalent), services and editor setup in `.devcontainer/devcontainer.json` where a container is warranted, and one bootstrap command (`make setup`, `npm run setup`, or `mise install` + install step) that takes a clean clone to a running app with tests passing. `.env.example` names every required variable with placeholder values; the app validates config at startup and fails fast, naming the missing variable (Twelve-Factor Factor III).
- **Key rules:**
  1. One command from clone to running app; any second manual step is a defect in the skill's output, not a README footnote.
  2. Every tool version is pinned exactly once, in one file; READMEs reference the file, never restate version numbers.
  3. No real secret ever appears in an example file; examples use obvious placeholders (`sk_test_...`, `change-me`).
  4. Setup must be idempotent — running it twice changes nothing and breaks nothing.
  5. The same pinned versions run in CI as on a laptop; CI installs from the pin file, not from `latest`.
- **Verification gates:** (Automatable) Fresh-clone test in a clean container/VM: run only the documented bootstrap, assert the app starts and the test suite passes; fail if any undocumented step was needed. (Automatable) `git grep` for real-looking secret patterns in `.env.example` and config examples returns nothing.
- **Sources:** Dev Containers metadata reference — https://containers.dev/implementors/json_reference/ ; mise dev tools — https://mise.jdx.dev/dev-tools/ ; Twelve-Factor Config — https://12factor.net/config

### monorepo-tooling

- **Core method:** One repository, many packages, orchestrated by a task graph. Workspaces (pnpm/npm/Yarn) link internal packages; a task runner (Turborepo or Nx) executes build/lint/test in dependency order with content-hash caching, locally and via a remote cache shared with CI. Shared configs (TypeScript, ESLint, test presets) live in internal packages, not copy-pasted files. Root scripts are the only entry points a developer needs.
- **Key rules:**
  1. Internal dependencies are declared in each package's manifest; the task graph is derived from those declarations — no hand-maintained build order.
  2. Every task declares its outputs; a task with undeclared outputs is not cacheable and must say why.
  3. Cache keys must include the lockfile and relevant env vars; a cache hit on changed inputs is a correctness bug, not a speedup.
  4. Packages may not import each other's source by relative path across package boundaries — only through the declared package entry point.
  5. Versioning is a stated choice up front: independent per package (Changesets-style) or one fixed version for the repo; never an accidental mix.
- **Verification gates:** (Automatable) Run the full pipeline twice from clean state; the second run must report cache hits for unchanged packages and byte-identical outputs. (Automatable) A change in one leaf package rebuilds only that package and its dependents in CI (`--filter` / affected-only run).
- **Sources:** Turborepo concepts and pipeline practice — https://www.devtoolsguide.com/turborepo-monorepo-guide/ ; mise (task/tool layer often paired at repo root) — https://mise.jdx.dev/dev-tools/

### code-generation

- **Core method:** Generate only from a machine-readable source of truth — an OpenAPI description for clients/server stubs/types (OpenAPI Generator), a schema for ORM models, or project templates for scaffolding — and regenerate in CI rather than editing output by hand. Generated files are marked with a header, excluded from manual review diffs where the platform allows, and either committed (so diffs of the source show as diffs of output) or built in CI, by a stated rule.
- **Key rules:**
  1. Never hand-edit generated output; change the source or the template, then regenerate. Hand edits are overwritten silently and are a defect.
  2. The generator and its version are pinned like any other dependency; output must be reproducible byte-for-byte from the same source and generator version.
  3. The source of truth (spec/schema) is reviewed like code; generation is not a way to smuggle unreviewed API changes in.
  4. Generated code still passes the project's lint, type, and test gates — "generated" is not an exemption.
  5. Custom templates are versioned with the project; stock templates are overridden minimally and the overrides documented.
- **Verification gates:** (Automatable) Drift check in CI: regenerate from source into a temp directory and `diff -r` against the committed output; any difference fails the build. (Automatable) Grep generated directories for manual-edit markers / missing generated-file headers.
- **Sources:** OpenAPI Generator overview and workflow — https://nordicapis.com/introduction-to-openapi-generator/ ; generator usage in practice — https://apidog.com/blog/openapi-generator-5/ ; OpenAPI Specification v3.1.0 — https://spec.openapis.org/oas/v3.1.0

### dependency-management

- **Core method:** Treat the dependency set as inventory under active management: committed lockfile, reproducible CI installs, automated update PRs grouped and scheduled (Dependabot or Renovate), security advisories triaged on a stated SLA, and every direct dependency justified (maintained, licensed compatibly, not replaceable by the standard library or an existing dependency).
- **Key rules:**
  1. The lockfile is committed and CI installs from it frozen; a PR that changes a manifest without the lockfile (or vice versa) fails.
  2. Update automation is configured in the repo (`.github/dependabot.yml` or `renovate.json`): grouped minor/patch updates, majors individually, security updates ungrouped and immediate.
  3. No ignored update PR older than the project's stated window (e.g. 30 days) without a recorded reason in the debt register.
  4. New direct dependencies require a one-line justification in the PR: what it does, why the platform/existing deps don't, maintenance status.
  5. Ranges are deliberate: pin exact versions for applications; use caret ranges only where the ecosystem convention (libraries) makes them the contract.
- **Verification gates:** (Automatable) `npm audit` / `pip-audit` / ecosystem equivalent in CI fails on high/critical advisories in production dependencies. (Automatable) Lockfile-consistency check: CI install with frozen lockfile succeeds without modifying the lockfile. (Automatable) The update-bot config file exists and validates against its schema.
- **Sources:** Dependabot version updates — https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/configure-version-updates ; Renovate npm manager and lockfile maintenance — https://docs.renovatebot.com/modules/manager/npm/

### tech-debt

- **Core method:** Make debt visible, classified, and scheduled. Every known shortcut is a register entry with: location, Fowler quadrant (deliberate/inadvertent × prudent/reckless), the interest it charges (what work it slows or risks), an owner, and a repayment trigger (date, or the next feature touching that area). TODO/FIXME comments in code must reference a register ID or be deleted. Repayment is budgeted as a standing slice of capacity, not negotiated per item.
- **Key rules:**
  1. Deliberate debt is only taken with a register entry created in the same PR that incurs it — quadrant "deliberate + prudent" requires the repayment trigger at birth.
  2. "Deliberate + reckless" is not a permitted category: if there is no plan, the review blocks or the scope is cut.
  3. Interest is stated concretely ("every billing change requires edits in three duplicated places"), never "code is messy."
  4. Debt items are closed by a merged change, not by deciding they no longer matter; closures are recorded.
  5. The register is reviewed on a cadence (per release or monthly) and the count/age of open items is reported like any other project metric.
- **Verification gates:** (Automatable) Lint/CI grep: every `TODO`/`FIXME`/`HACK` in the codebase carries a register reference (e.g. `TODO(DEBT-123)`); bare markers fail. (Manual gate) Register audit: sample open items, confirm each still has a live owner and a future trigger date.
- **Sources:** Technical Debt Quadrant (Fowler, 2009), summary — https://learningloop.io/glossary/technical-debt ; Workflows of Refactoring (debt repayment inside feature flow) — https://martinfowler.com/articles/workflowsOfRefactoring/fallback.html

### refactoring

- **Core method:** Fowler's discipline: a refactoring is a small, named, behavior-preserving transformation (Extract Function, Inline Variable, Change Function Declaration, …) applied in steps, with the full relevant test suite green before and after each step. Two hats: while refactoring, no behavior changes and no new features; while adding features, no opportunistic restructuring — switch hats explicitly, commit separately. Prefer preparatory refactoring ("first make the change easy, then make the easy change") ahead of a feature, and comprehension refactoring while reading unfamiliar code.
- **Key rules:**
  1. No refactoring without a safety net: if the area lacks tests, the first step is characterization tests that pin current behavior.
  2. Steps are small enough that the suite runs between them; a red suite mid-refactoring means stop and back up one step, not push through.
  3. Refactoring commits contain no behavior change and are separate from feature/fix commits, so review and revert stay trivial.
  4. Refactor toward a named design pressure (duplication, coupling, unclear names), not toward abstract "cleanliness"; the Rule of Three governs extraction of abstractions.
  5. Performance work is not refactoring: it changes a measurable quality, is benchmarked before/after, and is labeled as its own change type.
- **Verification gates:** (Automatable) The full test suite passes unchanged across the refactoring PR — the gate is that no test file needed modification to stay green (test edits in a "refactor" PR are flagged for review). (Automatable) Public API surface diff (exported symbols / OpenAPI contract) between base and PR is empty.
- **Sources:** Workflows of Refactoring, incl. two hats — https://martinfowler.com/articles/workflowsOfRefactoring/fallback.html ; Fowler, *Refactoring: Improving the Design of Existing Code* (2nd ed.) — catalog summarized at https://deepwiki.com/gmoral/Books/7.3-refactoring:-improving-the-design-of-existing-code

### legacy-migration

- **Core method:** Replace in slices behind a seam, never in a freeze-and-rewrite. For web/API surfaces, Strangler Fig: put a facade (proxy/router) in front, build the new implementation of one capability, route that slice's traffic to it, repeat, then delete the old path (transform → coexist → eliminate). Inside one codebase, Branch by Abstraction: introduce an abstraction over the thing being replaced, implement the new version behind it, flip callers over, remove the old. For data/API shape changes, Parallel Change: expand (add new alongside old), migrate readers/writers, contract (remove old). Characterization tests pin legacy behavior before anything moves.
- **Key rules:**
  1. Every migration plan names its slices, the seam for each, and the rollback for each step; a plan that is one big step is rejected.
  2. The legacy system stays deployable and is the fallback until its slice's replacement has run in production; deletion is a separate, later step.
  3. No new features are added to legacy code paths once their slice is scheduled — fixes only — or the target moves forever.
  4. Data migration is rehearsed on a copy and is reversible or has a stated point of no return with a backup taken at it.
  5. Coexistence has an end date in the plan; "both systems forever" is how migrations fail.
- **Verification gates:** (Automatable) Characterization/contract test suite runs against both old and new implementations during coexistence and passes on both. (Automatable) Traffic/route audit: the facade's routing table matches the migration plan's current stage; after the eliminate step, a repo-wide grep finds no references to the removed legacy module or endpoint.
- **Sources:** Strangler Fig, Branch by Abstraction, Parallel Change — https://kindatechnical.com/software-engineering/large-scale-change-strangler-branch-abstraction.html ; Strangler Fig pattern overview — https://microservices.io/post/refactoring/2023/06/21/strangler-fig-application-pattern-incremental-modernization-to-services.md.html ; toggle taxonomy for routing flips — https://martinfowler.com/articles/feature-toggles.html

### versioning

- **Core method:** SemVer 2.0.0 as the public contract for the product and each published package; API versions handled per the API-versioning contract (D2) with a deprecation window. Commit messages in Conventional Commits format so the next bump is mechanically derivable: the highest signal in the range wins (any `BREAKING CHANGE`/`!` → MAJOR, else any `feat:` → MINOR, else PATCH). Each release is a git tag matching the version, a Keep a Changelog section moved from `[Unreleased]`, and an immutable published artifact — a released version is never edited in place.
- **Key rules:**
  1. Pre-1.0 is stated explicitly as "anything may change," and 1.0.0 is cut when the API is a real public commitment, not when the code feels old enough.
  2. Deprecation precedes removal by at least one minor release for libraries/APIs, announced in the changelog's Deprecated section.
  3. The version lives in exactly one source of truth (tag, manifest, or generated file) — never hand-edited in several places that can disagree.
  4. Changelog entries are written for consumers (what changed for them), grouped by the six Keep a Changelog types, with breaking changes marked in place.
  5. Yanked/withdrawn releases are marked `[YANKED]` in the changelog with a reason, never silently deleted from history.
- **Verification gates:** (Automatable) Release check: the git tag, the package manifest version, and the top CHANGELOG heading are identical strings. (Automatable) Commit-lint (e.g. commitlint with the Conventional Commits config) passes on the release range, and the computed bump from commit types matches the version actually being released. (Automatable) Contract diff: if the API contract diff contains a breaking change, the major version must have increased.
- **Sources:** Semantic Versioning 2.0.0 — https://semver.org/ ; Conventional Commits 1.0.0 — https://www.conventionalcommits.org/en/v1.0.0/ ; Keep a Changelog 2.0.0 — https://keepachangelog.com/en/2.0.0/

## 4. Open risks for Phase 3 drafters

- **Single-agent execution vs. team-shaped practices.** Most sources assume a team (reviewers, on-call, debt negotiation). Each skill must translate gates into checks one agent can run alone — favor the automatable gates above (fresh-clone test, drift diff, frozen-lockfile install, TODO-reference lint, tag/manifest/changelog equality) over process language like "the team reviews."
- **Ecosystem breadth.** OmniForge skills must work across stacks, but every concrete command here is ecosystem-specific (`npm ci`, `pip-audit`, pnpm workspaces). Drafters need a per-stack substitution table per skill, or rules stated at the invariant level with one worked example stack — mixing the two inconsistently will produce vague skills.
- **Monorepo scope creep.** Most OmniForge projects are single apps. The monorepo-tooling skill must state its trigger (2+ deployables or a genuinely shared package) or agents will scaffold monorepos for landing pages.
- **Code generation vs. the Real Content Rule.** Generated stubs look like finished functionality (endpoints that return canned data). The code-generation skill must require generated scaffolds to be visibly incomplete (failing tests, explicit not-implemented errors) until implemented, or it will manufacture DET-FAKE findings.
- **Debt register placement.** The register format overlaps D10's decision-logs/changelog territory and the project's `docs/` file set; Phase 3 must fix one canonical location and cross-reference, or two skills will invent two registers.
- **Versioning for apps vs. libraries.** SemVer's contract logic fits libraries and APIs; for deployed web apps the "version" is largely internal. The versioning skill needs an explicit app-mode (release naming, tag + changelog still required, bump rules relaxed to deployment traceability) or agents will cargo-cult library rules onto websites.
