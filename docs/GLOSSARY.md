# GLOSSARY.md — Canonical definitions

One definition per shared term, used with this exact meaning across all departments, skills, playbooks, and gates in this repository. Where a term is defined by a specific skill or `gates/` file, this glossary points there instead of redefining it — the cited file wins if the two ever disagree.

## Core artifacts

- **Skill** — A single self-contained Markdown file at `skills/<department>/<skill>/SKILL.md` that teaches one capability: when to use it, its rules, its BAN list, its gates, its anti-patterns, examples, recall anchors, and a checklist. A skill is written to be loaded and used by one agent, mid-task, without reading the rest of the repo.
- **Rule** — A numbered, verifiable requirement inside a skill, cited by ID (`<CODE>-<NNN>`, e.g. `FE-041`). Every rule must be checkable against a named gate; an unverifiable rule is rewritten or cut (QB-01). Rule IDs are assigned from `docs/RULE_ID_REGISTRY.md`, are unique repo-wide, and are never reused or renumbered.
- **Gate** — A check with an ID (`G-<CODE>-<NNN>` for skill gates; family IDs such as `G-DES-01` for the inherited acceptance gates in `gates/ACCEPTANCE_GATES.md`), the rule IDs it verifies, an exact check (command, scan, or manual step), a pass criterion, a fail action, and a place where the result is recorded (`progress.md`). A gate that fails blocks shipment unless it is formally waived (see **Waiver**).
- **BAN entry** — A hard prohibition inside a skill's BAN list: ID (`BAN-<CODE>-<NNN>`), the banned pattern in one line, the detection parameter it defeats, a bad example, the correct replacement, and a severity (BLOCK = gate fails, WARN = flag for review). An item appears in exactly one of the BAN list or the anti-patterns, never both.
- **Anti-pattern** — A failure mode an agent must recognize in its own draft output. A hit triggers rework, not an automatic gate fail (contrast **BAN entry**).
- **Detection parameter** — One measurable tell of AI-generated or fake output, defined in `skills/detection/<family>/PARAMETERS.md` with an ID (`DET-<FAMILY>-<NNN>`): its signal, the AI-typical form, the professional form, how to check, false positives, severity, source, and the skill that fixes it. Families: VIS, CODE, INF, CON, UX, FAKE, CRWL.
- **DET-NONE** — The explicit null marker for a BAN entry whose banned pattern no detection parameter names. Written as `Defeats: DET-NONE — no DET parameter names this signal; governed by <rule IDs>`. Defined in `templates/SKILL_TEMPLATE.md`; it records an honest gap instead of citing a nearest-match parameter as if it were exact.
- **Bundle** — A generated file in `bundles/` that packages skills for loading into an agent's context: `core.md` (always-on core, under 10,000 tokens), one bundle per department, one per playbook, and `ALL_SKILLS.md` (reference only — never loaded whole). Bundles are generated by script, never hand-edited, and no bundle exceeds 30,000 tokens.
- **Playbook** — A file in `playbooks/` that sequences departments, skills, and gates for one project type (e.g. `playbooks/saas-web-app.md`): goal, order, skills to load with bundle names, docs to write first, decision points, must-pass gates by ID, failure handling, and a definition of done.
- **Provenance comment** — The HTML comment a generated bundle carries for each included skill, `<!-- generated from skills/... -->`, naming the source file the content was generated from. It is how a reader traces bundled content back to its single source.
- **Always-on core** — The four skills every consuming agent loads for every task: `project-templates` and `progress-tracking` (D10), `secrets-management` (D7), and `qa-gates` (D8). They ship inside `bundles/core.md`.

## Project records (per consuming project)

- **fact-sheet.md** — The project's single source of verified facts: every fact, name, number, quote, and testimonial with its source, kept per the D1 `fact-sheet` skill (`skills/product-requirements/fact-sheet/`). No fact-sheet entry means the content does not ship. Recording a claim here is not verification — verification is checking the source itself (Real Content Rule step 1b).
- **progress.md** — The project's running log: work done, gate results with evidence, blockers, gaps, waivers, and open items with dates. Maintained per the D10 `progress-tracking` skill (`skills/project-memory/progress-tracking/`). If it is not in `progress.md`, it did not happen.
- **DECISIONS.md** (project) — The project's decision log: skill conflicts and how precedence resolved them, gate waivers, dropped requirements, and user choices, each with reasons. Distinct from this repo's own build decisions in `docs/DECISIONS.md`.

## Rules of the house

- **Real Content Rule** — The mandatory rule (brief §6.2, QB-10) that no content, data, person, statistic, testimonial, social proof, or functionality may be invented. Every fact ships with a verified source or does not ship; gaps are filled by asking the user or by an honest empty state. Enforced by the `placeholder-scan` and `fact-sheet` gates, with the fake classes and scan patterns in `gates/placeholder-patterns.md` and the legitimate exceptions in `gates/placeholder-allowlist.md`.
- **Empty state** — The designed state of a section whose real content does not exist yet: it says what the section is, why it is empty, and what happens next. An empty state is the correct replacement for missing content — never lorem ipsum, a grey box, or invented filler.
- **Seed data** — Synthetic demo data, allowed only flagged `seed: true`, behind a persistent DEMO DATA banner, in a demo/preview environment — never in production. Rules in the D5 `seed-data` skill.
- **Single-agent compatibility** — The hard design constraint (QB-08) that everything in this repo must be usable by ONE agent with no sub-agents, no handoffs, and no multi-agent orchestration at consumption time, playing all roles sequentially with the skills' own checklists and gates. The multi-agent company exists only to build the repo.
- **Precedence** — The fixed order (brief §5.7, printed in `BOOTSTRAP.md`) that decides which skill wins when two loaded skills conflict: security first, then legal/privacy, the Real Content Rule, QA process gates, accessibility, and so on down to project memory. Precedence never excuses skipping a gate.
- **Posture tier** — The deployment label — validation posture or production posture — that states how production-grade a deployment currently is, with its promotion trigger and any knowingly waived detection parameters. Defined by rule DO-142 in the D6 `hosting` skill (`skills/devops-deployment/hosting/`).
- **Waiver (gate waiver)** — The recorded exception for a gate that cannot pass because the gate itself is wrong for the project (it contradicts another gate, tests a feature the project does not have, or needs tooling a single agent lacks). Recorded in `progress.md` and `DECISIONS.md` with what was checked instead; waivers of security, legal, or Real Content gates need the user's explicit agreement. A silently skipped gate is not a waiver — it is a failed deliverable.
- **Repo gap** — Something a consuming agent needed that this repo does not provide (a missing skill, playbook, or check). Gaps are logged in the project's `progress.md`, worked around provisionally with the closest skill, and reported through the feedback loop (see `docs/MAINTENANCE_RUNBOOK.md`) — never silently papered over with invented guidance.
- **Defect** — Any item in the defect taxonomy: P0 (security, data loss, crash), P1 (broken feature or gate failure), P2 (cosmetic or copy). Defined in full in `gates/DEFECT_TAXONOMY.md` (QB-01).
- **Ship gate** — The 16-criterion gate (brief §9.1) that this repository itself must pass before it ships, including bar-to-gate traceability in `docs/BAR_TRACEABILITY.md`, the proof projects, Technical Board sign-off, and user sign-off.
