# Contract: D4 ↔ D11 — Backend ↔ Payments/Integrations

- **Backbone link:** #6 of 13 (MASTER_BRIEF.md §3.11)
- **Link type:** SHARES
- **Owner departments:** D4 Backend & APIs and D11 Integrations & Payments (co-owners)
- **Liaisons:** D4 API builders ↔ D11 Payment engineers
- **Skills on each side:** api-building, queues-jobs (D4) ↔ payments, subscriptions, webhooks (D11)

## Artifact that passes

`PAYMENT_SECURITY.md` — the payment integration record: provider, mode (test/live),
the webhook event catalogue with the exact payload schema per event, signature
verification method, idempotency behaviour, and the entitlement rules that decide
what a payment grants. D11 owns provider mechanics; D4 owns the endpoints and
background jobs that receive and process events.

## Format

Markdown record plus the provider's event schemas as data (JSON examples captured
from the provider's test mode, secrets redacted). Amounts and entitlements are
always recomputed server-side (BE-003); the client never states a price.

## When it passes

Before any payment flow is built, and at every provider, price, or event-catalogue
change. Test mode end-to-end precedes live mode without exception.

## Acceptance test (how the receiver verifies)

**Joint gate — payment integration.** Each webhook event in the catalogue is
replayed against the local handler in test mode: signature verified from the raw
body, duplicate delivery absorbed idempotently, unknown events logged and ignored
safely. Checkout, refund, dispute, and subscription-lifecycle flows each complete
in test mode, and the resulting entitlement state is checked against
PAYMENT_SECURITY.md — a paid state the record does not predict blocks release.

## If the test fails

Payments stay in test mode. No flow is promoted on the strength of the provider's
dashboard alone; the local handler's behaviour is the evidence.
