# Contract: D13 → D3 — Accessibility + RTL on Every UI

- **Backbone link:** #5 of 13 (MASTER_BRIEF.md §3.11; written "D3 ↔ D13" there as
  pair shorthand — the link itself is one-directional CONSTRAINS, per the matrix rules)
- **Link type:** CONSTRAINS
- **Owner department:** D13 Accessibility & i18n
- **Consumer department:** D3 Frontend, Design & Motion
- **Liaisons:** D13 A11y auditors ↔ D3 Design system builders
- **Skills on each side:** wcag, keyboard-accessibility, rtl-layouts (D13) → design-system, component-library, ui-states (D3)

## Artifact that passes

The constraint set itself: WCAG 2.2 AA as the build target, the per-jurisdiction
version pins D13's accessibility-law skill records (EN 301 549 → 2.1 AA,
Section 508 → 2.0 AA, ADA Title II → 2.1 AA), and the shared `DESIGN_TOKENS.md`
values (contrast-checked pairs, focus indicators, motion limits) D3 builds with.

## Format

Rules and gates inside the D13 skills; token values in DESIGN_TOKENS.md in DTCG
format. D13 changes a constraint by amending the skill or the token file and
announcing it the same day — never by review comment alone.

## When it passes

At design-system setup, at every component addition, and at the pre-ship gate of
every UI playbook. No UI playbook ships without a D13 step.

## Acceptance test (how the receiver verifies)

**Joint gate — a11y + RTL.** D3 demonstrates, per UI: keyboard-only completion of
every flow, visible focus in order, computed contrast ≥ 4.5:1 (≥ 3:1 large text)
for every token pair, reduced-motion behaviour, and the RTL mirror pass for
locales that need it. D8's accessibility-testing runs the mechanical half;
the manual half (screen-reader pass, focus order) is recorded in progress.md.

## If the test fails

The UI does not ship. D3 adapts or drops the offending pattern — under the §5.7
precedence order, accessibility (rank 5) beats design preference (rank 15),
so "the design needs it" is never the resolution.
