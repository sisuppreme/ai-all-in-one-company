# Contract: D1 → D2 — Requirements → Architecture

- **Backbone link:** #1 of 13 (MASTER_BRIEF.md §3.11)
- **Link type:** FEEDS
- **Owner department:** D1 Product & Requirements
- **Consumer department:** D2 Architecture & System Design
- **Liaisons:** D1 Requirements writers ↔ D2 System designers
- **Skills on each side:** fact-sheet, requirements-writing (D1) → system-design, stack-selection (D2)

## Artifact that passes

`requirements.md` — the project's requirements record, backed by `fact-sheet.md` for every
externally checkable claim (prices, limits, dates, competitor facts). D1 authors both;
D2 consumes them as the sole input to architecture work.

## Format

Markdown per the project-templates skill: numbered requirements with stable IDs,
each with a source (user statement, fact-sheet entry, or research note), a priority,
and an acceptance criterion. Unverified items are marked UNVERIFIED and carry no
downstream citation rights.

## When it passes

After requirements-writing's gates pass and before any system-design work starts.
Any scope change re-issues the artifact the same day; D2 works only from the current
version, never from chat history.

## Acceptance test (how the receiver verifies)

**Joint gate — requirements traceability.** D2 lists every architecture element
(service, store, integration, boundary) against the requirement ID it traces to.
An element with no requirement is cut, or the requirement is written and verified
first. D1 re-checks that no requirement was silently dropped: every requirement ID
appears in the traceability list or in an explicit out-of-scope note.

## If the test fails

Architecture work stops. The gap is resolved on the D1 side (requirement written,
corrected, or formally descoped in DECISIONS.md) — D2 never invents a requirement
to justify a design it prefers.
