# Contract: D3 ↔ D4 — Frontend ↔ Backend via API Contracts

- **Backbone link:** #4 of 13 (MASTER_BRIEF.md §3.11)
- **Link type:** SHARES
- **Owner departments:** D3 Frontend, Design & Motion and D4 Backend & APIs (co-owners)
- **Liaisons:** D3 State & data fetching ↔ D4 API builders
- **Skills on each side:** data-fetching, frontend-state (D3) ↔ api-building, rest-conventions (D4)

## Artifact that passes

`API_CONTRACTS.md` with its OpenAPI 3.1 description — the single source both sides
build against. D4 implements it; D3 consumes only what it contracts. Neither side
invents an endpoint, a field, or an error shape the contract does not name.

## Format

OpenAPI 3.1 (machine-readable, diffed in review) plus the Markdown decision record
from contract d2-d4.md. Error responses follow the house Problem Details shape;
pagination, filtering, and versioning follow the D2 house style profile.

## When it passes

Before frontend data work starts on a feature, and again at every contract change:
the change is announced the same day and both sides re-verify before building on it.

## Acceptance test (how the receiver verifies)

**Joint gate — API contract.** D3 greps the frontend for every network call and
matches each URL, verb, and payload against the OpenAPI description; an unmatched
call is a defect. D4 runs contract tests against the running service (D8
contract-testing). UI states for loading, empty, error, and offline exist for every
consumed endpoint — a missing state is a contract breach, not a design detail.

## If the test fails

The side that drifted returns to the contract. The frontend never mocks an
uncontracted endpoint into production, and the backend never ships an uncontracted
field "temporarily" — temporary contract drift is how the two sides silently fork.
