# Contract: D6 ↔ D12 — Infrastructure ↔ Observability

- **Backbone link:** #7 of 13 (MASTER_BRIEF.md §3.11)
- **Link type:** SHARES
- **Owner departments:** D6 DevOps & Deployment and D12 Analytics & Observability (co-owners)
- **Liaisons:** D6 Reliability engineers ↔ D12 Monitoring & alerting
- **Skills on each side:** ci-cd, hosting, reliability (D6) ↔ logging, monitoring, alerting, dashboards (D12)

## Artifact that passes

`OBSERVABILITY_SPEC.md` — the signals every deployed service must emit and watch:
log format and levels, metric names, health endpoints, alert rules with thresholds
and escalation contacts, and the dashboards that display them. D6 owns the platform
the signals run on; D12 owns the signal policy and the alert rules.

## Format

Markdown spec; alert thresholds stated as numbers with the baseline they were
derived from. The split is fixed: D12 owns policy (what is watched, when it pages),
D6 owns mechanics (pipelines, retention, on-call plumbing).

## When it passes

At environment setup (spec written before the first deploy) and at every deploy
that adds a service, a job, or an integration.

## Acceptance test (how the receiver verifies)

**Joint gate — observability.** After deploy, D12 confirms the new service's logs,
metrics, and health checks appear in the dashboards named in the spec, and fires
one test alert end-to-end to the escalation contact. D6 confirms retention and
access match the spec. A service that deploys without visible signals is treated
as down, even if it responds.

## If the test fails

The deploy is rolled back or the gap is fixed before the next deploy — never
accepted as "monitoring comes later". An unobservable production service is a
production defect (DET-INF family), not a backlog item.
