# Contract: D4 ↔ D5 — APIs ↔ Schema

- **Backbone link:** #3 of 13 (MASTER_BRIEF.md §3.11)
- **Link type:** SHARES
- **Owner departments:** D4 Backend & APIs and D5 Databases & Data (co-owners)
- **Liaisons:** D4 API builders ↔ D5 Schema designers
- **Skills on each side:** api-building, data-access (D4) ↔ schema-design, migrations, tenant-isolation (D5)

## Artifact that passes

`SCHEMA.md` plus the migration files that realize it. D5 owns schema and migrations;
D4 owns the API surface that reads and writes through them. A change on either side
is incomplete until the other side has absorbed it — one change, both sides update.

## Format

SCHEMA.md as defined in contract d2-d5.md; migrations as numbered, reversible
migration files using expand-and-contract for any breaking change (add new, backfill,
switch reads, drop old — never a single destructive step against a live API).

## When it passes

Continuously: every schema change and every API change that touches stored data
passes through this contract in the same work unit, recorded in the same
progress.md entry.

## Acceptance test (how the receiver verifies)

**Joint gate — data contract.** For each change, the progress.md entry names both
halves: the migration and the API change that ships with it. D4 verifies its
serializers expose only contracted fields (BE-008) against the new schema; D5
verifies the API's access patterns against the schema's indexes and tenant
isolation rules. Contract tests run against the migrated schema in CI.

## If the test fails

Neither half merges alone. A schema change waiting on API work stays on its branch;
an API change waiting on a migration is blocked, not worked around with
application-level patches that bypass the data-access layer.
