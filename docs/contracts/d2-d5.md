# Contract: D2 → D5 — Architecture → Schema

- **Backbone link:** #2 of 13, schema side (MASTER_BRIEF.md §3.11)
- **Link type:** FEEDS
- **Owner department:** D2 Architecture & System Design
- **Consumer department:** D5 Databases & Data
- **Liaisons:** D2 Data architects ↔ D5 Schema designers
- **Skills on each side:** data-architecture, domain-driven-design (D2) → schema-design, migrations (D5)

## Artifact that passes

`SCHEMA.md` — the data model D2 designed: entities, fields, relationships, invariants,
tenancy and residency constraints, and the bounded contexts they belong to. D5 turns
it into physical schema and migrations; D5 does not redesign the model.

## Format

Markdown: one section per entity (fields with types and constraints, keys, indexes
implied by named queries), plus an invariants list stated as testable assertions.
Changes are versioned in the file header and announced the same day.

## When it passes

After the data-architecture review, before schema-design or any migration is written.
A model change after migrations exist goes through the D4 ↔ D5 data-contract
procedure as well (contract d4-d5.md).

## Acceptance test (how the receiver verifies)

**Joint gate — architecture-to-implementation (schema side).** D5 diffs the physical
schema (as migrated) against SCHEMA.md: every entity, field, and invariant is present
and nothing extra was added. Each invariant in SCHEMA.md maps to a constraint, a
transaction boundary, or a named test — an invariant with no enforcement point is
reported back to D2, not silently dropped.

## If the test fails

Migrations stop. Either the schema is corrected to the model, or D2 amends SCHEMA.md
with the reason recorded. Production data is never reshaped to match an uncorrected
implementation.
