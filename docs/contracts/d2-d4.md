# Contract: D2 → D4 — Architecture → API Contracts

- **Backbone link:** #2 of 13, API side (MASTER_BRIEF.md §3.11)
- **Link type:** FEEDS
- **Owner department:** D2 Architecture & System Design
- **Consumer department:** D4 Backend & APIs
- **Liaisons:** D2 API architects ↔ D4 API builders
- **Skills on each side:** api-architecture, api-paradigms, api-versioning (D2) → api-building, rest-conventions (D4)

## Artifact that passes

`API_CONTRACTS.md` — the architecture's API surface: resources, boundaries, the
house style profile (Zalando-based: snake_case, Problem Details, cursor pagination,
path-segment versioning), and the OpenAPI 3.1 description D4 implements against.

## Format

Markdown contract summary plus a machine-readable OpenAPI 3.1 document. The OpenAPI
description is the implementable form; the Markdown records the decisions and the
requirement IDs each endpoint traces to (backbone link #1).

## When it passes

After the architecture review for the feature, before api-building starts on it.
Contract changes are versioned and announced the same day; D4 never implements
against an unannounced draft.

## Acceptance test (how the receiver verifies)

**Joint gate — architecture-to-implementation (API side).** D4 diffs the implemented
OpenAPI description against API_CONTRACTS.md: every contracted endpoint exists with
the contracted shape, and no implemented endpoint is uncontracted. Contract tests
(D8 contract-testing) run against the running service in CI — BE-009: implementation
and contract may not drift silently.

## If the test fails

The implementation is fixed to the contract, or the contract is amended through D2
with the change recorded in DECISIONS.md. A drift discovered in review is a defect,
not a documentation task for later.
