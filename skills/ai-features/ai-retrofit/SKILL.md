## When to use / Do NOT use

- **Use when:** an AI capability is being added to a product that is already live and in use — an existing search, inbox, editor, checkout, support, reporting, or admin flow gains summarization, drafting, classification, extraction, recommendations, or a conversational surface — and existing users, existing data, existing habits, and uptime must survive the addition.
- **Do NOT use when:** the product is greenfield with no existing users or data (use llm-integration for the call path and ai-evaluation for quality, with no retrofit constraints), the task is only swapping one model or provider for another inside an already-AI feature (use llm-integration plus ai-evaluation), or the work is a pure prompt change (use prompt-engineering). This skill owns the seam between the old product and the new AI behavior: insertion, coexistence, rollout, and removal. It does not re-specify the wrapper (llm-integration), the guardrails (ai-safety), the golden-set method (ai-evaluation), or budget enforcement (ai-cost-control) — it applies them under live-product constraints.

## Rules

1. **AI-201 — The pre-AI baseline is recorded before anything changes.** Before the first AI code ships, record the existing flow's current behavior and numbers: task completion rate, time-on-task or handling time, error and support-contact rate, latency, and the current non-AI path's output for a fixed sample of real tasks. The retrofit is judged against this baseline, never against a demo or against memory of how the old flow performed.
2. **AI-202 — The non-AI path stays intact, reachable, and tested.** The existing flow remains fully functional with the AI layer removed or disabled, for the whole retrofit and until a recorded removal decision (AI-212). AI code is additive at a named insertion point — a suggestion panel, a pre-fill, a ranking signal, an assist action — and never becomes the only way to complete a task the product already supported. The non-AI path stays in the regression suite; a release that breaks it blocks like any other regression.
3. **AI-203 — Every insertion point is inventoried before building.** Produce a written inventory of candidate insertion points in the existing flow, each scored on: value if the model is right, harm if the model is wrong, whether a human sees the output before it takes effect, and whether the effect is reversible. Build first at points where output is human-reviewed and reversible; a point where model output takes effect unseen and irreversibly is built last, if at all, and only with the gating in AI-204 plus ai-safety's deterministic policy check for state-changing actions.
4. **AI-204 — AI output enters as a proposal, not a mutation.** Model output is stored separately from the product's canonical records, marked as AI-generated with its model ID, prompt version, source inputs, and timestamp. It changes a canonical record, sends a message, or alters a user's data only through the product's existing write path, after the validation and — where the existing flow had one — the human confirmation that path already required. Existing records are never overwritten in place by a model run; a correction or regeneration creates a new proposal, leaving the prior state recoverable.
5. **AI-205 — Consent, notice, and existing settings are respected.** Users learn that a surface is AI-assisted before or at first use, in the surface itself, not only in a changelog or terms update. Existing user preferences, defaults, templates, saved work, and keyboard or workflow habits are not silently changed by the retrofit: an AI default replaces an existing default only behind explicit opt-in, or behind the staged rollout in AI-209 with the old behavior one action away. Where existing terms, privacy notice, or plan entitlements did not cover sending user data to a model provider, that gap is closed before any real user data flows (with ai-safety's PII rules applied to what is sent).
6. **AI-206 — Fallback UX is designed for each failure, not improvised.** For every insertion point, define in advance what the user sees and can do when: the provider is down or times out, the model refuses, output fails validation, the user's quota or the feature budget is exhausted, and the model returns low-quality or empty output. In every case the user can complete the underlying task through the non-AI path (AI-202) without losing work already entered, and the surface states plainly that the AI help is unavailable or was not used — never a spinner that resolves to nothing, a fake success, or a canned answer presented as model output. Latency is part of fallback: the AI surface loads asynchronously and never blocks rendering or saving in the existing flow.
7. **AI-207 — Evaluation runs on the product's real data and real tasks.** The feature's golden dataset (per ai-evaluation) is built from this product's actual inputs — sampled production records, real documents, real queries, real edge cases already in the data such as empty fields, legacy formats, duplicates, very long records, and data created before current validation existed — with personal data handled per ai-safety before use in any eval set. A retrofit eval built only on clean, newly authored examples does not count. The eval also covers coexistence: the same tasks run through the non-AI path must still pass, and AI-assisted results are compared against the AI-201 baseline, not only against an absolute floor.
8. **AI-208 — Existing data is prepared, never silently rewritten.** Before a feature reads legacy data at scale, profile it: field completeness, format drift across record ages, encoding and language mix, and the share of records the model pipeline cannot process. Unprocessable records route to the non-AI path or a visible "couldn't process this" state; they are not dropped from results, silently skipped in a summary, or backfilled by model guesses presented as original data. Any bulk enrichment of existing records runs as a separate, resumable, auditable job that writes proposals per AI-204 — never as a side effect of a page view or a deploy migration.
9. **AI-209 — Rollout is staged, segmented, and reversible at every stage.** Release proceeds in recorded stages — shadow first, wherever the insertion point permits it (the model runs on real inputs, its output is shown to no one and changes nothing, and its divergence from the existing flow's output is recorded and read before any user is exposed), then internal users, then a small named cohort or percentage, then widening stages to full release — behind a server-side feature flag or kill switch that can disable the AI layer for all users, one cohort, or one insertion point without a deploy and without downtime. Each stage has, written before the stage starts: its entry criteria (eval pass per AI-207, cost within budget per AI-210, fallback verified per AI-206), its observation window, its abort thresholds on error rate, fallback rate, task completion versus baseline, and support contacts, and the named person who can pull the switch. Existing paying or long-tenure cohorts are never the unannounced first stage.
10. **AI-210 — Cost is projected from real volume before rollout, then capped per stage.** Estimate the retrofit's spend from the existing product's measured traffic at each insertion point — requests per active user, average input size from real records, expected retry and regeneration rates — using ai-cost-control's metered method, and record the projection next to the feature budget before stage one. Each rollout stage carries its own spend ceiling: widening the cohort without re-checking projected versus actual unit cost is forbidden, because a cost that is safe at a small cohort can be a budget failure at full volume. Retrofit-specific waste — re-processing unchanged records, regenerating over stored proposals, eval and shadow traffic — is metered as its own line, not blended into user-facing usage.
11. **AI-211 — Shadow and pilot results are reported as what they are.** Any shadow mode (model runs, output not shown), internal pilot, or cohort result is labeled with its cohort, size, and period wherever its numbers appear. Shadow agreement with the existing flow is evidence about divergence, not about user value; a pilot's satisfaction or time-saved figure is never presented as the whole user base's result. Users in a cohort whose data is used for evaluation or training-adjacent purposes are covered by the notice in AI-205.
12. **AI-212 — Rollback and removal are rehearsed, and the end state is decided.** Before the first external stage, rehearse the rollback once in staging: flip the kill switch, confirm the non-AI path serves all tasks, confirm AI proposals created so far remain readable and do not corrupt canonical records, and confirm no deploy or migration is needed. The retrofit plan also names its end state with a decision date: graduate (AI becomes a normal feature under the standing AI skills, and the extra retrofit gates retire), extend the pilot, or remove the AI layer and delete or retain its stored proposals under a stated data decision. A retrofit left indefinitely in "pilot" with no decision date is unfinished work, not a launch.

## BAN list

- **BAN-AI-101 — Big-bang replacement of a working flow.** Banned: shipping the AI version to all users at once, or replacing the existing flow so the old path no longer exists, with no flag, cohort, or rehearsed way back. Defeats: DET-INF-017. Bad: the support inbox's manual triage queue is replaced overnight by AI auto-triage for every customer; a bad prompt version misroutes tickets for a day and there is no switch to restore manual triage. Instead: keep the non-AI path intact, gate the AI layer behind a server-side kill switch, and stage the rollout with abort thresholds (AI-202, AI-209, AI-212). Severity: BLOCK.
- **BAN-AI-102 — Fake fallback presented as AI or as success.** Banned: when the model is unavailable, over budget, or fails validation, serving a template, cached, or canned answer presented as a live AI result, or showing a success state for work the AI did not do. Defeats: DET-FAKE-009. Bad: during a provider outage the "AI draft" button returns one of four stock paragraphs with a "Draft ready" toast, and users send them believing the drafts were written from their case notes. Instead: show the honest unavailable state and hand the user the working non-AI path with their input intact (AI-206); any disclosed non-AI fallback is labeled as such. Severity: BLOCK.
- **BAN-AI-103 — Model output written over canonical records unseen.** Banned: a model run that directly overwrites, deletes, merges, or sends from existing user records with no proposal state, no provenance, and no human or existing-flow confirmation. Defeats: DET-NONE — no DET parameter names this signal; governed by AI-204, AI-208. Bad: a nightly "AI cleanup" rewrites customer addresses and merges duplicate accounts in place; wrong merges are discovered weeks later and the original records no longer exist anywhere. Instead: write AI results as provenance-marked proposals and apply them only through the existing validated write path (AI-204), with bulk changes as separate auditable jobs (AI-208). Severity: BLOCK.
- **BAN-AI-104 — Silent behavior change for existing users.** Banned: changing an existing default, ranking, template, or workflow step to AI-driven behavior for current users with no in-product notice, no opt-in or cohort record, and no way back to the prior behavior. Defeats: DET-NONE — no DET parameter names this signal; governed by AI-205, AI-209. Bad: search results in a mature product are quietly re-ranked by a model; users' saved, learned workflows stop finding known records, support is told "nothing changed," and there is no setting or flag that restores the old ordering. Instead: announce the change in the surface, stage it per AI-209, and keep the prior behavior reachable until the AI-212 end-state decision. Severity: BLOCK.
- **BAN-AI-105 — Pilot numbers presented as product-wide proof.** Banned: reporting a small, internal, shadow, or opt-in cohort's quality, satisfaction, or cost figures as the live product's results, without cohort, size, and period. Defeats: DET-CON-011. Bad: a release note claims "AI summaries save users 30% of reading time" from eleven internal users on curated documents, while the real corpus — scanned, multi-language, decades old — was never evaluated. Instead: label every figure with its cohort and period, and evaluate on the product's real data before claiming product-wide effect (AI-207, AI-211). Severity: BLOCK.

## Gates

- **G-AI-101 — Baseline and non-AI regression gate.** Verifies: AI-201, AI-202. Check: open the retrofit record and confirm the pre-AI baseline metrics and the fixed real-task sample are stored with dates; then run the existing product's regression suite with the AI flag off and with the provider stubbed to fail, and confirm every pre-existing core task still completes. Pass: baseline exists and the flag-off suite is fully green. Fail: block the first external rollout stage. Recorded in: progress.md.
- **G-AI-102 — Real-data eval gate.** Verifies: AI-207, AI-208. Check (automated plus manual): run the feature's ai-evaluation runner on the golden set built from sampled real product data, including the legacy and unprocessable-record categories; confirm the data profile (completeness, format drift, unprocessable share) is attached, and confirm every unprocessable fixture routes to the non-AI path or a visible unprocessed state. Pass: overall and per-category floors recorded in advance are met, AI-assisted results meet or beat the AI-201 baseline on the comparison tasks, and zero unprocessable records are silently dropped. Fail: block rollout widening. Recorded in: progress.md.
- **G-AI-103 — Fallback and failure-drill gate.** Verifies: AI-206. Check (manual, in staging): at each insertion point, force each failure in turn — provider timeout, refusal, schema-invalid output, exhausted quota/budget — and complete the underlying task as a user. Pass: every failure shows the plain unavailable/not-used state, work already entered survives, the non-AI path completes the task, and no canned output is presented as AI. Fail: block shipment. Recorded in: progress.md.
- **G-AI-104 — Kill-switch and rollback rehearsal gate.** Verifies: AI-209, AI-212. Check (manual, in staging): with AI proposals already created, flip the kill switch for one insertion point and then for the whole AI layer; time the change taking effect with no deploy. Pass: the AI layer disappears within the recorded target time, the non-AI path serves all tasks, prior proposals remain readable, canonical records are unchanged, and re-enabling restores the AI surface cleanly. Fail: block the first external stage — an unrehearsed rollback does not count as a rollback. Recorded in: progress.md.
- **G-AI-105 — Stage-advance and cost gate.** Verifies: AI-209, AI-210, AI-211. Check (manual, at every stage boundary): read the stage report — cohort and period, error and fallback rates, task completion versus baseline, support contacts, actual spend and unit cost versus the stage projection and ceiling — and confirm the abort thresholds written before the stage were not crossed. Pass: all measures within thresholds and the next stage's criteria and ceiling are recorded before widening. Fail: hold or roll back the stage; do not widen on a verbal summary. Recorded in: progress.md.

## Anti-patterns

- **Demo-data confidence.** The retrofit is judged on the vendor demo, a handful of clean sample records, or the founder's own account, while the real corpus is older, messier, and larger. Catch it by asking which production records the eval set was sampled from (AI-207); no sampling story means no evidence.
- **Insertion-point sprawl.** AI badges appear on every screen in one release — a summary here, a rewrite there, a chatbot in the corner — so no surface has a measured baseline, a designed fallback, or an owner. Catch it by counting insertion points against the AI-203 inventory: anything shipping that is not in the inventory has skipped its scoring.
- **The permanent beta banner.** The feature lives for months behind a "beta" label that is used to excuse wrong outputs, missing fallback, and unmeasured cost, while being marketed as launched. Catch it against AI-212: no decision date and no end state means the retrofit never finished, whatever the banner says.
- **Regeneration churn as engagement.** Users regenerate repeatedly because first outputs are weak, and the team reads the click volume as adoption while cost per successful task climbs. Catch it in the AI-210 metering: report cost and success per completed task, not per generation, and treat a rising regeneration rate as a quality signal, not a usage win.
- **Training on the users who trusted you first.** Early cohorts' inputs quietly become prompt examples or eval goldens with no notice and no way to opt out, discovered later through a support question nobody can answer. Catch it by tracing one cohort input end to end — storage, logs, eval sets — against the AI-205 notice that cohort actually saw.

## Recall anchors

- The old flow is the fallback, the baseline, and the control group — keep all three alive.
- AI proposes; the product's existing write path disposes.
- Evaluate on the data you actually have, including the records nobody is proud of.
- No stage widens without its abort thresholds, cost ceiling, and a rehearsed way back.
- A pilot's numbers belong to the pilot — label the cohort or do not quote them.

## Checklist

- [ ] Pre-AI baseline metrics and the fixed real-task sample are recorded before AI code ships (AI-201, G-AI-101).
- [ ] The non-AI path is intact, reachable with the flag off, and green in regression with the provider failing (AI-202, G-AI-101).
- [ ] Every insertion point is in the scored inventory, human-reviewed and reversible points first (AI-203).
- [ ] AI output is stored as provenance-marked proposals and reaches canonical records only through the existing validated write path (AI-204).
- [ ] In-product AI notice is live, existing defaults and settings are unchanged without opt-in or a staged record, and provider data-sharing is covered by the product's terms and privacy notice (AI-205).
- [ ] Every failure mode at every insertion point has a designed fallback that preserves user work and completes via the non-AI path; the failure drill passes (AI-206, G-AI-103).
- [ ] The golden set is sampled from real product data including legacy and unprocessable records, and the real-data eval gate passes against the baseline (AI-207, AI-208, G-AI-102).
- [ ] Rollout stages — shadow before internal users wherever the insertion point permits — cohorts, abort thresholds, stage owners, and per-stage cost ceilings are written before stage one, and spend is projected from measured existing traffic (AI-209, AI-210).
- [ ] Shadow and pilot figures are labeled with cohort, size, and period wherever they appear (AI-211).
- [ ] The kill-switch rollback has been rehearsed in staging, and the graduate / extend / remove decision has a named date (AI-212, G-AI-104).
