# rebrand-execution

## Metadata

- **Owner department:** D16 Cloning & Replication (CL)
- **Skill version:** 1.0.0
- **Last verified:** 2026-11-21
- **Sources:** Google Search Central, site moves and redirects — https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes ; Google Search Central, Organization structured data (logo and name fields) — https://developers.google.com/search/docs/appearance/structured-data/organization ; WCAG 2.2 (contrast criteria 1.4.3, 1.4.11; name/role/value 4.1.2) — https://www.w3.org/TR/WCAG22/ ; Design Tokens Specification 2025.10 — https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/
- **Depends on:** design-system, inclusive-copy, technical-seo, social-open-graph, structured-data, sitemaps
- **Feeds into:** fidelity-verification, web-analytics

## When to use / Do NOT use

- **Use when:** an existing, live product is changing identity — product or company name, logo, color palette, typography, voice, or public copy — while its function, routes, and search equity must survive. This skill owns the execution discipline: the pre-swap inventory of every identity surface, the systematic swap, and the post-swap verification that nothing functional, legal, or search-related broke.
- **Do NOT use when:** designing the new identity itself (design-system owns tokens, components, and visual language; this skill consumes its finished token set and logo assets), judging whether copy is plain, inclusive, or translatable (inclusive-copy — this skill only schedules and verifies the replacement of copy, it does not set the wording standard), fixing a crawl, canonical, or redirect defect unrelated to an identity change (technical-seo owns the crawl-and-index contract; this skill invokes its checks as gates), building a clone of someone else's product (the other CL skills), or renaming with a domain or URL-structure change as the primary project (that is a site migration under seo-migration, executed with technical-seo's checks as its instruments — run this skill only for the identity surfaces inside it).
- **Boundary with clone-redesign:** building a product whose function is cloned and whose brand is created original in the same build is clone-redesign; this skill starts from a product that already exists. A redesign that keeps the existing brand runs clone-redesign for function, design, and copy with the brand surfaces inventoried here and marked `keep`; changing the identity of a live clone — one built by clone-redesign or by any other path — is this skill's work, with the clone as the existing, live product.

## Rules

1. **CL-701 — The rebrand starts from a signed identity decision record.** Before any surface changes, a dated record names: the old and new name (exact spelling, capitalization, and spacing), the new logo files, the new token set handed over from design-system, the approved voice/copy source, the launch date, and the surfaces explicitly out of scope. Work that starts from a chat message, a mood board, or a logo file alone has no authority to change a live product.
2. **CL-702 — Every identity surface is inventoried before the first swap.** The inventory is a written list, built by crawling the product and its repositories, covering at minimum: header/footer and navigation, favicons and app icons, the web-app manifest name and short name, the sender name shown on push notifications and installed-app surfaces, Open Graph and social-card images, structured data (`Organization` name and logo), page titles and meta descriptions, sitemap and robots references to the old name or host, email templates, sender names, and the sending domain (whose authentication records are re-proven under transactional-email and domains-dns when the domain itself changes), transactional and system messages, in-app strings and message catalogs in every locale, error and empty-state copy, legal pages (terms, privacy, imprint, copyright footer), PDF and downloadable assets, app-store listings, social profiles and handles, package and repository names where user-visible, support and help-center branding, and third-party integrations that display the name or logo (payment pages and the statement descriptor customers see on their card statements, OAuth consent screens, embedded widgets). A surface not on the inventory is assumed missed, not assumed unaffected.
3. **CL-703 — The inventory records old value, new value, and owner per surface.** Each inventory row states where the old identity lives (file, template, catalog key, CMS field, or third-party console), the exact replacement value, and who makes the change. Rows whose new value is not yet decided are marked `blocked` and block the swap schedule for that surface — they are never filled in by guesswork at swap time.
4. **CL-704 — URLs, routes, and identifiers do not change for identity alone.** A rebrand changes presentation, not addressing: existing paths, slugs, deep links, API identifiers, anchor IDs, and analytics property IDs stay byte-identical unless a separate, approved migration plan under technical-seo covers them. If the name appears inside a URL, that URL is listed in the inventory as `keep` or as an explicit migration item — never renamed as a side effect of a find-and-replace.
5. **CL-705 — The swap is token- and catalog-driven, never hand-edited per page.** Colors, typography, and logo references change in the design tokens and shared components (per design-system), and name and voice strings change in the message catalogs and shared templates. A value that must be edited in more than one place is first centralized, then changed once. Per-page hand edits are drift by construction and are reverted to the centralized source.
6. **CL-706 — The old name survives only where the record says so.** After the swap, the old name and old logo may remain only in places the decision record explicitly preserves: legal entity names in terms, privacy, contracts, and copyright lines where the registered entity has not changed; historical content (old blog posts, changelogs, press) left as an archive; and redirect or alias configurations kept for continuity. Every surviving instance found after launch maps to one of these recorded exceptions; an unmapped instance is a defect.
7. **CL-707 — Legal identity is checked separately from brand identity.** The brand name and the legal entity name are different facts. Before launch, a named reviewer confirms for each legal surface whether the registered entity, trading name, tax or registration details, and copyright holder actually changed. Brand copy is never copied into a legal surface, and a legal name is never "rebranded" by substitution.
8. **CL-708 — Search surfaces are swapped as data, not as decoration.** Page titles, meta descriptions, Open Graph and Twitter card fields, canonical URLs, sitemap entries, and structured data are updated from the inventory as structured fields and re-validated with the owning skills' checks (technical-seo, social-open-graph, structured-data, sitemaps). The Organization structured-data `name` and `logo` must match the visible brand and the logo file actually served at the declared URL; a logo URL that still serves the old mark is a failed swap, however new the page looks.
9. **CL-709 — The new palette and type pass accessibility checks before launch, not after.** New color pairs and new typography are verified against WCAG 2.2 contrast criteria (1.4.3, 1.4.11) and the design-system contrast gate on the real components that carry them — buttons, links, badges, charts, disabled and error states — before the swap ships. A brand color that cannot be used accessibly gets a documented accessible variant in the token set; body text is never shipped in a failing pair to preserve the palette.
10. **CL-710 — Voice and copy changes follow inclusive-copy, in every locale.** Replacement copy is written and reviewed under inclusive-copy (one glossary term per concept, plain language, no idiom carrying meaning), the new product name is added to the project glossary with its do-not-use variants (old name, wrong capitalization, abbreviations), and every shipped locale is inventoried and swapped — a rebrand that ships in the source locale while other locales still carry the old name and old voice is a partial rebrand and is reported as such, never as launched.
11. **CL-711 — Functional behavior is frozen during the swap window.** The rebrand change set contains identity changes only: no feature work, no flow restructuring, no dependency upgrades ride along. If a functional change is genuinely inseparable from an identity surface, it is split out, named in the inventory, and tested on its own. This freeze is what makes the post-swap regression check (G-CL-704) interpretable.
12. **CL-712 — The swap is rehearsed on staging and launched as one release.** The full inventory is executed once on staging and verified there before production is touched. Production launch is a single release containing the whole in-scope inventory — not a drip of surfaces over days — so that at no point does the live product present two identities as its current state. Deliberately phased rollouts (for example per-locale) are recorded as phases in the decision record, each phase complete in itself.
13. **CL-713 — A rollback keeps the old identity restorable for the launch window.** The pre-swap token set, logo files, catalogs, and templates are preserved as a versioned artifact until the post-launch verification window in the decision record closes. Rollback restores that artifact; nobody reconstructs the old identity from memory, screenshots, or a design file.
14. **CL-714 — Post-launch monitoring compares against the pre-rebrand baseline.** Before launch, baseline snapshots are recorded for the surfaces a rebrand can silently damage: top landing pages' titles and indexation status, sitemap validity, structured-data validity, 404 and redirect behavior on the highest-traffic URLs, and primary-flow completion. After launch these are re-checked against the baseline (G-CL-705); a difference is investigated as a rebrand defect until shown otherwise, not attributed to "normal fluctuation" without evidence.
15. **CL-715 — Third-party surfaces are verified in the third party's own console.** Every integration on the inventory that displays the name or logo — payment provider pages and statement descriptors, OAuth consent screens, app-store listings, social profiles, embedded chat or support widgets — is opened and checked where it actually renders after the change. A change made in the product's own codebase is not evidence that a third-party surface changed.
16. **CL-716 — The rebrand closes with a residue report.** At the end of the verification window, the inventory is re-run as an audit: each row is marked `swapped`, `kept by exception` (naming the CL-706 exception), or `missed`. The report, the surviving-old-name exceptions, and any missed surfaces with their fix dates are recorded in progress.md. A rebrand with no residue report is not closed, however clean the launch looked.

## BAN list

- **BAN-CL-701 — Global find-and-replace of the old name.** Banned: renaming by running a text substitution for the old name across the codebase, CMS, or catalogs. Defeats: DET-CON-017. Bad: a repository-wide replace turns "Acme" into "Northwind" inside a legal entity name, a URL slug, a historical changelog, and an integration key — four breakages from one command. Instead: swap per inventory row (CL-702, CL-703), where each surface's context decides whether and how it changes, and legal and URL surfaces are decided under CL-704 and CL-707. Severity: BLOCK.
- **BAN-CL-702 — Renaming URLs to match the new name.** Banned: changing paths, slugs, or deep links because they contain the old name or "look off-brand", without an approved migration plan and redirects. Defeats: DET-NONE — no DET parameter names this signal; governed by CL-704 and the redirect rules of technical-seo. Bad: `/acme-pricing` becomes `/northwind-pricing` at launch with no redirect; inbound links, bookmarks, and indexed URLs all land on a 404. Instead: keep the URL (CL-704), or move it only inside a technical-seo migration with one-hop permanent redirects verified by G-CL-703. Severity: BLOCK.
- **BAN-CL-703 — The visual-only swap.** Banned: declaring the rebrand done when the visible pages look new, without swapping the data surfaces — structured data, meta and OG fields, favicons, email templates, and third-party consoles. Defeats: DET-CON-023. Bad: the site renders the new logo while `og:image` still shows the old mark, the Organization schema still names the old company, and invoices still arrive from the old sender name. Instead: the inventory (CL-702) treats data and third-party surfaces as first-class rows, and G-CL-702 and G-CL-705 verify them independently of how the pages look. Severity: BLOCK.
- **BAN-CL-704 — Shipping the new palette unchecked.** Banned: launching new brand colors or type on live components without a contrast pass on the real foreground/background pairs. Defeats: DET-VIS-022. Bad: the new pale-mint primary button ships with white label text that fails contrast on every call to action, discovered from a user complaint a week later. Instead: run the accessibility pass of CL-709 before launch and record an accessible token variant for any failing pair. Severity: BLOCK.
- **BAN-CL-705 — Mixed-identity launch.** Banned: shipping the rebrand surface-by-surface over days so the live product simultaneously presents the old and new names or logos as current. Defeats: DET-CON-015. Bad: the marketing pages launch Monday, the app still shows the old logo until Thursday, and the help center is never scheduled — users screenshotting the mismatch conclude the product was acquired or compromised. Instead: rehearse on staging and launch the whole inventory as one release (CL-712); genuine phases are recorded in advance, each complete in itself. Severity: BLOCK.
- **BAN-CL-706 — Invented continuity copy.** Banned: publishing launch copy that fabricates the rebrand's history or reception — invented reasons presented as documented facts, fake customer reactions, or a founding story rewritten to pretend the new name was always the name. Defeats: DET-CON-014. Bad: the announcement claims "our customers asked us to rename" with no such record, and the About page is edited so the company appears to have launched under the new name. Instead: announcement copy states only the documented reason from the decision record (CL-701), and historical content stays historical under the CL-706 exceptions. Severity: BLOCK.
- **BAN-CL-707 — Deleting the old identity at launch.** Banned: removing the old tokens, logo files, catalogs, or templates from version control or storage as part of the launch, leaving nothing to roll back to. Defeats: DET-NONE — no DET parameter names this signal; governed by CL-713. Bad: on launch day the old logo files are deleted as "cleanup"; when the app-store listing rejects the new icon, there is no approved old asset to restore. Instead: preserve the pre-swap identity as a versioned artifact until the verification window closes (CL-713). Severity: BLOCK.

## Gates

- **G-CL-701 — Inventory completeness gate.** Verifies: CL-702, CL-703, CL-710. Check (automated + manual): crawl the staging product and grep all repositories, message catalogs (every locale), templates, and CMS exports for the old name and old logo file names; diff the hit list against the inventory. Every hit must correspond to an inventory row with old value, new value or `blocked`/`keep` status, and an owner. Pass: zero unlisted hits and zero `blocked` rows. Fail: block the swap; the inventory is extended and the crawl re-run. Recorded in: progress.md.
- **G-CL-702 — Residue scan.** Verifies: CL-706, CL-708, CL-715. Check (automated): after the staging swap, re-run the G-CL-701 grep over code, catalogs, rendered page HTML (including `<title>`, meta, OG/Twitter fields, and JSON-LD), sitemap, email templates, and downloadable assets; fetch the declared Organization logo URL and the favicon and confirm they serve the new mark. Pass: every remaining old-name or old-logo hit maps to a recorded CL-706 exception, and all fetched assets are the new identity. Fail: block launch; unmapped residue is swapped or formally excepted. Recorded in: progress.md.
- **G-CL-703 — URL and search-integrity gate.** Verifies: CL-704, CL-708, CL-714. Check (automated): diff the production URL set (from the sitemap and a crawl) before and after launch; assert every pre-launch URL still returns its pre-launch status or a single-hop permanent redirect to an approved migration target; re-run the technical-seo indexability checks and the structured-data and sitemaps validations on the top landing pages. Pass: zero unintended URL changes, zero new 404s or redirect chains, canonicals, sitemap, and structured data valid and carrying the new identity. Fail: block or roll back under CL-713; URL losses are fixed before any other rebrand work continues. Recorded in: progress.md.
- **G-CL-704 — Functional regression gate.** Verifies: CL-711. Check (automated): run the product's existing critical-flow test suite (or, where none exists, a scripted click-through of the primary flows: sign-up, sign-in, core task, checkout or equivalent, password reset) against staging before and after the swap, with identical test data. Pass: identical results; the only diffs are identity strings and assets named in the inventory. Fail: block launch; a behavior diff in a change set that was supposed to be identity-only is treated as an inseparable functional change and split out under CL-711. Recorded in: progress.md.
- **G-CL-705 — Post-launch verification and closure gate.** Verifies: CL-709, CL-714, CL-715, CL-716. Check (manual + automated): within the verification window in the decision record, (a) open every third-party surface on the inventory in its own console or live rendering, (b) re-check the CL-714 baseline (titles, indexation, sitemap, structured data, top-URL status codes), (c) confirm the design-system contrast gate result for the new token pairs is on record, and (d) file the residue report. Pass: all four done, baseline differences explained or fixed, residue report complete. Fail: the rebrand stays open in progress.md with named owners and dates; it is not reported as complete. Recorded in: progress.md.

## Anti-patterns

- **The logo swap that calls itself a rebrand.** Only the header logo and hero colors changed; the name in emails, schema, store listings, and legal footers is untouched. Catch it by comparing the launch diff against the inventory rows, not against the homepage screenshot — if most rows never appear in the diff, the rebrand is a logo swap.
- **Announcement-first scheduling.** The launch post and social announcement are dated before the inventory exists, so the swap is reverse-engineered under deadline pressure and surfaces get skipped silently. Catch it: no external announcement date is committed until G-CL-701 passes.
- **Two glossaries.** Marketing's launch copy uses one name form ("Northwind AI") while the product, glossary, and legal pages use another ("Northwind"), and both ship. Catch it by checking every launch artifact against the single glossary entry of CL-710, including capitalization.
- **Cleanup enthusiasm.** Redirects for the old domain, old asset files, and old-name aliases are "tidied away" in the weeks after launch, breaking the continuity they existed to provide. Catch it: continuity configurations are inventory rows with `keep` status; removing one requires the same decision record process as the rebrand itself.
- **Screenshot verification.** The post-launch check consists of looking at the homepage and the pricing page. Catch it: G-CL-702 and G-CL-705 exist because the surfaces a rebrand breaks — schema, OG cards, favicons, sender names — are precisely the ones no screenshot shows.

## Recall anchors

- Inventory first: a surface not on the list is a surface that will be missed.
- Identity changes presentation, never addressing — URLs stay unless a migration says otherwise.
- Brand name and legal name are different facts; check them separately.
- Launch whole, verify the invisible surfaces, close with a residue report.
- Keep the old identity restorable until verification closes.

## Checklist

- [ ] A dated decision record names old/new identity, scope, out-of-scope surfaces, and launch date (CL-701).
- [ ] The surface inventory covers rendered, data, catalog, legal, downloadable, and third-party surfaces in every locale, each row with old value, new value, and owner (CL-702, CL-703, G-CL-701).
- [ ] No URL, slug, identifier, or analytics property changed for identity alone; any exception is an approved migration item (CL-704, G-CL-703).
- [ ] The swap was made in tokens, shared components, and catalogs — not hand-edited per page (CL-705).
- [ ] Legal surfaces were confirmed by a named reviewer separately from brand copy (CL-707).
- [ ] Titles, meta, OG fields, sitemap, and Organization structured data carry the new identity and validate (CL-708, G-CL-702).
- [ ] New palette and type passed contrast checks on real components before launch (CL-709).
- [ ] New name is in the glossary with do-not-use variants; all locales swapped or the launch is reported as partial (CL-710).
- [ ] The change set contains identity changes only; functional diffs were split out (CL-711, G-CL-704).
- [ ] Staging rehearsal passed and production launched as one release or as recorded complete phases (CL-712).
- [ ] The pre-swap identity artifact is preserved until the verification window closes (CL-713).
- [ ] Post-launch baseline comparison, third-party checks, and residue report are filed; the rebrand is closed only then (CL-714, CL-715, CL-716, G-CL-705).
