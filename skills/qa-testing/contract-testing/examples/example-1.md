# Example 1 — The contract that broke on a harmless field

## Before

The consumer's pact is generated by snapshotting the provider's full order response. The consumer reads only `id`, `total`, and `status`, but the pact asserts all 23 returned fields literally:

```json
{
  "id": 441, "total": 59.99, "status": "paid",
  "customerName": "A. Example", "customerEmail": "a@example.com",
  "warehouse": "LHE-2", "pickerNotes": "aisle 7", "legacyCode": "X-991"
  // …15 more fields the consumer never reads, all asserted as literals
}
```

The provider adds a harmless `estimatedDelivery` field. Provider verification goes red, the team overrides the gate "because the contract always cries wolf," and a month later a real retype of `total` slips through under the same override habit.

## After

The pact records only the interaction the consumer depends on, with type matchers instead of literal copies:

```json
{
  "id": { "match": "integer", "example": 441 },
  "total": { "match": "number", "example": 59.99 },
  "status": { "match": "string", "example": "paid" }
}
```

Adding `estimatedDelivery` now passes verification untouched; retyping `total` to a string fails it — which is the only signal the contract exists to send.

Note: corrects QA-161 (consumer scope only) and QA-162 (additions pass, breakages fail).
