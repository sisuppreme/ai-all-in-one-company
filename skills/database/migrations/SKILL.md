## When to use / Do NOT use

- **Use when:** changing any database schema in any environment — adding or dropping tables, columns, constraints, or indexes — and when reviewing how a schema change will deploy and roll back.
- **Do NOT use when:** designing the target schema itself (use schema-design), moving data between systems (use etl-pipelines / data-ingestion), or changing only seed/reference content (use seed-data).

## Rules

1. **DB-121 — Versioned files, tracked application.** Every schema change is a versioned, ordered migration file in the repository. A runner applies them in order and records applied versions in a tracking table, so every environment converges to the same schema by construction.
2. **DB-122 — Applied migrations are immutable.** A migration that has run anywhere is never edited. A correction, however small, is a new migration. History that can be rewritten cannot be trusted.
3. **DB-123 — Reversible, or honestly irreversible.** Every migration is reversible (auto-reversed `change`-style or an explicit up/down pair). Where reversal is genuinely impossible, the migration says so in its header and names the recovery procedure that replaces rollback.
4. **DB-124 — Expand and contract.** Risky changes (renames, type changes, splits) run across deploys: add the new shape, backfill, dual-write or switch reads, then drop the old shape in a later deploy. No single deploy both changes the shape and depends on the new shape.
5. **DB-125 — Backfills are jobs, not migrations.** Data backfills on large tables run as separate, resumable, batched jobs. A schema migration never carries a full-table data rewrite.
6. **DB-126 — Concurrent index builds.** Indexes on large production tables are built with `CREATE INDEX CONCURRENTLY` (or the engine equivalent), outside a transaction block where the engine requires it.
7. **DB-127 — Know your engine's DDL transactions.** Migrations use transactional DDL where the engine supports it (PostgreSQL does; MySQL largely does not). On engines without it, each migration is written so a mid-migration failure leaves a state a re-run can finish.
8. **DB-128 — The full set runs from empty in CI.** Every change runs the complete migration set against an empty database in CI. A migration that fails from empty fails the build, however well it worked on the author's machine.
9. **DB-129 — The schema file is generated.** The committed schema file/structure dump is regenerated by the migration run. It is never hand-edited; a diff between the dump and a fresh run's output is a defect (see G-DB-061).
10. **DB-130 — Down is tested, not assumed.** CI tests rollback as well as roll-forward: apply all migrations, roll back the latest, re-apply it. An untested down path is an untested promise (subject to DB-123's documented exceptions).

## BAN list

- **BAN-DB-061 — Console cowboy DDL.** Banned: applying schema changes to production by hand in a SQL console or GUI, outside the migration runner. Defeats: DET-INF-018. Bad: during an outage someone runs `ALTER TABLE orders ADD COLUMN discount numeric` in a console; the fix works, no file records it, and the next deploy's migration fails against a schema nobody recognizes. Instead: write the migration, let the runner apply it, and let the tracking table be the record. Severity: BLOCK.
- **BAN-DB-062 — Editing an applied migration.** Banned: modifying a migration file after it has been applied in any environment, to "fix" it in place. Defeats: DET-INF-018. Bad: a developer corrects last week's migration; environments that already ran the original keep the old shape, new environments get the new one, and the tracking tables all claim the same version. Instead: leave the applied file untouched and ship a corrective migration (DB-122). Severity: BLOCK.
- **BAN-DB-063 — ORM auto-sync in production.** Banned: enabling schema auto-synchronization (`synchronize: true` and equivalents) against a production database, letting the ORM diff and alter the live schema at boot. Defeats: DET-CODE-020. Bad: a renamed model field boots in production, the ORM drops the "unknown" column and its data, and creates an empty one with the new name. Instead: auto-sync stays off outside disposable development databases; production changes are migrations only. Severity: BLOCK.
- **BAN-DB-064 — The in-migration backfill.** Banned: rewriting or backfilling a large table inside the schema migration that deploys with the release. Defeats: DET-CODE-033. Bad: the deploy migration runs `UPDATE sessions SET ...` over 40 million rows, holds its lock for the entire deploy window, and the release times out half-applied. Instead: ship the schema change, then run the backfill as a separate resumable batched job (DB-125). Severity: WARN.
- **BAN-DB-065 — The hand-edited schema dump.** Banned: editing the committed schema file/structure dump by hand so it matches a local database. Defeats: DET-INF-024. Bad: the dump now describes a schema no migration sequence produces; the declared state and the real state have drifted, and every future diff is noise. Instead: fix the migration, re-run, and commit the regenerated dump (DB-129). Severity: WARN.

## Gates

- **G-DB-061 — Reversibility and diff test.** Verifies: DB-121, DB-123, DB-129. Check: automated — CI runs all migrations from an empty database, diffs the resulting schema against the committed schema file, rolls back the last migration, and re-applies it cleanly. Pass: diff is empty and the rollback/re-apply cycle succeeds. Fail: block shipment. Recorded in: progress.md.
- **G-DB-062 — Immutability check.** Verifies: DB-122. Check: automated — CI diffs the change against the release tag and fails if any migration file older than the newest is modified. Pass: no applied migration touched. Fail: block shipment. Recorded in: progress.md.
- **G-DB-063 — From-empty build.** Verifies: DB-128. Check: automated — on every change, CI applies the complete migration set to a fresh empty database and runs the application's boot check. Pass: full set applies and the app boots. Fail: block shipment. Recorded in: progress.md.
- **G-DB-064 — Concurrent-index check.** Verifies: DB-126. Check: automated grep plus review — migration files that add an index to an existing table must use `CONCURRENTLY` (or carry the documented small-table exception); a plain `CREATE INDEX` on an existing table fails the check. Pass: zero findings. Fail: block shipment. Recorded in: progress.md.

## Anti-patterns

- **The mega-migration.** A month of schema changes lands in one file: unreviewable, unrollbackable, and guaranteed to conflict. Catch it: if the migration needs a table of contents, it should have been five migrations.
- **Down-migration theater.** Down methods exist but drop everything, do nothing, or have simply never been executed. Catch it: G-DB-061 runs them; a down path nobody has run is a rumor.
- **The deploy-day surprise.** The migration is written and merged but first executed against production-shaped data during the release itself. Catch it: DB-128's from-empty run plus one run against a production-sized snapshot in staging, before release day.
- **Environment archaeology.** Staging works because of a manual fix from March that exists in no file, and nobody remembers applying it. Catch it: rebuild the environment from migrations alone; whatever breaks was archaeology.

## Recall anchors

- Applied migrations are history: corrections are new migrations.
- Expand, backfill, switch, contract — never change and depend in one deploy.
- Backfills are resumable jobs, not migration steps.
- If CI cannot run it from empty, production should not run it at all.
- The schema dump is an output, never an input.

## Checklist

- [ ] The change is a versioned migration file; the runner and tracking table apply it (DB-121).
- [ ] No applied migration was edited (DB-122, G-DB-062).
- [ ] The migration is reversible, or declares itself irreversible with a named recovery procedure (DB-123).
- [ ] Renames/type changes follow expand-and-contract across deploys (DB-124).
- [ ] Any backfill is a separate resumable job, not part of the migration (DB-125).
- [ ] Indexes on large tables are built concurrently (DB-126, G-DB-064).
- [ ] From-empty CI run, schema diff, and rollback/re-apply all pass (DB-128, DB-130, G-DB-061, G-DB-063).
