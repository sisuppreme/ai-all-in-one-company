# c4-diagrams

## Metadata

- **Owner department:** D2 Architecture & System Design (AR)

- **Depends on:** system-design
- **Feeds into:** adr-writing, api-architecture

## When to use / Do NOT use

- **Use when:** architecture needs to be communicated or reviewed — a new system context or container view, a container whose internals are non-obvious, or a diagram that has drifted from the system it describes.
- **Do NOT use when:** there is no architecture decision to communicate yet (system-design comes first), or the audience needs the API surface rather than the structure (api-documentation). Do not produce a Level 3 component diagram for a container whose internals are a standard framework layout.

## Rules

1. **AR-021 — Produce only the levels the audience needs.** Level 1 (system context) and Level 2 (containers) are the default set. Level 3 (components) is drawn only where a container's internal structure is non-obvious. Level 4 (code) is generated by tools or omitted.
2. **AR-022 — Every element is typed.** Each element is declared as a person, software system, container, or component, and each container states its technology. An untyped box is incomplete.
3. **AR-023 — Every relationship is labeled.** Each line carries the interaction and its protocol or format ("Places orders via HTTPS/JSON"). An unlabeled line fails review.
4. **AR-024 — Stores and queues are containers.** Data stores and queues appear as first-class containers in Level 2, never as annotations, footnotes, or icons attached to another box.
5. **AR-025 — Diagrams live as code.** Diagram sources (Structurizr DSL, PlantUML, or Mermaid) are kept in the repo and reviewed like code, so they diff in pull requests. A pasted image with no source in the repo is not a diagram of record.
6. **AR-026 — One view per diagram, with a legend.** Each diagram serves one audience and one level, and carries a legend for its element types. Two audiences are never merged into one picture.
7. **AR-027 — No generic labels.** Element names name the actual thing ("Orders API", "PostgreSQL — orders store"). "Frontend / Backend / Database" as the whole model is an automatic fail.
8. **AR-028 — External systems show direction and mode.** Every external system is drawn with the direction of each integration and whether it is synchronous or asynchronous.
9. **AR-029 — Diagrams change with the architecture.** A diagram is updated in the same change that alters the architecture it depicts, and the ADR for that change links the updated diagram. A diagram known to be stale is a defect, not a backlog item.
10. **AR-030 — Context shows people and systems only.** The Level 1 diagram shows the system as one box, its users, and the external systems it touches — no internal containers leak into the context view.

## BAN list

- **BAN-AR-011 — The all-in-one mega-diagram.** Banned: one picture mixing context, containers, components, and code-level classes for every audience at once. Defeats: DET-CODE-016. Bad: a single wall-chart diagram with 60 boxes from "User" down to individual classes; every reader gives up and the diagram is never updated again. Instead: separate Level 1, 2, and (where earned) 3 diagrams, one view each, each with a legend (AR-021, AR-026). Severity: BLOCK.
- **BAN-AR-012 — Generic-label model.** Banned: a diagram whose elements are named only "Frontend", "Backend", "Database". Defeats: DET-CODE-008. Bad: the container diagram for a system that actually runs a web app, a worker, two stores, and a queue is three generic boxes. Instead: name each element for the real unit it represents, with its technology (AR-027). Severity: BLOCK.
- **BAN-AR-013 — The stale diagram.** Banned: leaving a diagram unchanged in a change that alters the architecture it depicts. Defeats: DET-INF-024. Bad: the payments container is replaced by a third-party checkout, the code ships, and the container diagram still shows the old in-house payments service for two releases. Instead: update the diagram source in the same pull request, and link it from the ADR (AR-029). Severity: BLOCK.
- **BAN-AR-014 — Image-only diagram.** Banned: a diagram that exists only as an exported PNG or a slide screenshot, with no source in the repo. Defeats: DET-CODE-031. Bad: the context diagram is a screenshot in a slide deck; nobody can diff it, review it, or update it without redrawing from scratch. Instead: commit the Structurizr/PlantUML/Mermaid source and let the image be a build artifact (AR-025). Severity: WARN.

## Gates

- **G-AR-011 — Diagram render check.** Verifies: AR-025. Check: automated — CI renders every diagram source with the pinned renderer (e.g., the project's locked Mermaid CLI or PlantUML jar) and fails on a non-zero exit; if the sandbox cannot run the renderer, the fallback is a manual render in the project's documented tool, recorded in progress.md. Pass: every source renders. Fail: block merge. Recorded in: progress.md.
- **G-AR-012 — Label lint.** Verifies: AR-023, AR-027. Check: automated — grep the diagram sources for elements named exactly "Frontend", "Backend", or "Database" and for relationship lines with empty labels. Pass: zero hits. Fail: block merge. Recorded in: progress.md.
- **G-AR-013 — Element-to-deployment diff.** Verifies: AR-024, AR-028, AR-029. Check: manual — each release, diff the container diagram element by element against the deployment config: every deployable, store, and queue appears, and every external system shows direction and sync/async mode. Pass: zero differences. Fail: block release. Recorded in: progress.md.

## Anti-patterns

- **Legend-free notation.** Boxes, cylinders, and dashed lines used with no legend, so each reader invents a meaning. Catch it: if you cannot point at the legend while explaining a line style, AR-026 was skipped.
- **The database as decoration.** A cylinder icon dangling off the application box, unnamed and untyped. Catch it: every store should be answerable to "which container, which technology, who writes to it" (AR-024).
- **Level inflation.** A Level 3 component diagram for a container that is a standard CRUD module, drawn to make the work look substantial. Catch it: ask what decision the diagram informs; if none, delete the level (AR-021).
- **Arrow soup.** So many unlabeled crossing lines that the flows cannot be followed. Catch it: pick any line and state its interaction and protocol aloud; if you cannot, the labels are missing, not implied (AR-023).

## Recall anchors

- Levels 1 and 2 by default; Level 3 only where it earns its keep.
- Typed elements, labeled lines, legend on every view.
- Stores and queues are containers, not decorations.
- Diagrams are code in the repo — they diff or they rot.
- Architecture changed? The diagram changes in the same pull request.

## Checklist

- [ ] Only the needed C4 levels exist, one view per diagram, each with a legend (AR-021, AR-026).
- [ ] Every element is typed and named for the real unit, with its technology (AR-022, AR-027).
- [ ] Every relationship line states the interaction and protocol (AR-023).
- [ ] Data stores and queues are first-class containers (AR-024).
- [ ] Diagram sources render cleanly in CI, or the manual fallback is recorded (G-AR-011).
- [ ] The release diff against the deployment config shows zero differences (G-AR-013).
- [ ] External systems show direction and sync/async mode (AR-028).
