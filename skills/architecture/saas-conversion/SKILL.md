## When to use / Do NOT use

- **Use when:** an application that is already running — with real users, real data, and an uptime obligation — must become multi-tenant SaaS: it was built for one client, one company, or one implicit organization, and now must serve many tenants from one deployment. This skill owns the conversion sequence and its live-system risks: inventorying the single-tenant assumptions baked into the running system, creating the legacy tenant, backfilling tenant ownership onto existing rows, retrofitting isolation and billing onto live traffic, and migrating existing users cohort by cohort without downtime. Use it from the conversion plan through the retirement of the last legacy code path.
- **Do NOT use when:** the product is a new build with no existing users or data — use multitenancy-saas, which owns the design-time tenancy model choice this skill consumes. Do NOT use it for the migration mechanics of any single schema change (expand-and-contract, reversibility, concurrent indexes — that is migrations in D5), for the database-level enforcement of isolation itself (row-level security, roles, transaction-local context — that is tenant-isolation in D5), or for the subscription lifecycle once billing exists (trials, renewals, cancellation, reconciliation — that is subscriptions in D11). This skill sequences and de-risks the conversion; it references those skills for the work inside each step instead of repeating them.

## Rules

1. **AR-261 — Conversion starts from an inventory, not from the schema.** Before any change, produce a written inventory of every place the single-tenant assumption lives: tables with no tenant key, globally unique constraints, global roles and admin paths, singleton settings and configuration rows, hardcoded organization names/IDs/domains in code and seed data, file-storage paths, cache keys, search indexes, background jobs, cron schedules, email templates, and third-party integrations registered for the one existing client. Every inventory item gets a named conversion treatment or an explicit "stays global, because" justification. A surface nobody inventoried is treated as unconverted until proven otherwise.
2. **AR-262 — The target model is an input, not a decision made here.** The conversion plan names the tenancy model chosen under multitenancy-saas (AR-182) and the isolation mechanism enforced under tenant-isolation, and records both in an ADR before conversion work starts. If no model has been chosen, stop and run multitenancy-saas first; converting toward an unchosen model guarantees a second conversion.
3. **AR-263 — The existing client becomes a real tenant, created first.** Before any new tenant can be provisioned, create the legacy tenant as an ordinary row in the tenant catalog through the same provisioning procedure new tenants will use (AR-188), and backfill its identity (name, domain, settings, integrations) from the values currently hardcoded or held in singleton rows. The running system must behave identically when it serves only this one tenant; any behavior change at this step is a defect in the conversion, not an improvement to sneak in.
4. **AR-264 — Tenant ownership is backfilled as data work, under migrations discipline.** Adding the tenant key and filling it follows migrations: the column ships nullable in an expand step, the backfill runs as a separate, resumable, batched job (never inside the schema migration), and the NOT NULL constraint plus tenant-leading index land only in a later contract step after the backfill is verified complete. On a live table, the backfill job is rate-limited and observable — rows done, rows remaining, error count — so it never becomes the incident it was meant to avoid.
5. **AR-265 — Every existing row gets a decided owner; orphans are reported, never swept.** Each row in a tenant-owned table is assigned to a tenant by a stated rule derived from the data (owning user, owning organization, creation context). Rows no rule can assign go to an orphan report reviewed by a human before cutover. Assigning unowned rows to the legacy tenant, to tenant 1, or to a default tenant "to make the count work" is forbidden (BAN-AR-133): a wrong owner is a cross-tenant leak with extra steps.
6. **AR-266 — Uniqueness is re-scoped, not dropped.** Every globally unique constraint on tenant-owned data (email, username, slug, external ID, invite code) is replaced by a composite unique constraint scoped to the tenant — e.g. `UNIQUE (tenant_id, email)` — in the same conversion step that makes the data multi-tenant. Before the replacement lands, run a collision check: values that are unique globally today stay valid, but the plan must state how two future tenants may each hold the same email/slug and how login, lookup, and password-reset resolve which tenant is meant when they do.
7. **AR-267 — Identity resolution changes before the second tenant exists.** Login, signup, invitation, and password-reset flows are converted to resolve the tenant first (from subdomain, invite, or an explicit tenant picker) and the user second, within that tenant. Existing users keep working throughout: their accounts are attached to the legacy tenant by the AR-265 backfill, and no existing user is required to re-register, reset a password, or lose a session as a side effect of the conversion itself (see BAN-AR-136).
8. **AR-268 — Isolation is retrofitted in shadow before it is enforced.** Tenant scoping ships in observe mode first: the new scoped path runs alongside the legacy path, compares results, and logs every divergence (rows the scoped path would hide, rows it would wrongly show) without changing what users see. Enforcement — the platform-level scoping and RLS of tenant-isolation — is switched on per surface only after that surface's divergence log is empty for an agreed observation window. A divergence is investigated as a conversion bug in the inventory or backfill, never dismissed as noise.
9. **AR-269 — Non-database surfaces are converted in the same pass.** File storage keys gain the tenant prefix and existing files are re-keyed or resolved through a mapping that is tested, not assumed; cache keys gain the tenant segment and the pre-conversion cache is invalidated at cutover rather than left to expire; search indexes are rebuilt per the new scoping or re-indexed with the tenant field before enforcement; scheduled and background jobs are converted to iterate tenants with context set per tenant (per tenant-isolation) instead of running once, globally, as they do today. A surface converted "later" is listed in the plan with its interim risk stated.
10. **AR-270 — Cutover is per cohort behind a flag, never a flag day.** Tenants are converted in cohorts — the legacy tenant first (it is the canary: it already works, so any breakage is the conversion's fault), then a small pilot cohort of new or low-risk tenants, then the rest — with each cohort gated by a conversion feature flag that can route that cohort back to the legacy path. The flag, its owner, and its retirement date are named in the plan before the first cohort moves. There is no single deploy after which everyone is multi-tenant (BAN-AR-131).
11. **AR-271 — Every cohort has a rehearsed way back.** Before a cohort converts, the rollback for that cohort is written down and rehearsed in staging: which flag flips back, which writes made under the new path remain valid under the old path (dual-write or a stated reconciliation), and what happens to data created during the converted window. A cohort whose writes cannot survive a rollback does not convert until they can. Rollback mechanics follow the rollback skill; this rule owns the requirement that they exist per cohort, before the cohort moves.
12. **AR-272 — Billing is retrofitted onto the tenant, not onto the user list.** The billable entity is the tenant. Existing users are mapped to provider customers and subscriptions under subscriptions — provider customer per tenant, subscription state mirrored from the provider, entitlement read from that mirror — and the mapping is built and reconciled in shadow while the legacy system still grants access exactly as before. Billing enforcement (paywalls, plan limits, dunning) is switched on per cohort only after G-AR-135 passes for that cohort — and only for a cohort whose isolation is already enforced, meaning G-AR-133 has burned down and G-AR-134 has passed for that same cohort: isolation before billing is an ordering this skill's gates enforce, not a preference the plan may reorder, because entitlement checks layered over unproven scoping wall tenants in or out of data that was never verified as theirs alone. The day billing code ships is never the day anyone's access changes.
13. **AR-273 — Existing customers are grandfathered explicitly.** The plan states, per existing customer or cohort, what they keep: their current price or a named migration price, their current limits, and the date and notice after which standard terms apply. Nobody who was using the product before the conversion is charged, downgraded, or limit-cut by the conversion itself; a price or plan change is a separate, communicated commercial decision, executed through subscriptions, not a side effect of a data migration. Silence in the plan means the existing terms continue.
14. **AR-274 — Dual-write windows are bounded and reconciled.** Where old and new shapes must both be written during conversion (per the expand-and-contract pattern in migrations), the plan names the window's start, its end condition, and the reconciliation job that compares the two shapes and reports drift. A dual-write with no end condition and no reconciliation is not a transition state; it is a second system of record being born.
15. **AR-275 — The legacy path is retired on a date, and its retirement is verified.** The plan names the date or trigger on which the legacy single-tenant path — the flag's old branch, unscoped queries, global-settings reads, the one-off integration registrations — is deleted, and a post-retirement check greps the codebase and the configuration for the inventoried legacy surfaces (AR-261) to confirm none still serve traffic. A legacy fallback left live "just in case" after retirement is a finding (BAN-AR-135), not a safety net.
16. **AR-276 — Conversion is observable per tenant from the first cohort.** Dashboards and logs can answer, per tenant: which path served this request (legacy or converted), backfill and reconciliation status, divergence count, and billing-mirror state. When the pilot cohort reports a problem, the team can tell within minutes whether non-converted tenants are affected; "convert and hope" with no per-tenant signal does not pass review.
17. **AR-277 — Third-party registrations are re-done per tenant, not assumed shared.** OAuth apps, webhook endpoints, SSO connections, API keys, and sending domains that were registered once for the single client are inventoried (AR-261) and either deliberately shared with the reason recorded, or re-registered per tenant through the provider's own flow. A webhook that still points at a legacy global handler, or an SSO connection only the legacy tenant can use, is a conversion defect discovered by the second tenant at the worst possible time if it is not discovered by the inventory.
18. **AR-278 — The conversion is not done until a second real tenant lives on it.** Conversion completes only when a tenant other than the legacy tenant has been provisioned by the standard procedure, has used the product, has been billed (or explicitly placed on a free plan) through the retrofitted billing, and has been exportable and deletable per the per-tenant operations of multitenancy-saas (AR-187). A system that has only ever served its legacy tenant under the new schema is converted on paper, not in fact.
19. **AR-279 — A confirmed cross-tenant exposure during conversion is a P0 incident, not a defect to schedule.** The moment any tenant's data is confirmed readable, writable, or exportable by another tenant on a converted path — through a query, job, export, file URL, cache entry, or billing surface — cohort progression halts: no new cohort converts and no further surface enforces until the hole is closed. The affected cohort is rolled back per AR-271 or fixed forward on the converted path (never routed onto the legacy path, per BAN-AR-135), the exposure is run as a security incident under incident-response with the disclosure path owned by D14, and conversion resumes only after the cross-tenant test suite (G-AR-091) passes again against the converted build and the exposure's root cause is traced to the AR-261 inventory item or backfill rule that missed it — the class is fixed, not just the instance. A shadow-mode divergence (AR-268) is not an exposure, because users still see legacy results; it becomes one the moment an enforced path serves the wrong tenant's rows.

## BAN list

- **BAN-AR-131 — The flag-day cutover.** Banned: converting the whole running system to multi-tenant in one deploy, maintenance window, or "quiet weekend," with all users on the new path at once. Defeats: DET-INF-017. Bad: a Saturday-night release adds `tenant_id`, backfills it, enables scoping, and turns on billing together; a missed join table leaks one client's projects to another, and there is no partial state to fall back to — the only way back is restoring Friday's backup and losing the weekend's data. Instead: cohort cutover behind a flag with a rehearsed per-cohort rollback (AR-270, AR-271). Severity: BLOCK.
- **BAN-AR-132 — The console backfill.** Banned: backfilling tenant ownership, re-keying files, or rewriting production data by hand-run SQL, console scripts, or one-off notebooks outside the versioned migration and job tooling. Defeats: DET-INF-018. Bad: an engineer runs `UPDATE documents SET tenant_id = 7 WHERE tenant_id IS NULL` from a console during the conversion; it works, no file records it, staging never had it run, and the next environment rebuilt from migrations diverges from production permanently. Instead: the backfill is a versioned, resumable, batched job under migrations discipline, run identically in every environment (AR-264). Severity: BLOCK.
- **BAN-AR-133 — The default-tenant sweep.** Banned: assigning rows whose owner is unknown to the legacy tenant, tenant 1, or any default tenant so the NOT NULL constraint can land. Defeats: DET-NONE — no DET parameter names this signal; governed by AR-265. Bad: 4,000 orphaned attachments are swept to the legacy tenant to finish the backfill; among them are a departed second client's files, which that client's former staff can now browse after the second tenant onboards. Instead: unassigned rows go to an orphan report, are decided by a human under a stated rule, and block the contract step until the report is empty (AR-265, G-AR-132). Severity: BLOCK.
- **BAN-AR-134 — Billing switched on before the mirror exists.** Banned: enabling paywalls, plan limits, or charges for existing users before each tenant's provider customer and subscription exist and are mirrored and reconciled under subscriptions. Defeats: DET-FAKE-006. Bad: the conversion release turns on plan enforcement against a local `plan` column copied from a spreadsheet; paying customers are walled off because their provider subscriptions were never created, while others keep full access free because no subscription object exists to charge. Instead: build the provider mapping in shadow, reconcile it, grandfather explicitly, and enforce per cohort only after G-AR-135 passes (AR-272, AR-273). Severity: BLOCK.
- **BAN-AR-135 — The immortal legacy fallback.** Banned: leaving the pre-conversion unscoped code path, global-settings read, or legacy flag branch serving traffic after the retirement date "as a safety net." Defeats: DET-CODE-020. Bad: six months after cutover, a support engineer flips a struggling tenant back to the legacy branch to fix a bug; the branch has no tenant scoping, and the tenant's dashboard briefly shows every tenant's data. Instead: retire the legacy path on the planned date and verify its removal by grep and configuration review (AR-275); a tenant in trouble is fixed on the converted path or rolled back per AR-271, never routed around isolation. Severity: BLOCK.
- **BAN-AR-136 — The mass logout migration.** Banned: converting identity or session storage in a way that invalidates every existing session, forces a global password reset, or requires re-registration as an accepted side effect of the conversion. Defeats: DET-UX-026. Bad: the release swaps the session table to add tenant context and drops the old one; every user is logged out mid-task, unsaved work is lost, and support spends the week on reset tickets from users who think they were hacked. Instead: attach existing accounts and sessions to the legacy tenant in place, carry sessions across with a dual-read of old and new session shapes during the cohort window, and expire the old shape naturally (AR-267). Severity: WARN.

## Gates

- **G-AR-131 — Inventory completeness check.** Verifies: AR-261, AR-269, AR-277. Check: manual plus automated — walk the AR-261 inventory against the live system: list every table, unique constraint, storage prefix, cache namespace, search index, scheduled job, and third-party registration from the actual schema and configuration, and diff against the inventory document. Pass: every discovered surface appears in the inventory with a treatment or a "stays global, because" justification; zero undiscovered surfaces. Fail: block conversion start; an incomplete inventory restarts the plan, not just the checklist. Recorded in: progress.md.
- **G-AR-132 — Backfill reconciliation.** Verifies: AR-264, AR-265, AR-266. Check: automated — after the backfill job reports done, run reconciliation queries: count of NULL tenant keys per tenant-owned table, the orphan report, per-tenant row counts before and after (totals must match the pre-conversion counts exactly), and a collision report on every re-scoped unique constraint. Pass: zero NULLs, zero orphans, totals reconcile, and every re-scoped constraint exists in composite form. Fail: block the contract step (NOT NULL, enforcement) for every table that does not reconcile. Recorded in: progress.md.
- **G-AR-133 — Shadow divergence burn-down.** Verifies: AR-268. Check: automated — during the observe-mode window, the scoped path's divergence log is reviewed per surface (API reads, exports, jobs, search, file access); each divergence is linked to a fixed inventory item, backfill correction, or scoping bug. Pass: zero open divergences on a surface for the agreed observation window before that surface's enforcement is enabled. Fail: block enforcement for that surface; other surfaces may proceed independently. Recorded in: progress.md.
- **G-AR-134 — Cohort cutover and rollback rehearsal.** Verifies: AR-270, AR-271. Check: automated plus manual — in staging, convert a copy of the legacy tenant plus one synthetic second tenant, exercise login, core workflows, export, and a background job for both, then execute the written rollback and confirm pre-conversion behavior and data created during the converted window are both intact. In production, the legacy tenant converts first and its error rate, latency, and divergence count are compared against its pre-conversion baseline for the observation window before any further cohort moves. Pass: rehearsal succeeds end to end and the legacy cohort's baseline holds. Fail: block the next cohort; fix on the converted path or roll the cohort back. Recorded in: progress.md.
- **G-AR-135 — Billing retrofit reconciliation.** Verifies: AR-272, AR-273. Check: automated — first confirm the ordering precondition: G-AR-133 and G-AR-134 have passed for this cohort, so its isolation is enforced before any entitlement is. Then, for each tenant in the cohort, diff the retrofitted billing state against ground truth: a provider customer exists for the tenant, the mirrored subscription state matches a live provider read (per subscriptions reconciliation), the entitlement the app grants matches the grandfathering terms recorded in the plan, and no charge was issued by the conversion itself. Pass: the ordering precondition holds, zero mismatches, and zero conversion-issued charges across the cohort. Fail: block billing enforcement for that cohort; access continues under legacy terms until the diff is clean. Recorded in: progress.md.
- **G-AR-136 — Second-tenant proof.** Verifies: AR-278, AR-275. Check: manual plus automated — provision a real second tenant by the standard procedure, run the cross-tenant test suite owned by multitenancy-saas (G-AR-091) and tenant-isolation against the converted system, verify the second tenant's billing state, export, and deletion, then grep code and configuration for the inventoried legacy surfaces. Pass: the second tenant lives entirely on converted paths, cross-tenant tests pass, and no legacy surface still serves traffic. Fail: the conversion is not declared complete, whatever the schema says. Recorded in: progress.md.

## Anti-patterns

- **Schema-first conversion.** The team adds `tenant_id` everywhere in week one and discovers in week six that login, file storage, the invoicing integration, and the founder's hardcoded admin account were the actual conversion. Catch it: if the plan's first artifact is a migration instead of the AR-261 inventory, the order is wrong.
- **The invisible second client.** The "single-tenant" app quietly serves a second client already — a white-label subdomain, a shared login, a spreadsheet of exceptions — and the conversion plan is written for one legacy tenant. Catch it: ask who else logs in, who else is billed, and whose logo appears anywhere; every answer is another legacy tenant to create under AR-263.
- **Grandfathering by vibes.** Everyone agrees existing customers "will be looked after," but no per-cohort terms are written down, so the billing retrofit applies list prices and limits by default. Catch it: pick one existing customer and state, from the plan alone, exactly what they pay and get the day after their cohort converts; if the plan cannot answer, AR-273 failed.
- **Converted but not converted.** The database is fully multi-tenant while emails still send from the old client's domain, exports still land in one shared bucket, and support still runs global queries — the surfaces nobody inventoried. Catch it: re-run G-AR-131 against the running system after cutover, not against the plan.
- **Pilot with no exit criteria.** The pilot cohort converts and "seems fine," so the rest follow on a date rather than on evidence. Catch it: the cohort advances on G-AR-134's baseline comparison and G-AR-133's divergence count, or it does not advance.

## Recall anchors

- Inventory first: the schema is the easy part of a conversion.
- The existing client becomes a real tenant — and the first canary.
- Orphans are reported and decided, never swept into a default tenant.
- Shadow, diverge, fix — then enforce, cohort by cohort; a leak on an enforced path is a P0 incident, never a scheduled bug.
- Billing enforces only after the mirror reconciles and grandfathering is written down.

## Checklist

- [ ] The AR-261 inventory covers data, identity, storage, cache, search, jobs, and integrations — and G-AR-131 found no undiscovered surface.
- [ ] The target model and isolation mechanism are recorded in an ADR from multitenancy-saas / tenant-isolation (AR-262).
- [ ] The legacy tenant exists as an ordinary catalog tenant and the system behaves identically serving it alone (AR-263).
- [ ] Backfill reconciliation passes: zero NULL tenant keys, zero orphans, totals match pre-conversion counts (G-AR-132).
- [ ] Uniqueness is re-scoped per tenant and identity flows resolve tenant before user (AR-266, AR-267).
- [ ] Shadow divergence is zero per surface before that surface enforces scoping (G-AR-133).
- [ ] Each cohort converted behind its flag with a rehearsed rollback, legacy tenant first (G-AR-134).
- [ ] Billing reconciliation passes per cohort and grandfathering terms are written per existing customer (G-AR-135, AR-273).
- [ ] A real second tenant lives on the converted system and the legacy path is retired and verified gone (G-AR-136, AR-275).
- [ ] Any cross-tenant exposure during conversion was handled as a P0: cohorts halted, the class fixed at its inventory/backfill root, and G-AR-091 re-passed before conversion resumed (AR-279).
