## When to use / Do NOT use

- **Use when:** any change that alters URLs, host, scheme, platform, templates, or information architecture at scale — a redesign that changes paths, a replatform/CMS change, a domain or www/non-www move, an HTTP→HTTPS move, a section merge/split, or a locale restructure. This skill owns the migration lifecycle only: inventory, mapping, carry-over, crawl-diff verification, launch sequencing, and post-launch monitoring with rollback triggers.
- **Do NOT use when:** the site is not changing URLs or host (a visual refresh on identical routes needs no migration — run technical-seo's per-release gates instead), a single page moves or retires (internal-linking CO-208 handles retirement as one change), the question is the standing crawl/index contract (technical-seo), what the sitemap file must contain (sitemaps — this skill supplies its post-migration inventory), what a page says (on-page-seo), or whether analytics is configured (web-analytics — this skill consumes its/Search Console's data for monitoring, it does not set measurement up).

## Rules

1. **CO-281 — The migration is frozen before it is mapped.** Before any mapping starts, the migration record names: type (redesign, replatform, domain, scheme, or restructure), old and new host/scheme, launch window, the owner, and the rollback owner. A change of type or host mid-migration restarts the inventory under CO-282; it is never absorbed silently into the existing map.
2. **CO-282 — Full pre-migration URL inventory, from every source.** The baseline inventory is the union of: a full crawl of the live site, the live XML sitemap(s), Search Console's indexed/pages report export, server-log or analytics landing-page URLs for the trailing 12 months where available, and the known backlink targets from Search Console's Links report. Every source is named in the record with its pull date. A crawl alone is not the inventory — URLs with traffic, indexation, or inbound links that the crawl misses (orphans, parameter-free landing pages, PDF/media URLs) are exactly the URLs a migration loses. For a host or scheme move, the inventory is taken per live variant: every variant that serves or redirects the site (http/https, www/non-www) is inventoried, or explicitly recorded in the map as covered by a host-level redirect rule — each variant is a separate site to a search engine, and a variant nobody mapped keeps resolving, or stops resolving, outside the map.
3. **CO-283 — Every inventoried URL gets exactly one disposition.** Each baseline URL is classified in the redirect map as exactly one of: `keep` (same URL on the new site), `redirect-1:1` (one named new URL), `redirect-merged` (one named new URL, with the merge reason recorded), `gone-410` (intentionally removed, no equivalent, with the removal reason and approver recorded), or `gone-404` (never existed as real content / already erroneous). No URL is left unclassified, and no classification is `TBD` at launch. The map is a file in the project repo (CSV or equivalent) with columns: old URL, disposition, new URL, approver/reason where applicable.
4. **CO-284 — 1:1 to the equivalent page is the default; equivalence is topical, not structural.** A `redirect-1:1` target must be the page a visitor following the old link would expect: same topic, intent, and where applicable same product/record/locale. Matching by path pattern, section, or slug similarity alone does not establish equivalence — a sampled human check under G-CO-143 verifies it. Where no equivalent exists, the honest dispositions are `gone-410` or a recorded `redirect-merged` to the closest parent/hub — never a forced match to an unrelated page.
5. **CO-285 — Permanent moves use permanent redirects, implemented once.** Every `redirect-*` row is implemented as a single-hop 301 or 308 from the exact old URL to the exact new URL, per technical-seo CO-007. Temporary codes (302/307), meta-refresh, and JavaScript redirects are not migration redirects. Redirect rules are written from the map file — the map and the server/CDN configuration are generated or checked from the same source, never maintained as two separate lists.
6. **CO-286 — Pre-migration baseline is captured before launch and kept.** Before launch the record stores, per inventoried URL where the tooling allows: HTTP status, canonical, title, meta description, H1, robots directives, structured-data types present, inbound internal-link count, and — at site/section level — Search Console clicks, impressions, and average position for a stated pre-period (28 days by default) plus the indexed-page count. Post-launch claims of loss or recovery are made only against this baseline, never from memory or a post-launch-only screenshot.
7. **CO-287 — Metadata and markup carry over by diff, not by assumption.** On the staging build, every `keep` and `redirect-1:1` URL's new page is diffed against its baseline for: title, meta description, H1, canonical (self-referencing on the new URL), robots directives, hreflang set where present, and structured-data types (validity itself belongs to structured-data). A difference is either an intentional change recorded in the map or a defect. New templates that emit a default, duplicated, or empty title/description fail here, not after indexation drops.
8. **CO-288 — Internal links point at the new URLs on day one.** At launch, internal links, navigation, breadcrumbs, hreflang return links, canonicals, and the sitemap reference the new URLs directly — no internal reference resolves through a migration redirect (the standing rule is internal-linking CO-206; this rule makes its re-verification a launch step). The old sitemap is replaced by the new one per the sitemaps skill, and for a domain change the old sitemap URL is kept reachable and submitted during the transition as Google's site-move guidance directs, alongside the Change of Address tool where the move is a domain change in Search Console's scope.
9. **CO-289 — Staging is crawlable by the team and invisible to engines; production is the reverse.** The pre-launch crawl runs on staging with its auth/`noindex` protections in place for engines but accessible to the crawl tooling. At launch, technical-seo's promotion diff (CO-005 / G-CO-001) runs as part of this skill's launch sequence: no staging `noindex`, `Disallow: /`, auth wall, or staging canonical survives, and robots.txt on the new host does not block the new URLs or their render assets. A migration never launches on a Friday-equivalent window the team cannot staff for monitoring under CO-291 unless the rollback owner accepts that in writing.
10. **CO-290 — Pre/post crawl comparison is the launch verdict.** Within 24 hours of launch, the new site is crawled with the same tool and settings as the baseline crawl, and the two crawls are diffed: every baseline URL's live outcome (status chain and final destination) is compared to its mapped disposition, and every new URL is checked for baseline regressions (status, canonical, directives, title/description presence). The diff report lists mismatches by URL; a narrative summary ("the migration went well") is not a substitute for it.
11. **CO-291 — Post-launch monitoring runs on a fixed schedule with named triggers.** Search Console coverage/indexing and performance, plus server-log or analytics 404s on old URLs, are checked daily for the first 7 days, then weekly until day 28, and each check is logged against the CO-286 baseline. The pre-agreed rollback/escalation triggers are: (a) any mapped URL returning the wrong disposition in a re-check; (b) indexed-page count for the migrated sections falling and not recovering across two consecutive checks after day 7; (c) a spike in 404s on baseline URLs with pre-migration clicks or inbound links; (d) staging protections found live at any point; (e) section-level Search Console clicks against the CO-286 baseline falling beyond the drop threshold agreed in the migration record across two consecutive checks, whether or not indexation has fallen — the signature of equivalence failures at scale that a crawl diff cannot see. A trigger fires the response in CO-292 — it is never merely noted.
12. **CO-292 — Rollback and fix-forward are decided in advance, and redirects are kept.** Before launch the record states the rollback mechanism (restore old site / revert DNS / re-point host), who can invoke it, and the fix-forward alternative for partial failures (patch the redirect config, templates, or directives in place). Rollback is invoked for launch-blocking failures (mass wrong dispositions, live staging protections, new site broadly unindexable); fix-forward is used for bounded defects with a named owner and deadline. Migration redirects are not removed after launch on an arbitrary date: they stay in place while the old URLs still receive requests, clicks, or inbound links, and any proposed removal is itself a change run through CO-290's diff.

## BAN list

- **BAN-CO-141 — The silent disappearance.** Banned: launching with any baseline URL unmapped, so it returns 404/410 or vanishes without a recorded disposition, approver, and reason. Defeats: DET-CRWL-015. Bad: the replatform launches from the new sitemap alone; 340 old help-centre URLs were never inventoried, several with inbound links, and they 404 for a month before a partner complains. Instead: build the union inventory (CO-282) and classify every URL (CO-283); G-CO-141 refuses launch on any unclassified row. Severity: BLOCK.
- **BAN-CO-142 — Everything redirects to the homepage.** Banned: pointing removed or unmatched old URLs at the homepage, a section hub, or a search page as a catch-all instead of a topical equivalent or an honest 410. Defeats: DET-CON-015. Bad: 900 discontinued product URLs all 301 to `/`, so the homepage absorbs irrelevant signals and visitors land somewhere that cannot answer the link they followed. Instead: redirect 1:1 to the equivalent (CO-284), merge with a recorded reason, or return a real 410 — the treatment technical-seo CO-008 already requires for gone content. Severity: BLOCK.
- **BAN-CO-143 — Pattern-matched redirects never sampled by a human.** Banned: generating the whole map from a regex/slug rule and shipping it without opening a sample of old→new pairs to check the destination is actually the equivalent page. Defeats: DET-CON-015. Bad: `/guides/spring-cleaning` pattern-maps to `/guides/spring` (a product collection), and 60 similar pairs send readers and crawlers to topically wrong pages that return 200, so no status check ever flags them. Instead: pattern rules may draft the map, but G-CO-143's human sample of pairs must pass before launch (CO-284). Severity: BLOCK.
- **BAN-CO-144 — Temporary or chained migration redirects.** Banned: implementing permanent moves as 302/307, meta-refresh, or JavaScript redirects, or leaving the old URL to hop through an intermediate URL (old → campaign URL → new) instead of one direct hop. Defeats: DET-CON-015. Bad: the agency ships 302s "so we can undo them easily" and half the map chains through the old homepage after a host rule fires first; months later the moves still read as temporary. Instead: single-hop 301/308 from the exact old URL to the exact new URL, generated or verified from the map file (CO-285). Severity: BLOCK.
- **BAN-CO-145 — Launching blind: no baseline, no monitoring, recovery declared by anecdote.** Banned: launching without a captured pre-migration baseline, skipping the post-launch checks, or reporting that rankings "recovered" / "were unaffected" from impressions, a single keyword check, or a stakeholder's search. Defeats: DET-CON-026. Bad: nobody exported Search Console data before the domain move; two weeks later the report states traffic is "back to normal" based on the homepage ranking for the brand name on one person's phone. Instead: capture the CO-286 baseline before launch, run the CO-291 schedule, and report only baseline-vs-current figures with their property, period, and source named. Severity: BLOCK.
- **BAN-CO-146 — Staging protections carried live by the migration.** Banned: the migrated site launching with staging `noindex`, `Disallow: /`, basic-auth, or staging-host canonicals copied across with the new build. Defeats: DET-CON-002. Bad: the new platform's templates inherit the staging meta robots tag; the redirect map is perfect and every old URL lands on a page engines are told not to index. Instead: run technical-seo's promotion diff (CO-289, G-CO-001 of technical-seo) inside the launch sequence and treat any hit as a CO-292 rollback trigger. Severity: BLOCK.

## Gates

- **G-CO-141 — Inventory and map completeness.** Verifies: CO-282, CO-283. Check: automated — join the baseline inventory (all CO-282 sources, pull dates recorded) against the redirect map on normalized old URL; assert every inventory row has exactly one disposition, every `redirect-*` row names a new URL, and every `gone-*` row names a reason and approver. Pass: zero unclassified, zero duplicate, zero `TBD` rows. Fail: block launch; the missing URLs are inventoried and classified first. Recorded in: progress.md.
- **G-CO-142 — Staging redirect verification.** Verifies: CO-284, CO-285. Check: automated — on staging (or a pre-production host carrying the real redirect config), request every old URL in the map and record the full status chain (a chain that revisits a URL is a loop and fails that row outright); assert per row: `keep` URLs return 200 at the same URL, `redirect-*` rows resolve in one hop with 301/308 to the exact mapped new URL which itself returns 200, and `gone-*` rows return the mapped 404/410 with no redirect. Pass: 100% of rows match their disposition. Fail: block launch; fix the config from the map and re-run the whole map, not only the failures. Recorded in: progress.md.
- **G-CO-143 — Equivalence and carry-over sample.** Verifies: CO-284, CO-287. Check: manual with tooling — a reviewer opens a sample of at least 25 `redirect-*` pairs (or all pairs if fewer; the sample must include the top 10 baseline URLs by pre-migration clicks) and confirms each new page is the topical equivalent of the old; in the same pass, the automated staging diff of title, meta description, H1, canonical, directives, hreflang, and structured-data types (CO-287) is reviewed and every difference is marked intentional-in-map or defect. Pass: zero wrong-equivalence pairs and zero unexplained carry-over differences. Fail: block launch; remap or fix and re-sample. Recorded in: progress.md.
- **G-CO-144 — Post-launch crawl diff.** Verifies: CO-288, CO-290. Check: automated — within 24 hours of launch, crawl production with the baseline crawl's tool and settings; diff live outcomes against the map and the baseline fields; assert additionally that no internal link, canonical, hreflang return link, or sitemap entry resolves through a migration redirect or names an old/staging host. Pass: zero disposition mismatches and zero through-redirect internal references. Fail: same-day fix-forward under CO-292 with a named owner; a mass mismatch (a whole section or template) is a rollback decision, not a ticket queue. Recorded in: progress.md.
- **G-CO-145 — Monitoring log and trigger review.** Verifies: CO-286, CO-291, CO-292. Check: manual — at day 7 and day 28, the monitoring log holds every scheduled check (daily to day 7, weekly to day 28) with indexed-count and performance figures stated against the CO-286 baseline (property, period, source named), every 404-on-old-URL cluster triaged, and every CO-291 trigger marked not-fired or fired-with-response. Pass: log complete and no fired trigger left without its recorded response. Fail: the migration is not closed; complete the missing checks before any "migration complete" report is issued. Recorded in: progress.md.

## Anti-patterns

- **Sitemap-as-inventory.** Building the baseline from the new sitemap the developers hand over, so the inventory describes the destination instead of the site being replaced — everything the new build forgot is invisible by construction. Catch it: the inventory's sources are the live site's crawl, sitemap, Search Console, and logs (CO-282); if a source list names only the new build, it is not an inventory.
- **The percentage shrug.** Reporting "98% of URLs redirect correctly" when the failing 2% includes the highest-traffic pages, because the check counted rows instead of weighting them. Catch it: G-CO-142 requires 100%, and G-CO-143 forces the top-clicked URLs into the human sample — check which URLs failed, never only how many.
- **Launch-day amnesia.** The map, baseline, and staging diffs exist, but nobody re-crawls after DNS/host changes, so the configuration actually live is never the one that was verified. Catch it: G-CO-144 runs on production within 24 hours with the baseline settings; a staging pass is not a launch verdict.
- **Premature cleanup.** Removing the migration redirects, the old Search Console property, or the old sitemap a few weeks after launch "to tidy up", cutting off straggler crawls, bookmarks, and inbound links. Catch it: CO-292 keeps redirects while old URLs still receive requests or links; a removal proposal needs its own crawl diff.
- **Two maps.** The SEO spreadsheet and the developer's server config drift apart during launch week as fixes are applied to whichever is open. Catch it: CO-285 names one source — the map file — and G-CO-142 verifies the live behavior against it; a fix that exists in only one place is a defect.

## Recall anchors

- No URL disappears silently: every baseline URL has one recorded disposition.
- Inventory from every source — a crawl alone misses the URLs that matter most.
- 1:1 to the equivalent page, one hop, 301/308 — or an honest, approved 410.
- Verify by crawl diff, pre against post — never by launch-day narrative.
- Baseline first, monitoring on a schedule, triggers decided before launch.

## Checklist

- [ ] Migration record names type, hosts, launch window, owner, and rollback owner (CO-281).
- [ ] Baseline inventory unions crawl, sitemap, Search Console, logs/analytics, and link targets, each source dated (CO-282).
- [ ] Every inventoried URL has exactly one disposition in the map file; no `TBD` rows (CO-283, G-CO-141).
- [ ] Redirects are single-hop 301/308 to topically equivalent pages, verified live against the map (CO-285, G-CO-142).
- [ ] Human sample confirms equivalence, including the top 10 URLs by pre-migration clicks (G-CO-143).
- [ ] Pre-migration baseline (per-URL fields + Search Console period figures) is captured and stored (CO-286).
- [ ] Metadata/markup carry-over diff reviewed; every difference is intentional-in-map or fixed (CO-287, G-CO-143).
- [ ] Internal links, canonicals, hreflang, and sitemap name new URLs directly; domain moves use Change of Address and keep the old sitemap reachable in transition (CO-288).
- [ ] Promotion indexability diff is clean — no staging protection live (CO-289).
- [ ] Post-launch crawl diff within 24 hours shows zero disposition mismatches (CO-290, G-CO-144).
- [ ] Monitoring log complete to day 7 and day 28, triggers reviewed, migration not closed early (CO-291, G-CO-145).
- [ ] Rollback mechanism and owner recorded before launch; migration redirects retained while old URLs still receive requests or links (CO-292).
