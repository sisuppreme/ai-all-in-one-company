# Example 3 — SaaS settings/billing area: schema-mirroring settings replaced by task-organised billing

Corrects rules **FE-362** (preserve what works), **FE-367** (zero behaviour regression), **FE-370** (the UI speaks only user-facing concepts), and **FE-371** (the leak audit is a veto).

## Before

A SaaS settings/billing area mirrors the database schema in the UI: the nav reads "users", "subscriptions", "invoices", "api_keys" — table names as navigation. The billing page shows "Field: stripe_customer_id", "Collection: invoices", and a footer counting the product's own structure ("4 sections · 12 routes"). An error state reads "Failed to fetch /api/v2/invoices (500)". The design is starter grey with a different accent per page, and every upgrade attempt before this one stalled because a restyle broke the billing flow — a "redesign" once renamed a route and silently dropped the invoice download, discovered by a customer, not a test. BEFORE score 34/80, BEFORE leak score 14 — the worst leak count in the app, because the settings area was built by copying field names into labels.

## After

The audit lists all 14 leaks by ban class before any UI is touched, and the behaviour baseline is frozen first (FE-362): every billing flow end-to-end, including invoice download and the failed-payment path. The upgrade is presentation-layer only — no route renamed, no API call changed, no feature deleted to make the design easier. The settings area is reorganised by user task (FE-370): "Your team", "Billing", "Notifications", "Security" — each page answering what the user came to do, with labels naming the action ("Download invoice (PDF)") instead of the field. The error becomes "Couldn't load your invoices — check your connection and try again". The signature element is a balancing ledger line across the plan table: debit and credit animate to the plan's real totals, so the element carries the product's core promise in real figures. Pass 5's motion is dial 2 throughout — a task flow earns restraint — and after every pass the regression checklist runs against the frozen baseline (FE-367): the pass that once would have renamed a route is caught by the checklist and rolled back the same day. AFTER score 68/80, AFTER leak score 0 — and the leak gate (FE-371) is what decided the ship date: the build scored 66/80 a week earlier with one leak still live ("api_keys" in a tooltip), and it did not ship until the leak was gone, whatever the /80 said.
