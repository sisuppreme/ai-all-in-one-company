## When to use / Do NOT use

- **Use when:** a rough MVP, demo, hackathon build, no-code export, or AI-generated prototype — software that was built to be shown, not to be trusted — is being promoted to real users, real data, or real money, and needs one deliberate conversion pass: replacing simulated behavior with real behavior, closing the security holes prototypes ship with, adding the error handling and data-integrity guarantees the demo never needed, and proving the result with tests. The output is a hardening ledger and a production / not-production verdict, not a prettier codebase.
- **Do NOT use when:** the code is already production-grade and only its internal structure needs improving with behavior unchanged — that is refactoring (DX-101–DX-120), and hardening rules must not be used to smuggle behavior changes into a refactoring change. Do NOT use when a working legacy system with live users is being replaced in slices while the old system keeps serving — that is legacy-migration (DX-121–DX-140); a prototype has no incumbent behavior worth preserving, which is exactly why it can be hardened in place instead of migrated. Do NOT use when the task is only to find placeholder or fake content — that verdict belongs to placeholder-scan (QA-281–QA-292), which detects; this skill repairs what it finds and must not re-define its fingerprints or probes. Do NOT use to catalogue known shortcuts without fixing them — that register work is tech-debt (DX-081–DX-100). Do NOT use when the honest answer is a rewrite: if the prototype's data model or core flow is wrong, say so and stop; hardening a wrong foundation produces a hardened wrong product. Do NOT use as the entry point for an inherited prototype that carries live obligations you have not yet taken ownership of: if the prototype came from someone else and has live users, production data, or live integrations, run project-takeover first (inventory, access map, as-found baseline, secret rotation) and harden only after its exit gate; an inherited prototype with none of those is hardened directly, with this skill's ledger as its entry record.

## Rules

1. **DX-161 — Inventory before touching code.** Before any fix, produce the hardening ledger: every route, screen, endpoint, job, and integration in the prototype, each classified as REAL (works end to end against the real store), SIMULATED (stub, fixture, in-memory, or client-only), or ABSENT (implied by the UI but not implemented). The ledger is built by exercising the running prototype — clicking, submitting, reloading, signing in with a wrong password — not by reading the code and believing its comments. No hardening work starts on an un-inventoried area.
2. **DX-162 — The prototype is untrusted input.** Every claim the prototype makes about itself — "login works," "payments are wired," "data is saved" — is treated as false until re-proven against the production-shaped stack. A feature is REAL only when its effect survives a reload, a re-login, and a server restart, and is visible in the underlying store, not only in the UI.
3. **DX-163 — Scope is the conversion, nothing else.** Hardening changes how trustworthy existing behavior is, not what the product does. New features, redesigns, and stack swaps discovered mid-pass are recorded as follow-ups, not built. The one exception: a simulated core function (DX-161) is implemented for real or removed from the shipped surface — leaving it simulated is not a scope option.
4. **DX-164 — Auth is real, server-side, and complete.** Authentication is implemented or replaced with a real mechanism: credentials are verified server-side against stored, properly hashed passwords (or a managed identity provider), sessions are issued and invalidated server-side, and password reset actually changes the credential and invalidates old sessions. The session cookie is HttpOnly, Secure, and SameSite, the session identifier is rotated at login and at every privilege change so a pre-login identifier can never be fixated, and the credential endpoints are rate-limited with lockout or progressive delay so the login form is not a guessing oracle (session mechanics per `session-security`, D7; throttling per `rate-limiting`, D4 — this skill requires both, it does not restate them). Client-side flags, stored "logged in" booleans, and any-password acceptance are deleted, not layered over. Authorization is checked server-side on every privileged request, independent of what the UI hides (see DET-FAKE-021).
5. **DX-165 — No secret ships in code, history, or bundle.** Every credential, API key, token, and connection string found in source, configuration defaults, committed history, or the client bundle is treated as compromised: it is rotated, moved to the environment or a secrets store, and the old value is revoked — moving it to an environment variable without rotating it does not close the finding. The hardened tree and the built client bundle are both scanned; a key that only left the source but still ships in the bundle is still shipped.
6. **DX-166 — Every boundary validates input.** Every value crossing a trust boundary — form fields, query and path parameters, headers, file uploads, webhook and API payloads — is validated server-side for type, range, length, and allowed values, and rejected with a safe error when it fails. Client-side validation may exist for UX but never counts as the control. Queries are parameterized, output in templates is escaped by the framework default, and file uploads are checked for type and size and stored outside executable paths.
7. **DX-167 — Errors are handled, logged, and safe to show.** No I/O boundary — database, network, filesystem, external API, payment provider — runs without an error path. Each failure is logged server-side with enough context to diagnose it (operation, correlation/request identifier, underlying error), and the user sees a generic message that reveals no stack traces, query text, internal paths, or provider internals. Empty catch blocks, catch-and-continue, and success responses returned on failure are removed wherever found.
8. **DX-168 — Data integrity is enforced by the store, not by hope.** The hardened schema carries the constraints the prototype skipped: primary and foreign keys, uniqueness where the domain requires it (account email, idempotency keys, external references), NOT NULL on required fields, and transactions around every multi-write operation so a failure mid-operation leaves no partial state. Retried or double-submitted writes — form resubmits, webhook redeliveries, client retries — are made idempotent where a duplicate would charge, create, or send twice.
9. **DX-169 — Fake and placeholder content is removed, not relabeled.** Seed users, fixture catalogs, canned search/AI responses, staged notifications, lorem ipsum, placeholder contacts, and demo numbers found by the inventory (DX-161) or by placeholder-scan are deleted from production code paths and production seed state. What replaces them is real data flow plus honest empty states: a new account sees an empty workspace, not staged content. A demo mode that must survive is isolated behind an explicit, labeled, non-production configuration and can never be enabled by the production environment.
10. **DX-170 — The critical paths get real tests.** Automated tests are added for, at minimum: authentication (correct password accepted, wrong password rejected, reset invalidates the old credential), authorization (a low-privilege account replaying a privileged request is rejected server-side), each core write flow (the write persists and survives reload), each payment or irreversible action if one exists (including its failure and duplicate-submission cases), and the error paths added under DX-167. A test that cannot fail — no assertion, assertion on a mock's own return value, or a stubbed subject — does not count toward this rule.
11. **DX-171 — Configuration is explicit and environments are separated.** All environment-specific values come from configuration, never from hardcoded URLs, keys, or per-machine files in code. Development, staging, and production use separate credentials and separate data stores; debug modes, verbose error pages, sample-data seeders, and admin or debug endpoints are disabled or absent in the production configuration, and the production configuration is the one the gates below run against.
12. **DX-172 — Dependencies are real, pinned, and patched.** Every import resolves to a package declared in the manifest; hallucinated or undeclared packages are removed or replaced with the real API. Versions are locked by the lockfile, the production install is reproducible from a clean checkout, and dependencies with known critical or high vulnerabilities affecting used code paths are upgraded or replaced before the verdict — the audit report is filed in the ledger, not just run and discarded.
13. **DX-173 — The prototype's shortcuts become register entries, not secrets.** Any shortcut deliberately kept at the end of the pass — a known weak spot, a deferred test, a temporary workaround — is entered in the tech-debt register under DX-081–DX-092 with its interest and repayment trigger, and named in the hardening ledger. A shortcut that exists only in the hardening agent's head or in a code comment is an undisclosed risk and blocks the verdict.
14. **DX-174 — The pass ends in a verdict, per area.** Each inventoried area is closed as HARDENED (all applicable rules met and gates passed), REMOVED (the simulated or unsafe surface was deleted), or BLOCKED (named reason, named owner, named follow-up). "Mostly done" is not a status. The product may be declared production-ready only when no core area is BLOCKED and no SIMULATED core function remains reachable in the production build.
15. **DX-175 — Rollback and recovery exist before real users arrive.** Before the hardened build takes real traffic: database migrations are rehearsed against a copy of production-shaped data and are reversible or preceded by a verified backup, a restore of that backup has been performed once, and the previous deployable build can be restored by one documented step. A hardening pass that makes the prototype safer to run but impossible to recover has not finished.
16. **DX-176 — Observability is the minimum, not the roadmap.** The hardened build emits structured server-side logs that persist beyond the process, exposes a health check that reflects its real dependencies (store reachable, not merely process alive), and surfaces server errors somewhere a named human or alert actually sees them. Console output on a developer's terminal is not observability.
17. **DX-177 — Proven behavior is pinned before it is changed.** Before any component classified REAL in the ledger (DX-161) is modified, its observable behavior — the flows the prototype actually proved — is pinned by characterization tests that pass against the unmodified component (the method is owned by `test-strategy`, D8; this skill makes pinning a precondition, it does not restate the technique). During hardening the pins run on every change: a failing pin means the change altered proven behavior, which is either a defect to fix or a deliberate behavior change recorded as a requirements change — never a test quietly edited to match the new behavior. Components classified SIMULATED or ABSENT have nothing to pin; their behavior is specified by DX-170's tests instead.

## BAN list

- **BAN-DX-081 — Client-only or any-password authentication.** Banned: shipping authentication that is decided in the browser, accepts any or a hardcoded password, or treats a stored "logged in" flag as a session. Defeats: DET-FAKE-001. Bad: the login form checks `if (password.length > 0) setLoggedIn(true)` and stores the flag in local storage, so every account is open to anyone. Instead: verify credentials server-side against properly hashed stored passwords (or a managed identity provider), issue a server-side session, and reject a wrong password — proven by the wrong-password test in DX-170. Severity: BLOCK.
- **BAN-DX-082 — Secrets in source, history, or the client bundle.** Banned: API keys, tokens, or credentials hardcoded in code, committed to version control, shipped as configuration defaults, or embedded in the built client bundle. Defeats: DET-CODE-018. Bad: the payment provider's secret key sits in a config file in the repo and is inlined into the production JavaScript bundle, readable by every visitor. Instead: rotate the exposed credential, revoke the old value, load the replacement from the environment or a secrets store at runtime, and re-scan the tree, history, and built bundle (DX-165). Severity: BLOCK.
- **BAN-DX-083 — Stub handlers presented as finished features.** Banned: an endpoint, handler, or function that returns a constant, an empty result, or a success response without doing the work, while the UI presents the feature as working. Defeats: DET-CODE-003. Bad: `POST /api/newsletter` returns `{ ok: true }` and stores nothing; the UI thanks subscribers whose addresses are discarded. Instead: implement the handler against the real store, or remove the feature from the shipped surface until it is implemented (DX-163). Severity: BLOCK.
- **BAN-DX-084 — Seed and fixture data shipped as real data.** Banned: demo users, fixture catalogs, canned result sets, or staged activity reachable from, imported by, or seeded into the production build as if they were real. Defeats: DET-FAKE-014. Bad: the production database is seeded with invented customers and orders so the dashboard "looks alive" for the first real user. Instead: delete the fixtures from production code paths and seed state, ship honest empty states, and isolate any surviving demo data behind a labeled non-production configuration (DX-169). Severity: BLOCK.
- **BAN-DX-085 — String-built queries from user input.** Banned: constructing SQL or query strings by concatenating or interpolating unvalidated user input. Defeats: DET-CODE-017. Bad: `"SELECT * FROM users WHERE email = '" + email + "'"` lets a crafted email value read or alter other accounts' rows. Instead: use parameterized queries or the ORM's bound parameters for every value, with server-side validation at the boundary (DX-166). Severity: BLOCK.
- **BAN-DX-086 — Swallowed errors and success-on-failure.** Banned: empty exception handlers, catch blocks that only log to the browser console or do nothing, and handlers that return a success response after an underlying operation failed. Defeats: DET-CODE-005. Bad: the checkout handler catches the payment provider's failure, ignores it, and renders "Order confirmed" — the customer is told they paid and nothing was charged or recorded. Instead: log the failure server-side with context, return a safe generic error to the user, and leave the operation's state consistent and retryable (DX-167, DX-168). Severity: BLOCK.
- **BAN-DX-087 — Security controls disabled to make the prototype run.** Banned: shipping with authentication or authorization checks commented out, TLS verification disabled, permissive wildcard cross-origin settings on authenticated endpoints, or framework security protections (such as CSRF or output escaping) turned off to silence an error. Defeats: DET-CODE-020. Bad: certificate verification is disabled in the payment client and the auth middleware is commented out "until login is finished," and both ship. Instead: fix the underlying cause — valid certificates, a finished login, an explicit origin allow-list — and re-enable the control before the verdict (DX-164, DX-166). Severity: BLOCK.
- **BAN-DX-088 — Tests that assert nothing, kept to look tested.** Banned: presenting a suite as coverage of a critical path when its tests contain no meaningful assertion, assert only a mock's own behavior, or have their failing cases deleted or skipped to go green. Defeats: DET-CODE-012. Bad: the auth test file contains `expect(true).toBe(true)` and a login test whose assertion was removed when it failed, and the pass reports "auth: tested." Instead: write tests that exercise the real path and can fail — wrong password rejected, privileged replay refused, write persisted (DX-170) — and keep a failing test red until the code, not the test, is fixed. Severity: BLOCK.

## Gates

- **G-DX-081 — Ledger completeness check.** Verifies: DX-161, DX-162, DX-174. Check: manual, against the ledger — pick three routes, one write flow, and the auth flow at random from the running production-configured build; exercise each (submit, reload, re-login, restart the server) and confirm its ledger classification (REAL / SIMULATED / ABSENT) matches the observed behavior and the underlying store. Pass: every sampled classification is accurate and every core area carries a DX-174 status. Fail: block the verdict; re-inventory the mismatched area. Recorded in: progress.md.
- **G-DX-082 — Auth and authorization probe.** Verifies: DX-164. Check: automated or scripted manual probe against the production-configured build — (1) sign in with a wrong password, (2) request a protected page with no session, (3) replay a privileged request captured from an admin session using a low-privilege session, (4) complete a password reset and confirm the old credential no longer works, (5) confirm the session identifier issued at login differs from any pre-login identifier (fixation probe). Pass: all five are rejected or behave as specified, server-side. Fail: block shipment; any single success is a P0 defect. Recorded in: progress.md.
- **G-DX-083 — Secret and placeholder sweep of the shipped artifact.** Verifies: DX-165, DX-169. Check: automated — run a secret scanner over the working tree, the full committed history, and the built client bundle, and run the placeholder-scan static sweep (QA-284's fingerprint set, run as gate G-QA-141) over the rendered production output; then create a fresh production account and confirm it shows empty states, not staged content. Pass: zero secret findings in tree, history, or bundle, zero placeholder findings, fresh account empty. Fail: block shipment; rotate any exposed credential under DX-165 before re-running. Recorded in: progress.md.
- **G-DX-084 — Failure and integrity drill.** Verifies: DX-167, DX-168. Check: automated or scripted manual drill in staging with production configuration — (1) force each external dependency (store, provider, API) to fail once and observe the user-facing error and the server log, (2) double-submit each core write form and redeliver one webhook or retried request, (3) interrupt one multi-write operation mid-way. Pass: users see generic safe errors with no internals, every failure is logged with a correlation identifier, no duplicate charge/record/send results, and no partial state remains. Fail: block shipment. Recorded in: progress.md.
- **G-DX-085 — Critical-path test run.** Verifies: DX-170, DX-172, DX-177. Check: automated — from a clean checkout, install from the lockfile, build, and run the full suite in CI; confirm the DX-170 test list exists by name (auth accept/reject, reset invalidation, authorization replay, core write persistence, irreversible-action failure and duplicate cases), that the DX-177 characterization pins for every kept component's proven flows exist and were recorded green against the unmodified prototype in the ledger before hardening began, and that the dependency audit report is filed in the ledger. Pass: build and suite green with every named test and pin present and passing, and no unaddressed critical/high audit finding on a used code path. Fail: block merge. Recorded in: progress.md.
- **G-DX-086 — Recovery rehearsal.** Verifies: DX-171, DX-175, DX-176. Check: manual drill in staging — restore the pre-release backup into a scratch environment and start the build against it, roll back to the previous deployable build by the one documented step, and call the health check with the data store stopped. Pass: restore and rollback both succeed, the health check reports unhealthy when its store is down, and the production configuration shows debug modes and debug/admin endpoints disabled or absent. Fail: block the production verdict until rehearsed successfully. Recorded in: progress.md.

## Anti-patterns

- **Hardening theater.** Headers, a linter, and a security checklist are added while login still accepts anything and checkout still stores nothing — the visible rituals of hardening without the conversion. Catch it: work the ledger in DX-161 order — SIMULATED core functions first, cosmetics last — and let G-DX-082 and G-DX-084, not the checklist, deliver the verdict.
- **The parallel rewrite that never lands.** Halfway through the pass the prototype is declared hopeless and a rewrite starts alongside it; the rewrite stalls, the prototype ships anyway, now with even less scrutiny. Catch it: the rewrite decision belongs at DX-161, before work starts, on ledger evidence — once hardening begins, finishing it is the plan.
- **Layering over the fake.** A real database is added but the fixture array is kept as a "fallback," real auth is added but the old client-side flag is still honored, so both the real and the simulated paths remain live. Catch it: for every replacement, name the old path and its deletion in the same change; a fallback to fake data is fake data.
- **Fixing only what the demo showed.** The flows from the sales demo get tests and error handling while the un-demoed paths — settings, export, account deletion, admin — stay exactly as rough. Catch it: the ledger, not the demo script, defines the scope; sample outside the demo path at G-DX-081.
- **Green by deletion.** Failing tests, strict type checks, and audit findings are removed, skipped, or downgraded until the pipeline passes. Catch it: diff the test and configuration files in the hardening change itself; a hardening pass that deletes more checks than it adds has gone backwards.
- **Environment amnesia.** Everything is verified in the developer's local setup — seeded, logged in, debug on — and declared hardened, while the production configuration was never run. Catch it: every gate above specifies the production configuration; a result from any other configuration does not count.

## Recall anchors

- A prototype's claims about itself are false until re-proven against the store.
- Inventory first: REAL, SIMULATED, or ABSENT — for every surface.
- Real auth, rotated secrets, validated input, handled errors, constrained data.
- Remove the fake; never layer the real over it.
- The pass ends in a verdict per area — "mostly done" is not one.

## Checklist

- [ ] Hardening ledger exists: every route, flow, and integration classified REAL / SIMULATED / ABSENT by exercising the running prototype (DX-161, DX-162).
- [ ] Auth is real and server-side; wrong-password, no-session, privileged-replay, and reset probes all pass (DX-164, G-DX-082).
- [ ] Every secret found in tree, history, or bundle was rotated and revoked, and the re-scan of tree, history, and bundle is clean (DX-165, G-DX-083).
- [ ] Proven flows of every kept component were pinned by characterization tests before modification, and every pin failure was resolved as a defect or a recorded behavior change (DX-177, G-DX-085).
- [ ] All boundary input is validated server-side and all queries are parameterized (DX-166).
- [ ] No swallowed errors remain on I/O boundaries; failures log server-side with context and show users a generic message (DX-167).
- [ ] Schema constraints and transactions are in place, and duplicate submission of core writes is idempotent (DX-168, G-DX-084).
- [ ] Placeholder-scan sweep of the production output is clean and a fresh account shows real empty states (DX-169, G-DX-083).
- [ ] Critical-path tests exist by name, can fail, and pass from a clean checkout in CI (DX-170, G-DX-085).
- [ ] Production configuration is separated, debug surfaces are off, and dependencies are locked with the audit report filed (DX-171, DX-172).
- [ ] Every shortcut kept is a tech-debt register entry named in the ledger (DX-173).
- [ ] Backup restore and one-step rollback were rehearsed, and the health check fails when its store is down (DX-175, DX-176, G-DX-086).
- [ ] Every area is closed HARDENED, REMOVED, or BLOCKED — no core area BLOCKED, no SIMULATED core function reachable (DX-174).
