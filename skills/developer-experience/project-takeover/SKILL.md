# project-takeover

## Metadata

- **Owner department:** D15 Developer Experience (DX)
- **Skill version:** 1.0.0
- **Last verified:** 2026-11-21
- **Sources:** https://github.com/gitleaks/gitleaks ; https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning ; https://12factor.net/config ; https://owasp.org/www-project-application-security-verification-standard/
- **Depends on:** dev-environment (the local run in DX-185 follows its bootstrap and pin discipline), tech-debt (the register that receives every non-stabilization finding under DX-190)
- **Feeds into:** refactoring, legacy-migration, dependency-management

## When to use / Do NOT use

- **Use when:** a team or agent inherits an existing project it did not build — a handover from a departing developer, a contractor delivery, an acquired or rescued codebase, an abandoned repo being revived — and must take responsibility for it. This skill is the entry protocol: inventory what exists, get it running locally, audit it, build the risk map, and stabilize it, in that order, before any other work begins.
- **Do NOT use when:** the project is your own ongoing work (no takeover is occurring), the system is being replaced rather than inherited (once takeover completes and the system is stable, use legacy-migration for the replacement), the task is a one-off code review of code you will not own (a review produces findings; a takeover produces an owned, running, risk-mapped system), or the inherited system is a throwaway prototype with no users, no production data, and no live integrations (archive it or rewrite freely; there is nothing to secure).
- **Boundary with neighbors:** this skill is the BEFORE phase. It ends at a stabilized, understood system and a signed-off takeover report. Everything the audit finds that is not stabilization is handed off, not done here: known shortcuts go to the tech-debt register (tech-debt), behavior-preserving cleanup waits for refactoring, system replacement waits for legacy-migration, and version currency waits for dependency-management. Where those skills define a discipline this skill needs — register fields, characterization tests, frozen installs — this skill references them instead of restating them. The overlap with prototype-hardening is decided by what the inherited system carries: a rough inherited prototype with live users, production data, or live integrations comes through takeover first, and hardening is scheduled as post-exit work under DX-190; a rough inherited prototype with none of those goes straight to prototype-hardening, and takeover never runs.

## Rules

1. **DX-181 — Takeover mode is declared and freezes the scope of work.** The takeover starts with a dated declaration in progress.md naming the project, the source it was inherited from, and the starting commit or snapshot (DX-183). From that moment until the exit gate (G-DX-095) passes, the only permitted work is inventory, local run, audit, risk mapping, and stabilization under DX-191. No feature work, no cleanup, no upgrades — however small, however obviously needed — are performed in takeover mode.
2. **DX-182 — Inventory before opinion.** Before any judgment about the project's quality or future is recorded, a takeover inventory exists listing: every repository and its branches; every deployable service and where it runs; every data store and its owner; every scheduled job, webhook, and external integration; every environment (dev, staging, production, and any per-machine variants); and every document, dashboard, and runbook that came with the handover. Each item is marked `verified` (the inheritor has seen it working or inspected it directly), `claimed` (asserted by the predecessor or the docs, not yet checked), or `unknown` (known to exist, not yet located). An item may not be marked `verified` on someone else's word — that is DX-186.
3. **DX-183 — The inherited state is preserved before it is touched.** The first action on the code is preservation, not exploration-by-edit: record the starting commit hash and `git status` output, preserve any uncommitted changes exactly as found (stash copy, patch file, or a snapshot branch — never discard, clean, or "tidy" them), and note the state of any non-versioned material that came with the handover (loose config files, database dumps, exported keys). If the inherited material has no version control, initializing a repository over it — committing the state exactly as received — is the first stabilization change and precedes all others.
4. **DX-184 — Access and ownership are mapped, including what is missing.** The inventory names, for each external thing the project depends on — domain registrar and DNS, cloud/hosting account, CI provider, package and container registries, app stores, payment and email providers, error-tracking and analytics accounts — who holds administrative access today: the inheritor, the predecessor personally, a company account, or nobody knows. Anything held only by the predecessor, or by nobody identifiable, is a top-section risk-map entry (DX-190) from the day it is discovered, not a surprise saved for later. Credentials are transferred through the project's secret store, never through chat, email, or committed files.
5. **DX-185 — It runs locally from a clean clone, from the repo's own instructions.** The inheritor clones the project fresh and brings it up following only what the repository itself documents, under dev-environment's bootstrap and pin discipline. Every step that is missing, wrong, or known only to the predecessor is recorded as a takeover finding with the exact step that had to be discovered. "It ran on the predecessor's machine" is not a run; the takeover run happens on a machine or container with none of the predecessor's local state. Setup defects found here are findings — repairing the bootstrap is stabilization (DX-191), redesigning the environment is not.
6. **DX-186 — Every handover claim is re-verified or stays `claimed`.** Statements from the predecessor, the README, or the delivery note — "tests pass," "deployed from main," "backups are on," "that service is unused," "the cron was disabled" — are claims, not facts. Each material claim is either reproduced by the inheritor (run, read, or queried directly) and upgraded to `verified` in the inventory, or it remains `claimed` and appears in the risk map with its potential impact if false. The takeover report — inventory, baseline, audit, and risk map, signed off at G-DX-095 — never restates a `claimed` item in the language of fact.
7. **DX-187 — The as-found baseline is recorded before anything changes.** Once the project runs locally (DX-185), the inheritor records its state exactly as inherited: build result, full test-suite result (pass/fail counts as found, not as hoped), lint/type-check result where configured, and a smoke pass over the primary user flows. Pre-existing failures are findings with their output preserved; they are not fixed during baselining, and the baseline is never re-recorded after a fix to make the inheritance look healthier. Every later change — in takeover and after — is judged against this baseline.
8. **DX-188 — A security audit precedes any change to the running system.** Before the first stabilization change, the audit covers at minimum: a secret scan over the working tree and the full version-control history (gitleaks or equivalent); a dependency vulnerability audit with findings routed per dependency-management (DX-071 there) to D7 dependency-safety; the authentication and authorization surface (who can log in, what roles exist, whether any test, default, or predecessor personal accounts are live); exposed debug, admin, or default surfaces in production configuration; and where production credentials and personal accounts are still active. A live secret found anywhere — tree, history, CI logs, a handover document — is treated as compromised: rotation is stabilization and happens under DX-191, and the finding records that rotation, not deletion of the file, is what closes it.
9. **DX-189 — The detection sweep is run and its hits are recorded by ID.** The inherited codebase and its infrastructure are swept with the repo's detection parameters — skills/detection/code/PARAMETERS.md and skills/detection/infra/PARAMETERS.md at minimum — and every hit is entered in the audit by its DET ID, with the file or configuration that triggered it. Hits are findings, not a work list: only hits that meet the stabilization bar (DX-191) are acted on during takeover; the rest transfer to the risk map and the tech-debt register under DX-190. A sweep that was "done mentally" while reading code does not count — the recorded hit list is the evidence it happened.
10. **DX-190 — Every finding gets a risk-map disposition.** The risk map is a single table in the takeover report: one row per audit, inventory, baseline, and access finding, each with likelihood, impact, a named owner, and exactly one disposition — `stabilize-now` (meets DX-191), `register` (transferred to the tech-debt register under tech-debt's field rules, with the register ID recorded here), `schedule` (named follow-on work under refactoring, legacy-migration, or dependency-management, with a trigger or date), or `accept` (a named decider consciously accepts the risk, recorded as such). A finding with no disposition is an unfinished takeover, and the highest-impact rows are summarized at the top of the report, not buried in the table.
11. **DX-191 — Stabilization is minimal, separable, and the only change permitted.** A change qualifies as stabilization only if it makes the inherited system safe or runnable without changing its intended behavior: rotating a compromised secret, restoring a broken build or a missing pin so the as-found code runs, enabling or verifying a backup for production data, closing an exposed debug/admin surface, or revoking a departed predecessor's live access. Each stabilization change is its own commit or pull request, labeled as takeover stabilization, and judged against the DX-187 baseline. Anything that improves structure, updates a version, or adds behavior fails this test by definition and waits for takeover exit — "while I'm in here" is precisely the failure this rule exists to prevent.
12. **DX-192 — Production data and backups are verified, never assumed.** The inventory names every production data store, where its backups live, how often they run, and when a restore was last actually performed. During takeover the inheritor performs or witnesses a restore of the most critical store into a non-production environment; a backup that has never been restore-tested is recorded as `claimed`, and the risk map carries the honest entry "no verified recovery path" until a restore succeeds. The first local run and all takeover experimentation use copies, fixtures, or anonymized data — never live production data on a laptop (see BAN-DX-094).

## BAN list

- **BAN-DX-091 — Work before the freeze lifts.** Banned: any feature, cleanup, refactoring, or dependency/framework upgrade change made between the takeover declaration and the exit gate, alone or mixed into a stabilization change. Defeats: DET-CODE-031. Bad: the first pull request of the takeover "fixes the login bug, bumps the framework two majors, and renames the services module" — afterward nobody can say which change broke production, or what the project looked like as inherited. Instead: record the bug, the upgrade, and the rename as risk-map findings with dispositions (DX-190); only DX-191 stabilization ships during takeover, each change separate. Severity: BLOCK.
- **BAN-DX-092 — Handover claims accepted as verified.** Banned: marking any inventory item `verified`, or reporting the project healthy, on the predecessor's statement, the README, or a delivery note, without the inheritor reproducing it. Defeats: DET-CRWL-004. Bad: the takeover report states "backups run nightly, tests green" because the handover call said so; the first restore attempt, three months later, finds the backup job has failed silently since before the handover. Instead: reproduce each material claim or leave it `claimed` and risk-mapped, under DX-186 and DX-192. Severity: BLOCK.
- **BAN-DX-093 — Inherited secrets left live or passed around in the clear.** Banned: finding a real secret in the tree, history, or handover material and leaving it in place "until later," or transferring predecessor credentials through chat, email, or a committed file. Defeats: DET-INF-005. Bad: the audit finds the production database password in a committed `.env` from two years ago; the team notes it in the report and moves on — the password stays valid and publicly recoverable from history the whole time. Instead: treat it as compromised, rotate it as stabilization (DX-188, DX-191), transfer all credentials through the secret store (DX-184), and record the rotation as the closure. Severity: BLOCK.
- **BAN-DX-094 — First run pointed at production.** Banned: running the inherited system locally or in a test environment while it is configured with production databases, queues, payment providers, email/SMS senders, or third-party webhooks. Defeats: DET-INF-003. Bad: the inheritor copies the predecessor's `.env` to get the app booting, runs the seed-and-notify script to "see if it works," and real customers receive test emails from the production provider. Instead: run against copies, fixtures, or sandbox credentials only (DX-192); an environment whose production separation cannot be established is itself a `stabilize-now` finding. Severity: BLOCK.
- **BAN-DX-095 — Unknown things deleted as "dead."** Banned: deleting, disabling, or decommissioning any inherited file, service, scheduled job, account, DNS record, or data store during takeover because it looks unused, unreferenced, or undocumented. Defeats: DET-NONE — no DET parameter names the deletion of a live-but-unrecognized component; governed by DX-182 and DX-190. Bad: an unreferenced nightly script is deleted as clutter in week one; it was the only thing reconciling the payment provider's records, a fact that surfaces at month-end. Instead: an unrecognized item is inventoried as `unknown` (DX-182) and risk-mapped; removal, if ever, is a post-takeover change made with evidence of non-use gathered while the system runs observed. Severity: BLOCK.

## Gates

- **G-DX-091 — Inventory completeness gate (manual + automated).** Verifies: DX-182, DX-184. Check: diff the inventory against independent sources of truth — the cloud/hosting account's resource list, DNS records for the project's domains, the CI provider's project list, and `git branch -a` plus top-level tree of every repository — and confirm every discovered resource appears in the inventory and every inventory item carries `verified` / `claimed` / `unknown` and, for external services, an access holder (DX-184). Pass: zero unlisted resources and zero unmarked items. Fail: block; takeover remains in inventory phase. Recorded in: progress.md.
- **G-DX-092 — Clean-clone run and baseline gate (automated).** Verifies: DX-185, DX-187. Check: in a clean container or VM, clone the repository, follow only the repo's documented setup, start the app, run the full test suite and the primary-flow smoke pass, and save the outputs as the baseline record. Pass: the app runs, the baseline record exists with build, test counts, and smoke results exactly as found, and every undocumented step needed is logged as a finding. Fail: block; a project that cannot be run by its inheritor has not been taken over — the blocker itself becomes the top stabilization item. Recorded in: progress.md.
- **G-DX-093 — Security and detection sweep gate (automated).** Verifies: DX-188, DX-189. Check: run the secret scanner over tree and history (`gitleaks detect --log-opts="--all"` or equivalent), the ecosystem dependency audit, and the DET sweep checklists for code and infra; confirm the audit document lists every hit by DET ID or scanner finding, and that every live-secret hit shows a rotation record. Pass: all three sweeps run, hits recorded, zero unrotated live secrets. Fail: block; no stabilization change to the running system precedes this gate. Recorded in: progress.md.
- **G-DX-094 — Risk-map disposition gate (automated + manual).** Verifies: DX-190. Check: parse the risk-map table: every row has likelihood, impact, owner, and one of the four dispositions; every `register` row names a tech-debt register ID that exists in `docs/tech-debt.md`; every `accept` row names a decider; every `stabilize-now` row links its stabilization change. Pass: zero undispositioned findings. Fail: block exit; a finding without a disposition is assigned one before takeover closes. Recorded in: progress.md.
- **G-DX-095 — Freeze and exit gate (automated + manual).** Verifies: DX-181, DX-191, DX-192. Check: audit every commit since the takeover declaration (`git log --oneline <start-commit>..HEAD` and the change list for non-git material) — each change is labeled stabilization and maps to a `stabilize-now` risk-map row; confirm the critical-store restore test (DX-192) is recorded as performed or the "no verified recovery path" risk stands at the top of the report with a named owner; a named owner signs the takeover report (inventory, baseline, audit, risk map) in progress.md. Pass: no non-stabilization change in the range, restore status honestly recorded, report signed. Fail: block; takeover mode continues and the offending change is reverted or formally reclassified as the start of post-takeover work with the takeover declared failed and restarted. Recorded in: progress.md.

## Anti-patterns

- **The guided tour as inventory.** The takeover "inventory" is a summary of the predecessor's walkthrough call — fluent, confident, and unverified, with the unknowns edited out by politeness. Catch it by counting the `claimed` and `unknown` marks: a real first-week inventory of an unfamiliar project has many; an inventory that is all `verified` on day one is a transcript, not an audit (DX-186).
- **Baseline amnesia.** Nobody recorded the as-found test results, so every failure discovered later becomes an argument about whether the inheritance arrived broken or was broken by the new team. Catch it at G-DX-092: if the baseline record with its original outputs does not exist, the argument is already lost — re-running now produces a baseline of the current state, not the inherited one.
- **Stabilization creep.** Each stabilization change grows a small improvement, then a tidy-up, then a version bump, until the takeover branch is an unreviewable mixture and the as-found state is unrecoverable. Catch it by reading the takeover diff as a stranger: any hunk you cannot tie to a `stabilize-now` risk-map row in one sentence is creep (DX-191).
- **Risk map as obituary.** Findings are written up thoroughly — after the incident they predicted. The map exists but no row has an owner or a disposition, so it documents the disaster instead of preventing it. Catch it with G-DX-094's mechanical check: ownerless, dispositionless rows fail the gate no matter how well written the prose around them is.
- **The empty-chair audit.** The security sweep covers the code carefully and never asks who else can log in: the predecessor's personal cloud account, a contractor's still-active deploy key, a shared admin login in a password spreadsheet. Catch it by reading the DX-184 access map next to the DX-188 audit — if the audit names no accounts, it audited the software and skipped the system.

## Recall anchors

- Understand and secure first — no feature work, no cleanup, no upgrades until the protocol completes.
- Inventory before opinion; every item is verified, claimed, or unknown — and only reproduction earns "verified."
- Preserve the as-found state, record the as-found baseline; later arguments are settled by those two records.
- A found live secret is a compromised secret: rotation is the closure, not deleting the file.
- Every finding leaves takeover with a disposition and an owner — stabilize, register, schedule, or a named acceptance.

## Checklist

- [ ] Takeover declared in progress.md with source and starting commit/snapshot; scope frozen (DX-181, DX-183).
- [ ] Inventory complete against independent sources; every item marked verified/claimed/unknown (DX-182, G-DX-091).
- [ ] Access and ownership map written, including everything held only by the predecessor or by nobody (DX-184).
- [ ] Project runs from a clean clone using only repo instructions; every undocumented step logged as a finding (DX-185, G-DX-092).
- [ ] As-found baseline (build, test counts, smoke results) recorded before any change (DX-187).
- [ ] Security audit and DET sweep done; hits recorded by ID; every live secret rotated (DX-188, DX-189, G-DX-093).
- [ ] Critical data store restore-tested, or "no verified recovery path" stands as a top risk (DX-192).
- [ ] Risk map complete: every finding has likelihood, impact, owner, and one disposition (DX-190, G-DX-094).
- [ ] Every change since the declaration is a separate, labeled stabilization change — nothing else (DX-191, G-DX-095).
- [ ] Takeover report signed by a named owner; post-takeover work handed to tech-debt, refactoring, legacy-migration, or dependency-management, not started here (DX-190, G-DX-095).
