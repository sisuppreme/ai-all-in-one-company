## When to use / Do NOT use

- **Use when:** setting up or reviewing a release pipeline, publishing any artifact others will run or deploy, or stating a build-integrity claim (SLSA level) for a release.
- **Do NOT use when:** choosing or patching the dependencies themselves (use dependency-safety — it owns selection and vulnerability scanning; this skill owns how what ships was built) or auditing a finished release after the fact (use security-audit).

## Rules

1. **SE-121 — Platform-built releases only.** Every release artifact is built by the hosted, access-controlled build platform from a named commit in version control. If an artifact cannot be rebuilt from that commit by the platform, it does not ship.
2. **SE-122 — Platform-generated provenance.** Every release artifact carries build provenance — builder identity, source repository, commit, and materials — generated by the build platform itself (SLSA Build L1 minimum). Provenance written by the release engineer is documentation, not evidence.
3. **SE-123 — Signed provenance; isolated builders for high-value targets.** The build platform signs the provenance (SLSA Build L2) and the signing identity is recorded in the release record. Artifacts that hold payments or sensitive personal data are built on hardened, isolated, ephemeral runners (SLSA Build L3).
4. **SE-124 — Immutable, digest-pinned artifacts.** Release artifacts are never overwritten in the registry, and every deploy and run step references them by digest (`image@sha256:…`), never by a mutable tag alone.
5. **SE-125 — Verify before anything runs.** Every consumer and deploy step verifies the artifact's signature and digest against the build record before executing it; a failed or missing verification stops the deploy.
6. **SE-126 — Pin build inputs by SHA or digest.** Third-party CI actions and build plugins are referenced by full commit SHA or digest, never by tag or branch, so a re-pointed tag cannot change what runs in the pipeline.
7. **SE-127 — Protect the source side.** The default branch requires review and passing status checks, force-push is disabled, and release tags are signed where the platform supports it (the repository side graded by the SLSA Source Track).
8. **SE-128 — SBOM per release.** The pipeline generates an SBOM (SPDX or CycloneDX) for each shipped artifact and stores it with the release record. Dependency selection and vulnerability scanning of its contents are owned by dependency-safety.
9. **SE-129 — Pinned is not frozen.** Pinned actions, plugins, and base images are updated through reviewed automation (Dependabot, Renovate, or equivalent) on a schedule; a pin that is never updated is an unpatched dependency with extra steps.
10. **SE-130 — State SLSA claims precisely.** A level is claimed per artifact ("Build L2") and only for artifacts the pipeline actually produced that way. Provenance states where an artifact came from; it never claims the code is safe.
11. **SE-131 — Rehearse the compromise drill.** A written drill exists and is rehearsed at least annually, with the date recorded: revoke the compromised credential, rotate its replacements, re-issue affected artifacts — in that order.

## BAN list

- **BAN-SE-061 — Laptop-built release.** Banned: building a release artifact on a developer machine and pushing or copying it into the registry or production. Defeats: DET-INF-004. Bad: `docker build -t app:1.4.0 . && docker push app:1.4.0` from a workstation, then deploying it. Instead: tag the commit and let the build platform build, generate provenance, and push; deploy the resulting digest. Severity: BLOCK.
- **BAN-SE-062 — Mutable-tag deploy.** Banned: deploying or running an artifact referenced by a mutable tag (`app:latest`, `app:1.4`) with no digest pin. Defeats: DET-INF-026. Bad: `kubectl set image deploy/app app=registry/app:latest`. Instead: deploy the exact digest the build produced and verified — `app=registry/app@sha256:<digest>`. Severity: BLOCK.
- **BAN-SE-063 — Tag-pinned CI action.** Banned: referencing a third-party CI action or build plugin by tag or branch. Defeats: DET-INF-026. Bad: `uses: actions/checkout@v4` or `uses: some-org/deploy-action@main`. Instead: pin the full commit SHA — `uses: actions/checkout@<40-char-sha> # v4` — and let update automation propose SHA bumps. Severity: BLOCK.
- **BAN-SE-064 — Self-attested provenance.** Banned: a provenance or attestation file written by hand, by script outside the build platform, or generated after the artifact was built. Defeats: DET-INF-004. Bad: the release engineer fills in `provenance.json` (builder: "my laptop", commit: "latest") and uploads it beside the artifact. Instead: the build platform generates and signs provenance as part of the build; if the platform cannot, the artifact ships with no provenance claim at all. Severity: BLOCK.
- **BAN-SE-065 — Unreviewed release path.** Banned: direct commits or force-pushes to the release branch, or a release cut from a branch that skipped required review and status checks. Defeats: DET-CODE-031. Bad: `git push --force origin main` to land a hotfix minutes before building the release from it. Instead: land the change by pull request with required review and checks green, then tag the merged commit for the platform build. Severity: BLOCK.

## Gates

- **G-SE-061 — Provenance verification.** Verifies: SE-122, SE-123, SE-125. Check: the release pipeline runs a verification step (e.g. `slsa-verifier verify-image <image>@sha256:<digest>` or the build platform's native attestation check) and the release job fails if provenance is absent, unsigned, or mismatched. Pass: verification step present, enforced, and green for the released digest. Fail: block the release. Recorded in: progress.md.
- **G-SE-062 — Build-to-deploy digest match.** Verifies: SE-124, SE-125. Check: compare the digest recorded at build time with the digest in the deployed manifest — `diff <(cat build/digest.txt) <(grep -o 'sha256:[a-f0-9]\{64\}' deploy/production.yaml | head -1)`. Pass: digests identical. Fail: block shipment and redeploy the built digest. Recorded in: progress.md.
- **G-SE-063 — CI pinning lint.** Verifies: SE-126, SE-129. Check: `grep -rhn "uses:" .github/workflows/ | grep -vE "uses: [^@]+@[a-f0-9]{40}\b" | grep -v "uses: \./"` (or the equivalent scan of the project's CI config). Pass: no third-party action referenced by tag or branch; local path actions exempt. Fail: block shipment until pinned. Recorded in: progress.md.
- **G-SE-064 — Drill and claims review.** Verifies: SE-130, SE-131. Check: manual — read the drill record and every SLSA claim in the release notes and README. Pass: a drill dated within the last 12 months names the revoke → rotate → re-issue order and its participants, and each claimed level names the artifact and pipeline that produced it. Fail: remove the claim and schedule the drill before the next release. Recorded in: progress.md.

## Anti-patterns

- **Provenance theater.** An attestation file sits beside the artifact, but it was written by a person or a post-build script. Catch it: ask which build-platform identity signed it; no signer identity, no provenance.
- **Level inflation.** Docs claim "SLSA L3" for the product while releases come from a shared, persistent runner. Catch it: match each claimed level to one artifact digest and its build record.
- **Verify-in-name-only.** The pipeline has a signature-check step that logs a warning and continues on failure. Catch it: read the step's exit behavior, not its name.
- **Pin-and-forget.** Actions and base images are SHA-pinned — to versions from two years ago with known vulnerabilities, and no update automation is configured. Catch it: check the update bot's config and the date of the last merged pin bump.

## Recall anchors

- If the platform cannot rebuild it from a named commit, it does not ship.
- Provenance is generated and signed by the builder — never written by a person.
- Deploy digests, not tags.
- Pin actions by SHA; update the pins on a schedule.
- A SLSA level is claimed per artifact, and it proves origin, not safety.

## Checklist

- [ ] Release artifact was built by the platform from a named, reviewed commit (SE-121, SE-127).
- [ ] Platform-generated, signed provenance exists for the released digest (SE-122, SE-123).
- [ ] Deploy manifest references the artifact by digest, matching the build record (SE-124, G-SE-062).
- [ ] Verification step is enforced in the pipeline and green (SE-125, G-SE-061).
- [ ] No CI action or plugin is referenced by tag or branch (SE-126, G-SE-063).
- [ ] SBOM for the shipped artifact is stored with the release record (SE-128).
- [ ] Any SLSA level claimed names its artifact; compromise drill is dated within 12 months (SE-130, SE-131).
