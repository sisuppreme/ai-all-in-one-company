## When to use / Do NOT use

- **Use when:** building or reviewing anything that creates, carries, rotates, or ends a login session — cookie sessions, server-side session stores, or signed session tokens — in a web application.
- **Do NOT use when:** the work is credential verification, password policy, or login rate limiting (use auth-hardening), token-based API authorization between services (use api-security), or a formal ASVS verification pass (use security-audit).

## Rules

1. **SE-021 — Server-issued, high-entropy session IDs only.** Every session ID is generated by the server with at least 128 bits of entropy from a CSPRNG and is either stored server-side or carried in a signed, server-verifiable token. A session ID supplied or invented by the client is never adopted.
2. **SE-022 — Session IDs travel in cookies, never in URLs.** No route accepts a session ID from a query string, path segment, or form field; URLs containing one are rejected, and session IDs never appear in links, redirects, or logs of full URLs.
3. **SE-023 — Rotate at authentication and at every privilege change.** A new session ID is issued at login and whenever privilege level changes (role elevation, MFA completion, account recovery); the pre-change ID is invalidated server-side in the same request.
4. **SE-024 — Cookie attributes set explicitly, per cookie.** Every session cookie is set with `Secure`, `HttpOnly`, and `SameSite=Lax` (`Strict` where the flows allow), with `Path` scoped to the application. Framework defaults are verified by the cookie-assertion gate, never assumed.
5. **SE-025 — Idle timeout enforced server-side.** A session untouched for longer than the idle limit in the project session policy is rejected by the server on its next request, regardless of what client-side code does.
6. **SE-026 — Absolute timeout enforced server-side.** A session older than the absolute limit in the project session policy is rejected even if it has been continuously active; re-authentication is required to continue.
7. **SE-027 — Logout invalidates server-side.** Logout destroys the session record (or revokes the token) on the server in the same request that clears the cookie; replaying the logged-out ID returns an authentication failure.
8. **SE-028 — Password change invalidates the account's other sessions.** A password change or reset kills every other live session for that account; if the platform cannot do this, the user is told plainly on the confirmation screen that other sessions remain signed in.
9. **SE-029 — Remember-me is a separate token, never a stretched session.** Remember-me uses its own long-lived, revocable token with its own storage and its own revocation path; the session's idle and absolute limits are never extended to imitate it.
10. **SE-030 — One written session policy, read by the code.** Idle limit, absolute limit, cookie attributes, and rotation points are recorded once in the project's session policy (config or doc), the runtime configuration is generated or checked from it, and the CI lint gate compares the two.
11. **SE-031 — Session visibility for sensitive accounts.** Accounts holding payments or sensitive personal data can list their active sessions (device, approximate location, last activity) and revoke any one of them; revocation takes effect server-side immediately.
12. **SE-032 — No session change ships without the test pack.** Any change to session creation, rotation, timeout, or invalidation code runs the session test pack (fixation, replay after logout, expired-ID reuse, cookie assertions) in CI and it must pass before merge.

## BAN list

- **BAN-SE-011 — Session ID in a URL or accepted from the client.** Banned: carrying the session ID in a query string, path, or form field, or adopting an ID the client proposed. Defeats: DET-CODE-020. Bad: `GET /account?sid=9f31…` works, and the app also honors a `sid` cookie value it never issued. Instead: issue IDs server-side only and transport them solely in the session cookie. Severity: BLOCK.
- **BAN-SE-012 — Login that keeps the pre-login session ID.** Banned: authenticating a user into the same session ID they held anonymously before login. Defeats: DET-CODE-020. Bad: an attacker plants a known anonymous ID in the victim's browser, the victim logs in, and the planted ID is now an authenticated session (fixation). Instead: issue a new ID at authentication and invalidate the pre-login ID in the same request (SE-023). Severity: BLOCK.
- **BAN-SE-013 — Session cookie relying on framework defaults.** Banned: setting the session cookie without explicitly declaring `Secure`, `HttpOnly`, and `SameSite`, because the framework "probably" sets them. Defeats: DET-INF-014. Bad: the framework default ships a cookie with no `Secure` flag, so the session also travels over plain HTTP. Instead: declare all attributes in the session policy and assert them on every `Set-Cookie` in the gate (SE-024). Severity: BLOCK.
- **BAN-SE-014 — Logout that only clears the browser cookie.** Banned: a logout handler that expires the client cookie while the server-side session stays valid. Defeats: DET-CODE-003. Bad: after "logout," replaying the captured session ID still returns the account page. Instead: destroy or revoke the session server-side in the logout request, then clear the cookie (SE-027). Severity: BLOCK.
- **BAN-SE-015 — Predictable IDs or a hardcoded token secret.** Banned: session IDs derived from timestamps, counters, usernames, or a non-cryptographic RNG, or a session-token signing secret committed in source. Defeats: DET-CODE-018. Bad: IDs are `base64(userId + loginTimestamp)`, and the HMAC key is the string `"dev-secret"` in the repo. Instead: draw IDs from a CSPRNG at ≥128 bits of entropy and load signing secrets from the secrets store (SE-021). Severity: BLOCK.

## Gates

- **G-SE-011 — Cookie-attribute assertion.** Verifies: SE-024. Check: automated test client performs login and every authenticated request flow, captures each `Set-Cookie` for the session cookie, and asserts `Secure`, `HttpOnly`, and `SameSite=Lax` (or `Strict`) are present. Pass: every captured session cookie carries all three attributes. Fail: block shipment. Recorded in: progress.md.
- **G-SE-012 — Fixation and rotation test.** Verifies: SE-021, SE-023. Check: automated test records the anonymous session ID, logs in with it, and asserts (a) the post-login ID differs and (b) a request bearing the pre-login ID is rejected. Pass: ID changed and old ID rejected. Fail: block shipment. Recorded in: progress.md.
- **G-SE-013 — Replay-after-logout test.** Verifies: SE-027. Check: automated test logs in, captures the session ID, logs out, then replays the captured ID against an authenticated route. Pass: replay returns 401 or a redirect to login. Fail: block shipment. Recorded in: progress.md.
- **G-SE-014 — Session configuration lint (CI).** Verifies: SE-025, SE-026, SE-030. Check: CI script compares the runtime session configuration (idle limit, absolute limit, cookie attributes, rotation points) against the project session policy file and fails on any mismatch or on a missing idle/absolute limit. Pass: config matches policy and both limits exist. Fail: block merge. Recorded in: progress.md.
- **G-SE-015 — Expired-ID reuse test.** Verifies: SE-025, SE-026. Check: automated test runs with policy limits shortened to seconds, creates a session, waits past the idle limit (and, in a second case, past the absolute limit with continuous activity), then replays the ID. Pass: both replays are rejected. Fail: block shipment. Recorded in: progress.md.

## Anti-patterns

- **Client-side-only timeout.** A JavaScript timer "logs the user out" by hiding the page while the server still accepts the session ID — visible in review when no server middleware checks session age.
- **Signed token with no revocation path.** A self-contained token is treated as the session, so logout and password change cannot actually kill it; catch it by asking, during drafting, "what server state changes when this user logs out?"
- **Tutorial timeouts, unwritten policy.** Idle and absolute values copied from a blog post live only in framework config, with no project session policy for the lint gate to check against.
- **Happy-path-only session tests.** Tests prove login works but never replay an old, rotated, or expired ID — the absence of a negative session test in the suite is the tell.
- **One endless admin session.** Back-office sessions exempted from idle and absolute limits "for convenience," making the most privileged sessions the longest-lived.

## Recall anchors

- The server issues the ID; the client only carries it.
- New privilege, new ID — the old one dies in the same request.
- Attributes are declared, never assumed.
- Logout is a server event, not a browser event.
- Idle and absolute: both clocks run on the server.

## Checklist

- [ ] Session IDs are server-generated from a CSPRNG at ≥128 bits of entropy, and no client-supplied ID is ever adopted (SE-021).
- [ ] No URL, form, or link carries a session ID (SE-022).
- [ ] Login and every privilege change rotate the ID and invalidate the previous one (SE-023).
- [ ] Every session cookie declares `Secure`, `HttpOnly`, and `SameSite`, and G-SE-011 passes (SE-024).
- [ ] Idle and absolute limits from the written session policy are enforced server-side, and G-SE-014 and G-SE-015 pass (SE-025, SE-026, SE-030).
- [ ] Logout and password change invalidate sessions server-side, and G-SE-012 and G-SE-013 pass (SE-027, SE-028).
- [ ] Remember-me, if present, is a separate revocable token with its own storage (SE-029).
- [ ] The session test pack ran green in CI for this change (SE-032).
