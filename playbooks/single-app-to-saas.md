# Playbook: Single-App-to-SaaS

An existing app built for one client — one organization, one set of users, data that all belongs to the same owner — is converted into a product that many unrelated customer organizations use from one deployment, sign themselves up for, and pay for by subscription. The app already works; that is the trap. Almost every assumption the codebase makes silently — "all rows are ours", "the admin can see everything", "if it matters, we set it up by hand", "nobody is billed, so nothing checks entitlement" — is exactly the assumption multi-tenancy breaks. This playbook changes those assumptions in a safe order, with the existing client still running on the system throughout: they become tenant #1, not a migration casualty.

## Goal

Convert the single-client app into a multi-tenant SaaS in staged, reversible steps: tenant isolation retrofitted onto the existing data and proven by a cross-tenant test suite before any second tenant exists, the original client migrated as tenant #1 with their workflows unchanged, subscription billing and entitlement added as a separate layer that never entangles itself with core app logic, and hand-held setup replaced by self-serve signup, provisioning, and onboarding — with no big-bang cutover, no cross-tenant data exposure at any stage, and every gate below green at the step that owns it.

## Departments + order

Step 0 (always-on core) → D1 (audit + conversion requirements) → D2+D7 (tenancy architecture + threat model) → D5+D4 (isolation retrofit + tenant #1 migration) → D1+D11 (pricing + billing) → D3+D13+D18 (self-serve signup + onboarding) → D14 (legal) → D12 (per-tenant observability, explicit step) → D7+D8 (verification) → D6 (staged cutover)

**Order deviations (and why they are the point of this playbook):**

- **Isolation before billing, billing before self-serve.** The SaaS Web App playbook builds D11 billing inside a product that already has tenants. Here the order is a safety sequence, not a preference: a second tenant must never be able to exist before isolation is proven (step 3 before step 5), and strangers must never be able to sign up before entitlement exists to say what they may use (step 4 before step 5). Reversing either pair creates the mission's worst failure modes — a leak, or free unlimited use — by construction.
- **D18 is a build step, not a conditional extra.** In the SaaS playbook, onboarding is conditional step 6b. Here self-serve *replaces* the hand-holding the single client received — provisioning by hand, setup done for them, questions answered by the developer personally — so onboarding, trial handling, and support surfaces are core conversion work (step 5), not an add-on.
- **D6 is a staged migration, not a deploy.** The system is already in production for a real client. Deployment here means moving live tenants through cohorts (tenant #1 first, alone, then invited tenants, then open signup), each cohort separately reversible — never one cutover weekend.

## Docs to write first

Before any code changes, scaffold from `project-templates` (the existing app keeps its own repo and history — the conversion docs are added to it, not started in a fresh project) and write:

The full mandated set for this type is `templates/mandated-manifest-single-app-to-saas.txt`, which governs (G-PM-001); the list below is the hand-written starting subset, not the whole set.

- `CONVERSION_AUDIT.md` — the saas-conversion skill's audit output: every place the codebase assumes one client. Queries with no owner scoping, global settings and singletons, hard-coded client name/branding/limits, file storage paths with no owner segment, background jobs and caches with no tenant key, admin surfaces that see all data, and every integration credentialed to the one client. Each finding gets a disposition: retrofit, replace, or explicitly out of scope with a reason. Nothing in steps 2–5 is designed from memory of the app; it is designed from this audit.
- `requirements.md` — the conversion requirement set: who the future tenants are (organization size, how they will be found, what "a tenant" contains — users, seats, data), what tenant #1 must experience (ideally: nothing changes), what is explicitly *not* converting (features that stay bespoke for tenant #1 are named, priced, and fenced off, or they silently become every tenant's expectation).
- `fact-sheet.md` — the SaaS product's verifiable commitments once it launches: plan names, prices, limits, trial terms, data-retention and export promises. Prices here must mirror the billing configuration written in step 4; until step 4 exists, the sheet records no price as final.
- `TENANCY.md` — the tenancy model record: the isolation model chosen in step 2 (from `multitenancy-saas`), how tenant context is established and propagated (request, job, cache, storage), the tenant key's place in the schema, and the list of surfaces exempt from tenant scoping (public pages, billing webhooks, platform admin) with the reason for each exemption. Every exemption is a named, reviewed hole in the wall — there are no unlisted ones.
- `MIGRATION_PLAN.md` — the staged cutover plan: how existing data gains a tenant, how tenant #1 is created and backfilled, the cohort order for steps 3 and 9, the verification queries run after each stage, and the rollback for each stage written *before* the stage runs.
- `BILLING.md` — the entitlement design: plans, what each plan entitles (features, seats, limits), where entitlement is checked (one enforcement point at the service boundary — never scattered through app logic, never trusted from the client), what happens on trial end, payment failure, cancellation, and downgrade, and tenant #1's arrangement (grandfathered plan, comped account, or a real subscription — decided and recorded, never left as "they just don't have a billing row, so checks skip them").
- `progress.md`, `DECISIONS.md` — session log and decision record, including every stage result from `MIGRATION_PLAN.md`.
- `.env.example` — additions by name + purpose only (§5.9): billing provider keys (test and live listed separately), webhook signing secret, per-environment database credentials. The existing client's provider credentials, if the app holds any, are inventoried here too — step 3 decides whose they become.

## Step-by-step sequence

**Step 0 — Core and scaffold.** Load `bundles/core.md`; add the docs above to the existing project (G-PM-001, G-PM-002); load `secrets-management` before any billing credential exists. Take and verify a full backup of the production database and file storage now, and record the restore drill date — every later stage's rollback depends on it (G-DB-101 backup-recovery gates). A conversion that cannot restore the one client's data is not started.

**Step 1 — Audit and conversion requirements (D1, with saas-conversion).** Run the saas-conversion audit and write `CONVERSION_AUDIT.md`; pass the saas-conversion skill's gates for the audit stage. Write `requirements.md` from it: the tenant definition, tenant #1's no-change guarantee, the bespoke fence, and the launch scope (which cohorts, which plans, whether a free trial or free tier exists). Requirements lint and traceability apply as usual (G-PR-031, G-PR-032) — every audit finding traces to a requirement or a recorded out-of-scope disposition, and every requirement traces to an audit finding or a named business decision. *What differs from building new:* a greenfield SaaS requirements doc describes a product; this one describes a *delta* — anything the audit missed is a single-tenant assumption still live in production, so audit completeness, not feature ambition, is this step's quality bar.
◆ **DECISION — what is a tenant, and what happens to tenant #1's bespoke parts?** One organization with many users, or one user per tenant? Are tenant #1's custom features productized for everyone, kept as a private tier, or retired by agreement? The answers decide the schema in step 3 and the plans in step 4; if unspecified, ask (§6.3 step 4). (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer; if none is recorded and no user is reachable, follow the §6.3 stuck protocol (log-and-continue, then the safe defaults) and record the substitution in `progress.md`.)

**Step 2 — Tenancy architecture + threat model (D2+D7).** Choose the isolation model under `multitenancy-saas` (G-AR-091–G-AR-094): shared schema with a tenant key, schema-per-tenant, or database-per-tenant — chosen against the audit's data shape, the tenants' expected count and size variance, and the export/deletion duties step 6 will impose; record it as an ADR (G-AR-121) and in `TENANCY.md`. `data-architecture` places the tenant key and data ownership (G-AR-071); `system-design` records how tenant context flows — how it is established from the authenticated session (never from a client-supplied tenant identifier alone), and how it reaches queries, background jobs, cache keys, file paths, emails, and exports. The threat model (`threat-modelling`, G-SE-091) is re-weighted for conversion: the top threat is no longer an outsider breaking in, it is a *legitimate authenticated user of tenant A reading tenant B's data* through an unscoped query, a guessable ID, a shared cache key, a job that processes "all rows", or an export built from an admin view. Every surface in the audit gets a line in the threat model.
◆ **DECISION — isolation model.** This is the hardest decision in the playbook to reverse: it shapes the schema, the migrations, per-tenant export/delete, and hosting cost for the product's life. If the brief does not record it, ask (§6.3 step 4) — do not let a migration default choose it. (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer. If none is recorded and no user is reachable, the isolation model is never log-and-continued and never safe-defaulted: it is the conversion's load-bearing security decision, and §6.3 Step 5 forbids defaulting a position whose wrong branch exposes one tenant's data to another. Log the blocker in `progress.md` (§6.3 step 3), ask the user with concrete options (§6.3 step 4), and do not start the step 3 schema work on a substitution — a migration default must never choose this.)

**Step 3 — Isolation retrofit + tenant #1 migration (D5+D4).** The heart of the conversion, done in the saas-conversion skill's order, in small stages, with the app deployable and tenant #1 unaffected after each stage:
  1. *Add, don't enforce.* Tenant table and tenant key columns added nullable; tenant #1's row created; the backfill then assigns existing rows, files, and cache namespaces by the saas-conversion skill's stated ownership rules (AR-264, AR-265) — in the common case the rule "created under the one client's operation" assigns nearly everything to tenant #1, but it assigns *by rule, never by default*: rows no rule can assign go to the skill's orphan report for a human decision, and sweeping them into tenant #1 to make the count work is the banned default-tenant sweep (BAN-AR-133) — the audit's invisible-second-client case is exactly where a blanket assignment becomes a leak. Migrations per G-DB-061 reversibility, G-DB-063 from-empty build. The stage closes on the skill's backfill reconciliation gate (G-AR-132): zero NULL tenant keys, an empty orphan report, and per-tenant counts matching pre-conversion totals, recorded in `MIGRATION_PLAN.md` — a row with no decided owner after this stage blocks the stage, not just the count.
  2. *Resolve context.* `backend-auth` sessions now carry tenant context; `rbac` roles become per-tenant (a tenant's admin is not a platform admin; the old global admin becomes the platform-admin surface under `admin-tools` rules, separately authenticated and audited). Dual-read period: code resolves tenant context but does not yet reject its absence, while logging proves every request path actually carries it.
  3. *Enforce at the data layer.* `tenant-isolation` scoping becomes mandatory: tenant keys enforced by the database where the model allows (constraints, row-level policies), and by the data-access layer everywhere else (G-DB-051–G-DB-054). Background jobs, scheduled tasks, search indexes, and cache keys are converted and re-verified one by one against the audit list — these are where retrofits leak, because they were written when "all data" was one client's data. Only after enforcement is live are the key columns made non-nullable, in a separate migration with its own down-path.
  4. *Prove it with a synthetic tenant.* A test-only tenant #2 is created in staging with its own data, and the cross-tenant suite runs: as tenant #2, attempt to read, modify, export, and guess the IDs of tenant #1's objects through every route, job output, and file URL the audit listed. **No second real tenant is provisioned, in any environment a customer can reach, until this suite passes.**
◆ **STOP AND ASK — production data migration (§5.9/§6.3).** The backfill and the enforcement migrations run against the only client's live data. Each stage needs the user's explicit go-ahead, with the backup from step 0 verified restorable first (restore drill current, G-DB-101) and the stage's rollback rehearsed in staging. (Unattended run: a go-ahead recorded in the commissioning brief or `requirements.md` for the specific migration stage counts as the answer. If none is recorded and no user is reachable, the stage is never log-and-continued and never safe-defaulted — migrating the only client's live production data is a destructive-class action on the §6.3 Step 5 never list. Log the blocker in `progress.md` (§6.3 step 3), ask the user with concrete options (§6.3 step 4), and run no backfill or enforcement migration until the explicit go-ahead for that stage exists.)

**Step 4 — Pricing + billing, as a separate layer (D1+D11).** `pricing-monetization` sets plans and tiers from the requirements and the fact sheet (G-PR-101–G-PR-104); `unit-economics` sanity-checks that per-tenant cost (hosting, storage, support load the onboarding in step 5 must absorb) fits inside the lowest paid plan (G-PR-111). Billing is then built under D11 in **test mode only**: `subscriptions` for plan state (G-IN-011–G-IN-014), `payments` for checkout (G-IN-001), `webhooks` as the only writer of billing state — the app never trusts a browser redirect as proof of payment (G-IN-051–G-IN-055) — `invoicing-tax` for invoices (G-IN-031), `dunning` for failed-payment recovery (G-IN-041), `refunds-disputes` for the money-back paths (G-IN-021), and `transactional-email` for receipts and payment-failure notices (G-IN-061). **The entanglement rule:** app code asks one entitlement service one question — "may this tenant do this, now?" — and billing writes entitlement state from provider events. Plan checks never appear inside domain logic, domain tables never store card or provider subscription internals, and removing the billing provider must leave a working app whose entitlement service answers from local state. Tenant #1 is placed on their recorded arrangement from `BILLING.md` and their existing workflows are regression-tested with entitlement enforcement *on* — the conversion's classic self-own is tenant #1 locked out of their own app by a plan limit written for future strangers.
◆ **DECISION — trial and failure policy.** Free trial (card up front or not), what a trialing tenant can do, grace period on failed payment before restriction, and what "restricted" means (read-only, export-only, or suspended) are product decisions recorded in `BILLING.md` before `subscriptions` is configured — the provider's defaults are not a policy. (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer. If none is recorded and no user is reachable, trial and failure policy is never log-and-continued and never safe-defaulted: prices, charges, and payment consequences are money decisions on the §6.3 Step 5 never list, and the provider's defaults are not a policy here either. Log the blocker in `progress.md` (§6.3 step 3), ask the user with concrete options (§6.3 step 4), and do not configure `subscriptions` on a substitution.)

**Step 5 — Self-serve signup + onboarding (D3+D13+D18).** Replace the hand-holding, surface by surface, against a checklist drawn from what the developer used to do for tenant #1 personally: account and organization creation, inviting teammates and assigning per-tenant roles, initial configuration and data setup, first-value moment, and "something is wrong" help. `user-onboarding` builds signup, tenant provisioning (automatic, idempotent — a retried signup creates one tenant, not two), and the guided first-run (G-CX-031–G-CX-035); `forms` owns the signup and settings forms (G-FE-121); `trial-conversion` wires trial start, trial-end notice, and the convert-or-restrict path decided in step 4 (G-CX-051); `activation-metrics` defines the activation event so "signed up but never got value" is measurable from day one (G-CX-041); `help-center` and `support-ticketing` replace emailing the developer (G-CX-021, G-CX-001). D13 runs in the same step — `accessibility-audit` on signup, onboarding, billing, and settings templates (G-AC-001, G-AC-005): these are the surfaces every future tenant touches first, and retrofitting them later is the expensive version. Provisioning is exercised end-to-end by a fresh test signup that receives no human help at any point; every manual intervention the test still needs is an onboarding defect, logged and fixed here — not a launch-week chore.

**Step 6 — Legal and privacy (D14).** The data register is rewritten for multi-tenancy (G-LG-001, G-LG-002): the business is now a processor/controller for *many* organizations' data, and the register says so per data class. `legal-documents` produces the SaaS terms, privacy text, and DPA from the register (G-LG-031) — including the clauses a single-client app never needed: tenant data ownership, export on exit, deletion after exit, and sub-processors (the billing provider among them). `dsar-handling` is proven *per tenant*: one tenant's export contains only their data, and one tenant's deletion request deletes only their data (G-LG-021) — run both against the staging pair from step 3, not against a single-tenant fixture. `data-residency` commitments, if any are made in the fact sheet, are checked against where the database and backups actually run (G-LG-011). Tenant #1's existing contract is reviewed against the new terms: converting their app into a SaaS does not silently convert their agreement.

**Step 7 — Per-tenant observability (D12, explicit step).** `performance-budgets` are re-based per tenant class — one large tenant must not be able to make the product slow for all others invisibly (G-AN-101). `monitoring` and `apm` gain tenant dimension on errors, latency, job runs, and billing events, with tenant identifiers handled per the privacy register (an identifier in a log is still tenant data) (G-AN-051, G-AN-091). Two alerts are conversion-specific and mandatory before step 9: cross-tenant access-denial spikes (the isolation layer suddenly rejecting at volume usually means a context bug, not an attack — either way a human looks), and billing-webhook failure (entitlement state silently going stale is a revenue and lockout bug at once).

**Step 8 — Verification (D7+D8).** The full suite, weighted to conversion risks: the cross-tenant suite from step 3 re-run against the finished build, now including billing and onboarding surfaces (tenant A cannot see, alter, or be billed for tenant B; a webhook for tenant B's subscription cannot change tenant A's entitlement); authorization matrix per tenant role (G-BE-061 via `rbac`, G-SE-021-class coverage through `security-audit`, G-SE-101); OWASP pass with 0 critical findings (G-SE-001 via `owasp`); billing verified end-to-end in test mode — purchase, decline, renewal, cancellation, downgrade, webhook replay, dunning path (the D11 gates from step 4, re-run as a set); tenant #1 regression — their named core workflows from `requirements.md` pass unchanged with isolation and entitlement both enforced; secret scan (G-SE-041) and dependency gate (G-SE-051); placeholder sweep over all new public and onboarding surfaces (G-QA-141 — scan rendered output, not source). `qa-gates` records the full result set (G-QA-111). **No cutover until green — and a cross-tenant failure at this step is a P0 that stops the playbook, not a defect to schedule.**

**Step 9 — Staged cutover (D6).** CI/CD carries the conversion in the same stages `MIGRATION_PLAN.md` defines (G-DO-001, G-DO-004 gating-job integrity): cohort 0 is tenant #1 alone on the fully enforced build, watched through one full billing-relevant cycle of their normal use; cohort 1 is a small number of invited tenants onboarded through the self-serve path with the developer watching the step 7 dashboards, not helping by hand; open signup is enabled only after cohort 1 completes onboarding unaided. Each cohort has its rollback rehearsed (G-DO-151) and its go/no-go recorded in `progress.md`. Live billing keys are switched only at the cohort where real strangers first pay, only after the step 8 test-mode suite is green, and only with the user's explicit approval naming the switch. External production check on the public surfaces (G-DO-071).
◆ **STOP AND ASK — the live switch and open signup (§5.9/§6.3).** Enabling live billing keys and opening public signup are the two irreversible-in-effect moments of the conversion: real money and real strangers. Both require the user's explicit go-ahead. (Unattended run: a go-ahead recorded in the commissioning brief or `requirements.md` for the specific switch counts as the answer. If none is recorded and no user is reachable, neither switch is log-and-continued or safe-defaulted — live billing keys and public signup are money-bearing, irreversible-in-effect actions on the §6.3 Step 5 never list. Log the blocker in `progress.md` (§6.3 step 3), ask the user with concrete options (§6.3 step 4), and leave billing in test mode and signup closed until the explicit go-ahead exists.)

## Failure handling

- **Cross-tenant exposure, at any stage, in any environment a customer can reach:** P0 — stop the playbook. Close the hole in the owning step (usually step 3's data layer, not the one endpoint that happened to show it — audit the class, not the instance), re-run the full cross-tenant suite, and record the incident in `progress.md` without reproducing the exposed data. If exposure reached real tenants' data, that is a legal/privacy event: step 6's register and the D14 incident path govern disclosure, and the user is told immediately. No cohort advances while this is open, and "the route required login" is not mitigation — the attacker model here *is* a logged-in tenant.
- **Audit finding with no clean retrofit (step 1/3):** a component so single-tenant in design (a global report over all rows, a cache that cannot be keyed per tenant) that scoping it would rewrite it. Options, in order: rebuild that component tenant-scoped under this playbook; fence it to platform-admin or tenant #1's private tier with the fence recorded in `TENANCY.md` and `requirements.md`; or stop and ask (§6.3). Silently leaving it global is not an option — an unscoped surface left behind is a leak waiting for tenant #2.
- **Backfill leaves unassigned rows (step 3):** the stage does not advance. Find the rows' true owner from the data (creation context, related records), assign, and re-verify counts; rows that genuinely predate any owner become tenant #1's only by a recorded decision in `DECISIONS.md`, never by a default in the migration script.
- **Tenant #1 regression after enforcement (step 3/4/8):** roll back the stage, not the conversion — the dual-read and staged design exists precisely so tenant #1's work is never hostage to a retrofit stage. Diagnose against the audit (the usual causes: a job or report that legitimately served tenant #1 across what is now a tenant boundary, or an entitlement limit applied to the grandfathered account), fix, re-run the tenant #1 regression set, and only then re-apply the stage.
- **Billing gate fails in test mode (step 4/8, e.g. G-IN-011):** billing does not ship and self-serve signup does not open. Shipping with manual invoicing for invited cohort-1 tenants is a legitimate §6.3 option *only* with the user's agreement and entitlement still enforced locally; never debug billing against live keys, and never let "no billing row" mean "unlimited access" in the entitlement service.
- **Entitlement entangled with app logic (found at any review):** stop adding plan checks. Extract them to the entitlement service per `BILLING.md`, re-run the tenant #1 regression and billing suites, and record the extraction in `DECISIONS.md`. Entanglement found late only gets later; this is the one refactor the playbook does mid-flight rather than scheduling.
- **Self-serve test signup needs human help (step 5):** onboarding defect, fixed in step 5 — the help the test needed is the spec for what to build (a missing invite flow, an unexplained first-run step, a configuration the developer used to set by hand). Launching with a "just book a call with us" substitute for a broken step is a scope change and needs a `requirements.md` decision, not a landing-page sentence.
- **A gate fails (any other):** fix in the owning step, re-run; same failure twice → §6.3 (log in `progress.md`, continue unblocked work, batch blockers with concrete options).
- **Two skills contradict:** §5.7 precedence (security 1, legal 2, data integrity 8 above payments correctness 11 and backend convenience 9); log in `DECISIONS.md`. Note the conversion-specific consequence: tenant-isolation findings outrank billing deadlines — a launch date never waives an isolation gate.
- **A gate is itself wrong:** recorded waiver in `progress.md` + `DECISIONS.md` (§6.3 step 5); security/legal waivers — and any waiver touching tenant isolation — need explicit user agreement.
- **A secret leaks** (billing keys are the new risk this playbook adds): revoke/rotate immediately with the provider, re-issue webhook secrets, record the incident without the value (§5.9 step 4).

## Definition of done

- Tenant isolation is enforced at the data layer and proven by the cross-tenant suite on the shipped build: no tenant can read, modify, export, or infer another tenant's data through any route, job, file, cache, or billing surface the audit listed — with the audit's disposition list showing no unscoped surface left global without a recorded fence.
- Tenant #1 runs on the converted system as tenant #1: their data backfilled and verified, their named core workflows regression-green with isolation and entitlement enforced, their billing arrangement the one recorded in `BILLING.md`, and their agreement reviewed against the new terms.
- Billing works end-to-end in live mode for real tenants (purchase, renewal, failed payment through dunning to the recorded restriction, cancellation, refund) with entitlement answered by the single enforcement point and billing state written only from provider webhooks.
- A stranger can sign up, provision, invite a teammate, reach the activation event, and pay — with no human intervention — and the step 7 dashboards show each stage of that happening per tenant.
- Cutover completed by cohorts per `MIGRATION_PLAN.md`, each cohort's go/no-go and rollback rehearsal on record; open signup enabled by the user's explicit approval; zero P0/P1 defects open (QB-01).
- All gates in the table above pass, with results in `progress.md`; `CONVERSION_AUDIT.md`, `TENANCY.md`, `MIGRATION_PLAN.md`, `BILLING.md`, `DECISIONS.md`, `runbook.md`, and `handover.md` current — the runbook includes the per-tenant operations the single-client app never needed: provisioning failures, per-tenant export and deletion, entitlement correction, and webhook replay.
- **Pre-provisioning complete:** where later cohorts or live billing cannot proceed yet (no payment provider account approved, no invited tenants named), the conversion may be recorded as *pre-provisioning complete* when every gate except the provisioning-waived ones is green — isolation and tenant #1's migration may **not** be among the waived gates — each waived gate is recorded as a provisioning waiver per §6.3, and the unblocking conditions are listed in `progress.md`. Pre-provisioning complete is not done: the product is a SaaS when strangers can sign up and pay, not before.

## Worked mini-example

Sample project: **Stockroom**, a small inventory app built for one wholesaler — their staff track stock, suppliers, and purchase orders; the developer set up their account, imported their catalogue by hand, and answers their questions by phone.

1. Step 0: core loaded; conversion docs added to the existing repo; verified backup taken and restore drill recorded.
2. Step 1: the saas-conversion audit finds: product and purchase-order queries carry no owner scoping (there was only ever one owner); a nightly low-stock report runs over all rows; catalogue photos live under one shared folder; the wholesaler's name is hard-coded in the page header and PDF invoices; one "admin" login sees everything. Requirements define a tenant as one business with multiple staff, record the no-change guarantee for the wholesaler, and fence the phone-support habit into help-center + ticketing scope.
3. Step 2: isolation model chosen — shared schema with a tenant key, recorded as an ADR; the threat model's top entry is a future tenant reading another's purchase orders (prices and supplier terms are the sensitive data here, more than the stock counts).
4. Step 3, stage 1: tenant key added; the wholesaler becomes tenant #1; backfill assigns all products, orders, and photos; counts verified against pre-migration totals and recorded.
5. Step 3, stage 2–3: sessions carry tenant context; the old all-seeing admin becomes a platform-admin surface; the low-stock report and photo paths are made tenant-scoped; enforcement switched on in staging, then production, each behind the user's go-ahead with the restore drill current.
6. Step 3, stage 4: a synthetic second tenant in staging (a fictional corner shop with its own small catalogue) cannot see the wholesaler's orders, photos, or report output through any route the audit listed — including by editing an order ID in the URL. The cross-tenant suite passes.
7. Step 4: two plans are set in `BILLING.md` (a small-shop plan and a wholesaler plan, differing in product-count and seat limits); the wholesaler is recorded on a grandfathered arrangement at their existing fee. Subscriptions, checkout, and webhooks are built in test mode; entitlement is one service the app consults, and the wholesaler's own workflows pass regression with enforcement on.
8. Step 5: self-serve signup replaces the developer's setup ritual — a new business creates its organization, invites staff, and imports its own catalogue through an import screen built from the steps the developer used to perform by hand. A test signup completes with no help; the one snag (invited staff landing on an empty dashboard with no next step) is fixed as an onboarding defect.
9. Step 6: terms and DPA drafted from the rewritten register; a per-tenant export run in staging returns only the corner shop's data; the wholesaler's existing agreement is reviewed and a short addendum agreed rather than silently replaced.
10. Steps 7–9: per-tenant monitoring and the two conversion alerts go live; verification passes with 0 critical findings; cutover runs by cohort — the wholesaler alone first, then two invited shops onboard themselves through the self-serve path, then live keys are switched with the user's approval and signup opens. Done.
