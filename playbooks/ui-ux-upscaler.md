# Playbook: UI/UX Upscaler

Take an EXISTING web application with an EXISTING UI and upscale it to OmniForge's premium standard — 50x, not a restyle. This is not a greenfield build and not a redesign from a blank page: the live app is the asset, its users, content, data, routes, and behaviour are the constraints, and every step in this playbook is ordered so the upgrade can be evaluated pass by pass, staged, and rolled back — while the original app keeps working throughout. If a step in a new-build playbook and a step here conflict, this playbook wins for the upgrade: never trade a working app for a prettier one that breaks what users depend on.

**Scope: web apps ONLY.** This playbook covers web applications — sites and web apps rendered in the browser. Native mobile apps are out of scope: where the same product also ships a native app, the upgrade's decisions (theme, tokens, type scale, motion dial) may be recorded as an adaptation note for the native team, but no native specs, components, or motion systems are designed here. A native-app upgrade is a separate commission.

**The spine.** This playbook is the full mission form of the v1.3.0 Existing-Project Upgrade Protocol (7 steps) in `custom-instructions/claude.md` lines 83–175: audit first, preserve what works, theme decision, 7 staged passes in order, hard rules, score gate, report. The protocol governs; this playbook adds the mission machinery around it — the baseline, the per-pass gates, the leak audit, the staged rollout, and the evidence trail. Where the two disagree, the protocol's hard rules (Step 5) still win.

## Goal

Ship the upgraded app such that: it scores ≥ 64/80 on the design-intelligence self-critique gate (G-FE-162) with every category at threshold and both hard categories at 10; **zero architecture leaks** remain in any user-facing surface (AFTER leak score 0 — a leak is a veto, not a deduction); every audit defect is fixed or explicitly reported with a reason; zero behaviour regression against the pre-upgrade baseline; every staged pass is independently reversible and the rollback is proven by rehearsal, not asserted; and the upgrade is staged and reversible at every stage — full rollout is the last decision, not the default outcome of finishing the polish pass.

## Departments + order

Step 0 (always-on core) → **D17+D15 audit (retrofit audit + leak audit, before any design decision)** → D8+D3 baseline and regression capture → **D3 theme decision** → D3 staged passes 1–7, each gated by D8, with D13 inside pass 4 and D12 inside passes 5–6 → D3+D8+D13 score gate (score + leak veto) → D6 staged rollout → D10 report and handover

**Order deviations (three, each deliberate):** (1) The audit **and** the baseline come before any design decision — in a new build the theme can be chosen from the brief, but in an upgrade the theme must be chosen against evidence: what the app already is, what is broken, what must be preserved, and what leaks. A theme picked before the audit is a guess the passes then have to defend. (2) Accessibility is **not** a final pass: D13 runs inside the components pass (pass 4), where states are actually built, and is re-checked at every later pass — a motion or scroll pass applied after an accessibility sign-off can re-break focus order, contrast over animation, and reduced-motion behaviour, so the check must travel with the work, not follow it. (3) The score gate runs **per pass, not once at the end**: each staged pass is scored on the categories it touches before the next pass starts, and the full ≥ 64/80 gate runs at step 11. A single end-gate would let seven passes of drift accumulate into one unfixable verdict; per-pass scoring catches the lowest category while its owning pass is still open.

What differs from building new, and why the order follows from it:

- **The app already exists and already works.** Every change is measured against a working baseline, not against a blank page. A pass that improves the look and breaks a flow has failed, however good the screenshots are.
- **The design must bend around the product.** The app's real content, real data volumes, real user tasks, and real edge cases are the design material. Never delete a working feature to make the design easier; never simplify a flow out of existence because the theme has no pattern for it.
- **The upgrade is presentation-layer first.** Functionality, content, data, routes, APIs, and behaviour keep working. Anything structural the audit says must change gets its justification written in the audit file before it is touched.
- **Reversibility is a property of each pass, not of the release.** Each of the 7 passes lands as its own reversible unit (branch or flag, per `ROLLOUT.md`), so a bad pass rolls back alone and the other six stand.

**The leak principle (governs every skill load above).** The UI agent USES all of the app's skills to understand the app — its data model, its architecture, its integrations — but surfaces NONE of their internals in the UI. Understanding is not display. A skill's knowledge is an input to design judgment; it is never content for a screen.

## Docs to write first

Before any design work — and, except for the baseline capture in step 2, before any change of any kind to the app — scaffold from `project-templates` and write:

- `UI-UPGRADE-AUDIT.md` — the audit file, at the project root. Template contents: (1) header — app name, current deployed version, audit date, auditor; (2) **BEFORE score** — the design-intelligence §5 score per category (0–10 each) with the evidence (screenshots at 1440 px and 390 px) behind each number; (3) **defect list** — every instance of AI slop found (mapped to the design-intelligence anti-slop table §4), every missing system (design tokens, type scale, motion system, scroll experiences, UI states, reduced-motion handling), every hard-rule violation (heavy custom cursor, content an animation can leave invisible, pasted-on decoration); (4) **leak audit** — see step 1 below: every architecture leak found, its surface, its category, and the BEFORE leak score (count of leaks); (5) structural-change justifications — anything the audit says must change structurally, with the justification written before it is touched; (6) what is deliberately left unchanged, with reasons; (7) closing section, filled at step 13 — the before/after summary (defects found, passes applied, BEFORE → AFTER score, BEFORE → AFTER leak score, anything left and why). Nothing is exempt from the audit: not the landing page only — every page and component.
- `BASELINE.md` — the regression baseline: the existing test suites and their results *before* any change, the critical-flow list (the flows existing users actually depend on) exercised by hand or by automation with their results, the measured performance numbers (load, interaction latency) with source and date, and the visual baseline — reference screenshots of every page at 1440 px and 390 px. Every later "no regression" claim traces to this file; a baseline written after the passes start proves nothing.
- `DECISIONS.md` — the decision record: the theme decision and its reasoning (step 3), every rejected alternative with why, the dial setting (design-intelligence FE-323, set once per page by content type), what is deliberately left unchanged, and every scope or structural decision taken during the passes. The decision record is checked at G-FE-161.
- `TOKEN_MAP.md` — the token map: every hard-coded value found in the app (hex colours, pixel spacing, font sizes, radii, shadows, durations, easings) mapped to the token it becomes in the single token source. A value with no token after pass 1 is a pass-1 failure, not a leftover.
- `ROLLOUT.md` — per-pass rollout: the branch or flag strategy for each of the 7 passes, the entry and exit criteria for each pass, the order the passes reach users (all passes staged, never big-bang), the metric that stops promotion, and the rollback procedure per pass: who rolls back, how fast the previous pass state is restored, and how that was rehearsed. A pass with no rehearsed rollback does not ship.
- `progress.md` — session log with gate results per pass, scores per pass, and the leak-score trail.

## Step-by-step sequence

**Step 0 — Core and scaffold.** Load `bundles/core.md`; generate the project files (G-PM-001, G-PM-002); write the docs above as stubs to be filled by steps 1–3; load `secrets-management` before any credential is touched. Record the app's current deployed version in `progress.md` — the upgrade is always described relative to a named, working release.

**Step 1 — Audit, including the leak audit (D17+D15+D3, no design, no fixes).** Run `ui-ux-upscaler` and `design-intelligence` over the whole app: scan every page and component against the design-intelligence anti-slop table (§4) and the UI/UX skills (design-system, design-tokens, typography, layout-responsive, component-library, ui-states, motion, scroll-experiences, webgl-3d). Score the app with the design-intelligence §5 gate and record the BEFORE score in `UI-UPGRADE-AUDIT.md`. Run `ai-retrofit` where the audit needs a structural read of the host app (seams, synchronous flows that cannot absorb animation or layout change, fallback behaviour) and `prototype-hardening` where the app is a prototype. **Leak audit (inside this step, not beside it):** walk every user-facing surface — every page, every component, every empty/error/loading state, every tooltip, label, placeholder, footer, settings screen, and error message — and record every place the app's structure or architecture shows through. The hard ban list, verbatim: **no DB names/types, no table/collection names, no page/route counts or structures, no API endpoints, no internal module/service names, no tech-stack labels, no schema/field names — UI expresses user-facing concepts only.** Each leak is recorded with its surface, its category from the ban list, and the leaking text verbatim. The BEFORE leak score is the count of leaks found. A surface the auditor has not walked is recorded as unaudited, never assumed clean. Nothing is fixed in this step — a fix made before the audit and baseline are complete is a fix made without knowing what outranks it, and a leak fixed before it is counted corrupts the BEFORE score.
◆ **DECISION — what is the app's identity: keep and deepen, or replace from the theme library?** If the app already has an identity worth keeping, the upgrade deepens it (full tokens, type scale, motion and scroll systems in its own style). If it has no identity, or its identity is generic AI slop, the theme decision at step 3 replaces it. Record the direction here, in `UI-UPGRADE-AUDIT.md`, with the evidence that supports it. (Unattended run: BOOTSTRAP's approval-points rule applies — a decision recorded in the commissioning brief or `requirements.md` counts as the answer; if none is recorded and no user is reachable, follow the §6.3 stuck protocol and record the substitution in `progress.md`. The safe default is keep-and-deepen: never replace an app's identity on a substitution.)

**Step 2 — Baseline and regression capture (D8+D3, before any change).** Freeze the baseline before designing anything: run the existing suites, exercise the critical flows by hand or automation, capture the reference screenshots, and record everything in `BASELINE.md`. Write the keep-working list into `requirements.md` (the flows that must work after every pass and after rollout — everything not on the list is out of scope for the upgrade). Re-run the leak audit's count against the baseline screenshots so the BEFORE leak score is evidenced by captures, not memory.
◆ **STOP AND ASK — a structural change the audit says is required (§5.9/§6.3).** If the audit says a structural change is required (a flow must be re-laid-out, a screen split or merged, a navigation structure changed), that change is user-approved work, not a build detail: the justification is written in the audit file first, and the user approves the specific change before the pass that makes it begins. (Unattended run: a go-ahead recorded in the commissioning brief or `requirements.md` for the specific structural change counts as the answer. If none is recorded and no user is reachable, the structural change is never log-and-continued and never safe-defaulted — changing what the app *is* is a scope decision on the §6.3 Step 5 never list. The passes proceed around it (design bends around the existing structure), the blocker is logged in `progress.md` (§6.3 step 3), and the user is asked with concrete options (§6.3 step 4).)
◆ **STOP AND ASK — retiring a feature to make the design easier.** Retiring a feature is banned without explicit approval. "Bend the design around the product, never the product around the design" — if a pass would be easier with a feature gone, the pass is redesigned, not the product. A feature-retirement proposal goes to the user with the audit evidence; until approval exists, the feature stays and the design accommodates it. (Unattended run: never log-and-continued, never safe-defaulted — same never-list treatment as the structural-change point above.)

**Step 3 — Theme decision (D3).** Run the design-intelligence decision system (§1) in order: theme, layout family, motion-intensity dial (set once per page by content type, FE-323), colour posture, typography posture — plus at least one named alternative rejected and why (FE-321, checked at G-FE-161). If the identity is kept, give it the full treatment. If it is replaced, select a theme from the theme library using the design-intelligence decision process and adopt that theme's full system — its palette anchors, typography, motion system, and scroll choreography — applied to the app's own content. Build from the theme's canonical expanded spec (`skills/frontend/theme-library/expanded/theme-NNN.md`, zero-padded) end to end, never from a range-index entry, a summary, or memory (G-FE-171). Record the decision and its reasoning in `UI-UPGRADE-AUDIT.md` and `DECISIONS.md`.
◆ **DECISION — theme, and what is deliberately left unchanged?** Record both halves in `DECISIONS.md`. The not-list matters as much as the pick: it stops scope creep mid-pass, when every adjacent screen suddenly looks like it also needs the new theme's full treatment. If unspecified, ask (§6.3 step 4). (Unattended run: BOOTSTRAP's approval-points rule applies; if none is recorded and no user is reachable, follow the §6.3 stuck protocol and record the substitution in `progress.md`. The safe default is the keep-and-deepen direction from step 1, or the single highest-ranked theme where no identity exists; never "all candidate themes".)

**Step 4 — Pass 1: Design tokens (D3).** One token source (colour, spacing, radii, shadows, durations, easings); no hard-coded values left outside it. Work `TOKEN_MAP.md` to zero: every hard-coded value in the app maps to a token, and a grep for hard-coded hex colours and pixel values outside the token source returns near zero. *Entry criterion:* audit and baseline complete, theme decided. *Exit criterion:* token source is the only source of those values; `TOKEN_MAP.md` closed; the app's behaviour is unchanged (baseline suites green, critical flows re-exercised); the pass's own rollback is recorded in `ROLLOUT.md`. *Per-pass score:* the categories pass 1 touches (hierarchy, readability) are re-scored; a drop sends the pass back, not forward.

**Step 5 — Pass 2: Typography (D3).** A real type scale, display/body/data registers, line-length and contrast rules from the typography skill. No page ships a size or family outside the scale. *Entry:* pass 1 exited. *Exit:* every page's computed styles match the token scale (count distinct sizes and families); body line length and line height measured; baseline suites green; rollback recorded. *Per-pass score:* readability re-scored — it is a hard category (≥ 9, and 10 where the leak audit touches copy: leaked technical text is often also unreadable text).

**Step 6 — Pass 3: Layout & responsive (D3).** Grid, rhythm, and breakpoint behaviour per layout-responsive; no page may overflow or collapse at any width. *Entry:* pass 2 exited. *Exit:* every page checked at 1440 px and 390 px (and the widths between); no overflow, no collapse, no content hidden by layout; baseline suites green; rollback recorded. *Per-pass score:* hierarchy and never-invisible safety re-scored.

**Step 7 — Pass 4: Components & UI states (D3+D13).** Every component gets its full state set (rest, hover, focus, active, disabled, loading, empty, error) per component-library and ui-states — and D13 runs **inside this pass**, not after it: accessibility-audit on every component and every state (G-AC-001, G-AC-005; axe-core 0 violations at WCAG 2.2 AA, G-EXP-05). Empty and error states are designed states, not raw text: this is where leaked internals most often hide (raw error codes, stack text, "No data", field names in validation messages), so every state string is checked against the leak ban list as it is written. *Entry:* pass 3 exited. *Exit:* every component's state matrix complete and screenshotted; accessibility gates green on every component; no state string leaks architecture; baseline suites green; rollback recorded. *Per-pass score:* readability, element integration, and never-invisible safety re-scored.

**Step 8 — Pass 5: Motion system (D3+D12).** The theme's full motion system on every page: scroll-triggered reveals, scroll-driven animation, parallax where the theme calls for it, staggered and masked reveals, counters, micro-interactions — designed per theme, never a library default, never copy-pasted between themes. D12's performance budgets are asserted inside this pass (G-AN-101): motion runs on transform/opacity and one shared animation loop; the theme's budget holds on a mid-range phone. Hard rules from the protocol apply in full: the normal system cursor only (remove any custom cursor that adds weight, lag, or a follower — a cursor effect that makes the pointer harder to move is a defect, not a feature); every reveal has a fallback (watchdog, timed reveal, or visible-by-default state) so content is never stranded; a `prefers-reduced-motion` variant ships in the same pass as every animation. *Entry:* pass 4 exited. *Exit:* the motion system is live on every page, not only the hero; budgets asserted and green; reduced-motion variant complete and readable; baseline suites green; rollback recorded. *Per-pass score:* motion smoothness and performance re-scored.

**Step 9 — Pass 6: Scroll experiences (D3+D12).** The page's scroll is a designed system (progress, pinned or scrubbed sections where the theme calls for them), driven by one shared lerped loop — never raw scroll handlers per element. Performance budgets re-asserted (G-AN-101); no long tasks tied to scroll events. *Entry:* pass 5 exited. *Exit:* scroll choreography live on every long page; JS-disabled load shows all content; reduced-motion variant complete; baseline suites green; rollback recorded. *Per-pass score:* motion smoothness, aliveness, and never-invisible safety re-scored.

**Step 10 — Pass 7: Polish (D3).** The theme's signature elements, merged into the content itself — 5–20 per theme, 3D where possible, otherwise excellently animated. Every signature element passes the merge test (design-intelligence §3.3, FE-327): remove the element and the page must lose information or story, not just decoration. An element that looks pasted on top of the content is a defect: integrate it or remove it. *Entry:* pass 6 exited. *Exit:* every signature element passes all four merge tests; no pasted-on decoration remains; baseline suites green; rollback recorded. *Per-pass score:* element integration and aliveness re-scored — the two categories this pass exists to move.

**Step 11 — Score gate (D3+D8+D13).** Re-score the upgraded app with the design-intelligence §5 gate at 1440 px and 390 px (G-FE-162): total ≥ 64/80, every category at or above its threshold, all three hard thresholds met (readability ≥ 9, never-invisible safety 10, reduced motion 10). Re-run the leak audit over the whole upgraded app and record the AFTER leak score. **The leak veto: any leak in the shipped UI = gate FAIL regardless of the /80 score.** A 78/80 with one leaked table name is a fail; a 64/80 with zero leaks is a pass. Re-run the full `BASELINE.md` suite and the critical flows against the final build, and the accessibility gates (G-AC-001, G-AC-005, G-EXP-05) on the final build, not on a pass-4 snapshot. If the score fails, loop back to the failing pass — fix the lowest category first, re-score the *whole* app (scores from before the fix are void). Do not declare completion below the gate; shipping below threshold "to fix later" is banned.
◆ **DECISION — score or leak gate missed: loop, narrow, or report?** If the score misses, the options are exactly three: loop to the lowest-scoring category's owning pass and fix it; narrow the upgrade's claimed scope (a signature element or a pass's ambition reduced, recorded in `DECISIONS.md` with the reason — the score is re-run against the narrowed scope, never lowered to meet the build); or report the shortfall honestly in the audit file and stop. Lowering the gate, averaging away a hard-category failure, or shipping to "fix later" are not options. A leak found at this gate sends the work back to the failing pass — the pass that introduced it owns the fix. Record the choice in `DECISIONS.md`. (Unattended run: BOOTSTRAP's approval-points rule applies; if none is recorded and no user is reachable, the safe default is: do not ship; loop to the lowest category, and report the failing categories in `progress.md`.)

**Step 12 — Staged rollout (D6).** Roll out by the `ROLLOUT.md` stages, promoting only on evidence: **dark** (deployed, previous UI still served, new UI exercised by synthetic checks only) → **internal** (staff accounts, real tasks, stop metrics read) → **named beta cohort** (users told the UI changed and given a feedback route — beta is a support state, not just a percentage) → **percentage stages** (each stage held long enough to read its stop metrics, with the hold duration recorded in advance in `ROLLOUT.md`, not decided by impatience) → decision at step 13. Any stage can end in a rollback to the previous pass state within minutes and without a redeploy where the flag/branch strategy permits (proven by the rehearsal in step 12's preparation, G-DO-151); a rollout whose rollback has never been executed is treated as having no rollback. Before the first stage: the rollback rehearsal is run end to end (G-DO-151), the pre-switch backup is verified current (G-DO-134), and production checks are defined (G-DO-071 external production check, G-INT-01 the flows nearest the change re-exercised, G-INT-06 owner approval naming the release).
◆ **STOP AND ASK — the go-live switch (§5.9/§6.3).** The rollout's first real-user stage, any DNS or domain change, and any migration against production data require the user's explicit approval naming the release and the rollback it can return to. The agent prepares the checklist; the user approves the switch. (Unattended run: an approval recorded in the commissioning brief or `requirements.md` naming this release and its rollback counts as the answer. If none is recorded and no user is reachable, the go-live switch is never log-and-continued and never safe-defaulted — it is an irreversible production action on the §6.3 Step 5 never list. Prepare everything up to the switch, log the blocker in `progress.md` (§6.3 step 3), and ask the user with concrete options (§6.3 step 4); the switch itself waits for the explicit approval.)

**Step 13 — Report (D10).** Close `UI-UPGRADE-AUDIT.md` with the before/after summary: defects found, passes applied, BEFORE → AFTER score, BEFORE → AFTER leak score, and anything deliberately left unchanged with its reason. In the reply to the user, state plainly: what was upgraded, the before/after score, the before/after leak score, and what (if anything) was left and why. No claim of "premium" without the score. `handover.md` and `runbook.md` (restart, rollback, restore — all three proven during the playbook, not merely described) are current; `progress.md` shows the full gate trail per pass.

## Failure handling

- **A gate fails:** fix in the owning pass, re-run; same failure twice → §6.3 (log in `progress.md`, continue unblocked work, batch blockers with concrete options). A failing gate never gets "one stage to prove itself live" — the pass stays where it is until green.
- **A pass breaks a flow (baseline suite red, critical flow fails, G-AN-101):** roll back **that pass**, not the whole upgrade. Each pass is independently reversible by design (`ROLLOUT.md`); the rolled-back pass returns to its own step with the failing flow as the work order, the other passes stand, and the upgrade resumes from a green baseline. A pass that cannot be rolled back on its own was too big — split it.
- **The score fails (G-FE-162):** loop to the lowest-scoring category's owning pass, fix it, re-score the *whole* app — scores from before the fix are void. Never declare completion below the gate; never average away a hard-category failure with high scores elsewhere.
- **A leak is found after a pass:** fix it in that pass, re-audit that pass's surfaces, and re-count. A leak found at the step 11 score gate sends the work back to the failing pass — the pass that introduced it owns the fix; the gate does not pass with a leak "to be fixed after launch". A leak found after rollout starts: roll back the affected stage first (the leak is user-visible), fix in the owning pass, re-audit, and only then re-promote.
- **A signature element fails the merge test (FE-327):** integrate it or remove it. An element that fails is pasted-on spectacle, whatever it cost to build: first try integrating it with the page's real content (the element must carry information or story); if it cannot be integrated, it is removed, not decorated further. A second failure on the same element escalates to a `DECISIONS.md` entry naming what went wrong with the handoff.
- **Performance budget exceeded (G-AN-101):** cut list, in this order — (1) cap particles and ambient loops; (2) drop parallax and pinned sections where the theme allows it; (3) reduce the motion dial for the affected page (recorded reason, FE-323); (4) remove the heaviest signature element (merge-test failure is not required — budget outranks spectacle); (5) defer the motion/scroll pass's most expensive section to a later iteration, recorded in the audit file. Never trade the reduced-motion variant or the never-invisible fallback for budget — those are hard categories, not cuts.
- **A structural change is required mid-pass that the audit did not foresee:** stop that pass, write the justification into the audit file, and take it through the step 2 STOP AND ASK point. Do not improvise structure inside a presentation pass.
- **A gate is itself wrong:** recorded waiver in `progress.md` + `DECISIONS.md` (§6.3 step 5); security/legal waivers need explicit user agreement. The score gate (G-FE-162) and the leak veto are never waived for a shipped UI — an upgrade that needs either waived is an upgrade that loops or stops at step 11, early.
- **A secret leaks:** revoke/rotate immediately; incident recorded without the value (§5.9 step 4).

## Definition of done

- BEFORE → AFTER scores recorded in `UI-UPGRADE-AUDIT.md`, AFTER ≥ 64/80 with every category at threshold and both hard categories at 10 (G-FE-162).
- **Zero leaks (AFTER leak score 0)** — the leak audit re-run over the whole upgraded app finds no user-facing surface expressing the app's structure or architecture; the leak veto is satisfied.
- All audit defects fixed or explicitly reported with a reason in the audit file; nothing silently dropped.
- Baseline suites green on the final build; every critical flow passes end to end; visual baseline diffed with no unexplained change.
- Rollback proven by rehearsal (G-DO-151) for every pass; the pre-switch backup verified current (G-DO-134); rollout reached its step 13 decision on stored evidence.
- The fallback is still live and tested at the moment of completion where the app had one; retiring a feature or a fallback is explicitly *not* part of done.
- Zero P0/P1 defects (QB-01); `progress.md`, `DECISIONS.md`, `ROLLOUT.md`, `TOKEN_MAP.md`, `runbook.md`, and `handover.md` current; the audit file closed with the before/after summary.
- **Pre-provisioning complete:** where no production environment exists yet to roll out into, the project may be recorded as *pre-provisioning complete* — every gate except the provisioning-waived ones green, each waived gate recorded as a provisioning waiver per §6.3, and the unblocking conditions listed in `progress.md`. The rollout requirements above remain open until the environment exists; pre-provisioning complete is not done, and it never justifies taking the old UI down early.

## Worked mini-example

Sample project: **a small shop's storefront** — a live web app selling handmade ceramics: home, shop listing, product pages, cart, checkout, order confirmation. Its UI is generic AI slop: one gradient hero, copy-pasted cards, no motion system, no states. The owner wants it premium without losing a single order.

1. Step 0: core loaded; app release v1.8 recorded as the upgrade base; docs scaffolded.
2. Step 1: audit scores the app **BEFORE 31/80** — hierarchy 5, element integration 2, readability 6, motion smoothness 3, performance 5, never-invisible safety 4, reduced motion 2, aliveness 4. Defects: no token source (47 hard-coded hex values), no type scale, no motion or scroll system, loading states are bare spinners, error states show raw text. **Leak audit: BEFORE leak score 6** — the cart's empty state reads "No rows in cart_items" (table name); the checkout error shows "POST /api/v2/orders failed: 500" (API endpoint); the footer says "Built with Next.js + PostgreSQL" (tech-stack labels); the admin link in the shop footer reads "Admin — 12 pages" (page count); a product filter label reads "Filter by category_id" (schema/field name); the order-confirmation page says "Saved to orders table" (table name).
3. Step 2: baseline frozen — existing suites green; critical flows exercised (browse → add to cart → checkout → confirmation; empty-cart and failed-payment paths); reference screenshots at 1440 px and 390 px; measured load recorded. Keep-working list: the five flows above, plus the failed-payment retry.
4. Step 3: theme decision — the shop has no identity worth keeping (generic gradient, stock copy), so a theme is selected from the theme library using the design-intelligence decision process: **#50 Charcoal & Ink** (kiln-fired, ink-on-paper — the theme's material language fits handmade ceramics; motion dial 2, restrained in the checkout flow). Rejected alternative recorded: a spectacle dial-4 cinematic theme — rejected because checkout is a task flow and spectacle there costs trust (FE-322). Canonical spec `skills/frontend/theme-library/expanded/theme-050.md` read end to end (G-FE-171).
5. Step 4 (pass 1, tokens): `TOKEN_MAP.md` maps all 47 hard-coded values to tokens — kiln-charcoal, glaze whites, ink, one clay accent; the single token source is the only source afterwards. Baseline suites green; rollback recorded.
6. Step 5 (pass 2, typography): display serif for product names, grotesque body, mono only for order numbers the customer actually uses. Line length and contrast measured; readability re-scored 6 → 8.
7. Step 6 (pass 3, layout): grid and rhythm per layout-responsive; product pages stop overflowing at 390 px; no page collapses. Never-invisible safety re-scored 4 → 8 (reveals gain fallbacks).
8. Step 7 (pass 4, components & states): every component's state matrix built; accessibility-audit green (G-AC-001, G-AC-005, G-EXP-05). **Leak fixes land here:** "No rows in cart_items" → "Your basket is empty — here are pieces other buyers loved"; "POST /api/v2/orders failed: 500" → "We couldn't place your order. Your card hasn't been charged — try again"; "Filter by category_id" → "Filter by type"; the footer tech-stack line is removed outright (users never needed it); "Admin — 12 pages" is removed from the shop footer (admin lives behind login, unnamed in the storefront); "Saved to orders table" → "Your order is confirmed — we've emailed your receipt". Each fix is re-checked against the ban list as written; leak count after this pass: 0 on the touched surfaces.
9. Step 8 (pass 5, motion): the theme's motion system on every page — staggered reveals on the shop grid, masked reveals on product names, counters only where real counts exist (pieces in stock, pieces sold). Budgets asserted (G-AN-101); cursor stays the system cursor; reduced-motion variant ships in the same pass.
10. Step 9 (pass 6, scroll): scroll progress on product pages, one shared lerped loop, no raw scroll handlers; JS-disabled load shows all content.
11. Step 10 (pass 7, polish): signature elements merged with real content — a kiln-firing progress ring on the order-confirmation page that fills as the order moves from thrown → glazed → fired → shipped (the element *is* the order status, not decoration beside it; remove it and the customer loses the story of their piece); a glaze-swatch strip on product pages built from the actual glazes that piece is available in. Both pass the merge test (FE-327).
12. Step 11: score gate — **AFTER 71/80** (hierarchy 9, element integration 9, readability 9, motion smoothness 9, performance 8, never-invisible safety 10, reduced motion 10, aliveness 7). Leak audit re-run over the whole app: **AFTER leak score 0** — veto satisfied. Baseline suites green; accessibility gates green on the final build.
13. Step 12: rollout dark → internal → named beta (regular buyers told the shop's look changed, feedback route open) → percentage stages; rollback rehearsed (G-DO-151) before the first real-user stage; the owner approves the switch naming the release and its rollback (G-INT-06).
14. Step 13: audit file closed — defects found, passes applied, **BEFORE 31/80 → AFTER 71/80**, **BEFORE leak score 6 → AFTER 0**, nothing deliberately left except the blog (out of scope, recorded in `DECISIONS.md`). Done.
