# Playbook: Prototype to Production

A working prototype — an MVP, a demo, or a no-code / AI-generated build — already exists and demonstrably does the job in front of a friendly audience. It is not a product yet: its auth, its data, its secrets handling, and its error paths were built to be *shown*, not to be *trusted*. This playbook takes that artifact to production without throwing away what it proved — and without shipping what it faked. The order is the discipline: audit before architecture, hardening before features, real auth and real data before polish.

## Goal

Ship the prototype as a real production product: every component explicitly kept, hardened, or rebuilt on evidence; no mock data, fake auth, demo login, or client-side secret reaching production; real authentication, authorization, and persistence replacing every shortcut the prototype took; the public behavior the prototype proved preserved and pinned by tests; and a monitored deployment with a tested rollback — with zero critical security findings and every QA gate green.

## Departments + order

Step 0 (always-on core) → D1 → D15+D7 (audit) → D2+D7 → D5+D4 → D3+D13 → D8 → D12+D14 → D7+D8 (verification) → D6

**Order deviation (one line):** D15 (`prototype-hardening`) and D7 run *before* D2, not after the build group as a greenfield playbook would have them, because the keep-or-rebuild verdicts from the audit are inputs to the architecture — designing production architecture before knowing which prototype components survive designs it twice. D8 also appears twice on purpose: characterization tests are written in step 2 to pin the prototype's proven behavior before anything is touched, and the full contract/integration suite is stood up in step 6 and enforced at step 8. There is deliberately **no new-features step**: a feature the prototype does not already demonstrate is new product work under the closest matching playbook (usually SaaS), and it starts only after this playbook's step 8 is green. D11 and D17 appear as conditional steps 5b and 5c, only where the prototype faked those surfaces. D9 appears as a conditional step 10, only if the product has a public search surface.

## Docs to write first

Before any code is changed, scaffold from `project-templates` and write:

The full mandated set for this type is `templates/mandated-manifest-prototype-to-production.txt`, which governs (G-PM-001); the list below is the hand-written starting subset, not the whole set.

- `requirements.md` — what the production product must do, derived from what the prototype *actually demonstrates* (step 1), with a named Must set and an explicit out-of-scope list. Anything the prototype only appears to do is recorded as unbuilt, not as a requirement already met.
- `fact-sheet.md` — the product's verifiable commitments (what it does, what data it keeps, any price or plan the prototype displays), each with its source. A claim the prototype's UI makes but its backend cannot honor goes in as a gap, never copied forward as fact.
- `PROTOTYPE_AUDIT.md` — the step 2 record: the component inventory, the fake/mock inventory, and the keep / harden / rebuild verdict per component, each with its evidence. This file is this playbook's equivalent of the API playbook's contract file: verdicts change only by a new entry, never by silent drift.
- `progress.md`, `DECISIONS.md` — session log and decision record; every keep-or-rebuild verdict and every gate waiver lands in one of these two.
- `stack.md` — the production stack decision with dated criteria (G-AR-023). If the prototype's stack is kept, the criteria say why it can carry production load, security, and hiring/maintenance reality — "it is already written" is not a criterion.
- `ARCHITECTURE.md` — the production target: components, data ownership, trust boundaries, failure behavior. Started as a stub now, completed in step 3.
- `SCHEMA.md` — the invariants the real database must enforce, written against the prototype's *demonstrated* data shapes, with every place the prototype's storage contradicts them (no uniqueness, no types, browser-only storage) listed as a migration task.
- `SECURITY.md` — one file with two named sections: a vulnerability-reporting section and the project's security-design section (authentication scheme, authorization model, threat model summary).
- `.env.example` — every secret by name + purpose, no values (§5.9). Its first draft is written from the audit's secret inventory, including every key found in the prototype's client code — those keys are listed as *compromised, to be rotated*, not as values to be reused.

## Step-by-step sequence

**Step 0 — Core and scaffold.** Load `bundles/core.md`; generate the project record (G-PM-001, G-PM-002); write the docs above; load `secrets-management` before any credential is touched. The prototype itself is committed or archived untouched as the reference baseline before any edit — hardening work never happens on the only copy of the thing that was demonstrated to work.

**Step 1 — Requirements from evidence (D1).** Run the prototype with the user and record, flow by flow, what it genuinely does end-to-end, what it does only with seeded/demo data, and what is a static screen pretending to be a flow. `requirements-writing` turns the first category into the Must set; `scope-control` holds the line that the second and third categories are build work, not existing behavior. `fact-sheet.md` is populated from the same pass.
◆ **DECISION — what did the prototype actually prove?** Demand validated, design validated, or only the concept demonstrated to stakeholders? The answer sets how much of step 2's audit can trust the prototype's flows as the specification. If unspecified, ask (§6.3 step 4). (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer; if none is recorded and no user is reachable, follow the §6.3 stuck protocol (log-and-continue, then the safe defaults) and record the substitution in `progress.md`.)

**Step 2 — Audit before architecture (D15+D7).** Run `prototype-hardening`: inventory every component, every external call, every stored datum, and every credential in the prototype, and record a verdict per component in `PROTOTYPE_AUDIT.md` — **keep** (sound enough for production as-is), **harden** (right shape, unsafe or unfinished execution), or **rebuild** (the shortcut *is* the design: mock auth, browser-local "database", business rules enforced only in the UI). The audit explicitly hunts the prototype's usual fakes: hard-coded or shared demo logins, auth checks that live only in the frontend, API keys and provider secrets in client code, `localStorage`/in-memory state presented as persistence, seeded rows presented as real data, payment and email flows that render success without calling anything, and validation that exists only as form attributes. In parallel: `threat-modelling` and the `owasp` checklist run against the prototype as it stands, so step 3 designs against real findings, not assumptions; `tech-debt` opens the debt register for everything kept-but-imperfect; and D8 writes **characterization tests** pinning the observable behavior the prototype proved — the flows from step 1's first category — so every later step can prove it preserved them (the pinning precondition is prototype-hardening's DX-177). The prototype-hardening skill's audit gate, G-DX-081 (ledger completeness), must pass before step 3 starts.
◆ **DECISION — keep or rebuild, per component.** Each verdict is decided on evidence from the audit (test coverage, secret exposure, data integrity, dependency health), never on effort already spent. A component whose core is a fake — auth, persistence, billing — is rebuilt however good its screens look; a component that is merely rough is hardened, however tempting a rewrite feels. Record each verdict and its evidence in `DECISIONS.md`. (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer; if none is recorded and no user is reachable, follow the §6.3 stuck protocol (log-and-continue, then the safe defaults) and record the substitution in `progress.md`.)
◆ **STOP AND ASK — a secret is found in client code or in the prototype's history (§5.9).** Any key, token, or credential the audit finds shipped to the browser, committed, or shared with demo users is treated as compromised: stop, tell the user to revoke/rotate it, and record the incident (name + date + rotation status, never the value) in `progress.md`. Hardening does not proceed on the assumption that an exposed key is still safe because "only the demo used it." (Unattended run: there is no approval to substitute at this point and no default to apply — an exposed secret is a security incident, not a decision the stuck protocol may continue past. Stop, record the incident in `progress.md` (name, date, rotation status — never the value), log the rotation as a blocker (§6.3 step 3), and tell the user to revoke/rotate, with concrete options (§6.3 step 4). Work that depends on the exposed credential does not proceed, and nothing proceeds on the assumption the key is still safe; unrelated hardening may continue.)

**Step 3 — Production architecture + security design (D2+D7).** Design the target the verdicts point at: `system-design` places the kept components, the rebuilt components, and the boundaries between them; `stack-selection` confirms or replaces the prototype's stack on dated criteria (G-AR-023). The security design is settled here, before build: authentication scheme, authorization model, where every secret lives server-side, and how the prototype's trust assumptions invert — in the prototype the client was trusted; in production the client is hostile input. Threat model weighted to the failures prototypes actually ship: broken access control (the UI hid it, so it must be safe), secrets in the shipped bundle (G-ENG-11 — 0 secrets, keys, tokens, or connection strings in client code, logs, screenshots, or the report), injection through unvalidated demo inputs, and excessive data exposure from APIs built to feed one friendly screen.

**Step 4 — Real data and real auth first (D5+D4+D7).** This step precedes all UI work, deliberately: the prototype's most dangerous fakes live here, and polishing screens against them entrenches them. Schema first: invariants in `SCHEMA.md` become database constraints (G-DB-001, G-DB-002), exact types where the prototype used loose ones (G-DB-003); migrations are reversible (G-DB-061) and `seed-data` is rebuilt so demo fixtures are visibly fixtures — seed data is a development input, never the production dataset and never shipped as if real. Auth second: `backend-auth` replaces every demo login, shared password, and frontend-only check with real accounts and server-side sessions/tokens, hardened per `auth-hardening` and `session-security`; `rbac` enforces per-role authorization on the server (G-BE-051 auth test pack, G-BE-061 authorization matrix test). Handlers third: every endpoint validates at the boundary (G-BE-021, G-BE-023 mass-assignment probe), recomputes trusted values server-side (G-BE-004 in the API playbook's step 3 pattern), and is rate-limited where the prototype left it open (G-BE-151/G-BE-152 pattern from `rate-limiting`). All secrets move server-side under `secrets-management`; the frontend receives only publishable values. The characterization tests from step 2 run throughout this step: a rebuilt component that changes a proven flow fails here, in the open, not at launch.
◆ **DECISION — does any prototype data become production data?** Demo accounts, seeded rows, and data entered during stakeholder demos are presumed disposable. Real user data exists only if real users were onboarded onto the prototype — in which case their data is migrated under step 4's schema with the migration rehearsed on a copy first, and their credentials are force-reset, because prototype credential storage is never trusted. If unspecified, ask (§6.3 step 4). (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer. If none is recorded and no user is reachable, data is never classified as disposable by default: destruction sits on the §6.3 Step 5 never list. Preserve all prototype data untouched, log the question as a blocker in `progress.md` (§6.3 step 3), and ask the user with concrete options (§6.3 step 4); the migration route above runs only on a recorded answer.)

**Step 5 — Frontend rewire, not repaint (D3+D13).** The kept UI is rewired to the real API from step 4: mock modules, fixture imports, and client-side "business logic" are deleted, not left dormant; every screen gains the loading, empty, and error states the prototype skipped because its data was instant and local (G-ENG-13 pattern — every async surface has loading, empty, and error states). Client code is swept for secrets and provider keys (G-ENG-11) and for demo affordances — test-account shortcuts, debug panels, "skip login" buttons. D13 runs inside this step: `accessibility-audit` and `wcag` against every kept template (G-AC-001, G-AC-005), because prototypes routinely fail keyboard and contrast basics that are cheap to fix now and expensive after launch. **No visual redesign happens in this playbook.** A screen that looks rough but works is hardened; redesign is separate product work after launch, and doing it here is how security steps get starved — see Failure handling.
**Step 5b — Real payments (D11, conditional).** Only if the prototype displays a checkout, a paywall, or a paid tier: the fake is replaced under `payments`/`subscriptions`, verified in the provider's test mode before any live key is touched, following the SaaS playbook's step 4 gates for those skills. A prototype "payment success" screen with no provider behind it is recorded in the audit as an unbuilt feature, and the production scope either builds it properly here or removes the surface — it never ships as a simulation.
**Step 5c — Real AI features (D17, conditional).** Only if the prototype contains AI features: demo calls (hard-coded responses, a key in the browser, an unguarded direct provider call) are rebuilt under `ai-retrofit` with `llm-integration` and `ai-safety` — provider access moves server-side behind one wrapper, and the AI gates of those skills join the step 8 list.

**Step 6 — Contract and integration testing stood up (D8).** The contracts the production product now actually offers — its API surface, its provider integrations, its webhook and email boundaries — are captured as `contract-testing` suites and published (G-QA-083 publication completeness), with the deploy pipeline wired so `can-i-deploy` is a real gate (G-QA-084 pipeline wiring inspection). `integration-testing` covers the seams the prototype never had: frontend against the real API and real database, auth across roles, and every external provider in its sandbox. `e2e-testing` promotes the step 2 characterization flows into the permanent regression suite (G-QA-021). From this step on, a change that breaks a proven flow or a published contract fails the build — the prototype's behavior is now protected by tests, not by memory.

**Step 7 — Performance, observability, and legal (D12+D14, explicit steps).** `performance-budgets` are set per route/endpoint class and asserted in CI (G-AN-101, G-AN-102) — prototypes are usually measured never, so the first real measurement happens here, against the real data layer from step 4, not against the prototype's in-memory speed. `monitoring` and `apm` are defined here (signals, SLOs, dashboards; G-AN-091 apm gates) and wired live in step 9. D14 in the same step: `privacy-laws` builds the register of what the production product stores and processes (G-LG-001, G-LG-002) — written from the step 4 schema, not from the prototype's claims, because prototypes routinely collect data (analytics keys, form fields, uploaded files) nobody inventoried — and `legal-documents` are drafted from that register (G-LG-031 document-vs-register diff).

**Step 8 — Verification (D7+D8).** The full pass, on the hardened product, never on the prototype: OWASP checklist (G-SE-003) and ZAP baseline (G-SE-001) — 0 critical; API authorization matrix and inventory diff where an API exists (G-SE-021, G-SE-022); secret scan over the full history of the *production* repository, including anything copied in from the prototype (G-SE-041); dependency gate (G-SE-051) — prototype dependency trees are pinned late or never, so the lockfile is committed and audited here (G-ENG-12); placeholder sweep over the shipped build (G-QA-141 — scan rendered output, not source: no demo copy, lorem text, sample names, or fixture rows survive); qa-gates meta-checks (G-QA-111); the acceptance-register engineering gates for the shipped artifact (G-ENG-01 type check / lint / production build clean, G-ENG-14 no TODO/FIXME or commented-out blocks in the shipped bundle); and the prototype-hardening skill's remaining gates (G-DX-082 auth and authorization probe, G-DX-083 secret and placeholder sweep, G-DX-084 failure and integrity drill, G-DX-085 critical-path test run, G-DX-086 recovery rehearsal). **No deployment until green.**

**Step 9 — Deploy (D6, last build step).** `ci-cd` with the contract gate in the pipeline (G-DO-001 broken-test drill, G-DO-004 gating-job integrity scan); `hosting` chosen for production, not inherited from wherever the demo happened to live (G-DO-071 external production check, G-DO-072 readiness honesty test); the build reproduces from a clean checkout (G-INT-02); a rollback plan exists for the release (G-INT-04) and the rollback drill runs before the first production deploy (G-DO-151); monitoring and alerts from step 7 go live with the deploy (`reliability`, G-DO-131 SLO inventory audit).
◆ **STOP AND ASK — production go-live (§5.9/§6.3).** First production deploy, first connection to a production database, any migration of real user data identified in step 4, and the switch from provider test mode to live keys each require the user's explicit go-ahead, with the production approval naming the release, the address, and the source (G-INT-06) and the expected cost change stated before the deploy (G-INT-07). (Unattended run: an approval recorded in the commissioning brief or `requirements.md` naming the release counts as the answer. If none is recorded and no user is reachable, production go-live is never log-and-continued and never safe-defaulted — first production deploy, production data migration, and live payment keys are irreversible and money-bearing actions on the §6.3 Step 5 never list. Prepare everything up to the switch, log the blocker in `progress.md` (§6.3 step 3), and ask the user with concrete options (§6.3 step 4).)

**Step 10 — Launch surface (D9, conditional).** Only if the product has public pages: `technical-seo` indexability check on the production routes (G-CO-001 pattern from the SaaS playbook's step 9), and a final sweep that no prototype URL, staging domain, or demo subdomain is what search engines or shared links point at.

## Failure handling

- **A gate fails:** fix in the owning step, re-run; same failure twice → §6.3 (log in `progress.md`, continue unblocked work, batch blockers with concrete options). No gate is waived silently; a waiver needs a `DECISIONS.md` entry, and security/legal waivers need the user's explicit agreement.
- **The audit finds a fake wired deep (mock auth or browser-local data under most screens):** this is a rebuild verdict arriving late, not a hardening task. Stop the affected component's step 5 work, return it to step 4 as a rebuild, and re-run the characterization tests against the rebuilt component. Shipping the fake "temporarily, behind the real UI" is the one outcome this playbook exists to prevent — a fake that reaches production acquires real users and becomes a migration.
- **Keep-or-rebuild verdict is contested on sunk-cost grounds ("we spent weeks on this module"):** effort spent is not evidence in `PROTOTYPE_AUDIT.md` and does not change a verdict. The evidence that changes a verdict is new test, security, or integrity evidence about the component. If the user overrules a rebuild verdict anyway, record the overrule, the audit evidence, and the accepted risk in `DECISIONS.md` — the component then ships as known debt in the `tech-debt` register with a named trigger for revisiting it, never as silently "fine."
- **UI polish is consuming the schedule before steps 4–5 are done:** freeze all visual work and return to the sequence. A prettier screen on fake auth is further from production than the rough screen was, because it raises stakeholder confidence in a product that cannot yet be trusted with a real user.
- **Characterization tests fail during hardening:** the change altered proven behavior. Either the change is wrong (fix it) or the prototype behavior was itself a bug the user wants changed (record the behavior change as a requirements change in `DECISIONS.md` and update the test deliberately). Never edit the test quietly to make the suite green — that deletes the only record of what the prototype proved.
- **Exposed secret confirmed (step 2 stop point ignored or discovered late):** revoke/rotate immediately, purge the value from the shipped bundle and history per `secrets-management`, and re-run G-SE-041 and G-ENG-11 before any deploy. The deploy does not proceed on the old key "one last time."
- **Two skills contradict:** §5.7 precedence (security 1, legal 2, data integrity 8 above backend convenience 9 and performance 12); log in `DECISIONS.md`.
- **A gate is itself wrong:** recorded waiver in `progress.md` + `DECISIONS.md` (§6.3 step 5); security/legal waivers need explicit user agreement.

## Definition of done

- Deployed on a real production host; external production check and readiness honesty test green; monitoring, SLOs, and alerts live; rollback drill on record (QB-02).
- Every component in `PROTOTYPE_AUDIT.md` carries a verdict, and every verdict is discharged: kept components passed the step 8 pass as-is, hardened components pass the prototype-hardening skill's gates, rebuilt components pass the full step 4/6 gate set.
- No prototype fake survives in the shipped product: no mock or seeded data presented as real, no demo account or shared login, no frontend-only auth or authorization, no secret in client code (G-ENG-11, G-SE-041, G-QA-141 all clean).
- Real auth, real persistence, and real integrations proven by the step 8 suites — authorization matrix, inventory diff, contract gate with its seeded-break negative control — not by inspection or by the fact that the demo worked.
- The flows the prototype proved still work, proven by the promoted e2e suite (G-QA-021); every deliberate behavior change from the prototype is recorded in `DECISIONS.md`.
- Zero P0/P1 defects (QB-01); `progress.md`, `DECISIONS.md`, `runbook.md`, and `handover.md` current.
- **Pre-provisioning complete:** where no production environment exists yet, the project may be recorded as *pre-provisioning complete* — every gate except the provisioning-waived ones green, each waived gate recorded as a provisioning waiver per §6.3, and the unblocking conditions listed in `progress.md`. The deployment requirements above remain open until the environment exists; pre-provisioning complete is not done.

## Worked mini-example

Sample project: **SlotBook**, a lesson-booking prototype for a small tutoring centre, built quickly with an AI app builder to demo to the centre's owner. It "works": parents pick a tutor and a time slot, see a confirmation, and the owner views bookings in a simple list. Underneath: login is one shared demo account named on the login screen, bookings are stored in the browser, the confirmation is rendered without anything being saved anywhere else, and an email provider's API key sits in the frontend code that was supposed to send confirmation emails later.

1. Step 0: core loaded; the prototype is archived untouched as the baseline; the docs are scaffolded; the email key is listed in `.env.example` by name only.
2. Step 1: walkthrough with the owner separates fact from theatre — booking selection and the owner's booking list are real flows; accounts, persistence, and email are not. Requirements Must set: real parent accounts, durable bookings, double-booking prevention, owner view. Email confirmation is Must; online payment is out of scope (the prototype never showed it).
3. Step 2: `prototype-hardening` audit verdicts — booking UI: **keep**; slot-selection logic: **harden** (it trusts the client to reject overlapping slots); auth: **rebuild** (shared demo account); storage: **rebuild** (browser-only); email: **rebuild** (never wired). The exposed email key triggers the stop point: the owner revokes it and issues a new one for server-side use only; the incident is recorded without the value. Characterization tests pin the two real flows.
4. Step 3: target architecture recorded — web app, API, one relational database; stack kept on dated criteria (the builder's stack is a mainstream framework the centre's part-time developer already knows), with the security design stating that slot availability and overlap are decided server-side only.
5. Step 4: schema enforces one booking per tutor per slot as a database constraint (G-DB-002); real parent accounts replace the demo login (G-BE-051); the authorization matrix proves a parent cannot open another family's bookings (G-BE-061); the email key now lives only in the server environment, and confirmation email is sent by the API after a booking is persisted (G-BE-002).
