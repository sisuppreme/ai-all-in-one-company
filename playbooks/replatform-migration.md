# Playbook: Replatform Migration

A live product is moved from the stack or platform it runs on today to a new one — new framework, new host, new database engine, or a managed platform replacing a self-hosted one — while it keeps serving real users, real data, and real search traffic. Nothing here is greenfield: every decision is constrained by what already exists, and the two ways this mission fails are both silent — data that quietly does not survive the move, and URLs that quietly stop resolving to what search engines (and users' bookmarks, and other sites' links) expect. This playbook exists to make both failures loud before cutover, not after.

## Goal

Move the product to the new stack/platform with **zero data loss proven by counts and checks, not assumed**, every legacy URL either preserved or permanently redirected to a named successor, the new implementation at behavioral parity with the old one for everything users actually do, and a **tested** rollback that stays available for a defined window after cutover. The old platform is not decommissioned until the rollback window closes with the new platform verified in production.

## Departments and order

D1 → D15+D2 → D5+D9 (in parallel with the build) → D3+D4 → D7+D8 → D12+D14 → D6 → D9+D12 (post-cutover watch)

This order differs from a new build in three ways that are the whole point of the playbook. First, **D15 (`legacy-migration`) runs before any build step and owns the plan**: slices, seams, parallel-run stages, and each slice's point of no return are decided up front, because a replatform improvised during the build becomes a big-bang switch by default. Second, **D9's SEO work starts in parallel with the build, not at the end**: the redirect map is built from the legacy URL inventory while the new routes are being designed, so a URL-structure change is a decision made with the map open — never a surprise discovered by a crawler after launch. Third, **D6 appears twice in effect**: the cutover mechanics (deployment strategy, DNS, rollback) are designed and drilled in staging well before the real cutover, which is the last step, and the old platform stays live and restorable until the rollback window closes after it.

## Docs to write first

Before any code, scaffold from `project-templates` and write:

The full mandated set for this type is `templates/mandated-manifest-replatform-migration.txt`, which governs (G-PM-001); the list below is the hand-written starting subset, not the whole set.

- `requirements.md` — why the move is happening (the forcing reason: end-of-life stack, cost, capability, vendor exit), what "same product on a new platform" means in scope terms, and the explicit non-goals (a replatform is not a redesign and not a feature release; anything that changes behavior is listed as an intended change with a named decider, per `legacy-migration`).
- `fact-sheet.md` — the legacy product's verifiable facts that must still be true after the move: public claims, prices, retention commitments, the canonical domain, each with its source.
- `MIGRATION_PLAN.md` — the `legacy-migration` plan and this playbook's central artifact: every slice with its seam, its parallel-run stage, its rollback, its data point-of-no-return and the backup that covers it, and the coexistence end date. No slice is built before this plan passes its completeness review (G-DX-065).
- `DATA_MAP.md` — every dataset on the legacy platform: owner, row/object counts as measured (not estimated), the transformation it undergoes, and the verification query that will prove it arrived. This is the checklist the step 3 counts run against.
- `REDIRECT_MAP.md` — the redirect map as a deliverable in its own right, produced by `seo-migration` in step 4: every legacy URL that has ever been indexable, linked, or bookmarked, with its disposition — preserved (same URL on the new platform), redirected (301/308 to a named successor URL), or retired (404/410, with the reason recorded). A legacy URL with no row in this map is an unfinished migration.
- `CUTOVER_RUNBOOK.md` — the timed cutover sequence, the abort thresholds, the exact rollback command, and the rollback window (start, end, and what closes it). Written in step 2, drilled in step 8's staging run, executed once.
- `progress.md`, `DECISIONS.md` — session log and decision record; migration state (each slice's stage and current routing) is recorded in `progress.md` at the moment it changes, per `legacy-migration`.
- `.env.example` — new-platform credentials, DNS provider access, and legacy-platform read access by name + purpose (§5.9). Legacy credentials are read-only wherever the platform allows it.

## Step-by-step sequence

**Step 0 — Core and scaffold.** Load `bundles/core.md`; generate the project (G-PM-001, G-PM-002); write the docs above; load `secrets-management` before any credential for either platform exists. Access to the legacy production system is arranged read-only first; write access to legacy production is never needed by this playbook and is not requested.

**Step 1 — Requirements (D1).** Name what must not change: the user-visible behaviors, the data, the URLs, the integrations that call the product (webhooks, API consumers, scheduled jobs, email links already sent). Name also the forcing deadline, if any (a vendor shutdown or end-of-life date is a fact in `fact-sheet.md` with a source, not a vibe), because it decides how much parallel-run the schedule can afford.
◆ **DECISION — what is allowed to change during the move?** URLs, visual design, and behavior are each answered separately: frozen, or changing under a named decision. The default for all three is frozen; a replatform that also redesigns and also restructures URLs has three independent failure modes landing on the same day, and this playbook will not schedule that. If unspecified, ask (§6.3 step 4). (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer; if none is recorded and no user is reachable, follow the §6.3 stuck protocol (log-and-continue, then the safe defaults) and record the substitution in `progress.md`. The safe default here is all three frozen.)

**Step 2 — Migration plan and target architecture (D15+D2).** `legacy-migration` slices the move: by route group, by dataset, or by subsystem — whichever gives seams where old and new can coexist behind one routing point (a reverse proxy, a DNS split, or the platform's own routing). For each slice the plan names the seam, the parallel-run stage, the rollback, and the data point-of-no-return (G-DX-065 plan completeness review — a plan missing a rollback or a coexistence end date is not yet a plan). `stack-selection` records the target stack with dated criteria (G-AR-023); `system-design` records how the two platforms coexist during the window — which one is authoritative for writes at each stage, and how the non-authoritative one is kept from accepting writes it would lose.
◆ **DECISION — cutover strategy: sliced parallel-run, or single switch?** Sliced parallel-run (strangler-style: slices move one at a time, both platforms live, each slice independently reversible) is the default and the only strategy this playbook runs without an explicit recorded exception. A single switch (one maintenance window, everything moves at once) is permitted only when the product genuinely has no seam — and then the plan must say why, the window must be sized from a timed staging rehearsal rather than estimated, and the rollback is a full restore, drilled as such. (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer; if none is recorded and no user is reachable, follow the §6.3 stuck protocol (log-and-continue, then the safe defaults) and record the substitution in `progress.md`. The safe default here is sliced parallel-run.)

**Step 3 — Data migration built and proven on copies (D5).** The target schema is designed under `schema-design` (G-DB-001/G-DB-002/G-DB-003 where the schema itself changes); schema changes deploy under `migrations` with reversibility proven (G-DB-061, G-DB-063). The data movement itself is a pipeline, not a script run once by hand: `data-ingestion` lands a faithful copy of each legacy dataset, `etl-pipelines` applies the recorded transformations, and the whole move is **re-runnable from scratch** — it will be run at least three times (trial, rehearsal, cutover) and must give the same result each time. Verification is defined before the first run, in `DATA_MAP.md`: per dataset, the row/object count on legacy, the count after transformation, and the reconciliation for any deliberate difference (merged duplicates, dropped orphaned rows — each category counted and explained, never a bare mismatch); content-level checks (checksums or sampled field-by-field diffs on the records that matter most: accounts, orders, payments, published content); and the `data-quality` suite asserting uniqueness, referential integrity, and not-null on the migrated data as a gate, not a report (G-DB-191 suite gate wiring, G-DB-193 coverage scan). Before the first trial run, `backup-recovery` is verified on the legacy platform: a current restore drill (G-DB-101, G-DB-104) — the migration's safety net is a legacy backup that has actually been restored, and a backup that has never been restored is treated as no backup.
◆ **STOP AND ASK — production data access and the trial run (§5.9/§6.3).** The first copy of production data out of the legacy platform, and any later step that writes to or freezes production data, requires the user's explicit go-ahead, with the restore drill verified current first. Trial runs use the copy; nothing in this step writes to legacy production. (Unattended run: a go-ahead recorded in the commissioning brief or `requirements.md` for the specific data copy or write counts as the answer. If none is recorded and no user is reachable, this point is never log-and-continued and never safe-defaulted — production data access and writes sit on the §6.3 Step 5 never list. Log the blocker in `progress.md` (§6.3 step 3), ask the user with concrete options (§6.3 step 4), and copy or write no production data until the explicit go-ahead exists; planning and staging work may continue.)

**Step 4 — URL inventory and redirect map (D9, parallel with steps 3 and 5).** `seo-migration` builds the legacy URL inventory as the union of every source that knows a URL existed (CO-282): a full crawl of the legacy site, the live XML sitemap(s), the Search Console indexed/pages report export, server-log or analytics landing-page URLs for the trailing 12 months where available, and the known backlink targets from Search Console's Links report — each source named in the record with its pull date. The inventory is reconciled — a URL found by one source and missing from another is investigated, not dropped. Each inventoried URL gets its disposition in `REDIRECT_MAP.md`. Where the new platform preserves the URL structure, the map is mostly "preserved" — and still written, because "mostly" is where the losses hide. Where URLs must change, each old URL maps to the single closest new successor (never a blanket redirect to the homepage, which search engines treat as a soft 404 and users experience as losing the page). Redirects are permanent (301/308), chains are designed out at the map stage (an old URL points at the final new URL, never at another redirect), and retired URLs are a deliberate, recorded list — small, and each with a reason. The new sitemap is generated against this map under `sitemaps` (G-CO-092 count reconciliation: sitemap count vs inventory count, every difference explained). This step's gates are **the seo-migration skill's gates (G-CO-141–G-CO-145)**, run as that skill specifies them; this playbook additionally requires the map itself to be complete before step 8 — a cutover with an unfinished redirect map does not proceed.
◆ **DECISION — are any URLs changing at all?** If the new platform forces a structure change (different route scheme, different slug rules), the changed set is enumerated in `REDIRECT_MAP.md` and accepted explicitly here, while redirects can still be designed — not discovered in step 9's coverage review. If unspecified, ask (§6.3 step 4). (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer; if none is recorded and no user is reachable, follow the §6.3 stuck protocol (log-and-continue, then the safe defaults) and record the substitution in `progress.md`. The safe default here is: no URL changes beyond those the new platform structurally forces, each one mapped.)

**Step 5 — New implementation at parity (D3+D4).** The new platform's implementation is built (or configured, for a managed platform) against the legacy product's observed behavior. Parity is proven, not eyeballed: the slice's characterization/parity suite runs against **both** implementations over a production-shaped case set, and every output difference is either fixed or recorded in `MIGRATION_PLAN.md` as an intended change with a named decider (G-DX-061). Content is not retyped or re-created — published content arrives via step 3's pipeline, so what users read after the move is the migrated record, not a copy of it. Anything the new platform cannot do that the legacy one could is surfaced here as a named gap with a decision (accept, work around, or stop) — never silently dropped from the feature set.

**Step 6 — Verification (D7+D8).** Security pass on the new platform as a new production surface: OWASP checklist (G-SE-003 — 0 critical), secret scan (G-SE-041), dependency gate (G-SE-051); credentials for the new platform are fresh, never copied from legacy config files by hand. QA: the parity suite green on both implementations (G-DX-061), placeholder sweep over the new platform's rendered output (G-QA-141 — migration projects leak staging text, sample content, and "coming soon" surfaces more than most), and the route audit: the effective routing table diffed against the migration plan's stated stage, empty diff required (G-DX-062). **No cutover until green.**

**Step 7 — Performance, observability, and legal (D12+D14).** The new platform gets budgets before it gets traffic: performance budgets asserted in CI (G-AN-101) with the legacy platform's measured production latency as the comparison baseline recorded in `progress.md` — the new platform must not be slower than what it replaces on the routes that carry the traffic. `monitoring` is wired on the new platform **before** cutover, including the migration-specific signals: redirect hit rates, 404 rate on legacy URLs, error rate per slice, and data-sync lag during parallel-run. D14: the data register is updated for the new platform (G-LG-001, G-LG-002) — what is stored, where, and by which processor; if the move changes the data's region or the processors touching it, privacy-laws and legal-documents are updated and the change is treated as a user-facing fact, not an internal detail.

**Step 8 — Rehearsal, cutover, and the rollback window (D6).** First, a full rehearsal in staging: the entire `CUTOVER_RUNBOOK.md` executed against staging copies, timed, including the data pipeline's final-sync procedure and the rollback (G-DX-063 rollback drill — flip routing back to legacy using only the documented configuration change, smoke tests green on the legacy path, no code change and no redeploy; G-DO-151 staging rollback drill, G-DO-153 migration down-path check, G-DO-154 runbook rollback-step check). A rollback that has never been executed is assumed not to exist, and cutover is blocked until it has been. Then the production cutover, per slice where the plan is sliced: final data sync, verification counts re-run against production and matched to `DATA_MAP.md`, routing flipped, redirect map deployed **in the same change as the routing flip** — there is no moment at which the new platform serves traffic while legacy URLs still resolve to a platform that no longer answers. DNS changes are prepared under `domains-dns` (G-DO-101 record-sheet match) with TTLs lowered in advance so the flip and any rollback propagate in minutes, not hours. Production checks run immediately (G-DO-071 external production check, G-DO-072 readiness honesty test). The **rollback window** then runs for the duration recorded in the runbook: during it, the legacy platform stays up, restorable, and — where slices still write — kept in sync or write-frozen by design, and the redirect map and routing can be reverted as one drilled motion. The window closes only on the step 9 evidence, not on the calendar alone.
◆ **STOP AND ASK — the production cutover (§5.9/§6.3).** Flipping production routing/DNS and freezing legacy writes requires the user's explicit go-ahead at the time, with the rehearsal record, the verification counts, and the drilled rollback all shown. This point is never pre-approved by an earlier "go ahead with the migration" — the go-ahead is for this cutover, on this evidence. (Unattended run: no earlier approval substitutes for this one. If no go-ahead for this cutover is recorded and no user is reachable, the cutover is never log-and-continued and never safe-defaulted — flipping production routing and freezing legacy writes is an irreversible production action on the §6.3 Step 5 never list. Complete everything up to this point, log the blocker in `progress.md` (§6.3 step 3) with the evidence assembled, and ask the user (§6.3 step 4); production does not move until the go-ahead exists.)

**Step 9 — Post-cutover watch and legacy decommission (D9+D12+D15).** For the rollback window's duration: `technical-seo`'s route inventory crawl on the new platform (G-CO-002 — every indexable URL returns 200 with a self-referencing canonical), the redirect and status audit (G-CO-003 — chains ≤2 hops, permanent moves 301/308, retired URLs returning a real 404/410), the sitemap audit (G-CO-091, G-CO-095 — the submitted sitemap lists only new-platform URLs on the canonical host), and the Search Console coverage review (G-CO-005) watched for indexation drops on migrated URLs, with `web-analytics` comparing organic landing-page traffic against the pre-move baseline recorded in step 4. Monitoring watches the step 7 signals; any abort threshold in the runbook being hit executes the rollback, not a meeting. Only when the window closes clean: the legacy platform is decommissioned under `legacy-migration`'s elimination step — references swept (G-DX-064 post-elimination dead-reference sweep), legacy credentials revoked, the final legacy backup retained per the register's retention rule, and the decommission recorded in `progress.md`. Decommissioning before the window closes converts a reversible migration into an irreversible one and is a failure of this playbook even if nothing goes wrong.

## Failure handling

- **A gate fails:** fix in the owning step, re-run; same failure twice → §6.3 (log in `progress.md`, continue unblocked work, batch blockers with concrete options).
- **Verification counts do not reconcile (step 3 or step 8):** the migration stops at that dataset. A count mismatch is never "close enough" and never explained away verbally — either the pipeline is fixed and re-run until the counts match with every deliberate difference itemized, or the dataset's slice does not cut over. This is the silent-data-loss failure mode, and the count is the only thing that catches it; a migration reported successful on unmatched counts is recorded as failed.
- **Parity suite fails on a slice (G-DX-061):** that slice does not cut over; other slices are unaffected — this is what the slicing bought. The diff list is the work order. If a difference turns out to be intended, it is recorded with a named decider; if it cannot be resolved, the slice stays on legacy past the coexistence end date only by a recorded decision extending the window, never by quietly abandoning the plan.
- **Redirect map incomplete at cutover time (step 4's gates unmet):** cutover is blocked, full stop. Launching the new platform with unmapped legacy URLs trades a schedule date for search rankings and inbound links that took the product's whole life to accumulate, and the loss is typically discovered weeks later in the coverage review, after the old URLs have been dropped from the index. If the URL structure genuinely cannot be fully inventoried (a source is unavailable), the gap is recorded as a named risk with the user's explicit acceptance — the map is never presented as complete when it is not.
- **Cutover goes wrong inside the rollback window (abort threshold hit):** execute the drilled rollback — routing and redirects revert to legacy as one motion — then diagnose on the new platform while it carries no traffic. Do not debug under production traffic on an unproven platform while a working legacy platform sits idle; that is what the window is for. A rollback executed is a success of the process, recorded as such in `progress.md`, and the next cutover attempt starts from the failure's fix, with the drill re-run.
- **Cutover goes wrong after the window closed / legacy decommissioned:** this is now an incident, not a rollback — `reliability`'s restore path from the retained final legacy backup (G-DO-134 restore drill currency) is the recovery route, and the postmortem records that the window was closed on insufficient evidence. The prevention is step 9's rule: the window closes on evidence, not on the calendar.
- **Legacy platform fails or is shut off mid-migration (vendor exit, outage, account loss):** the verified legacy backup (G-DB-101/G-DB-104, proven in step 3 before any dependency on it existed) becomes the source of truth for data, and the URL inventory falls back to the crawl/sitemap/search-console sources already gathered in step 4. The schedule decision — accelerate cutover onto a possibly less-proven new platform, or restore legacy elsewhere first — is the user's, presented with both options and their risks (§6.3).
- **Two skills contradict:** §5.7 precedence (security 1, legal 2, data integrity 8 above backend convenience 9 and performance 12); log in `DECISIONS.md`. In this playbook the recurring case is schedule pressure (a coexistence end date) against data-integrity and SEO gates: the gates win, and the end date moves by recorded decision.
- **A gate is itself wrong:** recorded waiver in `progress.md` + `DECISIONS.md` (§6.3 step 5); security/legal waivers need explicit user agreement. The data-count and redirect-map gates are not waivable by the agent — only by the user, explicitly, with the risk named.
- **A secret leaks:** revoke/rotate immediately on both platforms; incident recorded without the value (§5.9 step 4).

## Definition of done

- New platform live on the canonical domain; external production check and readiness honesty test green; monitoring, budgets, and alerts live, including the redirect/404/sync-lag signals.
- Every dataset in `DATA_MAP.md` reconciled: counts match, or every difference is itemized as a deliberate transformation with its count — zero unexplained differences. The final production counts were re-run at cutover, not inherited from the rehearsal.
- Every legacy URL has a disposition in `REDIRECT_MAP.md`, and the post-cutover audits prove the map is real: indexable URLs return 200 with self-referencing canonicals (G-CO-002), redirects are single-hop permanent moves to their named successors (G-CO-003), the submitted sitemap lists only new-platform URLs (G-CO-091).
- Parity suite green on the new implementation for every slice; every accepted difference recorded as an intended change with a named decider.
- The rollback was drilled before cutover (G-DX-063, G-DO-151), the rollback window ran its recorded duration and closed on step 9 evidence, and only then was the legacy platform decommissioned — dead references swept (G-DX-064), legacy credentials revoked, final legacy backup retained per the register.
- Zero P0/P1 defects (QB-01); `progress.md` shows every slice's stage history and the full gate trail; `MIGRATION_PLAN.md`, `CUTOVER_RUNBOOK.md`, `runbook.md`, and `handover.md` current — the runbook records what actually happened at cutover, including any rollback executed.
- **Pre-provisioning complete:** where the new production environment does not exist yet, the project may be recorded as *pre-provisioning complete* — migration plan, data pipeline proven on copies with reconciled counts, redirect map complete, parity green in staging, rollback drilled in staging; every gate that needs the real production environment recorded as a provisioning waiver per §6.3, with the unblocking conditions listed in `progress.md`. Cutover, the rollback window, and decommission remain open until the environment exists; pre-provisioning complete is not migrated.

## Worked mini-example

Sample project: **a small online bookshop** — a self-hosted legacy store on a VPS (product catalog, customer accounts, order history, a blog that carries most of its search traffic) moving to a managed commerce platform, because the VPS stack has reached end of life. Same domain, same products, no redesign.

1. Step 0: core loaded; project scaffolded; read-only legacy access arranged; both platforms' credentials listed by name in `.env.example`.
2. Step 1: requirements freeze behavior, data, and design; the one accepted change is forced — the managed platform's blog URLs carry a `/blog/` prefix the legacy blog did not use. Recorded as a URL change requiring redirects, with a named decider.
3. Step 2: `MIGRATION_PLAN.md` slices the move into three: blog/content first (no writes, lowest risk), catalog second, accounts + order history last (the data point-of-no-return lives here; its backup is named). Coexistence: a reverse proxy in front of both platforms routes by path, so each slice flips independently. Cutover strategy: sliced parallel-run; G-DX-065 passes.
4. Step 3: legacy restore drill run and recorded before anything is copied (G-DB-101). The pipeline lands catalog, accounts, orders, and posts; first trial run's counts show the orders table short by exactly the number of orders the legacy system itself flags as test orders — itemized in `DATA_MAP.md` as a deliberate exclusion, counts then reconcile to zero unexplained differences. The `data-quality` suite catches a set of migrated customer rows with duplicate emails (the legacy system allowed them; the new one does not) → merged under a recorded rule, recounted, green.
5. Step 4: URL inventory from sitemap + crawl + Search Console export.
