# Playbook: AI-ify Existing Product

Add AI features to a product that is already live and already works, without destabilizing what its existing users depend on. This is not a greenfield build with an AI feature in it: the non-AI product is the asset, the AI feature is the risk, and every step in this playbook is ordered so the AI work can be evaluated, contained, switched off, and — if it fails — removed while the original product carries on unchanged. If a step in a new-build playbook and a step here conflict, this playbook wins for the retrofit: never trade a working product for an unproven model call.

## Goal

Ship one or more AI features into a live non-AI product such that: the pre-existing product is regression-proven before the first AI change lands and still passes afterwards; every AI feature sits behind a feature flag with a tested non-AI fallback, so the product works with the model provider down, over budget, or switched off; no AI feature reaches any real user before it has passed an evaluation run against a golden dataset built from this product's real usage; spend is capped server-side before launch, not discovered on the provider invoice; and users are told, before AI touches their data, what is sent where, and can use the product without the AI feature where the underlying task allows it. Rollout is staged and reversible at every stage — full rollout is the last decision, not the default outcome of building the feature.

## Departments + order

Step 0 (always-on core) → D1 (baseline + candidate selection) → **D14+D7 pre-flight (consent, data, threat — before any user data reaches a provider)** → D17 (retrofit audit + evaluation design, before build) → D2+D4 (isolation architecture + flag scaffold) → D17+D4+D3+D13 (build behind the flag) → D8+D17+D7 (evaluation, safety, and regression verification — before any real user is exposed) → D12+D6 (cost/observability wiring + staged rollout) → D18+D14 (trust surfaces, support readiness, updated legal documents) → D6 (full rollout, hold, or kill — decided on evidence)

**Order deviations (three, each deliberate):** (1) D14 and D7 run a pre-flight at the front, not in their usual late position, because the consent and data-flow questions — may this product's user data be sent to a third-party model provider at all, under the privacy commitments already made to existing users? — decide whether the retrofit is allowed to exist, and retrofitting consent after data has flowed is not consent. (2) D17 runs twice: first before the build, to audit the host product and design the evaluation, and again inside the build; in a new build the evaluation can grow alongside the feature, but in a retrofit the eval set must exist *before* the feature does, or "it works" will be judged on demos. (3) D8's verification step gates *exposure*, not deployment: the code may be deployed dark behind its flag while evaluation is still running, but no flag is turned on for any user — internal, beta, or general — until step 7 is green. There is deliberately **no big-bang launch step**: D6 appears as staged rollout only, and a separate, evidence-based decision at the end chooses full rollout, indefinite hold at a partial percentage, or removal.

## Docs to write first

Before any AI code, scaffold from `project-templates` and write:

The full mandated set for this type is `templates/mandated-manifest-ai-ify-existing-product.txt`, which governs (G-PM-001); the list below is the hand-written starting subset, not the whole set.

- `requirements.md` — the candidate AI features considered, the one(s) selected, the existing user task each one changes, and the non-AI behavior that must survive unchanged. Names the existing users affected, not just the new capability.
- `fact-sheet.md` — the host product's verifiable baseline facts: what it does today, the flows in scope, current latency and error behavior as measured (with the measurement source and date), and the privacy commitments already made to users (current privacy policy and terms, quoted, with where they live).
- `BASELINE.md` — the regression baseline: the existing test suites, the critical-flow list exercised by hand or by automation, and their results *before* any change. Every later "no regression" claim traces to this file; a baseline written after the build starts proves nothing.
- `RETROFIT_AUDIT.md` — produced by `ai-retrofit` in step 3, scaffolded here: host-product seams where AI can attach without touching core logic, data available and data off-limits, synchronous flows that cannot absorb model latency, and the fallback that already exists (or must be built) for each candidate feature.
- `AI_DATA_MAP.md` — per feature: exactly which fields leave the product, to which provider, for what purpose, retained by the provider under what terms as recorded at decision time, and which fields are redacted or never sent. This is the input to the D14 register update in step 8, not a substitute for it.
- `EVAL_PLAN.md` — per feature: the golden dataset's source (real usage, support failures, observed failure modes), its mandatory failure and adversarial categories, the grading stack, the quality floor and per-category regression tolerances — all recorded *before* the first eval run, per `ai-evaluation`.
- `COST_PLAN.md` — per feature: the per-request token budget, per-user quota, per-period spend budget, and the named owner of each, per `ai-cost-control`; the model tier proposed and the eval evidence that will justify it. A feature with no entry here does not ship.
- `ROLLOUT.md` — the flag name, the stages (dark → shadow where the seam permits → internal → named beta cohort → percentage stages → full), the entry and exit criteria for each stage, the metric that stops promotion, and the kill procedure: who flips the flag, how fast the fallback takes over, and how that was tested.
- `progress.md`, `DECISIONS.md` — session log and decision record; every stage promotion, hold, and kill is recorded in both.
- `.env.example` — provider credentials and flag-service credentials by name + purpose only (§5.9); provider keys are server-side secrets from the first commit, never client configuration.

## Step-by-step sequence

**Step 0 — Core and scaffold.** Load `bundles/core.md`; generate the project files (G-PM-001, G-PM-002); write the docs above; load `secrets-management` before any provider key exists. Record the host product's current deployed version in `progress.md` — the retrofit is always described relative to a named, working release.

**Step 1 — Baseline and candidate selection (D1).** Freeze the baseline before selecting anything: run the existing suites, exercise the critical flows, and record the results in `BASELINE.md`. Then select candidate features against the baseline, not against enthusiasm. A candidate is admissible only if all four hold: (a) the underlying task already exists in the product, so a non-AI fallback exists or can be kept; (b) a wrong, empty, or refused model answer is recoverable by the user in the flow (they can edit, retry, ignore, or do the task manually) — AI that can silently commit an irreversible action is out of scope for a first retrofit; (c) the data it needs is data the product already lawfully holds for that user; (d) its value can be stated as a change to an existing measure (time to complete the task, completion rate, support contacts about that task) rather than as "engagement with AI". Rank admissible candidates by (recoverability × measurable value) ÷ (data sensitivity × latency added); build the top one first, alone.
◆ **DECISION — which feature, and what is explicitly not being AI-ified?** Record both halves in `DECISIONS.md`. The not-list matters as much as the pick: it stops scope creep mid-build, when every adjacent flow suddenly looks like it also needs a model call. If unspecified, ask (§6.3 step 4). (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer; if none is recorded and no user is reachable, follow the §6.3 stuck protocol (log-and-continue, then the safe defaults) and record the substitution in `progress.md`. The safe default here is the single highest-ranked admissible candidate only; never "all of them".)

**Step 2 — Consent, data, and threat pre-flight (D14+D7, before any provider sees any data).** Run `privacy-laws` against `AI_DATA_MAP.md`: does the product's existing privacy policy and the consent it was collected under actually cover sending this data to this provider, for this purpose? Three outcomes, all legitimate: covered as written; covered only with an updated policy and user notice *before* the flag reaches anyone; or not coverable (the data, the provider's retention terms, or the user population — for example minors — forbids it), in which case the feature is redesigned to send less, to use a provider whose terms fit, or is dropped. Threat-model the AI surface specifically (`threat-modelling`, `owasp`): prompt injection through every field a user or a third party can influence, extraction of other users' data through the model's context, the model as a confused deputy holding the user's permissions, and unbounded consumption as a cost attack. No real user data — including in "just one test call" from a developer machine — goes to a provider before this step is recorded as passed.
◆ **STOP AND ASK — sending existing users' data to a new third party (§5.9/§6.3).** If the pre-flight outcome is "covered only with updated policy and notice", the policy update and the notice are user-approved work, not a build detail: the operator approves the new data-flow wording before step 5 connects it. (Unattended run: BOOTSTRAP's approval-points rule applies at this point — an approval recorded in the commissioning brief or `requirements.md` counts as the answer. If none is recorded and no user is reachable, the policy approval itself is never log-and-continued and never safe-defaulted: it is a legal position on the §6.3 Step 5 never list. Build and evaluation proceed on synthetic and consented test data only, the feature stays flag-dark, and the data flow stays disconnected; log the approval as a blocker in `progress.md` (§6.3 step 3) and ask the user (§6.3 step 4). No real user data moves to the new third party on a substitution.)

**Step 3 — Retrofit audit and evaluation design (D17, before build).** Run `ai-retrofit` over the host product and complete `RETROFIT_AUDIT.md`: the seams (an existing extension point, a post-processing hook, an adjacent new endpoint — in that order of preference; editing core logic to inline a model call is the last resort and is recorded as such), the latency budget each seam can absorb, and the fallback at each seam. Then design the evaluation under `ai-evaluation` before a line of feature code exists: build the golden dataset from this product's real usage — production examples, support failures, and the awkward inputs real users actually produce — with the mandatory malformed/empty, unanswerable, refusal, and adversarial categories; pin the graders and, if a model judge is used, its model, temperature, and calibration plan; record the floor and tolerances in `EVAL_PLAN.md`. In parallel, complete `COST_PLAN.md` under `ai-cost-control`: budgets, quotas, owner, and the tier the eval will have to justify. The ai-retrofit skill's gates apply to this step's audit output and must pass before step 4 designs around its seams.
◆ **DECISION — what does the user see when the AI is wrong, slow, or off?** For each feature, choose the fallback shape now, while it is still a design choice: the pre-AI manual flow (preferred — it is the flow users already know), a reduced non-AI result (for example exact-match search instead of semantic search), or an honest unavailable state. "Show the model's output anyway" and "show a spinner until it works" are not fallbacks. Record the choice in `ROLLOUT.md`; step 5 builds exactly this, and step 6 tests exactly this. (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer; if none is recorded and no user is reachable, follow the §6.3 stuck protocol (log-and-continue, then the safe defaults) and record the substitution in `progress.md`. The safe default is the pre-AI manual flow.)

**Step 4 — Isolation architecture and flag scaffold (D2+D4).** Design the AI feature as an addition the host can lose, not a change the host depends on. Concretely: all model calls go through the single server-side wrapper `llm-integration` will own in step 5 — no provider SDK anywhere else, ever (enforced at step 6 by G-AI-001); the feature reads host data through the product's existing APIs or service layer, never through new direct reads of core tables from AI code; any new storage (prompts, traces, eval artifacts, cached results) lives in its own tables or namespace, with its own migration and its own down-path, so removing the feature does not migrate core data; and the synchronous request path of any existing flow gains no hard dependency on a model response — where AI output enhances a flow, the flow renders and functions without it and fills in, replaces, or omits the AI part when it does not arrive. Stand up the flag here (`feature-flags`): flag created in the registry with an owner and an expiry/review date, default **off** in every environment including staging demos, targeting by user/cohort/percentage available, and the fallback path wired to the flag's off state from the first commit — the flag is scaffolded before the feature, so there is never a version of the feature that exists unflagged.

**Step 5 — Build behind the flag (D17+D4+D3+D13).** Build in wrapper-first order. (a) `llm-integration`: the wrapper with typed errors for rate limit, timeout, refusal, incomplete, and invalid output; timeout, token budget, and retry cap from configuration on every call; keys server-side only. (b) `prompt-engineering`: prompts as canonical, versioned files with their contract headers — never strings assembled inside handlers. (c) `ai-safety`: guardrails around the call — user and retrieved content treated as untrusted data, output handled as inert text (never executed, never rendered as raw HTML, never concatenated into SQL), state-changing actions gated by a deterministic server-side policy check with human confirmation where the action is a payment, a deletion, or an external send. (d) `ai-cost-control` enforcement *in the wrapper*: metering on every call, per-user quota and per-feature budget checked before the provider request is made — an alert is not a cap. (e) `ai-observability`: one trace per call carrying prompt version, model ID, tokens in/out, latency, cost, and outcome, with user content redacted before storage, and user feedback (accept, edit, dismiss, report) linked to the trace it judges — this linkage is what makes step 9's evidence review and the production-failure intake possible. (f) The surface (D3+D13): AI output is labeled as AI output wherever a user could mistake it for human, system, or factual content; the user can always reach the manual path from the AI surface in one action; loading, empty, refused, timed-out, and budget-exhausted states are designed states (`ui-states`), not error pages; and the surface passes the same accessibility bar as the rest of the product (G-AC-001, G-AC-005) — a retrofit does not get to ship the product's first inaccessible screen. Throughout: the flag stays off outside development, and every merge keeps the host's baseline suites green — a red baseline suite is fixed or the change is reverted the same day, never carried as "known failure" into step 6.

**Step 6 — Evaluation, safety, and regression verification (D8+D17+D7 — before any real user is exposed).** Three verifications, all blocking, in this order. (1) *Evaluation before launch:* run the full golden set through the real wrapper, prompt, model, and retrieval stack (G-AI-071 CI eval gate, G-AI-073 dataset integrity and contamination scan, G-AI-072 judge calibration where a judge grades); the feature must meet the floor recorded in `EVAL_PLAN.md` with no category beyond its tolerance — a floor lowered in the same change that fails it is a failed gate, not a new floor. (2) *Safety and containment:* the red-team injection suite (G-AI-021), tool-call policy audit (G-AI-022), output-handling scan (G-AI-023), leakage and redaction tests (G-AI-024, G-AI-082), SDK containment (G-AI-001), live contract and fault-injection bounds (G-AI-002, G-AI-004 — a provider that only ever returns errors must produce the typed error and the fallback, within the timeout budget, not a hang), and the cost guards (G-AI-091 budget-guard test, G-AI-092 runaway-loop test, G-AI-093 metering reconciliation, G-AI-095 degradation drill — performed as an end user, flag on, budget exhausted). (3) *No regression to the host:* the full `BASELINE.md` suite re-run against the flag-off build and the flag-on build; both must match the baseline, and the flag-off build must additionally pass the staging flip test (G-BE-032) — flag off removes the feature completely, with no redeploy, and the pre-AI flow works exactly as baselined. Plus the standard verification the host would get for any change: security suite (G-SE-001, G-SE-003 — 0 critical), secret scan (G-SE-041, and G-AI-003 for provider keys), dependency gate (G-SE-051), qa-gates (G-QA-111), placeholder sweep over rendered output including every AI state (G-QA-141). **No deployment to users until green** — where "users" includes the beta cohort; internal dogfooding on synthetic and consented test data is the only exposure allowed before this step passes.
◆ **DECISION — eval floor missed: improve, narrow, or drop?** If the feature misses its recorded floor, the options are exactly three: improve the stack and re-run; narrow the feature's claimed scope until the passing subset *is* the feature (and re-record the floor against the narrowed scope, with the dataset unchanged); or drop the feature and remove it behind its flag. Averaging away a failing category, re-rubric-ing the items it fails, or shipping to "see how it does live" are not options. Record the choice in `DECISIONS.md`. (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer; if none is recorded and no user is reachable, follow the §6.3 stuck protocol (log-and-continue, then the safe defaults) and record the substitution in `progress.md`. The safe default is: do not promote; leave the flag dark and report the failing categories.)

**Step 7 — Cost/observability wiring and staged rollout (D12+D6).** Before the first stage: production budgets asserted like any other budget (G-AN-101, applied to the AI feature's added latency on any existing flow it touches — the pre-AI flow's budget does not silently expand to absorb model latency; the AI part is async, cached, or budgeted separately), cost and quality dashboards reading from the trace store (G-AI-083 dashboard data-change test, G-AI-081 trace completeness), and alerts on the stop metrics named in `ROLLOUT.md` — spend rate against budget, error/refusal rate, fallback rate, and eval-relevant user feedback — wired to a human, not a log file. Then roll out by the recorded stages, promoting only on evidence: **dark** (deployed, flag off, wrapper and traces exercised by synthetic calls only) → **shadow** (where the seam permits: the model runs on real inputs with its output shown to no one and changing nothing, and divergence from the existing flow is recorded and read before any exposure, per `ai-retrofit` AI-209/AI-211) → **internal** (staff accounts, real tasks, feedback linkage checked, G-AI-084) → **named beta cohort** (users who were told the feature is AI, told it is a trial, and given the manual path and a feedback route — beta is a consent and support state, not just a percentage) → **percentage stages** (bucketing stability proven, G-BE-033; each stage held long enough to read its stop metrics, with the hold duration recorded in advance in `ROLLOUT.md`, not decided by impatience) → decision at step 9. Any stage can end in a flag flip back to the fallback within minutes and without a deploy (proven at step 6 by G-BE-032, re-proven at the first real flip); a rollout whose kill path has never been executed is treated as having no kill path.

**Step 8 — Trust surfaces, support readiness, and legal documents (D18+D14).** In parallel with the beta and percentage stages — and completed before full rollout, not after: the in-product disclosure is live wherever the feature is on (what the AI does, that output can be wrong, where the manual path is); the privacy policy, terms, and the D14 register are updated to match `AI_DATA_MAP.md` as actually built (G-LG-001, G-LG-002 register and data-map completeness; G-LG-031 document-vs-register diff) — documents describe the shipped data flow, not the planned one; onboarding for the feature (`user-onboarding`, G-CX-031) teaches the fallback as well as the feature; and support is ready before users are (`support-ticketing`): the support team has seen the feature's failure states, has a script for "the AI gave me a wrong answer" that starts from the trace ID the feedback link provides, and has an escalation that reaches the flag owner. A user harmed by a confident wrong answer who meets an unprepared support desk loses trust in the whole product, not just the feature — that asymmetry is why this step exists.

**Step 9 — Full rollout, hold, or kill (D6, decided on evidence).** At the final percentage stage's recorded review point, decide from the stored evidence only: eval reports per version (G-AI-074 change-record eval audit), production-failure intake completed — every failed production case added to the golden set or rejected with a reason (G-AI-075), cost report per feature and per model reconciled against metering (G-AI-093) and inside the `COST_PLAN.md` budget at the current volume, and the host's measures from step 1 (task time, completion, support contacts) compared against `BASELINE.md`. Three outcomes: **full rollout** (flag to 100%, flag and fallback retained — full rollout is not flag removal; the flag is retired only under `feature-flags`' normal expiry discipline, G-BE-031 registry-vs-codebase diff, after a recorded stability period, and the fallback's retirement is a separate decision); **hold** (stay at the current percentage with the reason and the next review date recorded — a hold is a decision, not a stall); or **kill** (flag off for everyone, fallback confirmed live, feature code and its storage removed or archived under the rollback plan, G-DO-151, and a postmortem entry in `progress.md` stating what the evidence showed — a killed feature with a clean kill is a successful retrofit outcome, not a failed project).
◆ **STOP AND ASK — retiring the non-AI path (§6.3).** Making the AI path the *only* path — removing the manual flow, the fallback, or the flag — is a separate commission from this playbook and requires the user's explicit go-ahead, with the step 9 evidence on the table. This playbook never retires the fallback as a side effect of success. (Unattended run: a go-ahead recorded in the commissioning brief or `requirements.md` for the retirement counts as the answer. If none is recorded and no user is reachable, the retirement is never log-and-continued and never safe-defaulted — removing the only non-AI path is a safety decision on the §6.3 Step 5 never list. The fallback stays, the flag stays, the blocker is logged in `progress.md` (§6.3 step 3), and the user is asked with the step 9 evidence (§6.3 step 4).)

## Failure handling

- **A gate fails:** fix in the owning step, re-run; same failure twice → §6.3 (log in `progress.md`, continue unblocked work, batch blockers with concrete options). The flag stays at its current stage — or off — while any step 6 gate is red; a failing gate never gets "one stage to prove itself live".
- **No eval set exists when build is proposed (the classic retrofit failure):** stop the build at step 3. The dataset is built from real usage first, even if that takes longer than the feature would. A feature launched with no eval set has no quality claim, no regression protection for its first prompt change, and no evidence for step 9 — it is not launched "temporarily unevaluated"; it is not launched.
- **Eval floor missed (G-AI-071):** the step 6 decision applies — improve and re-run, narrow the claimed scope against the *unchanged* dataset, or drop the feature. Editing golden items to pass, grading against a stubbed model, or presenting a happy-path demo set as the eval are banned practices under `ai-evaluation`, not shortcuts.
- **Runaway or runaway-shaped costs (G-AI-091/G-AI-092 fail, or a production stop metric trips):** flip the flag to the fallback first, investigate second. Cost enforcement lives in the wrapper precisely so this is a configuration event, not an incident: confirm zero provider calls past the cap, then find the loop, retry path, maximal-input abuse, or missing quota that leaked. The feature does not return to its previous stage until the budget-guard and runaway-loop tests pass again in staging.
- **Model or provider fails in production (outage, latency collapse, refusal spike):** the typed-error and degradation paths from step 5 carry the product — users see the fallback or the honest unavailable state, never a hung flow, a raw provider error, or an empty success. If the fallback itself is what fails, that is a host-product incident (P0, QB-01) and is handled as one; the AI feature stays off until the *fallback* is re-proven by G-BE-032.
- **AI output shown without a human path (wrong answer acted on, user cannot reach the manual flow, support cannot find the trace):** treat as a trust incident, not a quality bug. Freeze promotion, check the disclosure, the one-action manual path, and the feedback-to-trace linkage (G-AI-084) as built — not as designed — and fix whichever is missing before any further stage. Output that commits a state change without the policy check and required human confirmation (G-AI-022) is a security defect and blocks the feature outright.
- **Host regression traced to the retrofit (baseline suite red, host flow over its latency budget, G-AN-101):** the AI change is reverted or flag-killed to restore the baseline; the retrofit resumes only from a green baseline. The host product's health outranks the feature's schedule in every conflict (§5.7 precedence; log in `DECISIONS.md`).
- **Consent or data-map defect found after exposure (data sent beyond `AI_DATA_MAP.md`, policy text not matching the shipped flow, G-LG-031):** flag off immediately for the affected feature, D14 owns the remediation and any user notice, and the incident is recorded without reproducing the data (§5.9). Re-exposure requires step 2 to be re-run, not just the document fixed.
- **A gate is itself wrong:** recorded waiver in `progress.md` + `DECISIONS.md` (§6.3 step 5); security/legal waivers need explicit user agreement. The eval floor (G-AI-071) and the budget guard (G-AI-091) are never waived for a launch stage — a feature that needs either waived is a feature that holds or dies at step 9's table, early.
- **A secret leaks:** revoke/rotate immediately; incident recorded without the value (§5.9 step 4). Provider keys are rotated, not just removed from the repo (G-AI-003).

## Definition of done

- The host product's `BASELINE.md` suites pass unchanged on the final build, flag off and flag on; the flag-off state is the pre-AI product, proven by the flip test (G-BE-032), not asserted.
- Every shipped AI feature: passed its recorded eval floor on the committed golden dataset (report stored per version), passed the safety and cost-guard suites, is metered with reconciled per-feature cost inside its recorded budget, and has a named budget owner.
- Rollout reached its step 9 decision on stored evidence — full rollout, recorded hold, or clean kill — with the production-failure intake completed and the golden set updated from live failures.
- Users were told before exposure: in-product AI disclosure live, privacy policy and register matching the shipped data flow (G-LG-031), the manual path reachable in one action from every AI surface, and support able to trace any reported output to its call.
- The fallback is still live and tested at the moment of completion; retiring it is explicitly *not* part of done.
- Zero P0/P1 defects (QB-01); `progress.md`, `DECISIONS.md`, `ROLLOUT.md`, `runbook.md` (including the kill procedure and the budget-exhaustion procedure), and `handover.md` current.
- **Pre-provisioning complete:** where no production environment or provider account exists yet, the project may be recorded as *pre-provisioning complete* — every gate except the provisioning-waived ones green (evaluation may run against the provider's sandbox/test mode with the eval report recorded as sandbox-sourced), each waived gate recorded as a provisioning waiver per §6.3, the flag dark by default in all configuration, and the unblocking conditions listed in `progress.md`. The rollout and exposure requirements above remain open until the environment exists; pre-provisioning complete is not done, and it is never a state in which real users have seen the feature.

## Worked mini-example

Sample project: **a small invoicing tool for freelancers** — live, paying users, no AI anywhere — adding one feature: when a user writes a free-text note about a job ("fixed the shop's leaking sink Tuesday, two hours, plus parts"), the tool drafts the invoice line items (description, quantity, unit) for the user to review and edit before anything is saved.

1. Step 0: core loaded; provider key listed by name in `.env.example`; host release v2.4 recorded as the retrofit base.
2. Step 1: baseline frozen — existing suites green; the critical flows (create invoice manually, edit line items, send, record payment) exercised and recorded. Three candidates considered; line-item drafting picked because a wrong draft is fully recoverable (nothing saves without the user's review and explicit save), the note text is data the user just typed for exactly this purpose, and success is measurable as time-to-complete an invoice against the baseline timing recorded for the manual flow. Explicitly not AI-ified, recorded in `DECISIONS.md`: automatic sending of invoices, and payment chasing messages — both commit actions toward third parties.
3. Step 2: pre-flight finds the current privacy policy names no third-party processing of invoice content. Outcome: policy and an in-product notice must be updated and approved before the flag reaches anyone; build proceeds on synthetic notes only. Threat model flags the note field as injection surface — a note is user text, and a pasted note could contain text copied from a client's email.
4. Step 3: `ai-retrofit` audit finds the seam — the invoice form already has a "prefill from note" hook point in the editor's draft state, so the feature attaches there and core invoice logic is untouched; fallback is the existing blank line-item editor, exactly as users know it. Golden dataset built from anonymized, consented examples the operator collected from support conversations and the developer's own test invoices: ordinary notes, notes with no quantities (correct behavior: draft descriptions, leave quantities blank rather than inventing them), notes in the product's second supported language, an empty note, and an adversarial note containing an embedded instruction to discount the total — which the draft must ignore, because totals are computed by the product, never by the model.
5. Step 4: wrapper-first architecture; new storage limited to traces and eval artifacts in their own tables; flag `ai-line-item-draft` created, default off, fallback wired to the blank editor from the first commit.
6. Step 5: built behind the flag — wrapper with typed errors and a short timeout suited to an interactive form; prompt as a versioned file whose output schema is line items only (no totals, no tax fields, so the model structurally cannot set them); guardrails treat the note as untrusted data and render drafts as inert, editable text; per-user daily quota and a per-period budget enforced in the wrapper; traces redacted; the draft panel labeled as an AI draft, with "start blank instead" one click away in every state, including the timed-out state.
7. Step 6: first eval run fails its floor on one category — notes with no quantities, where the draft invents a quantity of 1 instead of leaving it blank. Floor not lowered, items not edited: the prompt and output handling are fixed so a missing quantity stays blank, and the re-run passes all categories. Red-team suite confirms the discount-instruction note produces an ordinary draft with no discount. Fault injection (provider stub returning only errors) shows the editor falling back to blank line items within the timeout budget. Baseline suites pass flag-off and flag-on; flip test proves flag-off restores the exact pre-AI editor.
8. Step 7: dashboards read from traces; spend alert set from `COST_PLAN.md`. Rollout: dark for a week of synthetic calls, then internal, then a named beta of users who were emailed that the trial is AI-assisted and optional — two beta users turn it off and keep invoicing manually, which is recorded as the fallback working, not as churn.
9. Step 8: privacy policy updated to name the provider and the note-text flow, matching `AI_DATA_MAP.md` as built (G-LG-031 clean); support given the trace-lookup script and the wrong-draft script before the percentage stages begin.
10. Step 9: at the final stage review, the evidence is: eval reports per prompt version, production failures from beta added to the golden set (a note mixing two jobs, now a named category), reconciled cost inside budget, and invoice completion time down for beta users against the step 1 baseline timing with no increase in support contacts about invoicing. Decision: full rollout — flag to 100%, flag and blank-editor fallback retained. The manual path is not retired. Done.
