# Playbook: Clone-and-Redesign

Take a reference product, clone what it *does*, and redesign everything it *is*: a new implementation of the same function under an original design, an original brand, and original copy. This is not the Clone / Rebuild playbook — that one matches a source's design language; this one is forbidden from doing so. Where Clone / Rebuild asks "how close is it?", Clone-and-Redesign asks two questions at once: "does it do the same job?" and "is every visible thing about it ours?"

> **The legal line, which governs every step below: function may be cloned; protected expression may not be copied.** Ideas, workflows, feature behaviour, and functional patterns are the clone target. Text, images, brand assets, logos, trade dress, and distinctive visual expression are never copied — not verbatim, not paraphrased line-by-line, not traced, not recoloured. If a step below ever appears to require the reference's expression to proceed, the step is being done wrong: stop and redesign that part from the function spec instead.

## Goal

Ship a product that performs the reference product's in-scope functions — proven against a frozen function spec built from observed behaviour — while sharing none of the reference's protected expression: original name and brand, original design system (tokens, layout, typography, motion), original assets, and original copy throughout. Every function is accounted for in the spec as *cloned* (observed in the reference and re-implemented), *designed* (not observable in the reference; designed fresh), or *excluded* (out of scope, with the reason recorded) — and no parity claim is ever made about how the product *looks*, only about what it *does*.

## Departments + order

Step 0 (always-on core) → **D14 pre-flight (authorization only)** → D16 → D1 → D3 (design) → D9 (copy) → D3+D13+D4+D5 (build) → D14 (full) → D12 → D7+D8+D16 (verification) → D6 → D9 (finish)

**How this differs from Clone / Rebuild, and why the order changes.** Three structural differences drive the sequence. (1) **D1 sits between D16 and the build.** In a rebuild, the inventory itself is the build contract; here the inventory describes someone else's product, so D1 must first convert it into an original function spec — the only D16-derived artifact the build is allowed to consume. (2) **D3 and D9 run as their own steps before the build, not inside it.** The design system and the copy are authored from the function spec and the redesign brief, never from reference captures; if designers or writers work inside the build step with reference screenshots open, the output drifts into a copy (see Failure handling). (3) **D16 returns at verification, but with the opposite job:** in a rebuild, D16's fidelity-verification proves similarity; here D16 verifies *functional* parity against the behaviour specs and *dissimilarity* of expression — the clone-redesign skill's gates, not a visual-parity suite. There is deliberately **no visual-parity step anywhere in this playbook**: a page that scores well against the reference visually is a defect here, not a success.

## Docs to write first

BOOTSTRAP's four project docs are created at scaffold (step 0); the mission docs below are additions to them, not replacements. The full mandated set for this type is `templates/mandated-manifest-clone-and-redesign.txt`, which governs (G-PM-001); the list below is the hand-written starting subset, not the whole set.

**Before any crawl** (steps 0–1):

1. `requirements.md` — the new product's goal, audience, key features, and acceptance criteria (BOOTSTRAP step 4). This is the file the ◆ decision notes below mean when they say a decision may already be recorded in `requirements.md`.
2. `stack.md` — the new product's stack record, with dated selection criteria (the reference's stack is not observable and is never a target).
3. `fact-sheet.md` — the reference product's verified facts (owner, purpose, public claims) with sources; nothing about the reference is asserted without evidence. Facts may inform the function spec; the reference's *wording* of those facts may not be reused.
4. **Authorization record** (per clone-ethics) — who authorized the work, the legal basis, scope, and date. Written and committed **before any crawl**. The record additionally names the mission type — clone-and-redesign — so the scope it grants is function study, not expression reuse.
5. `progress.md`, `DECISIONS.md` — playbook trace, gate results, deviation log; decision record (scope changes live here, nowhere else).

**Produced during the walk** (not before the crawl — each is an output of the step that writes it):

6. `function-spec.md` — the build contract, written in step 3 from D16's behaviour specs and inventory: every in-scope function, its observable behaviour, its inputs and outputs, and its status (cloned / designed / excluded). Once frozen at step 3, this file — not the reference — is what the build is checked against.
7. `redesign-brief.md` — the new product's identity before it exists: working name, audience, design direction, voice, and the **protected-items list** (the reference's brand names, marks, slogans, distinctive copy strings, and signature visual traits that must never appear in the redesign). Started in step 2 alongside D16, finalized in step 4.

**Workspace separation rule (set up in step 0, enforced throughout):** reference material — captures, screenshots, harvested files, the reference's copy — lives only in the D16 analysis workspace. The build workspace receives exactly three inputs: `function-spec.md`, the new design system, and the new copy. If reference material is found in the build workspace, that is a process failure, handled under Failure handling.

## Step-by-step sequence

**Step 0 — Core and scaffold.** Load `bundles/core.md`; set up project files (project-templates — the mandated set is `templates/mandated-manifest-clone-and-redesign.txt`, G-PM-001), start `progress.md`, apply the secrets baseline, and create the two separated workspaces (analysis / build) described above.

**Step 1 — D14 pre-flight — authorization before anything touches the reference.** Run clone-ethics: write the authorization record, then pass **G-LG-091** (pre-flight authorization check) and **G-LG-092** (authorization-vs-crawl timestamp comparison — the record must be older than the first crawl log entry).
◆ **DECISION — is there an authorization basis for studying this reference?** Own product, client engagement, or a legitimate study purpose (per clone-ethics' grounds). If there is no basis, stop and ask (§6.3). No authorization, no crawl, no exceptions — and note that authorization to *study* a reference is never authorization to *reuse its expression*; the legal line at the top of this playbook applies even to the user's own earlier product if third-party assets, stock, or licensed material are in it (licensing rules on those items individually). (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer. If none is recorded and no user is reachable, this decision is carved out of the stuck protocol's continuation path: an authorization basis is a legal position, and §6.3 Step 5's never list forbids resolving a legal position by safe default. Log the blocker in `progress.md` (§6.3 step 3), ask the user with concrete options (§6.3 step 4), and stop the playbook at this step — no crawl, no analysis, and no design work happens until a basis is recorded. There is no substitution to record, because no default exists for this point.)

**Step 2 — D16 analysis — extract function, quarantine expression.** site-discovery and page-inventory map the reference's routes and surfaces (G-CL-001 authorization pre-flight, G-CL-002 robots and terms compliance, G-CL-003 three-source reconciliation; G-CL-011 reconciliation diff, G-CL-013 canonical uniqueness). behavior-cloning records observable interactions as behaviour specs (G-CL-041 authorization and account pre-flight, G-CL-042 spec coverage diff). Functions the vendor's own documentation describes but this engagement cannot observe — behind a login, a paid tier, or an integration it has no access to — enter the inventory under clone-redesign's `documented` evidence class (CL-143), carrying the citation that rule requires; the class is defined in the skill, not here. In this playbook's walk the class discharges at the step 3 freeze: a `documented` function is dispositioned *designed* there — specified fresh from the documentation's stated behaviour — unless it first becomes observable, in which case it routes back to behavior-cloning like any other flow. design-extraction runs under clone-redesign **CL-144** — its output is a negative reference, never a value source: it records the reference's structural and layout *patterns* (component inventory, layout rules, state coverage) as characteristics in the redesign brief — its tokens, palette, and type choices are **not** carried into the build; they are recorded only so step 9 can prove the redesign does not reproduce them. Assets are inventoried with verdicts (G-CL-031 manifest completeness, G-CL-034 verdict enforcement audit), and in this playbook the verdict set narrows: nothing from the reference is `owned`/`licensed` into the redesign unless the authorization record explicitly covers that asset class — the default verdict for every reference asset is `replace`, and the replace-list (G-CL-024) is seeded into the redesign brief's protected-items list.
◆ **DECISION — for each auth-gated or unobservable function: design fresh or exclude?** Behaviour that cannot be observed cannot be cloned; it is either designed fresh in step 3 (and marked *designed* in the function spec, never presented as cloned) or excluded with the reason recorded. A function the vendor documentation describes but the engagement cannot observe (the `documented` class, CL-143) takes the *designed* branch by default — the documentation is the design input, cited as documentation; a function neither observable nor documented is excluded. Never guess-and-present-as-cloned. (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer; if none is recorded and no user is reachable, follow the §6.3 stuck protocol (log-and-continue, then the safe defaults) and record the substitution in `progress.md`.)

**Step 3 — D1 function spec — freeze what "the same function" means.** requirements-writing converts the behaviour specs and inventory into `function-spec.md`: each function stated as behaviour (trigger, inputs, outputs, states, errors), with no reference to the reference's layout, wording, or branding. fact-sheet facts may be cited; the reference's phrasing of them may not. scope-control freezes the list. One spec, two axes (CL-142): the cloned / designed / excluded statuses used here are statuses **inside the function column** of clone-redesign's two-column spec — *cloned* is a function-column entry sourced from a behaviour spec, *designed* is a function-column entry specified fresh (including every `documented` entry from step 2), *excluded* is an inventoried item held out of scope with its reason. The expression column is not classified in this step at all: it carries the originality obligation, discharged in steps 4–5 and proven at step 9(b). G-CL-071 runs at this freeze and checks exactly that assignment — every inventory item in exactly one column, every function entry cited to a spec or carried as `unobserved`.
◆ **DECISION — the parity list is frozen here; what is on it?** Every function is cloned, designed, or excluded, by name. This freeze is the playbook's defence against feature-parity creep: after this step, "the reference also does X" is not a reason to build X — a new function enters only as a DECISIONS.md scope change, re-costed as new product work. (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer; if none is recorded and no user is reachable, follow the §6.3 stuck protocol (log-and-continue, then the safe defaults) and record the substitution in `progress.md`.)

**Step 4 — D3 redesign — a design system that owes the reference nothing.** design-system and design-tokens author the new product's tokens, layout rules, and component patterns from the redesign brief alone (component-library builds the kit). The reference's extracted characteristics are used only as a *negative* checklist: same component *types* where the function requires them (a data table is a data table), never the same visual treatment. The design must pass the design gates on its own merits — G-DES-01 (design rubric), G-DES-02 (no attractor cluster), G-DES-06 (distinguishable from a component-library default) — and the redesign brief's protected-items list is checked against every template before build.
◆ **DECISION — name and brand direction.** The new product's name, mark, and visual identity are approved here, before build, and cleared under the clone-redesign skill's CL-153 — searched against the reference's marks, the protected-items list, and the launch markets' trademark registers, with the search and its result recorded in the design record — a name or mark that trades on the reference's identity fails the legal line even if every pixel differs. Record the approved direction in `redesign-brief.md`. Unattended default for this decision: if no name is recorded and no user is reachable, proceed under a **working name** — collision-checked under CL-153 against the reference's marks and the protected-items list, marked as a working name in `redesign-brief.md`, with final name approval deferred and the substitution logged in `progress.md`. (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer. If none is recorded and no user is reachable, final approval of the name and mark is never log-and-continued and never safe-defaulted: approving an identity is a legal position (§6.3 Step 5 never list). Proceed only under a clearly marked working name that has passed the CL-153 search above, log the approval as a blocked item in `progress.md` (§6.3 step 3), and ask the user with concrete options (§6.3 step 4); the working name ships nowhere until the approval exists.)

**Step 5 — D9 copy — written from the function spec, never from the reference.** copywriting drafts every string — pages, UI microcopy, empty states, errors, emails — from `function-spec.md` and the redesign brief's voice. Writers do not open the reference: a paraphrase produced with the source text on screen is a copy with the words changed, and it fails step 9's residue checks. real-content governs every factual claim: facts verified in `fact-sheet.md` may be stated in original wording; testimonials, statistics, and customer claims from the reference are its expression *and* its evidence — they are never carried over (G-DES-05: no fabricated items; the redesign launches with only claims the new product can source itself).

**Step 6 — Build — D3+D13+D4+D5, from the three permitted inputs only.** frontend-core and component-library build the surfaces from the function spec + new design system + new copy. D13 runs in the same step — accessibility-audit on every template (G-AC-001, G-AC-005; G-EXP-05 axe-core 0 violations, G-EXP-06 contrast). Backend and schema are designed fresh (api-building, schema-design): the reference's backend is not observable, and its data model is inferred from behaviour only where the function spec requires it — never claimed to be matched. clone-redesign supervises the build's inputs: any request from the build side for a reference screenshot, capture, or text is refused and logged — the answer is always in the function spec, or the spec is amended through step 3's process.

**Step 7 — D14 full pass.** privacy-laws register for the new product's own data handling; legal-documents for its own terms/privacy text (original documents for the new brand, not adapted reference documents). G-LG-093 runs here, and **G-LG-094** (brand-residue scan) gets its first full run: the reference's brand names, trademarked terms, slogans, and distinctive copy strings are grepped against the whole build, and shipped media is hash-compared against the harvested-asset set. In this playbook G-LG-094 is not a formality — it is the primary proof that the legal line held.

**Step 8 — D12 performance.** performance-budgets set and asserted for the new templates (G-AN-101 CI budget assertion; G-ENG-02 lab performance budgets, G-ENG-04 page-weight budgets). Budgets are the new product's own, set from its requirements — the reference's performance is not a target and its numbers are not copied into the fact sheet as claims.

**Step 9 — Verification — D7+D8+D16.** Security pass (owasp; G-SE-001 ZAP baseline, 0 critical findings; G-ENG-11 no secrets in shipped code). QA: qa-gates (G-QA-111) and placeholder-scan (G-QA-141 — scan rendered output, not source; no placeholder text survives). Then the mission-specific pass, run by clone-redesign under the clone-redesign skill's gates: (a) **functional parity** — the frozen behaviour-spec suite runs against the redesign (G-CL-043 frozen-suite acceptance run, G-CL-045 click-through verification): every *cloned* function behaves as specified. *Designed* functions have no frozen spec to run, so they are proven by the new-function acceptance route, at the same evidence standard: for each designed function, an acceptance test is written from its `function-spec.md` entry and the acceptance criteria recorded for it at step 3 (acceptance-criteria form, D1 — loaded with step 3's `bundles/product-requirements.md`), implemented under e2e-testing and run in the same CI suite as the frozen behaviour suite (G-QA-021, suite green on the preview deployment), and its result is recorded per function in the verification report under qa-gates (G-QA-111). A designed function with no acceptance test, or whose only evidence is the assertion that it "behaves as D1 specified it", fails this step. And no report language upgrades a designed function to cloned (the claims sweep in the clone-redesign skill's G-CL-075, under CL-151); (b) **expression separation** — the clone-redesign skill's distance gates run and recorded: G-CL-072 (token distance diff against the extracted set), G-CL-073 (copy-overlap scan), G-CL-074 (layout-signature review), and G-CL-076 (brand and imagery clearance — the check that catches traced or style-derived imagery, which G-LG-094's hash comparison cannot see); G-LG-094 re-run clean, and the protected-items list checked item by item against the shipped build. A visual-parity suite (G-CL-061) is **not** run — similarity to the reference is not a quality this playbook measures, except as a failure signal under Failure handling — and its NOT APPLICABLE disposition is recorded in the divergence log (CL-150, CL-152), not only in the acceptance record via G-CL-075(c).

**Step 10 — D6 deploy.** ci-cd (G-DO-001) then hosting (G-DO-071 external production check; G-INT-06 production deploy approval, G-INT-02 clean-checkout reproducibility). Deployment happens only after steps 7–9 pass.

**Step 11 — D9 finish.** technical-seo on the new product's own behalf (G-CO-001 promotion indexability diff; G-SCH-01 unique titles/descriptions, G-SCH-02 canonical URLs) — canonical tags, structured data, and sitemap describe the new product under its own name and domain, and no metadata field carries the reference's name except a factual, sourced comparison the user has explicitly approved in `DECISIONS.md`.

## Failure handling

- **G-LG-091/092 fails (no or late authorization):** stop the playbook. Delete any crawl data gathered before the record existed; do not "backdate" anything. Resume only with a real authorization record, and re-run analysis from scratch.
- **Drift into copy (the mission's characteristic failure):** a template, component, or page is found to reproduce the reference's layout, trade dress, or visual treatment — whether by working from captures, by "matching it roughly," or by a design that converged on the reference because the reference was the only example anyone looked at. The affected surface returns to step 4 as a design task with the deviation log entry as the work order: redesign from the brief, re-check against the protected-items list and the token-separation record, and re-run step 9(b). Never fix drift by changing just enough to pass — a surface redesigned under time pressure twice is escalated to a DECISIONS.md entry naming what went wrong with the handoff.
- **Protected copy or assets reproduced:** any reference text (verbatim or close paraphrase), image, icon, font, or brand asset found in the build — including material a team member reproduced from memory or from a screenshot kept "just for reference." Remove it, replace with an original equivalent from steps 4–5, re-run G-LG-094; any hit triggers a full-manifest audit (G-CL-034) and a sweep of the whole build for the same asset class before proceeding, and the workspace-separation breach that let it in is recorded in `progress.md`.
- **Feature-parity creep:** a request — from any stakeholder, including the build team — to add a reference function that is not on the frozen parity list, or to match an unobserved backend behaviour "because the reference probably does it." Refused at the step level; the only route in is a DECISIONS.md scope change through scope-control, re-costed as new product work. "The reference has it" is never, by itself, a requirement.
- **Functional parity gate fails (step 9a):** the function returns to step 6 with the failing behaviour spec as the work order. If parity is unreachable because the behaviour was never observable, the function is reclassified *designed* in the function spec and rebuilt as a design task — never tune the spec or the test to force a pass, and never let the report call it cloned.
- **Copy too close to the reference:** strings flagged at step 9(b) as tracking the reference's wording are rewritten from the function spec by a writer who has not seen the reference text; if the same surface is flagged twice, the whole surface's copy is rewritten, not patched line by line.
- **Any other gate fails mid-playbook:** fix in the owning department, re-run that gate, record both results in `progress.md`. No gate is waived silently; a waiver needs a DECISIONS.md entry.

## Definition of done

Authorization record predates all crawl data; function spec frozen with every function classified (cloned / designed / excluded) and the shipped product matching it; the clone-redesign skill's gates green, including the token-separation record and item-by-item protected-items clearance; G-LG-094 clean on the shipped build; all gates above green; verification report published with evidence per function claim, designed functions labeled as designed, and **no visual-parity or similarity claim made anywhere in the report**; the shipped product carries its own name, brand, design system, assets, and copy, with no protected expression of the reference in it; deployed and reachable (G-DO-071); `progress.md` shows the full gate trail. **Pre-provisioning complete:** where no production environment exists yet, the project may be recorded as *pre-provisioning complete* when every gate except the provisioning-waived ones is green, each waived gate is recorded as a provisioning waiver per §6.3, and the unblocking conditions are listed in `progress.md` — the deployment requirements above remain open until the environment exists.

## Worked mini-example — a freelance invoicing tool, cloned-and-redesigned from a reference invoicing product

Scenario: the user runs a small studio and wants an invoicing tool for freelancers that does what a well-known reference invoicing product does — client records, invoice creation with line items and tax, PDF export, payment-status tracking, and overdue reminders — under the studio's own brand, for its own clients.

1. Core loaded; two workspaces created (analysis / build). fact-sheet records the reference product's owner, purpose, and public plan facts from its public pages, with sources.
2. Authorization record committed: client engagement, scope = public pages and the user's own paid account's observable behaviour. G-LG-091/092 pass.
3. D16 analysis: site-discovery and page-inventory map the public marketing pages and, from the user's own account, the app surfaces. behavior-cloning captures the invoice-creation flow, the tax calculation behaviour (including its rounding on multi-line invoices), the status transitions (draft → sent → paid / overdue), and the reminder scheduling behaviour. design-extraction records structural patterns only — a list-plus-detail layout, a line-item table, a status timeline — and the reference's palette and type are logged into the redesign brief as characteristics to *avoid*. The logo, the product's illustration set, and all page copy go on the protected-items list; every harvested asset is verdicted `replace`.
4. One function — the reference's automatic bank-feed reconciliation — sits behind a paid integration the user's account does not have. It cannot be observed: marked *excluded* at the step 2 decision point, with the reason recorded, rather than guessed at.
5. D1 function spec frozen: 5 function groups (clients, invoices, PDF export, payment status, reminders), each stated as behaviour. The reference's multi-currency function is not requested by the studio's clients and is excluded by scope-control — the first parity-creep request ("but the reference does it") is declined here, on the record.
6. D3 redesign: new name and mark approved at the step 4 decision point after a collision check against the reference's marks. New design system authored from the brief — its own type pairing, palette, and a card-based invoice builder instead of the reference's list-plus-detail — and checked against the protected-items list.
7. D9 copy: all strings written from the function spec in the studio's voice. The reference's pricing-page claims and customer testimonials are not carried over; the new product launches with no testimonials, because it has no customers yet (G-DES-05).
8. Build from the three permitted inputs only. Mid-build, a developer asks for a reference screenshot of the line-item table "to get the columns right" — refused and logged; the columns are in the function spec, and the table is built to the new design system instead.
9. Verification: the frozen behaviour suite passes, including the tax-rounding cases. Step 9(b)'s imagery clearance review (G-CL-076) finds one failure — an empty-state illustration traced from the reference's style. It is replaced with an original illustration, G-LG-094 re-runs clean, and the token-separation record shows the shipped palette and type share no values with the reference's extracted characteristics.
10. G-AC-001 passes on all templates; G-SE-001 reports 0 criticals; G-QA-141 clean. Deploy via ci-cd; G-DO-071 confirms the live product. Report ships: function claims cite the behaviour suite per function group; the excluded bank-feed function is listed as excluded; no claim anywhere compares the product's appearance to the reference's.
