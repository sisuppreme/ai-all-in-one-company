# Playbook: Localize New Market

An existing, working product is launched in a country it was not built for. Nothing about the core product is new — what is new is everything around it: the language, the script direction, the money, the law, and the local expectations a user brings before they ever read a feature list. This playbook sequences that work so the checks that can kill a launch (legal, data residency, payments) run **before** the expensive work (translation, RTL layout, local marketing) is built on top of them.

## Goal

Launch the existing product in one named target market so that a local user can discover it, read it in their own language, pay for it the way people in that market actually pay, and be served under that market's privacy, consumer, and tax rules — with every one of those claims proven by a gate, not assumed from the home-market build. The product's features do not change; its locale, payment rails, legal documents, data placement, and support surfaces do. A market is launched per-locale and per-capability, never as a flag flip: a locale that is translated but cannot take a local payment, or that takes payments but stores data somewhere the market forbids, is not launched — it is a liability with a landing page.

## Departments + order

Step 0 (always-on core) → D1 (market case) → **D14 pre-flight (legal + data-residency feasibility, before any build)** → D13 (internationalization engineering) → D13+D3 (localization + RTL, conditional) → D11 (payments, currency, tax) → D14 (full: documents, consent, rights) → D9 (local search + content) → D18 (support surfaces) → D12 (analytics + observability) → D7+D8 (verification) → D6 (staged launch)

**Order deviation (one line):** D14 runs twice and its pre-flight runs second, not in its usual late position, because a residency or market-entry prohibition discovered after translation and payment work is finished wastes both — the feasibility verdict must predate the first translated string and the first payment-provider application.

The anchor for the whole run is the skill **market-expansion** (Phase 8) at `skills/product-requirements/market-expansion/SKILL.md`. It owns the readiness record — one per market, six dimension verdicts scored on evidence, and the written GO / CONDITIONAL GO / NO-GO decision — that every department below feeds. Its gates (G-PR-131–G-PR-135) are cited where they bite: the record checks at step 1, the payments live-fire evidence at step 5, the claims-versus-record check at steps 7 and 10, and the blocker scan again at step 11 before the locale goes public.

## Docs to write first

Before any string is translated or any provider is applied to, scaffold from `project-templates` and write:

The full mandated set for this type is `templates/mandated-manifest-localize-new-market.txt`, which governs (G-PM-001); the list below is the hand-written starting subset, not the whole set.

- `market-entry.md` — the market-expansion readiness record (PR-261): the one target country, the locale(s) in scope (language + region, e.g. `ar-SA`, not "Arabic"), the script direction, the currency, the named local payment methods in scope, the data categories the product processes, and the launch tier claimed for this market. It carries the skill's six dimension sections, the criteria registered before scoring (PR-263), the pilot plan (PR-274), and the decision (PR-262). One market per run of this playbook; "launch globally" is not a market entry.
- `requirements.md` — what "launched in this market" means for this product: which flows must work end-to-end in the locale (discovery, signup, core task, payment, refund, support, account deletion), and which are explicitly out of scope for this launch.
- `fact-sheet.md` — the market-local facts that will appear in public copy: local price and currency, tax treatment as stated to customers, support hours and language, data-location claim if one is made. Each fact carries its source (provider document, counsel note, registry entry) and date; nothing local is published from memory or from the home market's sheet.
- `legal-register.md` — the D14 pre-flight output: the market's applicable privacy/data regime, residency or transfer restrictions per data category, consumer-protection duties (pricing display, cancellation, refund rights), sector rules if any, and the verdict per item — clear, clear-with-changes, or blocked. Written in step 2, consumed by steps 5, 6, and 11.
- `locale-plan.md` — string scope and string classes (interface, transactional email, legal, payment, marketing), the translation route per class, the named native-speaker reviewer per locale, and the fallback policy per class (from localization-workflow).
- `progress.md`, `DECISIONS.md` — session log and decision record, including every per-locale tier decision and every gate result.

## Step-by-step sequence

**Step 0 — Core and scaffold.** Load `bundles/core.md`; set up the project files (project-templates), start `progress.md`, apply the secrets baseline. The existing product's current locale configuration, payment configuration, and hosting regions are inventoried into `market-entry.md` as the starting state — the delta this playbook ships is measured against that inventory, not against assumptions.

**Step 1 — The market case (D1, anchored by market-expansion).** Run market-expansion to produce the readiness record (`market-entry.md`) — six dimensions scored separately on dated evidence against criteria registered before any scoring — and pass its record gates for the entry assessment (G-PR-131 completeness scan, G-PR-132 blocker scan, G-PR-133 criteria-before-scores audit). Support it with user-research (evidence about this market's users gathered or cited, G-PR-011 register discipline — the home market's personas are not evidence about this market), competitive-analysis (who already serves this market locally, in the local language, with local payments — G-PR-081), and pricing-monetization (the local price is a decision, not a currency conversion: purchasing power, local competitor prices, and the provider's fees all feed it, G-PR-101). The output is a scoped launch: named flows, named locale, named payment methods, and a claimed support tier the product will actually honour.
◆ **DECISION — which tier does this market launch at?** Full local launch (local language, local payments, local support), language-only launch (translated UI, home-market payments and support, publicly claimed as exactly that), or no launch. The tier decides the scope of steps 4–8 and what public copy may claim — localization-workflow's rule that a locale's public claim must match its recorded tier is enforced at step 10 (G-AC-073). If unspecified, ask (§6.3 step 4). (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer; if none is recorded and no user is reachable, follow the §6.3 stuck protocol (log-and-continue, then the safe defaults) and record the substitution in `progress.md`.)

**Step 2 — D14 pre-flight: legal and residency feasibility, before any build.** privacy-laws builds or extends the obligations register for the new market (G-LG-001, G-LG-002 data-map completeness — the data map now includes where this market's users' data would flow). data-residency then checks every store, backup, log sink, CDN, and sub-processor against the market's residency and transfer rules (G-LG-011 data-residency gates). Three outcomes are possible per data category: data may stay where it is; data must move (new region, new processor, or a transfer mechanism the register names); or the category may not be processed for this market at all. The verdicts land in `legal-register.md`.
◆ **DECISION — a residency or entry blocker is found.** Options are exactly: change the architecture or processor set so the category complies, drop the data category (and the feature that needs it) for this market, or stop the launch. Proceeding and "sorting legal out after launch" is not an option — this step exists to run while stopping is still cheap. (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer. If none is recorded and no user is reachable, a residency or entry blocker is never log-and-continued and never safe-defaulted: proceeding past a blocked legal position is a legal decision on the §6.3 Step 5 never list. Work on the blocked data category stops, the blocker is logged in `progress.md` (§6.3 step 3), and the user is asked with the three options (§6.3 step 4); unblocked preparation may continue, but no launch step proceeds on a substitution.)
**Handoff:** steps 3–5 may not start for any flow whose data category is still verdict-less. Translation of a flow that will be dropped, and a payment application for an entity structure the register rejects, are the two wastes this ordering prevents.

**Step 3 — Internationalization engineering (D13).** internationalization makes the new locale data, not a code change: every user-facing string externalized into catalogs (G-AC-061 hard-coded string scan — zero findings, including emails, error messages, alt text, and PDFs, which are the places home-market builds hide literals), ICU MessageFormat for plurals and gendered forms (the target language's plural rules are the target language's, not the source's), `Intl` formatting for dates, numbers, and currency (G-AC-062 and family), and correct `lang`/`dir` metadata per page and per embedded fragment. Layout flexibility is engineered here, not patched later: containers must survive the target language's text expansion, and no view may assume left-to-right geometry — that assumption is removed in this step even before step 4b designs the RTL presentation.
**Handoff:** localization-workflow consumes this step's catalogs and context notes; if the catalogs are incomplete, translation starts on a moving source and every downstream review is invalidated. The string freeze in step 4 is only meaningful against this step's finished catalogs.

**Step 4 — Localization (D13+D3).** localization-workflow runs the translation pipeline: string freeze, translator handoff with context notes and screenshots, automated import checks, in-context review, and the per-locale release decision. The gates are the substance of this step: G-AC-071 (key parity and placeholder integrity — zero missing keys in the primary locale, zero unparsable messages, zero placeholder mismatches), G-AC-072 (length-limit check against the limits recorded with each string), G-AC-073 (visible-fallback check — an untranslated string renders visibly marked in staging, and production fallback follows the recorded per-class policy), G-AC-074 (in-context review sign-off — the named reviewer walks the primary flows on the staging build in the locale, including one error path and one empty state). String classes are routed differently, and the routing is not negotiable: **legal, payment, health, and safety strings require native-speaker human review with the review evidence recorded (G-AC-074)** — machine translation may draft interface strings for human post-editing, but a machine-translated terms page, consent text, or checkout disclosure that ships unreviewed is a failure mode, not a shortcut (see Failure handling). inclusive-copy reviews the translated copy for idiom, register, and imagery that does not travel: the source's metaphors, humour, date references, and stock imagery are checked against the market, and what does not travel is rewritten for the market, not translated literally. D3 (frontend-core, typography) confirms the locale's fonts actually cover the script, load without blocking, and render at sizes the script remains legible at — a script rendered in a fallback font with broken shaping is a failed localization even when every string is correct.

**Step 4b — RTL layout rebuild (D13, conditional — RTL markets only).** rtl-layouts treats the RTL presentation as a layout rebuild, not a flip: document direction set per locale, directional CSS written in logical properties, and a deliberate per-component verdict on what mirrors and what does not — navigation, progress, and directional icons mirror; media playback controls, clocks, logos, and embedded LTR content (code, numbers, URLs, the product's own Latin-script brand strings) do not, and embedded LTR fragments are isolated so they cannot corrupt the surrounding sentence (G-AC-081 and family, through G-AC-085). The per-script visual QA pass runs on the staging build at real viewport sizes, including the checkout and the longest-form flow. A CSS `transform: scaleX(-1)` on the root, or a theme that merely reverses a flex direction, fails this step by definition: reading order, focus order, form alignment, chart direction, and icon semantics are each checked, not inferred from one screenshot.
**Handoff:** step 4's in-context review (G-AC-074) for an RTL locale is signed off **on the step 4b build** — reviewing translated strings in an LTR staging layout and shipping them in an RTL one voids the sign-off.

**Step 5 — Payments, currency, and tax (D11).** This step answers one question: can a person in this market pay the way people in this market expect to pay? payments wires the market's payment methods through the provider that actually supports them for a merchant of this product's entity type — the local methods named in `market-entry.md` (for example a national card scheme or a dominant local wallet where one exists), not only the international cards the home market uses. A checkout that offers only foreign cards in a market with a dominant local scheme is a launched checkout in name only. Currency is handled as data end-to-end: prices stored and charged in the market's currency in exact types, formatted via `Intl` (step 3), never converted silently at display time from a home-currency amount, and never rounded by a display rule that differs from the charged amount. subscriptions mirrors the local prices and trial/renewal terms from the provider exactly; dunning verifies the failed-payment recovery flow — retry cadence, notices, grace period — against the local methods' real failure behaviour, not the home market's; invoicing-tax captures the market's invoice requirements — numbering, required fields, tax registration details, credit notes, retention — with the rates and thresholds themselves taken from the operator's qualified local accountant or the configured tax engine, never from this playbook or the skill (that determination is explicitly outside invoicing-tax's scope). refunds-disputes confirms the refund path works through the local methods (a method that can take money but not return it through the same rail is flagged here, with the customer-facing refund route written before launch), and webhooks + transactional-email prove the full money lifecycle in the locale: payment confirmation, receipt/invoice, failed-payment notice, and refund confirmation all arrive, in the local language, with local-currency amounts.
◆ **DECISION — the provider cannot support a named local method or the product's entity cannot contract locally.** Options: launch at the lower tier recorded in step 1 with public copy that claims only what works, add the provider or local entity as a pre-launch work item, or stop. Launching at full tier on home-market rails while the copy implies local support is the dishonest outcome this decision point exists to prevent. (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer. If none is recorded and no user is reachable, this decision is never log-and-continued and never safe-defaulted — it sets the launch tier and the public claims the product may make, a legal and money position on the §6.3 Step 5 never list. Log the blocker in `progress.md` (§6.3 step 3) and ask the user with concrete options (§6.3 step 4); in particular, a full-tier launch on home-market rails is never reached by default.)
◆ **STOP AND ASK — provider accounts, tax registration, and money movement (§5.9/§6.3).** Opening a payment-provider account for a new market, registering for local tax, and the first live charge in the new currency require the user's explicit go-ahead; credentials are handled under secrets-management and never appear in project files. (Unattended run: a go-ahead recorded in the commissioning brief or `requirements.md` for the specific account, registration, or first charge counts as the answer. If none is recorded and no user is reachable, this point is never log-and-continued and never safe-defaulted — provider accounts, tax registration, and money movement sit on the §6.3 Step 5 never list. Log the blocker in `progress.md` (§6.3 step 3), ask the user with concrete options (§6.3 step 4), and open no account, register for no tax, and move no money until the explicit go-ahead exists.)

**Step 6 — D14 full pass: documents, consent, rights (D14).** legal-documents produces the market's terms, privacy notice, and any market-specific disclosures, drafted from the step 2 register and the actual data inventory — and reviewed by qualified local counsel before publication, because legal-documents drafts and never presents its output as reviewed law. The localized versions of these documents come through step 4's human-review route for legal strings, in that order: counsel-reviewed source first, reviewed translation second, never translation of an unreviewed draft. The document-vs-register diff must be clean (G-LG-031): a privacy notice that names the home region while step 2 moved the data fails here. cookie-consent is configured to the market's consent standard (G-LG-041 and family; consent-banner behaviour is also checked against G-EXP-11 in `gates/ACCEPTANCE_GATES.md`), dsar-handling confirms a user in this market can exercise access, export, and erasure rights within the market's response clocks (G-LG-021 and family), and compliance-audit runs the market's register end-to-end (G-LG-061 and family).

**Step 7 — Local search and content (D9).** technical-seo makes the locale discoverable as its own surface: locale URL structure, canonical tags pointing at the locale's own pages, and hreflang across every locale pair — reciprocity and alternate-URL liveness are gated by G-SCH-11 in `gates/ACCEPTANCE_GATES.md` (mandatory for multilingual sites) and by the technical-seo gates (G-CO-001 and family). copywriting and real-content produce the market's landing and pricing copy from the market-local `fact-sheet.md`: local price, local payment methods, local support claim — every factual claim sourced, none carried over from the home market's pages with the currency symbol swapped. Machine-translated marketing pages published without the step 4 review route are treated as untranslated for tier purposes: they may not be indexed until they pass it.

**Step 8 — Support surfaces (D18).** help-center publishes the core help articles for the launched flows in the locale (through the step 4 pipeline, not ad-hoc translation), user-onboarding localizes the first-run path, and support-ticketing confirms a user in this market can reach support in the channel and language the tier claims — with response expectations set from what the team can actually staff. If support in the local language cannot be staffed, the tier recorded in step 1 must already say so, and the product's local pages must say so too; discovering the gap here sends the run back to the step 1 decision, not to a quiet hope that nobody writes in.

**Step 9 — Analytics and observability (D12).** monitoring and performance-budgets are extended to the new market as a first-class slice: traffic, conversion, payment success rate per local method, and error rates are visible per locale from launch day, and performance budgets are asserted from the market's realistic network and device conditions, not the home market's lab profile. Consent-gated analytics follow the step 6 consent configuration (G-INT-05 in `gates/ACCEPTANCE_GATES.md`: analytics events fire only after consent where required). A launch that cannot see its own payment failures per method is not observable, and step 11 does not start.

**Step 10 — Verification (D13+D7+D8).** The full pass, in the locale, on the staging build that will ship: accessibility-audit on the localized templates (G-AC-001, G-AC-005) — including screen-reader order in the RTL build where step 4b ran; owasp security pass (G-SE-001, 0 critical findings); qa-gates (G-QA-111); placeholder-scan over rendered localized output (G-QA-141 — scan rendered output, not source: untranslated keys, source-language leftovers, and lorem in the new locale are found here if earlier gates missed them); and the tier-claim check from G-AC-073 re-run against production configuration — what the market's pages claim (language coverage, payments, support, data location) is diffed against what steps 2–9 actually delivered. **No launch until green.**

**Step 11 — Staged launch (D6).** ci-cd (G-DO-001) deploys the locale behind a staged rollout: internal accounts in the locale first, then a limited local release, then full availability — each stage checked against step 9's per-locale monitoring before the next opens. The limited local release is the market-expansion pilot (PR-274), not a soft launch: before the first stage opens, `market-entry.md` carries the pilot's cohort or region limit, its stated period, and pre-registered success and kill thresholds (activation, first-transaction completion, support contacts per user, refund rate — the project's own metrics, registered before the pilot starts). Moving from the limited release to full availability requires the post-pilot review decision (PR-278 — EXPAND, HOLD, or EXIT, citing the pilot's actual values against those thresholds) and a fresh G-PR-132 blocker scan against the record: no dimension BLOCKED, and every CONDITIONAL GO condition closed or re-dated by the decider. A pilot whose review date passes in silence is a HOLD by default, never an automatic expand. hosting confirms the production configuration serves the locale from the regions step 2 approved (G-DO-071 external production check, run against the locale's URLs, in the locale). Rollback for a locale is locale-scoped: withdrawing the new locale must not disturb the existing markets, and the rollback path is named in `progress.md` before the first stage opens.
◆ **STOP AND ASK — public launch in the new market (§6.3).** Flipping the locale from staged to public, with the public claims step 7 wrote, requires the user's explicit go-ahead after step 10 is green. (Unattended run: a go-ahead recorded in the commissioning brief or `requirements.md` for the public launch counts as the answer. If none is recorded and no user is reachable, the public launch is never log-and-continued and never safe-defaulted — publishing the locale with its public claims is an irreversible-in-effect legal and commercial act on the §6.3 Step 5 never list. Keep the locale staged, log the blocker in `progress.md` (§6.3 step 3), and ask the user (§6.3 step 4) once step 10 is green.)

## Failure handling

- **A gate fails:** fix in the owning step, re-run; same failure twice → §6.3 (log in `progress.md`, continue unblocked work, batch blockers with concrete options). Locale-scoped failures block that locale, not the existing markets — and never the reverse reasoning: an existing market's green gates are not evidence about the new one.
- **Residency or entry blocker confirmed (step 2):** the launch stops or re-scopes at the step 2 decision point. Shipping first and relocating data later means the product processed a market's data unlawfully in the interval; there is no waiver for this in `DECISIONS.md` that a later fix makes retroactively clean.
- **Machine-translated legal or payment text found shipped or staged for ship (G-AC-074 evidence missing):** the affected documents and checkout strings are pulled from the release, the locale drops to a tier that does not include those flows, and the strings re-enter step 4's human-review route. "The translation reads fine" is not review evidence; the named reviewer's recorded sign-off is.
- **A named local payment method cannot be delivered (step 5):** the step 5 decision point governs — lower tier with honest copy, pre-launch work item, or stop. Quietly launching on international cards only, while local copy lists the local method, fails the step 10 tier-claim check and is treated as a false public claim, not a payments gap.
- **Currency or tax mishandling found (displayed price ≠ charged amount, wrong tax treatment on invoices):** P0 defect. Sales in the market pause until payments and invoicing-tax gates re-pass; already-issued incorrect invoices are corrected through invoicing-tax's credit-note path, and affected customers are notified through the localized transactional-email route. Never fix a money discrepancy by editing the display layer to match a wrong charge.
- **RTL visual QA fails (step 4b):** the locale does not ship its RTL presentation. Options are a real layout fix under rtl-layouts, or launching the locale in an LTR presentation only if the tier and public copy say exactly that — shipping a broken mirror because the strings are ready inverts this playbook's ordering.
- **Translation quality fails in-context review (G-AC-074):** the locale waits or drops a tier; the release date does not lower the bar. Partial coverage ships only under the recorded fallback policy with visible marking (G-AC-073), and the public claim matches the tier actually delivered.
- **Two skills contradict:** §5.7 precedence (security 1, legal 2, data integrity 8 above backend correctness 9 and performance 12); log in `DECISIONS.md`. Legal and residency positions outrank launch dates in every conflict this playbook produces.
- **A gate is itself wrong:** recorded waiver in `progress.md` + `DECISIONS.md` (§6.3 step 5); security/legal waivers need explicit user agreement.
- **A secret leaks:** revoke/rotate immediately; incident recorded without the value (§5.9 step 4).

## Definition of done

- The market is publicly launched at the tier recorded in step 1, and every public claim in that market (language coverage, payment methods, price and tax display, support language and hours, data location) is backed by a green gate in this run — the step 10 tier-claim diff is clean.
- Legal and residency: obligations register and data map cover the new market (G-LG-001, G-LG-002); every data category's residency verdict is implemented where the data actually runs (G-LG-011); counsel-reviewed local documents are published and match the register (G-LG-031); a local user can exercise their data rights end-to-end (G-LG-021).
- Locale quality: zero hard-coded strings (G-AC-061); key parity, length, and fallback gates green (G-AC-071–073); in-context native review signed off for every shipping flow, with human-review evidence for legal and payment strings (G-AC-074); for RTL markets, the RTL gate family green on the shipped build (G-AC-081–085).
- Money: a local user can pay with the named local methods, in the local currency, at the displayed price; the full lifecycle — confirmation, invoice, failed-payment notice, refund — is proven in the locale (G-IN-001 family, G-IN-031 family, G-IN-021 family).
- Discoverability and support: hreflang reciprocity verified (G-SCH-11); help and onboarding live in the locale at the claimed tier.
- Operations: per-locale monitoring and payment-success visibility live; locale-scoped rollback named and tested; `progress.md` shows the full per-locale gate trail and `market-entry.md` matches what actually shipped.
- Pilot discipline: the limited release ran as the PR-274 pilot with pre-registered success and kill thresholds, and full availability was opened only by the recorded PR-278 post-pilot decision (EXPAND) — or the market is honestly recorded as still in pilot or HOLD, not launched.
- **Pre-provisioning complete:** where the market's production prerequisites do not exist yet (provider account not yet approved, local tax registration pending, target region not yet provisioned), the project may be recorded as *pre-provisioning complete* — every gate except the provisioning-waived ones green, each waived gate recorded as a provisioning waiver per §6.3, and the unblocking conditions listed in `progress.md`. The launch requirements above remain open until those prerequisites exist; pre-provisioning complete is not launched.

## Worked mini-example

Sample project: **TaskBoard**, an existing English-language subscription task manager (LTR, card payments in its home market), launching in **Saudi Arabia** as a full local launch: Arabic (`ar-SA`, RTL), Saudi riyal pricing, and mada — the national card scheme — alongside international cards.

1. Step 0: core loaded; inventory records the starting state — one locale (`en`), one hosting region, card-only checkout, no Arabic strings anywhere.
2. Step 1: the market-expansion readiness record names the country, locale, direction (RTL), currency (SAR), and payment methods in scope (mada + international cards). user-research and competitive-analysis record that local competitors sell in Arabic with mada at checkout; pricing-monetization sets a SAR price from local competitor prices rather than converting the home price. Tier decision recorded: full local launch.
3. Step 2: privacy-laws extends the register for Saudi Arabia's personal-data regime; data-residency checks each store and sub-processor, and one analytics processor is replaced for this market's data before any build starts. Verdicts land in `legal-register.md` — no category blocked.
4. Step 3: internationalization externalizes the strings the scan finds hiding in transactional emails and PDF invoices (G-AC-061 clean on re-run); Arabic plural forms are authored as ICU messages; dates and SAR amounts move to `Intl` formatting.
5. Step 4: string freeze; a translator works from context notes and screenshots; G-AC-071 and G-AC-072 pass on import. The terms, privacy notice, and checkout disclosures are routed to native-speaker human review and held out of the release until their G-AC-074 evidence exists — the machine draft of the privacy notice is never staged for ship.
6. Step 4b: rtl-layouts rebuilds the app shell in logical properties; the board's drag handles and progress indicators mirror, the media controls and embedded Latin-script workspace names are isolated as LTR fragments. In-context review (G-AC-074) is signed off on this RTL staging build, error path included.
7. Step 5: the user approves opening the provider configuration for the market; mada is enabled alongside cards, prices are created in SAR in the provider and mirrored by subscriptions, and invoicing-tax is configured from the local accountant's determination — invoice fields and credit-note flow included. A test purchase, a failed payment, and a refund are each run end-to-end in Arabic, and the confirmation, dunning, and refund emails arrive in Arabic with SAR amounts.
8. Step 6: local counsel reviews the Arabic terms and privacy notice against the register (G-LG-031 clean); consent configuration is set to the market's standard; a test DSAR export and erasure are run against a Saudi test account inside the required clock.

12. Step 11: staged rollout — internal Arabic accounts, then a limited release that runs as the recorded pilot (cohort limit and success/kill thresholds registered in the record before it opens), then public launch on the post-pilot EXPAND decision and the user's go-ahead.
