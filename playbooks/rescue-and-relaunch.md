# Playbook: Rescue and Relaunch

A live product that is broken, abandoned, or both — built by someone else, documented by no one, and still used by real people whose data is in it. There is no green field here and no clean requirements document to start from: the state of the system is unknown until it is audited, the credentials may be lost, the last deploy may be unrecorded, and every fix is made next to production traffic. This playbook therefore inverts the normal build order. Nothing is fixed before it is triaged, nothing is triaged before the product can be restored from backup, and nothing is relaunched before the rollback has been proven — because the cost of a mistake is not a delayed launch, it is existing users losing a working (if flawed) product or their data.

## Goal

Take over a broken or abandoned live product, establish its true state with evidence — what is running, where, on whose accounts, with what data, and what is actually broken — fix its defects in risk order (containment and security first, data integrity second, user-visible breakage third, cosmetics last), and relaunch it safely: backed up, restorable, monitored, and reversible, with no existing user locked out and no existing data lost or silently changed in meaning.

## Departments + order

Step 0 (always-on core) → **D15+D6+D7 takeover and containment (project-takeover)** → D8+D7+D15 audit and triage → D14 → D5+D4+D3+D13 fixes in priority order → D12 → D7+D8 verification → D6 relaunch → D18+D9+D10 handover

**Order deviation (one line):** D6 and D7 run first, before any requirements or design work, unlike every build playbook in this repo — a takeover starts with backups, access, and containment, because the product is already live and already at risk while it is being understood; D1 appears only in reduced form at the triage step, to record what the rescued product must keep doing, never to redesign it.

What differs from building new, and why the order follows from it:

- **Unknown state, not a blank slate.** A new build knows its stack, schema, and deploy target because it chose them. A takeover knows none of these until they are discovered and evidenced. Every claim about the inherited system — framework version, database contents, who else has access — is a finding to verify, not a fact to assume.
- **No docs, or lying docs.** Any inherited README, runbook, or architecture note is treated as an unverified claim and checked against the running system. Where the two disagree, the running system wins and the disagreement is recorded.
- **Live users and live data.** There is no "test data to purge" step and no breaking-change freedom. Fixes are shipped the way migrations are shipped: backward-compatible first, reversible by default, and announced when a user's behavior-visible surface changes.
- **Credentials and secrets recovery is part of the work.** The previous owner may be unreachable, accounts may sit under a personal email, keys may exist only in a production environment file, and some secrets must be assumed compromised and rotated — a workstream that simply does not exist in a new build.
- **Triage before fixes.** In a new build the sequence is set by the plan. In a rescue the sequence is set by risk found in the audit: an exposed secret or an unauthenticated admin route outranks every broken page, however visible the broken page is.

## Docs to write first

Before any fix — and, except for the backup and access records in step 1, before any change of any kind to the live system — scaffold from `project-templates` and write:

The full mandated set for this type is `templates/mandated-manifest-rescue-and-relaunch.txt`, which governs (G-PM-001); the list below is the hand-written starting subset, not the whole set.

- `TAKEOVER.md` — the takeover record produced under `project-takeover`: who is handing the product over (or the recorded fact that no handover was possible), the legal/engagement basis for taking control, every account, domain, host, repository, and data store found, who holds access to each, and the date access was verified by actually signing in or deploying — not by being told a password. This file names secrets by name and purpose only; it never contains a value (§5.9).
- `STATE.md` — the evidenced state of the inherited system: what is deployed (commit SHA or the recorded absence of one), stack and versions as found running, schema as found, scheduled jobs, external services wired in, and every place where the running system disagrees with inherited documentation. Each line is marked *verified* (with its evidence) or *unverified*.
- `TRIAGE.md` — the single prioritized defect register for the rescue: every audit finding with its DET ID or gate ID where one applies, its severity, its user/data impact, its fix order, and its status. This register, not enthusiasm and not visibility, sets the fix sequence.
- `fact-sheet.md` — what the product publicly claims today (prices, limits, promises on its live pages), each claim sourced from the live surface. A rescue does not silently change a public claim; a claim that must change is a relaunch communication, decided in step 9.
- `requirements.md` — written in step 3 as the rescue's acceptance scope: the keep-working list of flows existing users actually depend on, which must work after every fix batch and after the relaunch. Everything not on this list is out of scope for the rescue. (BOOTSTRAP's remaining scaffold doc, `stack.md`, is created at step 0 under the manifest; the inherited stack as found is recorded in `STATE.md`.)
- `progress.md`, `DECISIONS.md` — session log with gate results, and the decision record: every keep / fix / retire decision about an inherited component, with its reason.
- `docs/tech-debt.md` — the debt register (`tech-debt`), opened at triage for everything found but deliberately not fixed in this rescue.
- `.env.example` — reconstructed from the running environment: every secret the system needs, by name + purpose (§5.9). In a takeover this file usually has to be reverse-engineered; the running environment is the source, and the reconstruction is itself an audit finding when a needed variable is undocumented.
- `runbook.md` — started in step 1, not step 9: how to restart, roll back, and restore *this* product as found, written while the knowledge is being discovered, so the product is operable from the first day of the takeover, not only after the relaunch.

## Step-by-step sequence

**Step 0 — Core and scaffold.** Load `bundles/core.md`; generate the project record (G-PM-001, G-PM-002); write the docs above as stubs to be filled by steps 1–2; load `secrets-management` before any inherited credential is touched.

**Step 1 — Takeover and containment (D15+D6+D7, `project-takeover`).** Secure control before understanding: inventory every account (hosting, registrar/DNS, repository, database, email/SMTP, payment and analytics providers) and verify access to each by using it; recover or reset access through the provider's own account-recovery route where credentials are lost, and record in `TAKEOVER.md` any account that cannot be recovered and what it blocks. Take a full backup of every production data store and **prove it restores** into a scratch environment before anything else happens (restore drill current, G-DO-134) — an untested backup is a hope, not a backup. Snapshot the deployed code and configuration exactly as found, including code that exists only on the server and not in any repository. Then contain: if the product is actively failing users, run `incident-response` discipline — stabilize the symptom, communicate status, and stop; do not fold opportunistic fixes into an incident. Rotate, do not merely collect, any secret that a departed owner, contractor, or unknown party may still hold; a secret whose holders cannot be enumerated is treated as compromised. The project-takeover skill's gates must pass before step 2 begins.
◆ **DECISION — is the product safe to leave running during the audit?** If containment finds an actively exploited hole, data being corrupted, or a secret exposed publicly, the choice is: patch that one thing immediately under incident discipline, or take the affected surface offline until step 5 reaches it. "Leave it live and fix it in order" is not an option for an active compromise. Record the choice and its basis in `DECISIONS.md`. (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer. If none is recorded and no user is reachable, this safety decision is never log-and-continued and never safe-defaulted. Where the audit evidence shows an active compromise, contain first — take the affected surface offline, or patch that one hole under incident discipline — log the blocker in `progress.md` (§6.3 step 3), and ask the user with concrete options (§6.3 step 4). "Leave it live and fix it in order" is never a default.)
◆ **STOP AND ASK — production credentials and data (§5.9/§6.3).** First connection to a production database, any rotation that will invalidate a credential the live system is using, and any restore of production data requires the user's explicit go-ahead, with the verified backup from this step named in the request. (Unattended run: a go-ahead recorded in the commissioning brief or `requirements.md` for the specific connection, rotation, or restore counts as the answer. If none is recorded and no user is reachable, this point is never log-and-continued and never safe-defaulted — production credentials and production data sit on the §6.3 Step 5 never list. Log the blocker in `progress.md` (§6.3 step 3), ask the user with concrete options (§6.3 step 4), and touch no production credential or data until the explicit go-ahead exists; audit work that needs neither may continue.)

**Step 2 — Audit and triage (D8+D7+D15, no fixes).** Audit read-only wherever the system allows it: auditing must not break production, so scans run against a staging copy or the restored backup wherever a scan is load-heavy, state-changing, or unproven against this stack, and any audit action that must touch production is listed in `progress.md` before it runs. Run `security-audit` and the `owasp` checklist over the inherited surface (G-SE-003), the full-history secret scan (G-SE-041), and the dependency vulnerability gate (G-SE-051) — inherited dependencies are assumed stale until the scan says otherwise. Run `placeholder-scan` over the rendered live output (G-QA-141; scan rendered output, not source) and the detection families named above: DET-FAKE for features users believe exist but that are stubbed or simulated, DET-CODE for stub handlers, swallowed errors, and unreachable code, DET-INF for missing backups, absent monitoring, and single-point infrastructure. Establish whether a test suite exists and whether it passes as found; a suite that has never been run green is evidence about the codebase, not a safety net. File **everything** into `TRIAGE.md` via `bug-triage` and open the `tech-debt` register (G-DX-042 register completeness) for what will not be fixed now. Nothing is fixed in this step — a fix made before triage is complete is a fix made without knowing what outranks it.
◆ **DECISION — rescue, partial rebuild, or retire?** If the audit shows the product cannot be made safe on its current base (framework past end-of-life with known exploited vulnerabilities, data model corrupting records by design, license or ownership of the code itself in dispute), stop and present the three options with the audit evidence: continue the rescue, rebuild the failing layer under `legacy-migration` while the old product keeps running, or retire the product with data export for its users. Do not drift into a rebuild one "fix" at a time. (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer. If none is recorded and no user is reachable, this decision is never log-and-continued and never safe-defaulted — where the trigger is a license or ownership dispute it is a legal position, and in every case it ends the rescue as commissioned (§6.3 Step 5 never list). Log the blocker and the audit evidence in `progress.md` (§6.3 step 3) and ask the user with the three options (§6.3 step 4); do not begin rebuild or retirement work on a substitution.)

**Step 3 — The keep-working list (D1, reduced form).** From evidence — analytics, support mail, the live surface itself — write the short list of flows existing users actually depend on, in `requirements.md` as the rescue's acceptance scope: these flows must work after every fix batch and after the relaunch. Everything not on the list is explicitly out of scope for the rescue and goes to the debt register or a later roadmap; a rescue that grows a feature list does not finish. `scope-control` governs every later "while we're in here" request.

**Step 4 — Legal and privacy as found (D14, explicit step).** A takeover inherits obligations, not just code: build the processing register for what the product actually stores and processes today (G-LG-001, G-LG-002), check the published privacy/terms text against that reality (G-LG-031) — inherited legal text routinely promises deletion, regions, or subprocessors the system does not honor — and record each mismatch in `TRIAGE.md` at the priority its risk earns. If the audit finds personal data held with no lawful basis or exposed beyond its stated purpose, that finding is a step 5 security/data fix, not a copy edit.

**Step 5 — Fixes in priority order (D5+D4+D3+D13+D15).** Work `TRIAGE.md` strictly in its order, in small batches, each batch independently deployable and reversible:
1. **Security and containment** — exposed secrets rotated (step 1) and their code paths fixed, unauthenticated or wrongly authorized routes closed, injection and broken access control fixed (`security-audit`, `owasp`, `backend-auth`). Cosmetic and content fixes are banned from this batch, however quick they look.
2. **Data integrity** — schema and migration defects, silent write failures, corrupt-record repair (`schema-design`, `migrations`: every migration reversible, G-DB-061, with its down-path checked before it runs against production).
3. **Keep-working flows** — the step 3 list restored end to end (`api-building`, `frontend-core`, `e2e-testing` coverage added around each flow as it is fixed, so the rescue leaves a safety net it did not inherit).
4. **Everything else in triage order** — accessibility failures on the kept flows (G-AC-001, and G-EXP-05 in `gates/ACCEPTANCE_GATES.md`), placeholder and fake-functionality findings, performance defects that users feel.
Refactoring is permitted only as preparatory work for a named fix in this list, under `refactoring` discipline — behavior pinned by tests first, refactoring commits separate from fix commits — never as a general cleanup of inherited code. Each batch closes its `TRIAGE.md` entries with evidence and moves unfixable-now items to the debt register with a trigger, not a shrug.
◆ **DECISION — a fix that changes behavior users depend on.** Some inherited "bugs" are load-bearing: users have built habits, exports, or integrations around them. If a fix changes observable behavior on a keep-working flow, the choice — fix silently, fix with notice in the relaunch communication, or preserve the behavior and record it as decided debt — is recorded in `DECISIONS.md` before the batch ships, with the step 9 communication updated to match. (Unattended run: BOOTSTRAP's approval-points rule applies at this point — a decision recorded in the commissioning brief or `requirements.md` counts as the answer; if none is recorded and no user is reachable, follow the §6.3 stuck protocol (log-and-continue, then the safe defaults) and record the substitution in `progress.md`.)

**Step 6 — Observability before relaunch (D12, explicit step).** A product that was abandoned usually cannot answer "is it up, and is it working?" — fix that before relaunch, not after the first post-relaunch incident: `monitoring` and `alerting` live on the kept flows, error tracking wired, and performance budgets set from measured inherited baselines (G-AN-101, G-AN-091) — budgets in a rescue start from what the product actually does today, tightened only where the step 5 fixes already improved it.

**Step 7 — Verification (D7+D8).** Re-run the step 2 audit suite against the fixed system and diff it against the original findings: security suite in full (G-SE-001 ZAP baseline, 0 critical; G-SE-003; G-SE-041; G-SE-051), placeholder sweep (G-QA-141), the qa-gates meta-check (G-QA-111), the engineering gates from `gates/ACCEPTANCE_GATES.md` (G-ENG-01 build/type/lint clean, G-ENG-11 no secrets in client code or logs, G-ENG-12 lockfile committed and dependency audit recorded), and a clean-checkout reproduction of the rescued codebase (G-INT-02) — if the product only runs on the one server it was found on, it has not been rescued. Every keep-working flow passes its end-to-end test against a copy of production-shaped data. **No relaunch until green**, and any original audit finding still open is either fixed, or carried into the debt register with an owner, a trigger, and the user's recorded acceptance.

**Step 8 — Relaunch (D6, last build step).** Relaunch is a deployment, not a rewrite going live: CI/CD in place (G-DO-001), the fix batches deployed by the least-risk route the host supports (staged or off-peak where traffic patterns are known, a single reversible release where they are not), a written rollback plan for the release (G-INT-04) and a rollback drill already proven (G-DO-151), and a fresh verified backup taken immediately before the switch (G-DO-134 current). Production checks after the switch (G-DO-071 external production check, G-INT-03 start/health check, G-INT-01 the flows nearest the change re-exercised, G-INT-06 owner approval naming the release). Existing sessions, bookmarks, and integrations are checked explicitly after deploy — a relaunch that logs every user out or breaks every saved link without warning has failed its brief even if every gate is green.
◆ **STOP AND ASK — the go-live switch (§5.9/§6.3).** The relaunch deploy, any DNS or domain change, and any migration against production data require the user's explicit approval naming the release and the backup it can roll back to. The agent prepares the checklist; the user approves the switch. (Unattended run: an approval recorded in the commissioning brief or `requirements.md` naming this release and its rollback backup counts as the answer. If none is recorded and no user is reachable, the go-live switch is never log-and-continued and never safe-defaulted — it is an irreversible production action on the §6.3 Step 5 never list. Prepare everything up to the switch, log the blocker in `progress.md` (§6.3 step 3), and ask the user with concrete options (§6.3 step 4); the switch itself waits for the explicit approval.)

**Step 9 — Handover and communication (D18+D9+D10).** Tell existing users what happened in proportion to what changed for them: `status-communications` for any downtime or behavior change from step 5's decisions, support routes checked live (`support-ticketing`) before users are invited to report problems. Close the rescue as a record, not a memory: `handover` and the completed `runbook.md` (restart, rollback, restore, rotate — all four proven during the playbook, not merely described), a `postmortem-writing` account of why the product broke or was abandoned where that is known, `STATE.md` rewritten to describe the system as relaunched, and technical-seo checks (G-CO-001) confirming the relaunch did not change public URLs, canonicals, or indexability by accident.

## Failure handling

- **A gate fails:** fix in the owning step, re-run; same failure twice → §6.3 (log in `progress.md`, continue unblocked work, batch blockers with concrete options).
- **No backup can be taken, or the restore drill fails (G-DO-134):** the rescue stops at containment. No fix batch, no migration, no relaunch is attempted against data that cannot be restored; the only work permitted is work that makes a restorable backup possible. A product that cannot be backed up cannot be rescued, only gambled with.
- **An account cannot be recovered:** record it in `TAKEOVER.md` with what it blocks. If it blocks deploy, DNS, or data access, the playbook cannot pass step 1 — escalate to the user with the provider's recovery requirements (proof of ownership, billing records) as concrete options; never work around a missing account by quietly re-creating the service under a new one and orphaning the old data or domain.
- **The audit breaks production:** stop the audit action, run `incident-response`, restore service first, and record the incident in `progress.md`. The audit method that caused it (scan load, a probe against a fragile endpoint) is changed before the audit resumes, and the step's read-only/staging-first rule is re-checked — this failure mode is exactly what that rule exists to prevent.
- **A fix batch regresses a keep-working flow:** roll the batch back (each batch is independently reversible by design), return the finding to `TRIAGE.md` at its original priority, and re-attempt with the flow's end-to-end test written first. A batch that cannot be rolled back on its own was too big — split it.
- **Priority inversion is spotted (cosmetics fixed while a security finding is open):** stop the batch, return it to its triage position, and record the inversion in `progress.md`. Visibility is not severity; the register's order is the order.
- **Relaunch fails or post-deploy checks go red:** execute the rollback plan (G-INT-04, G-DO-151 as drilled), confirm the previous version serves users and their data is untouched, and only then diagnose — on the rolled-forward copy, not on production.
- **A secret is found exposed (in the repo, in logs, in a public file):** revoke/rotate immediately under step 1's rule; incident recorded without the value (§5.9 step 4). Rotation outranks triage order — it is containment, not a fix batch.
- **Two skills contradict:** §5.7 precedence (security 1, legal 2, data integrity 8 above backend convenience 9 and performance 12); log in `DECISIONS.md`.
- **A gate is itself wrong for the inherited system:** recorded waiver in `progress.md` + `DECISIONS.md` (§6.3 step 5); security/legal waivers need explicit user agreement. A gate that cannot run because the inherited system predates its tooling is recorded as such with the compensating check that ran instead — never as a pass.

## Definition of done

- Control is proven, not asserted: every account in `TAKEOVER.md` verified by use, every production data store backed up with a current, successful restore drill (G-DO-134), and every secret a departed party may hold rotated.
- The audit is complete and accounted for: every finding in `TRIAGE.md` is fixed with evidence, or sits in the debt register (`docs/tech-debt.md`) with location, owner, trigger, and the user's recorded acceptance — zero findings unaccounted for.
- Every flow on the keep-working list works end to end, proven by tests the rescue leaves behind; existing users can sign in, reach their data, and follow their existing links and integrations.
- All gates above green; the rescued codebase reproduces from a clean checkout (G-INT-02); monitoring and alerting answer "is it up?" without anyone reading logs by hand.
- Relaunched by a reversible deploy with a drilled rollback, a fresh pre-switch backup, and owner approval on record (G-INT-06); the delivery report is complete and honest (G-INT-08) — including what was *not* fixed.
- `STATE.md` describes the system as relaunched; `runbook.md` covers restart, rollback, restore, and rotate as proven procedures; `progress.md` and `DECISIONS.md` current.
- **Pre-provisioning complete:** where the rescue itself is finished but no new production environment exists yet to relaunch into (the inherited host is being replaced and not yet provisioned), the project may be recorded as *pre-provisioning complete* — every gate except the provisioning-waived ones green, each waived gate recorded as a provisioning waiver per §6.3, the old product left running untouched in the meantime, and the unblocking conditions listed in `progress.md`. The relaunch requirements above remain open until the environment exists; pre-provisioning complete is not done, and it never justifies taking the old product down early.

## Worked mini-example

Sample project: **a small appointment-booking site for a local clinic**, built by a freelancer two years ago, unmaintained for the last year, still taking bookings. The contact form has stopped sending email, patients report the booking page "sometimes loses" appointments, and nobody knows where the site is hosted.

1. Step 0: core loaded; takeover record and triage register scaffolded; no fix attempted.
2. Step 1: hosting found under the freelancer's personal account and transferred to the clinic's own account with the provider's ownership process; the domain registrar account is recovered by the clinic using its business registration documents. A full database backup is taken and restored into a scratch environment — the restore works, so work may proceed. The database password and the SMTP password, both known to the departed freelancer, are rotated; the old SMTP password is found to be the only credential the mail provider will accept, so rotation is scheduled with the user's go-ahead and the site's mail configuration is updated in the same window.
3. Step 2: audit against the restored copy. `security-audit` finds the admin page reachable without a login, protected only by an unlinked URL (DET-INF-021 — debug/admin surface exposed in production, filed as the top triage item); G-SE-051 flags two dependencies with high-severity findings; `placeholder-scan` (G-QA-141) finds the "confirmed" booking page still carrying template placeholder text in its footer. The "lost appointments" report is traced to DET-CODE-005 (empty or swallowed exception handlers): the booking handler swallows a database error and returns success, so failed bookings look confirmed. There is no test suite at all — recorded as a finding, not a surprise.
4. Step 3: keep-working list agreed from the clinic's reception staff: online booking, the confirmation email, and the admin day-list. The blog and the photo gallery are explicitly out of scope.
5. Step 4: the privacy page promises patients their details are deleted after each appointment; the database shows every record since launch retained.
