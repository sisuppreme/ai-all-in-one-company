# placeholder-allowlist.md — Placeholder-scan allowlist (§6.2)

Patterns the placeholder scan must **not** flag, with the reason for each and the condition that turns the same pattern back into a real finding. Companion to `gates/placeholder-patterns.md`; the scan's allow-list audit gate is G-QA-144 (`skills/qa-testing/placeholder-scan/SKILL.md`).

**How entries work (QA-288).** Two kinds of entries live here. *Standing scope rules* (Sections A and D) describe contexts the sweep excludes by construction — code comments, test fixtures, documentation paths; they do not expire. *Honesty-label entries* (demo and sample content, Section A-05 and wherever a label is named) are exceptions granted to specific shipped content: each such use names the visible label that makes it honest (demo banner, "sample" tag) and an expiry tied to a named release. An expired or unlabeled use fails the scan like any other hit. When a project adopts this list, it records its labeled uses (pattern, location, label, expiry release) in its own allowlist record — this file is the rule set those records cite.

Evidence base: the DET parameters' own false-positive clauses (`skills/detection/fake/PARAMETERS.md`, `skills/detection/content/PARAMETERS.md`) and the Phase 1 false-positive tests against known-good sites and projects (`build/validation/fp-test-visual-content.md`, `build/validation/fp-test-code-infra.md`), which found that the confirmed false positives came from three gaps — scans without path exclusions, clauses naming products instead of classes, and single-deployment parameters applied to distributable software. This list closes those gaps by class.

## A. Standing scope rules (brief §6.2 step 5 + placeholder-scan)

| # | Pattern | Why it is legitimate | Becomes a real finding when |
|---|---|---|---|
| A-01 | `#` fragment links that navigate within the page (in-page anchors, skip links, tab controls wired to real panels) | A fragment that resolves to a real in-page target is navigation, not a dead control. | The fragment resolves to nothing, or the control presents as an action/navigation and does nothing on click (fake-functionality class; probe decides). |
| A-02 | `TODO` / `FIXME` in code comments | Developer bookkeeping in source is not user-visible copy; DET-CON-004 and pattern S-04 target shipped strings. | The marker text renders in any user-visible field, meta description, alt text, or structured data. |
| A-03 | Test fixtures, spec/test directories, and seeded-fault test branches | Fixtures exist to test with; the scan's own seeded-fault control (G-QA-142) depends on them. | Fixture or seed code is imported by, bundled into, or reachable from a production code path (QA-291, pattern S-10). |
| A-04 | Documented test credentials and test cards in test code and fixtures — e.g. the payment provider's published test card `4242…` and documented test keys | Provider-documented test values are how real integrations are verified; DET-FAKE-006/007's checks depend on them existing. | Test values appear in production code paths, or a test-mode integration ships to production unlabeled (see A-06). |
| A-05 | Clearly labeled demo or sample content: a demo banner, a "sample" tag, a published demo account with labeled credentials | A labeled demo is honest and is never a finding (placeholder-scan: "a labeled demo is honest; an unlabeled one is a finding"). DET-FAKE-001/014 false-positive clauses say the same. | The label is removed, hidden, or expires: every labeled use carries an expiry tied to a named release (QA-288); an expired entry fails the scan. Unlabeled staged content in production is DET-FAKE-014. |
| A-06 | Sandbox / test-mode payment integration, visibly labeled as test mode, with test keys | Charges nothing by design; DET-FAKE-006 distinguishes it by the visible test-mode labeling and test keys. | Test mode or test keys reach production without the label — then the "successful payment" is simulated and files under DET-FAKE-006. |
| A-07 | Labeled sample downloads: a clearly marked sample template or example file offered as a sample | DET-FAKE-019: a labeled sample is legitimate; the user asked for a sample and got one. | The same file is delivered as "your report" / "your export" — i.e. presented as generated from the user's data. |
| A-08 | Lorem ipsum quoted as the subject of a design-history or typography article | DET-CON-001's false-positive clause: the filler is the topic under discussion, framed by surrounding context. | Filler appears in any slot presented as the site's own copy (body, headings, titles, pricing/checkout — blocker there). |
| A-09 | Template syntax (`{{…}}`, `${…}`) inside `<code>` / `<pre>` in developer documentation | DET-CON-003's false-positive clause: documentation showing syntax is instructional, and the check excludes code elements. | The syntax renders in prose, headings, or titles outside code contexts — i.e. a template printed without its data. |
| A-10 | "Coming soon" in a changelog or roadmap entry with a date or roadmap context | DET-CON-004's false-positive clause: an honest announcement that does not imply the feature exists now. | "Coming soon" / "content to follow" sits in a live field, meta description, or alt text implying current availability (pattern S-05). |
| A-11 | `example.com` / `example@` in code samples, documentation, and instructional text | RFC 2606 reserved domains are the correct way to write examples; DET-CON-005 distinguishes instructional context. | A reserved-domain address appears in a live contact block, footer, or checkout help text as the way to reach the business (pattern S-06). |

## B. Content patterns (Phase 1 false-positive test — visual/content)

| # | Pattern | Why it is legitimate | Becomes a real finding when |
|---|---|---|---|
| B-01 | A first-party statistic whose source is published anywhere on the same domain (annual letter, status page, docs) but not cited on the page carrying the figure | DET-CON-011 as amended by the FP fix pass: provenance anywhere on the same domain clears the claim; per-claim on-page citation is stricter than known-good professional practice (stripe.com). Also clears the DET-VIS-035 stat band: a linked source for the band's figures anywhere on the page clears the visual flag. | The figure has no provenance anywhere on the domain, or it is a third-party / market claim (ratings, market share, comparisons) with no source — blocker under DET-CON-011. |
| B-02 | Self-attested first-party operational counters (the operator's own usage numbers: accounts, projects, items processed) with no external citation | Their dataset is the operator's own database, which no external check can inspect (basecamp.com). They route to the DET-CON-015 consistency check and a fact-sheet entry, at most major. | A counter contradicts itself across the site (DET-CON-015), or is facially implausible, or is presented as a third-party measurement. |
| B-03 | Unmeasurable comparative puffery ("most comprehensive", "easiest-to-use", "sets a new standard") with no measurable ranking claim | Ordinary marketing register, not a fabricated ranking (DET-CON-026 as amended: measurable claims only). At most a minor copy note. | The copy states a measurable ranking or superlative of fact ("#1", "largest by revenue", "best-rated", "industry-leading" attached to a figure) with no ranking, survey, or criteria behind it — DET-CON-026 / DET-CON-011. Where a superlative wraps a sourced figure, only the figure's provenance is checked. |
| B-04 | A generic hero or feature-card sentence on a page that elsewhere descends to specifics | DET-CON-006 as amended: the competitor-verbatim test applies at page level on homepages and heroes; disciplined professional copy is often uniform and broad at the top of a page (linear.app, stripe.com). | The whole page stays at that altitude — no product-specific fact anywhere on the page (DET-CON-006), or generic copy is an interior page's only substantive content. |
| B-05 | Cards with near-uniform copy lengths and identical structure, where the content is product-specific | Length uniformity alone is a craft signal, not a generation signal (DET-VIS-003 as amended); the flag needs uniformity **plus** generic, interchangeable content. | Uniform structure coincides with generic content that passes the competitor-verbatim test (DET-CON-006 territory). |
| B-06 | Sample data inside a product screenshot or UI mock, presented as the product's interface | A screenshot of a real product's UI containing sample records is a depiction of the product, not social proof (linear.app); DET-CON-010/019 did not fire on it. | Sample people or quotes are presented as testimonials, customers, or team members rather than as interface content (DET-CON-010 / DET-FAKE-014). |

## C. Behavior patterns (DET-FAKE false-positive clauses)

| # | Pattern | Why it is legitimate | Becomes a real finding when |
|---|---|---|---|
| C-01 | Client-side route guard hiding protected UI, **when the API also enforces authorization** | DET-FAKE-002/021: the guard is UX; enforcement is server-side. Check the API, not the guard. | The guard is the only enforcement — a direct API request from an unauthorized session succeeds (DET-FAKE-021, P0). |
| C-02 | Optimistic UI updates | DET-FAKE-005: legitimate when the server value replaces the optimistic value after the request resolves. | The counter resets to its hardcoded base on reload, or the optimistic value is never reconciled (DET-FAKE-005). |
| C-03 | Cached or periodically aggregated metrics, within one stated refresh cycle | DET-FAKE-004: aggregation lag is normal engineering. | A forced known change does not move the figure after one stated refresh cycle (DET-FAKE-004). |
| C-04 | Aggregated or delayed figures labeled with their window ("last 24 hours") | DET-FAKE-018: the label makes the figure honest. | The word "live" sits over a timer- or random-driven number (DET-FAKE-018). |
| C-05 | Draft-versus-published workflows where the draft state is visible as a draft in the admin UI | DET-FAKE-010: delayed public visibility with a visible state is a workflow, not a fake save. | The UI claims "Saved"/published while the change is nowhere retrievable (DET-FAKE-010). |
| C-06 | Soft-delete with a visible "Archived" or trash state | DET-FAKE-011: labeled retention is honest. | The item is hidden with no state anywhere and resurfaces on reload, search, or direct URL (DET-FAKE-011). |
| C-07 | Client-side preview of an upload before the upload completes | DET-FAKE-012: previews are normal; the violation is the completed state. | An "Upload successful" state exists with no server copy of the file (DET-FAKE-012). |
| C-08 | A labeled welcome or onboarding notification in a new account's feed | DET-FAKE-013: one labeled system message is onboarding, not staged activity. | The feed contains fabricated activity from other "users" (DET-FAKE-013). |
| C-09 | Client-side filtering of a genuinely small, fully loaded dataset that does not claim to be larger | DET-FAKE-017: the UI's claim matches what it holds. | The UI presents the fixture as a large or live dataset, or counts disagree with results (DET-FAKE-017). |
| C-10 | Enumeration-safe password-reset messaging ("if an account exists…") | DET-FAKE-020: correct security practice — honest because the email genuinely arrives for real accounts. | No email arrives for a real account, or the old password keeps working after a "successful" reset (DET-FAKE-020). |
| C-11 | Autosave with a visible pending state during the request | DET-FAKE-022: the indicator tells the truth about an in-flight save. | The indicator claims completion before the server response, or claims success with the network disabled (DET-FAKE-022). |
| C-12 | Pending-verification states (new email, new account) that are labeled as pending | DET-FAKE-003/016: the pending record exists, the duplicate check fires, and the current value is shown as current until verification completes. | The pending state is a dead end — no record exists and nothing ever verifies (DET-FAKE-003). |
| C-13 | Third-party (provider-hosted) form endpoints whose submissions the owner can retrieve in that provider | DET-FAKE-015: the submission is real if it lands somewhere the owner can read it. | Submissions are irretrievable by anyone (DET-FAKE-015). |

## D. Code and infrastructure patterns (Phase 1 false-positive test — code/infra)

| # | Pattern | Why it is legitimate | Becomes a real finding when |
|---|---|---|---|
| D-01 | `TODO` markers inside sample, template, example, or scaffold files, addressed to the person deploying or configuring (prompts to supply a value) | The file is a form and TODO is its label for a blank field (Discourse's `samples/standalone.yml`). Exclude `samples/`, `templates/`, `examples/`, and files whose header says they are meant to be copied and edited. | A TODO describes deferred core functionality in shipped runtime code with no ticket, owner, or date (DET-CODE-011). |
| D-02 | Obviously non-functional example credentials in sample/template configuration (`pa$$word`, `changeme`, `example`, values paired with `example.com` hosts) | Dictionary-fake values in a file whose role is to be copied and edited are placeholders, not secrets (DET-CODE-018 / DET-INF-005 as amended). | The value is high-entropy or verifiably live, or it sits in executable production configuration rather than a sample/template file. |
| D-03 | `example.com` and other reserved domains/IPs in locale files, documentation, and user-facing help or example text | Reserved domains exist so help text is correct for every deployment (DET-CODE-024 as amended). | The reserved value appears in executable config, routes, seeds, or defaults that would run in production. |
| D-04 | `localhost`, raw IPs, and `http://` literals in docs, READMEs, samples, and templates | Those files are the documented place where per-deploy values go (DET-INF-007 as amended); the scan runs over built artifacts and runtime source, excluding `docs/`, `samples/`, `templates/`, `examples/`, and READMEs. | The literal survives into the artifact that actually runs (DET-INF-007). |
| D-05 | Single-node / all-in-one topology in distributable, self-hosted software whose own documentation records the decision and documents a multi-node path | DET-INF-019 as amended: for distributable software the vendor's documented default, with a recorded decision and an exit path, satisfies the recorded-decision test. Deployment-scoped parameters judge a named production deployment, not a product's sample template. | A named production deployment with stated availability requirements runs single-node with no recorded decision or redundancy path (DET-INF-019). |
| D-06 | Infrastructure declared in a companion deployment repository or a non-listed declarative system (pups/launcher, Kamal, Capistrano, Docker Compose, Helm) | IaC is defined functionally — infrastructure declared in version-controlled files that a tool applies convergently (DET-INF-024 as amended); check sibling deployment repos before failing. | No version-controlled declarative description of the infrastructure exists anywhere (DET-INF-024). |
| D-07 | A documented, scripted on-host deploy/rebuild tool (Discourse's `launcher`, Capistrano, Kamal, deployer) named as a class | DET-INF-004 as amended: a scripted, documented procedure whose live revision maps to a commit is automated, not manual. | The deploy procedure is undocumented hand-steps, or the live revision cannot be identified (DET-INF-004). |
| D-08 | A vendor-supported rolling release default (`latest`) where a pinning mechanism exists and versioned releases are available | DET-INF-026 as amended: record as a noted risk, not a fail — the default tracks the vendor's tested release channel and pinning is documented. | No pinning mechanism exists, or the floating target is an ungated development branch (DET-INF-026). |
